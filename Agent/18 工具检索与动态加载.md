[[18 工具检索与动态加载|工具检索与动态加载]] 的本质是:**工具不全给,按需给**——当工具数从几个涨到几十上百个(尤其接了多个 MCP server),把全部工具 schema 一股脑塞进上下文会同时撞两堵墙:① token 爆,工具定义先把窗口占掉一大半;② 模型在太多工具里挑花眼、选错调用。解法不是「写更好的提示词让它别选错」,而是把工具当成可检索的文档:对当前 query 检索出 top-k 个相关工具,**只把这 k 个的 schema 放进上下文**。

它是 [[16 工具设计与工具层|工具设计与工具层]] 的延伸:工具层负责把异构后端抹平成「带 schema 的工具」,而工具检索负责回答「这么多工具,这一步该让模型看见哪几个」。它和 [[21 上下文压缩与卸载|上下文压缩与卸载]] 是同一场战争的两条战线——后者压的是历史和工具返回,前者压的是**工具定义本身**。

![[工具检索与动态加载.png]]

## 本质:窗口被工具 schema 撑爆

先把这个「真问题」讲透。一个 [[15 Function Calling 工具调用|Function Calling 工具调用]] 的工具定义不是一行字,而是一整段 JSON Schema:工具名、自然语言描述、每个参数的类型/枚举/必填/默认值/嵌套对象、返回结构、错误码说明。一个设计认真的工具,schema 轻则两三百 token,重则上千。算笔账:

- **10 个工具**:几千 token,无所谓。
- **50 个工具**:1~2 万 token 没了。
- **接 3~5 个 MCP server**:每个 server 暴露十几个工具很常见,合起来上百个工具、**几万 token 的工具定义常驻上下文**,而且每一轮请求都要重发。

这是一种被低估的浪费。它撞的是 [[20 上下文工程|上下文工程]] 里那三重硬约束:**容量有限**(工具定义先吃掉预算,留给历史和任务的空间被挤没)、**越长越贵越慢**(每轮都重发全部工具 schema,token 数直接乘单价)、**越长越笨**(上百个工具描述堆在一起,模型出现 lost-in-the-middle,真正该用的那个被淹在中段)。

第二堵墙更隐蔽:**选择质量随工具数下降**。工具一多,描述之间容易语义重叠(`search_web` / `search_docs` / `lookup_kb` 到底用哪个?),模型在几十个相似选项里反而更容易选错、或者调用参数填错。学术上这个现象有名字——RAG-MCP 论文(arXiv:2505.03275)管它叫 **prompt bloat**(提示膨胀),并实测:工具一多,基线模型的工具选对率掉到 13.6%,引入检索后回到 43.1%,约 **3.2 倍**提升,同时 prompt token **降约 50%**。这组数字是本篇最该记住的实证。

> 一句话:工具不是越多越好用,**工具多到一定程度,「全给」既烧钱又降智**。

## 机制:把工具当文档来检索

核心思想就是把 [[36 Agentic RAG|Agentic RAG]] 那套搬到工具上——工具是被检索的对象,query 是检索的输入,top-k 工具是检索的输出。分步:

### 1. 对工具的「名 + 描述」建索引

不索引整个 schema(那太重),只索引**工具名 + 自然语言描述**(必要时加几个示例 query)。两条路线:

- **向量索引**:把每个工具的描述 embedding 成向量,存进向量库。query 来了也 embedding,按余弦相似度取最近的 k 个。优点:能匹配语义(query 说「查天气」也能召回名为 `get_forecast` 的工具)。
- **关键词 / BM25**:对工具描述做倒排索引,query 按词命中。优点:精确、可解释、无需 embedding 模型;缺点:同义改写召不回。

实务里常是**混合检索**:BM25 保精确 + 向量保语义,再融合。这正是 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 在「工具」这个语料上的具体应用。

### 2. 按当前 query 检索 top-k

每一步(或每个新子任务)拿当前意图去检索,取相似度最高的 k 个工具(k 常取 3~10)。k 是个旋钮:太小可能漏掉关键工具(召回不足),太大又退回到「塞太多」。

### 3. 只把这 k 个的 schema 注入上下文

检索只用轻量的「名+描述」,但**注入时要把这 k 个工具的完整 schema** 放进上下文的 tools 区,供模型 [[15 Function Calling 工具调用|Function Calling 工具调用]]。其余几十上百个工具的完整定义**根本不进上下文**。这一步是省 token 的关键动作。

### 4. 分阶段 / 分组暴露 + 按任务态切换

进阶玩法,处理「不同阶段需要不同工具」:

- **命名空间 / 分组**:把工具按领域分组(`fs.*` 文件、`web.*` 网络、`db.*` 数据库),先选组再选工具,两级收敛。
- **MCP server 级筛选**:不在单个工具粒度检索,而是先判断「这一步该用哪个 MCP server」,再暴露该 server 的工具。RAG-MCP 论文做的正是这个粒度——先检索相关 MCP,再把它的工具描述给模型。
- **按任务态切换工具集**:规划阶段只给「搜索/读取」类工具,执行阶段才放出「写入/部署」类。状态机驱动工具可见性,既降噪又是一种 [[16 工具设计与工具层|工具设计与工具层]] 级别的权限护栏(纯文本意义上的安全与权限护栏:危险工具默认不可见)。

![[工具检索与动态加载-注入流程.png]]

### 5. 模型主导的工具搜索(2026 新范式)

最新的做法把检索这步也交给模型自己。Anthropic 在 2026-01-14 上线的 **Tool Search**(`tool_search_tool_regex` / `tool_search_tool_bm25`)就是这个思路:绝大多数工具用 `defer_loading: true` 标记,**默认不渲染进上下文**,模型先调一个「搜索工具」按正则/BM25 找出需要的工具,框架再把命中的工具定义动态加载进来。官方数据:对工具繁多的场景 **token 开销降约 85%**;且 `defer_loading: true` 的工具在算缓存 key 前就被剥离,所以延迟加载本身不破坏 [[102 KV-Cache|KV-Cache]]。这把「工具检索」从应用层下沉成了模型原生能力。

## 来源 / 出处

- **RAG-MCP**(Gan & Sun, arXiv:2505.03275, 2025-05):首次系统量化「工具/MCP 一多就 prompt bloat」,提出检索式工具选择,实测 token ↓~50%、选对率 ↑~3.2×。本篇的核心数字来源。
- **Anthropic「Advanced tool use」/ Tool Search**(2026-01-14):`defer_loading`、`tool_search_tool_regex`,把动态工具加载做成 API 原生能力,token 开销 ↓~85%。
- **LangChain / LlamaIndex 文档**:把「many tools」当作 retrieval 问题的工程化封装(下文开源实现)。
- 思想根可追到 Gorilla / ToolBench 这一系「让模型在大规模工具库里检索调用」的研究,但它们重点在「学会用工具」,RAG-MCP 这代重点才转到「**怎么 scale 工具发现**」。

## 可跑的最小实现(伪码)

对工具描述建索引 + 按 query 检索 top-k + 动态注入:

```python
from dataclasses import dataclass

@dataclass
class Tool:
    name: str
    description: str          # 用于检索的自然语言
    schema: dict             # 完整 JSON Schema,注入时才用
    fn: callable

class ToolRetriever:
    def __init__(self, tools, embed):
        self.tools = tools
        self.embed = embed
        # 只对「名+描述」建索引,不碰重的 schema
        self.index = [(t, embed(f"{t.name}: {t.description}")) for t in tools]

    def retrieve(self, query, k=5):
        q = self.embed(query)
        scored = sorted(self.index, key=lambda ts: -cos(q, ts[1]))
        return [t for t, _ in scored[:k]]          # top-k 工具对象

def agent_step(query, retriever, llm):
    picked = retriever.retrieve(query, k=5)        # ① 检索
    tools_payload = [t.schema for t in picked]     # ② 只注入这 k 个 schema
    resp = llm(messages=[{"role": "user", "content": query}],
               tools=tools_payload)                # ③ 模型只在 k 个里选
    if resp.tool_call:                             # ④ 执行
        tool = next(t for t in picked if t.name == resp.tool_call.name)
        return tool.fn(**resp.tool_call.args)
    return resp.text

# 进阶:按 MCP server 粒度先收敛(RAG-MCP 风格)
def retrieve_by_server(query, servers, embed, k_srv=2, k_tool=4):
    srv = top_k(servers, embed(query), k_srv)      # 先选相关 server
    tools = [t for s in srv for t in s.tools]
    return top_k(tools, embed(query), k_tool)      # 再在其工具里选
```

要点:① 索引只放「名+描述」,**注入才用完整 schema**——检索轻、注入准;② k 是召回/开销的旋钮;③ 工具区尽量放在前缀稳定段、批量切换,别每步乱改顺序,护 [[102 KV-Cache|KV-Cache]];④ 描述质量直接决定召回——写不好的描述检索不到,工具等于不存在。

## 对比:全塞 vs 检索 top-k

| 维度 | 全塞(所有工具 schema 常驻) | 检索 top-k 动态注入 |
|---|---|---|
| 工具定义 token | 随工具数线性涨,几万起 | 恒定 ≈ k×单工具,与池子大小解耦 |
| 工具池上限 | 撞窗口,实际只能挂几十个 | 池子可上千,进上下文的永远 k 个 |
| 选对率 | 工具多时显著下降(prompt bloat) | 候选少、噪声低,选对率 ↑约 3× |
| KV-Cache | 工具区固定时缓存好,但占预算 | 注意:每步换工具会破缓存,需批量/固定段 |
| 召回风险 | 不会漏(全在),但淹没 | **可能漏关键工具**(检索不到=不存在) |
| 适用 | 工具 ≤ ~15、固定 | 工具多、接多 MCP、跨阶段任务 |

## 何时用 / 坑

**该上工具检索的场景**:工具数超过十几个、接了多个 MCP server、不同任务阶段用不同工具集、对 token 成本敏感的生产 agent(联动 [[35 Agent 成本与延迟优化|Agent 成本与延迟优化]])。**工具就五六个、固定不变,别上**——检索的额外延迟和召回风险不划算,直接全塞最简单。

**坑**:
- **检索漏了关键工具就废**:这是头号风险。召回不到=工具对模型不存在,任务直接卡死。对策:k 给足、混合检索、给高频/关键工具兜底常驻(永远注入,不参与检索)。
- **工具描述质量决定召回**:描述写得含糊、和 query 用词对不上,向量/关键词都召不回。**工具描述就是它的「检索文档」**,要按能被检索到的标准写(动词开头、说清何时用、放典型 query)。这点和 [[16 工具设计与工具层|工具设计与工具层]] 强耦合。
- **每步换工具集破坏 KV-Cache**:工具区在上下文里位置/内容一变,从变动点起缓存全失效。对策:批量切换(按阶段而非按步)、工具区放相对固定段;或用 `defer_loading` 这类不进缓存 key 的机制。
- **检索本身的延迟与成本**:每步多一次 embedding + 向量查询。高频时用缓存、用快的本地 embedding(或 semantic-router 这类毫秒级路由)。
- **描述语义重叠召回一堆近义工具**:`search_a/b/c` 全被召回,模型还是选困难。对策:合并冗余工具、描述里写明区别、用 rerank 拉开。
- **分组/命名空间设计不当**:组分错,先选组就把对的工具排除了。组的粒度要和任务的自然边界对齐。

## 关键事实

- 工具检索 = 把工具当文档,**对「名+描述」建索引 → 按 query 取 top-k → 只注入这 k 个完整 schema**。把「进上下文的工具数」和「工具池大小」解耦。
- 解决两个真问题:**token 爆**(工具 schema 撑爆窗口)+ **选错**(工具多到 prompt bloat,选对率跳水)。
- RAG-MCP 实证:token ↓~50%,工具选对率 13.6%→43.1%(≈3.2×)。这是「全塞 vs top-k」最硬的对比数据。
- 2026 新范式:Anthropic **Tool Search**(`defer_loading`+`tool_search_tool_regex`),模型自己搜工具、框架按需加载,token 开销 ↓~85% 且不破缓存。
- 进阶手段:命名空间分组、**MCP server 级筛选**、按任务态切换工具集——既降噪又当(纯文本意义的)权限护栏。
- 头号坑是**召回漏**(检索不到=不存在)+ **描述质量**(描述就是检索文档),次坑是每步换工具破 [[102 KV-Cache|KV-Cache]]。
- 它和 [[21 上下文压缩与卸载|上下文压缩与卸载]] 一体两面:那个压历史和工具返回,这个压工具定义;都服务于 [[20 上下文工程|上下文工程]] 的「有限预算里放最该放的」。[[25 Agent Skills(SKILL.md)|Agent Skills(SKILL.md)]] 的「技能按需加载、不常驻上下文」是同一逻辑在「技能」上的复刻。

## 主流开源实现 / Python 库

> 均经 2026-06 web 核验在维护。

- **LangChain `create_retriever_tool`**(`langchain-core`):把一个检索器包成可被 agent 调用的工具;配合「对工具集建向量索引、按 query 取相关工具再绑定」的 retrieve-tools 模式,实现工具的动态选择。
- **LlamaIndex `ObjectIndex` + `ObjectRetriever`**(`llama-index`):对一组 `Tool` 对象建索引,query 时只检索出相关工具的函数签名喂给模型——官方文档明确定位为「too many functions to fit in the prompt」的解法,是本概念最对口的库。
- **Anthropic Claude Tool Search**(Claude Developer Platform,`tool_search_tool_regex` / `defer_loading: true`):API 原生的延迟加载 + 工具搜索,模型自主发现工具,token 开销 ↓~85%。
- **aurelio-labs/semantic-router**(`semantic-router`,MIT):毫秒级语义路由层,用向量空间直接把 query 路由到 route/工具,不等 LLM 慢生成——适合做工具检索的快前置。
- **MCP 网关 / 路由类**:`microsoft/mcp-gateway`(MCP 反向代理与生命周期管理)、`globalpocket/mcp-routing-gateway`(跨多后端 MCP server 的工具筛选/路由,防误调)、`igrigorik/MCProxy`(聚合多上游 MCP + 内置工具搜索,按需暴露)——在 MCP server 粒度做工具聚合与筛选。
- **论文参考实现 RAG-MCP**(arXiv:2505.03275):检索式工具选择的范式来源(token ↓~50%、选对率 ↑~3.2×)。

## 工业界实践

工具检索从「学术 trick」变成「生产 agent 标配」,就是被 [[17 MCP 模型上下文协议|MCP]] 生态逼出来的——一旦能一键接入近两千个 Registry server,工具池轻松上百上千,「全塞」物理上不可能。

### 三条工程路线(按下沉层次)

1. **应用层向量检索(最经典)**:自己对工具「名+描述」建向量/BM25 索引,每步按 query 取 top-k 注入。LangChain `create_retriever_tool` + retrieve-tools 模式、LlamaIndex `ObjectIndex`/`ObjectRetriever` 都是这层的现成封装。LlamaIndex 官方把 `ObjectIndex` 直接定位为「too many functions to fit in the prompt」的解法,是最对口的库。优点:可控、跨厂商;缺点:每步多一次 embedding + 向量查,且自己维护索引。
2. **MCP server 级筛选(RAG-MCP 范式)**:不在单工具粒度检索,先判断「这步该用哪个 server」,再暴露该 server 的工具,两级收敛。生产里由 **MCP Gateway** 承担(`microsoft/mcp-gateway`、`globalpocket/mcp-routing-gateway`、`igrigorik/MCProxy` 这类聚合多上游 server + 内置工具搜索的网关)。粒度粗、收敛快,适合「几十个 server」的场景。
3. **模型原生延迟加载(2026 主流下沉)**:Anthropic **Tool Search**(`2026-01-14` 上线,`tool_search_tool_regex` / `tool_search_tool_bm25` + `defer_loading: true`)把检索这步交给模型自己——绝大多数工具默认不渲染进上下文,模型先调「搜索工具」找出需要的,框架再动态加载命中工具的完整定义。官方数据:工具繁多场景 **token 开销 ↓~85%**;且 `defer_loading` 工具在算缓存 key 前就被剥离,**延迟加载本身不破坏 [[102 KV-Cache|KV-Cache]]**。这把工具检索从应用层下沉成 API 原生能力,是当下首选。

### 规模化与成本/延迟

- **token 账**:工具定义 token 从「随工具数线性涨(几万起、每轮重发)」变成「恒定 ≈ k×单工具」,和池子大小解耦。RAG-MCP 实测 prompt token ↓~50%,Tool Search 报 ↓~85%。这是生产 agent 降本最直接的杠杆之一(联动 [[35 Agent 成本与延迟优化|Agent 成本与延迟优化]])。
- **延迟账**:多一次检索(embedding + 向量查或模型自搜)。对策:本地快 embedding、缓存高频 query 的检索结果、用 `semantic-router` 这类毫秒级语义路由做快前置(不等 LLM 慢生成)。
- **缓存账**:头号陷阱是**每步换工具集破 KV-Cache**——工具区在上下文里位置/内容一变,从变动点起缓存全失效。生产对策:按**阶段**而非按步批量切换工具集、工具区放相对固定段、或用 `defer_loading` 这类不进缓存 key 的机制。

### 可观测与运维

- **召回监控**:埋点记录「检索命中了哪些工具、模型最终用了哪个、有没有出现『我没有合适工具』的卡死」。**召回漏(检索不到=工具不存在)是头号生产事故**——任务直接卡死且难定位。
- **描述即检索文档**:工具描述写不好就召不回,等于工具不存在。生产里把「工具描述质量」纳入 review(动词开头、写清何时用、放典型 query),和 [[16 工具设计与工具层|工具设计与工具层]] 强耦合。
- **兜底常驻**:高频/关键工具(如 `read_file`、`finish`)永远注入、不参与检索,避免被检索漏掉。

```text
[query] → [混合检索: BM25+向量, 取 top-k]
              │ (高频关键工具旁路, 永远常驻)
              ▼
       [只注入 k 个完整 schema] → [模型在 k 个里选] → [执行]
              ▲
   监控: 召回命中率 / "无合适工具"率 / 描述覆盖度
```

## 面试高频

**Q1:工具检索要解决什么问题?为什么不能全塞?**
解决两个真问题:① **token 爆**——工具 schema 不是一行字而是整段 JSON Schema,单工具几百到上千 token,50 个工具就 1~2 万 token,接几个 MCP server 上百个工具几万 token 常驻且每轮重发;② **选错**——工具一多语义重叠,模型在几十个相似选项里选困难、选错率飙升(prompt bloat)。撞的是 [[20 上下文工程|上下文工程]] 三重约束:容量有限、越长越贵越慢、越长越笨。
- 陷阱:别答「写更好的 prompt 让它别选错」——根因是候选太多,要从「全给」改成「按需给」。

**Q2:工具检索的核心机制?一句话讲清。**
**把工具当文档来检索**:对工具的「名+描述」(不是整个 schema)建索引 → 按当前 query 取 top-k → **只把这 k 个的完整 schema 注入上下文**。把「进上下文的工具数」和「工具池大小」解耦——池子可上千,进上下文的永远 k 个。
- 追问「为什么索引只放名+描述,不放整个 schema?」——schema 太重,检索只需语义匹配;注入时才用完整 schema(检索轻、注入准)。

**Q3:有哪些硬数据支撑工具检索有效?**
**RAG-MCP**(arXiv:2505.03275,Gan & Sun,2025-05):工具一多,基线选对率掉到 **13.62%**,引入检索后回到 **43.13%**(约 **3.2×**),同时 prompt token **↓~50%**。Anthropic **Tool Search**(2026):工具繁多场景 token 开销 **↓~85%**。
- 这两组数字是这个概念最该背的实证,能报出来直接区分「读过」和「听说过」。

**Q4:工具检索最大的坑是什么?**
**召回漏**——检索不到的工具对模型等于不存在,任务直接卡死。对策:k 给足、混合检索(BM25 保精确 + 向量保语义)、高频关键工具兜底常驻不参与检索、监控「无合适工具」率。次坑:**描述质量**(描述就是检索文档,写不好召不回)、**每步换工具破 KV-Cache**。
- 陷阱:很多人只会答「token 省了」,讲不出召回漏这个反面——能讲反面说明真在生产里踩过。

**Q5:2026 年工具检索有什么新范式?**
**模型主导的工具搜索**:Anthropic Tool Search,工具标 `defer_loading: true` 默认不进上下文,模型先调一个搜索工具(正则/BM25)找需要的,框架按需加载。把检索从应用层下沉为模型原生能力,token ↓~85% 且不破缓存(deferred 工具在算缓存 key 前被剥离)。
- 对比老范式:老的是「应用层先检索再喂模型」,新的是「模型自己搜、框架动态加载」。

**Q6:什么时候不该上工具检索?**
工具就五六个、固定不变时别上——检索的额外延迟 + 召回风险不划算,直接全塞最简单。该上的场景:工具 >十几个、接多个 MCP server、跨阶段用不同工具集、对 token 成本敏感的生产 agent。

## 知识拓展

- **它和上下文压缩是同一场战争的两条战线**:[[21 上下文压缩与卸载|上下文压缩与卸载]] 压的是历史和工具返回,工具检索压的是**工具定义本身**;都服务于 [[20 上下文工程|上下文工程]] 的「有限预算里放最该放的」。
- **它是 Agentic RAG 在「工具」语料上的应用**:把 [[36 Agentic RAG|Agentic RAG]] 那套(query 检索 → top-k → 注入)搬到工具上,工具是被检索对象。检索路线选择同 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]]——BM25 精确可解释、向量保语义,生产常混合再 rerank。
- **同一逻辑的姊妹概念**:[[25 Agent Skills(SKILL.md)|Agent Skills(SKILL.md)]] 的「技能按需加载、不常驻上下文」是同一思想在「技能」上的复刻——能力默认不进上下文,需要时才拉。
- **进阶手段**:命名空间分组(`fs.*`/`web.*`/`db.*`,先选组再选工具)、MCP server 级筛选、**按任务态切换工具集**(规划阶段只给搜索/读取类,执行阶段才放出写入/部署类)——后者既降噪又是一种纯文本意义的**权限护栏**(危险工具默认不可见,呼应 [[16 工具设计与工具层|工具设计与工具层]])。
- **思想根与前沿**:可追到 **Gorilla / ToolBench** 系(让模型在大规模工具库里检索调用),但它们重点在「学会用工具」,RAG-MCP 这代重点才转到「**怎么 scale 工具发现**」。2026 趋势是「检索」继续下沉进模型(Tool Search)、并和 MCP Gateway 的 server 级路由结合,形成「模型自搜 + 网关粗筛」两级。
- **反模式**:k 设太大退回「塞太多」;分组粒度和任务边界不对齐(先选组就把对的工具排除);冗余近义工具不合并(`search_a/b/c` 全被召回,模型仍选困难)。
