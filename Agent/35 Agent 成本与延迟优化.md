[[35 Agent 成本与延迟优化|Agent 成本与延迟优化]] 的本质是:agent 把一次 LLM 调用变成了**多步推理 × 每步都带着大 prompt**,于是 token 花费与端到端延迟相对单次问答**乘性暴涨**——成本 ≈ 步数 × 每步 token × 单价,延迟 ≈ 步数 × 每步往返(串行累加)。要把它压下来,得**系统性地从每个乘数下手**:压单价(model routing、小模型)、压每步 token(上下文压缩)、压步数/往返(并行)、压重复计算(prompt caching、语义缓存、缓存工具结果)。这不是单点技巧,而是一套互相联动的杠杆组合。

它是把 [[05 Routing|Routing]]、[[06 Parallelization|Parallelization]]、[[21 上下文压缩与卸载|上下文压缩与卸载]]、[[102 KV-Cache|KV-Cache]] 这些散落的概念,从"成本/延迟"这一根工程主线上串起来看的整合视角——多数实践都在 [[37 Agent 框架对比|Agent 框架对比]] 选型与生产部署阶段绕不开。

## 本质:乘性暴涨,逐个乘数压

单次问答只调一次模型;agent 不一样。一个 [[09 ReAct|ReAct]] 或 [[10 Plan-and-Execute|Plan-and-Execute]] 任务跑十几二十步,而且**每一步都要把不断增长的历史(Thought / Action / Observation、工具结果、记忆)重新发回模型**。于是两笔账都炸:

- **成本**:`总 token ≈ Σ(各步的输入+输出 token)`。因为每步要重发前序历史,token 随步数**超线性**累积;乘上单价,一个复杂 agent 单次任务花掉单次问答几十上百倍 token 是常态。
- **延迟**:`总延迟 ≈ Σ(各步往返时间)`。串行的步骤逐个等模型返回,延迟**线性累加**;长程任务从用户视角看就是"转好久"。

**代入手算(caching 读 10% 的威力)。** 取一个 $15$ 步的 agent,每步平均输入 $8000$ token(含重发的前序历史)、输出 $300$ token,单价按 \$3/M 输入、\$15/M 输出。**不开缓存**:输入累计 $15\times8000=1.2\times10^5$ token,成本 $1.2\times10^5\times\$3/\text{M}=\$0.36$;加输出 $15\times300\times\$15/\text{M}=\$0.068$,合计 $\approx\$0.43$/任务。**开 prompt caching**:每步 $8000$ 里有 $6000$ 是稳定前缀(系统提示 + 工具表),命中后**只按 10% 计价**,变价部分 $2000$ 全价。输入成本 $=15\times[(6000\times0.10+2000)\times\$3/\text{M}]=15\times2600\times\$3/\text{M}=\$0.117$;加同样的输出 $\$0.068$,合计 $\approx\$0.185$/任务。**单这一招省 $\approx57\%$**——而且改动只是把稳定前缀标个缓存断点、放最前面,质量零损失。这就是为什么落地优先级把 prompt caching 排第一。

所以优化的心智不是"找一个银弹",而是**盯住公式里的每个乘数,各个击破**:

![[Agent 成本与延迟优化.png]]

把杠杆按"压哪个乘数"分三类:
- **压单价 / 每步 token**:[[05 Routing|Routing]] 难易分流、小模型/蒸馏、[[21 上下文压缩与卸载|上下文压缩与卸载]]、推测解码。
- **压步数 / 往返**:[[06 Parallelization|Parallelization]] 并行与批处理、减少问大模型次数([[11 ReWOO|ReWOO]] 式批量规划)、流式输出降感知延迟。
- **压重复计算**:prompt caching(前缀复用,底层即 [[102 KV-Cache|KV-Cache]])、语义缓存、缓存工具结果。

下面逐个拆。

## 杠杆一:model routing —— 别让所有请求都用最贵的模型

核心观察:agent 的多步里,**大部分步骤其实很简单**(格式化、抽字段、判断是否继续),只有少数步骤需要最强模型的推理力。把每一步都丢给最贵的模型是巨大浪费。

**model routing** 就是先**判断这一步/这个请求的难易**,再**分流**:简单的给便宜的小模型(弱模型),难的才给昂贵的大模型(强模型)。这直接联动 [[05 Routing|Routing]] —— 那里讲的是"按意图把请求路由到不同分支",这里是它在**成本维度**的应用:按难度路由到不同**价位**的模型。

实现上有两类 router:
- **学习型 router**(如 RouteLLM):用数据训练一个判别器,预测"弱模型能否胜任",在保证质量前提下最大化弱模型承接比例。
- **规则/复杂度型 router**:按 token 长度、关键词、复杂度打分等启发式分流,零额外 API 调用、亚毫秒延迟,但不如学习型精细。

收益:在质量几乎不降的前提下,把相当比例的调用从大模型转到小模型,**整体成本可观下降**。

## 杠杆二:prompt caching —— 复用前缀,底层就是 KV-Cache

这是 2026 年**性价比最高的成本杠杆**。agent 的每一步 prompt 里,有一大块是**稳定不变的前缀**:系统提示、工具定义表(可能几千 token 的 [[15 Function Calling 工具调用|Function Calling 工具调用]] schema)、few-shot 示例、长背景文档。每步都把这块重新发、重新计算,纯属浪费。

**prompt caching** 让提供商**缓存这段稳定前缀对应的 KV 张量**(就是 [[102 KV-Cache|KV-Cache]]:注意力层算出来的 key/value),下次命中就**跳过这段前缀的重新计算**,只算新增部分。两种形态:
- **Anthropic**:显式 `cache_control` 断点;写入约 1.25× 正常输入价,**读取仅 10%**(即命中省 ~90% 输入成本)。
- **OpenAI**:稳定前缀超阈值(约 1024 token)**自动缓存**,命中部分按 50% 输入价计。

官方数据:命中可**降本最高约 90%、降长 prompt 延迟最高约 85%**;独立评测里跨提供商节省约 41%–80%。对 agent loop / RAG 这类"前缀大且稳定"的负载,这是几乎零质量损失的纯赚。

**用好的关键**(也是坑):把**稳定的东西放最前面**(系统提示、工具表),把**多变的东西放后面**(当前 query、最新观测)。一旦在前缀中间插入了变化内容,后面全部 KV 失效、缓存被打散——这就是社区说的 "**Don't break the cache**"。

## 杠杆三:语义缓存 + 工具结果缓存 —— 跨请求复用整答

prompt caching 复用的是**同一请求内的前缀**;**语义缓存(semantic cache)**复用的是**跨请求的整段答案**:当一个新 prompt 与历史某个 prompt **语义相同**(即便措辞不同),直接返回缓存的答案,**0 次 LLM 调用**。它靠 embedding 相似度匹配,比只认字面的精确缓存能抓到多得多的重复。

类似地,**缓存工具结果**:同样参数的工具调用(查同一个 API、读同一个文件)不必每次真跑,缓存结果按需失效即可——既省钱又省那一跳的延迟。

注意语义缓存有**正确性风险**:语义"相似"不等于"答案可复用"(同一问法在不同上下文下答案可能不同),阈值定太松会返回错答。适合**问答型、答案稳定**的场景,慎用于强上下文依赖的步骤。

## 杠杆四:并行 / 批处理 —— 把延迟从"相加"变成"取最大"

延迟的串行累加是 agent 慢的主因。**[[06 Parallelization|Parallelization]]** 的洞见:**无依赖的步骤可以并发跑**——多个独立工具调用、对多个文档分别抽取、多个子任务([[07 Orchestrator-Workers|Orchestrator-Workers]] 式分派),并发后总延迟从 `Σ(各步)` 降到 `max(各步)`。[[12 LLMCompiler|LLMCompiler]] 更进一步,把计划编译成 DAG 自动并行无依赖节点。

**批处理(batching)**:把多个独立请求合并提交(很多提供商有 batch API,折扣明显但有延迟换成本的 tradeoff),或在本地把多条短请求拼批推理,提高吞吐、摊薄固定开销。

**流式输出(streaming)**:不降真实总延迟,但**先吐首 token**能大幅降低**用户感知延迟**——对交互式 agent 体验提升显著。

## 杠杆五:上下文压缩、小模型/蒸馏、推测解码

- **[[21 上下文压缩与卸载|上下文压缩与卸载]]**:每步 prompt 越小,输入 token 越少、越快、缓存也越易命中。把长历史摘要化、把不常用信息卸载到外部记忆只留指针——直接压"每步 token"这个乘数。
- **小模型 / 蒸馏**:用便宜模型承接多数步骤;或把大模型在特定任务上的能力**蒸馏**到小模型,用小模型常驻、大模型兜底。与 routing 协同。
- **推测解码(speculative decoding)**:小模型快速"猜"若干 token,大模型一次性"验证",验证通过就跳过逐 token 生成 —— 在不损质量前提下**提速**。这是推理层的延迟杠杆,通常由推理引擎(vLLM 等)提供。

## routing + cache 的数据流

![[Agent 成本与延迟优化-routing与cache数据流.png]]

生产里这几个杠杆常串成一条流水线:**先查语义缓存(命中即 0 调用)→ 未命中再 router 判难易分流到强/弱模型 → 请求带稳定前缀命中 prompt caching(省 ~90% 输入)→ 结果写回语义缓存供下次复用**。一层 **LiteLLM** 网关就能把 router + 两类 cache 串起来,业务代码几乎不动。

## 可跑的最小实现:LiteLLM router + cache

```python
import litellm
from litellm import Router

# ① 配置一个 router:把"强模型"和"弱模型"放进同一组,按难易/负载分流
router = Router(
    model_list=[
        {"model_name": "weak",   # 简单步骤走这个
         "litellm_params": {"model": "gpt-4o-mini"}},
        {"model_name": "strong", # 复杂步骤走这个
         "litellm_params": {"model": "claude-sonnet"}},
    ],
)

# ② 打开语义缓存:相似 prompt 直接复用答案(0 次 LLM 调用)
litellm.cache = litellm.Cache(type="redis", host="localhost", port=6379)
litellm.enable_cache()

def step(prompt: str, hard: bool):
    name = "strong" if hard else "weak"          # 难易分流(可接 RouteLLM 自动判)
    return router.completion(
        model=name,
        messages=[
            # ③ prompt caching:稳定前缀(系统提示/工具表)放最前并标缓存断点
            {"role": "system",
             "content": [{"type": "text", "text": SYSTEM_PROMPT,
                          "cache_control": {"type": "ephemeral"}}]},  # Anthropic 风格
            {"role": "user", "content": prompt},   # 多变内容放后面,别打散前缀缓存
        ],
        caching=True,                              # ④ 命中语义缓存则跳过调用
    )
```

要点:① **router** 把难易分到不同价位模型;② **语义缓存**让重复问 0 调用;③ **prompt caching** 靠"稳定前缀在前、多变在后"省 ~90% 输入;④ 四件事在一层网关内组合,无侵入。

## 对比:各杠杆的收益与代价

| 杠杆 | 压的乘数 | 典型收益 | 主要代价 / 风险 | 联动 |
|---|---|---|---|---|
| **prompt caching** | 重复(前缀) | 输入降最高 ~90%、延迟降最高 ~85% | 前缀被打散就失效;需"稳定在前" | [[102 KV-Cache|KV-Cache]] |
| **model routing** | 单价 | 大比例调用转小模型,显著降本 | 误判把难题给弱模型→质量降 | [[05 Routing|Routing]] |
| **语义缓存** | 重复(整答) | 命中 0 调用、近 0 延迟 | 相似≠可复用,阈值松会返错答 | — |
| **并行 / 批处理** | 步数/往返 | 延迟从 Σ 降到 max;批省吞吐 | 增并发复杂度;batch 有延迟 tradeoff | [[06 Parallelization|Parallelization]] |
| **上下文压缩/卸载** | 每步 token | 每步更便宜更快、利缓存命中 | 压过头丢信息→质量降 | [[21 上下文压缩与卸载|上下文压缩与卸载]] |
| **小模型/蒸馏** | 单价 | 便宜模型扛多数 | 能力上限低,需大模型兜底 | [[05 Routing|Routing]] |
| **推测解码** | 延迟 | 不损质量提速 | 靠推理引擎支持,自托管才好用 | — |

落地优先级经验:**先上 prompt caching + routing**(改动小、收益大、质量近乎无损),再做并行与上下文压缩,最后才考虑小模型/蒸馏/推测解码(投入大、需调优)。

## 何时用 / 坑

**该上**:任何**多步、长 prompt、规模化**的 agent——客服、研究、编码 agent 在生产高 QPS 下,这些杠杆是省钱保命的;前缀大且稳定、请求有重复模式的负载收益尤其高。

**先别上**:**低频原型 / 一次性脚本**别过早优化,先把功能跑通;过早堆 router + 多级缓存只增复杂度。

**常见坑**:
- **缓存被打散**(头号坑):在稳定前缀中间插了变化内容(动态时间戳、随请求变的检索结果放在系统提示里),导致 prompt caching 全程不命中,白付写入溢价。原则:**稳定前缀在前、多变内容在后**。
- **routing 误判降质量**:router 把难题路由给弱模型,答错的代价(返工、用户流失)可能远超省下的钱。要监控分流后的质量,保留"不确定就升级到强模型"的兜底。
- **语义缓存返错答**:阈值太松、或在强上下文依赖步骤用语义缓存,会复用不该复用的答案。给严格阈值 + 限定到答案稳定的场景。
- **过度压缩丢关键信息**:[[21 上下文压缩与卸载|上下文压缩与卸载]] 压过头,模型丢掉决策必需的细节,省了 token 却办错事。
- **只看单价不看总账**:一味追便宜模型,若它把任务做错触发更多重试/步数,**总成本反而升**。优化目标是**单位成功任务的成本/延迟**,不是单次调用单价。
- **缓存一致性 / 失效**:工具结果缓存若不及时失效,会用过期数据决策。要有合理 TTL 与失效策略。

## 关键事实

- 根因:agent = **多步 × 大 prompt**,成本/延迟相对单次问答**乘性暴涨**;优化即盯住 `步数 × 每步 token × 单价` 与 `步数 × 每步往返` 的每个乘数。
- 三类杠杆:**压单价/token**(routing、小模型、压缩、推测解码)、**压步数/往返**(并行、批处理、少问大模型)、**压重复**(prompt caching、语义缓存、缓存工具结果)。
- **prompt caching 是性价比最高的杠杆**:命中省最高 ~90% 输入、~85% 延迟;底层是复用前缀的 [[102 KV-Cache|KV-Cache]];铁律是"稳定前缀在前、别打散缓存"。
- **model routing** 是 [[05 Routing|Routing]] 在成本维度的应用:按难易分流到不同**价位**模型,简单给小模型、难给大模型。
- **语义缓存**跨请求复用整答(0 调用),**prompt caching** 同请求内复用前缀——两者不同层、可叠加。
- **并行**(联动 [[06 Parallelization|Parallelization]]/[[12 LLMCompiler|LLMCompiler]])把延迟从"相加"变"取最大",是降延迟的主力。
- 优化目标是**单位成功任务的成本/延迟**,不是单次调用单价;一味求便宜可能因返工反升总账。
- 落地顺序:caching + routing 先行(小改动大收益),再并行/压缩,最后小模型/蒸馏/推测解码。

## 主流开源实现 / Python 库

- **`BerriAI/litellm`**(GitHub,pip `litellm`):统一 100+ 模型的 OpenAI 兼容网关,内置 **Router(负载均衡/分流)+ 缓存(含语义缓存)+ 预算/限流**;把 routing 与多级缓存串起来的最常用一层,生产自托管首选。
- **`lm-sys/RouteLLM`**(GitHub,pip `routellm`):专做 **LLM 路由**的框架,提供为"强/弱模型对"优化的预训练 router,在不降质量前提下省成本;可作为 LiteLLM 的分流策略来源。
- **`aurelio-labs/semantic-router`**(GitHub,pip `semantic-router`):基于 embedding 的**超快决策层**,按语义把请求路由到不同分支/模型,亚毫秒级,常用于难易/意图分流。
- **`zilliztech/GPTCache`**(GitHub,pip `gptcache`):**语义缓存**库,识别"语义相同"的 prompt 直接返缓存答案;与 LangChain、llama_index 原生集成。
- 推理层延迟杠杆:**`vllm-project/vllm`**(GitHub,pip `vllm`)提供 **prefix caching(前缀 KV 复用)+ speculative decoding(推测解码)+ 连续批处理**,自托管时这些是降延迟/提吞吐的底层实现。

## 工业界实践

**谁在用、用在哪。** 成本/延迟优化不是可选项,是任何**规模化 agent 上线后的生存问题**——客服 agent、研究 agent、编码 agent 一旦高 QPS,token 账单和 p95 延迟直接决定能不能继续跑。工业界的标准做法是**在网关层(gateway)统一治理**,而非散落在业务代码里:用一层 LLM 网关(LiteLLM / Portkey / Cloudflare AI Gateway / 各家自研)把 routing、两类缓存、预算/限流、可观测全收口,业务代码只管发请求。

**典型生产架构(请求流水线)。** 一条经过治理的 agent 调用链通常是:
1. **语义缓存查询**:命中 → 0 次 LLM 调用直接返回(近 0 延迟、0 成本)。
2. **未命中 → router 判难易**:简单步骤路由到便宜小模型,难步骤到强模型;router 自身用规则/embedding(亚毫秒)或学习型判别器(RouteLLM)。
3. **构造请求带稳定前缀 → 命中 prompt caching**:系统提示、工具表等稳定前缀缓存住,命中省 ~90% 输入成本、~85% 长 prompt 延迟。
4. **结果写回语义缓存** 供下次复用;**工具结果按 TTL 缓存**省重复外部调用。
全程叠加**预算账本 + 限流 + 重试退避**,并把每次调用的 token/成本/延迟/缓存命中率打到可观测系统。

**规模化、成本与延迟的真实数据感。**
- **prompt caching 是 2026 性价比最高的杠杆**:Anthropic 显式 `cache_control`(写入 ~1.25× 价、读取仅 10%,命中省 ~90% 输入);OpenAI 稳定前缀超 ~1024 token 自动缓存、命中部分 50% 价。官方称命中可降本最高 ~90%、降长 prompt 延迟最高 ~85%;独立评测跨提供商节省约 41%–80%。对 agent loop / RAG 这类"前缀大且稳定"的负载,这是几乎零质量损失的纯赚。
- **routing 的省钱来自结构**:agent 多步里大部分步骤(格式化、抽字段、判断是否继续)很简单,只有少数需要最强模型。把简单步骤转到小模型,在质量几乎不降下整体成本可观下降。
- **并行把延迟从 Σ 变 max**:无依赖步骤并发后,总延迟从"各步相加"降到"取最大",是降延迟主力([[12 LLMCompiler|LLMCompiler]] 把计划编译成 DAG 自动并行)。

**可观测与运维(关键指标)。** 生产 agent 的成本/延迟治理离不开这几个看板指标:
- **缓存命中率**(prompt cache hit rate + 语义缓存命中率):命中率掉了往往意味着前缀被打散("Don't break the cache"被违反),要立刻排查。
- **单位成功任务成本/延迟**:不是单次调用单价,而是**完成一个任务的端到端账**——一味用便宜模型若触发更多重试/步数,总账反升。
- **路由分流后的质量**:监控弱模型承接步骤的失败率/返工率,守住"不确定就升级到强模型"的兜底。
- **token 预算消耗速率 + 限流命中**:防某个 agent 失控烧钱(尤其无人值守的 [[33 长程任务与自我改进(Ralph loop)|Ralph loop]])。

**踩坑与最佳实践。**
- **稳定前缀在前、多变内容在后**(头号铁律):系统提示/工具表放最前并标缓存断点,当前 query/最新观测放后面。任何在前缀中间插入的变化内容(动态时间戳、随请求变的检索结果塞进系统提示)都会让后面全部 KV 失效、缓存被打散、白付写入溢价。
- **routing 误判有非对称代价**:把难题路由给弱模型,答错的返工/用户流失代价可能远超省下的钱;要监控质量并保留升级兜底。
- **语义缓存设严格阈值并限定场景**:语义"相似"不等于"答案可复用",阈值松会返错答;只用于问答型、答案稳定的步骤,慎用于强上下文依赖步骤。
- **工具结果缓存要有合理 TTL 与失效**:否则用过期数据决策。
- **落地优先级**:先上 prompt caching + routing(改动小、收益大、质量近乎无损),再并行 + 上下文压缩,最后才小模型/蒸馏/推测解码(投入大、需调优)。

## 面试高频

**Q1:为什么 agent 的成本和延迟相对单次问答会"暴涨"?**
标准答:因为 agent 把一次调用变成**多步推理 × 每步都带大 prompt**,两笔账乘性炸:成本 ≈ `步数 × 每步 token × 单价`(且每步要重发前序历史,token 随步数**超线性**累积),延迟 ≈ `步数 × 每步往返`(串行**线性累加**)。所以优化不是找银弹,而是**盯住公式里每个乘数各个击破**。

**Q2:prompt caching 的底层是什么?用好的铁律是什么?**
标准答:底层就是复用前缀的 [[102 KV-Cache|KV-Cache]]——把稳定前缀(系统提示、工具 schema、few-shot、长背景)对应的 KV 张量缓存住,下次命中跳过这段的重新计算,只算新增部分。铁律是 **"稳定前缀在前、多变内容在后,别打散缓存"**:一旦在前缀中间插入变化内容,后面全部 KV 失效。
- **追问:Anthropic 和 OpenAI 的 prompt caching 有何不同?** Anthropic 是**显式** `cache_control` 断点(写入 ~1.25× 价、读取 10%);OpenAI 是稳定前缀超阈值(~1024 token)**自动**缓存(命中部分 50% 价)。

**Q3:prompt caching 和语义缓存有什么区别?能叠加吗?**
标准答:**不同层、可叠加**。prompt caching 复用的是**同一请求内的稳定前缀**(省的是前缀的重复计算);语义缓存复用的是**跨请求的整段答案**(新 prompt 与历史某 prompt 语义相同就直接返缓存答案,0 次 LLM 调用)。前者底层是 KV-Cache,后者靠 embedding 相似度匹配。生产里常串成流水线:先查语义缓存,未命中再走带 prompt caching 的真实调用。

**Q4:model routing 在成本优化里指什么?最大风险是什么?**
标准答:它是 [[05 Routing|Routing]] 在**成本维度**的应用——先判这一步的难易,简单的分流到便宜小模型、难的才给昂贵大模型。实现分**学习型**(RouteLLM,训练判别器预测弱模型能否胜任)和**规则/复杂度型**(按 token 长度/关键词/复杂度打分,零额外调用、亚毫秒)。最大风险是**误判**:把难题路由给弱模型答错,返工/用户流失的代价可能远超省的钱。要监控分流质量 + 保留升级兜底。

**Q5:怎么把 agent 的延迟降下来?**
标准答:① **并行**——无依赖步骤并发,总延迟从 `Σ(各步)` 降到 `max(各步)`(联动 [[06 Parallelization|Parallelization]],[[12 LLMCompiler|LLMCompiler]] 自动并行 DAG);② **prompt caching** 降长 prompt 的首 token 延迟;③ **流式输出**先吐首 token,不降真实总延迟但大幅降**感知延迟**;④ **推测解码**(小模型猜、大模型一次性验证)在不损质量下提速,通常由 vLLM 等推理引擎提供;⑤ **上下文压缩**让每步 prompt 更小更快。

**Q6(陷阱):一味用最便宜的模型一定省钱吗?**
标准答:不一定。**优化目标是"单位成功任务的成本/延迟",不是单次调用单价。** 便宜模型若把任务做错,触发更多重试/步数,总账反而升。正确做法是按难度路由 + 守住质量,算端到端的"完成一个任务花多少钱"。

**Q7:为什么说缓存被打散是头号坑?**
标准答:因为 prompt caching 的命中依赖前缀**逐字节稳定**。一旦在稳定前缀中间插入了任何变化内容(动态时间戳、随请求变的检索结果放进系统提示),从那个位置往后的 KV 全部失效、缓存全程不命中,反而白付了写入的溢价(~1.25×)。所以工程纪律是**稳定的东西全部前置、多变的全部后置**。

## 知识拓展

**这篇是整合视角,不是新概念。** 它把散落的 [[05 Routing|Routing]]、[[06 Parallelization|Parallelization]]、[[21 上下文压缩与卸载|上下文压缩与卸载]]、[[102 KV-Cache|KV-Cache]] 从"成本/延迟"这一根工程主线串起来。理解它的钥匙是那两个公式:`成本 ≈ 步数 × 每步 token × 单价`、`延迟 ≈ 步数 × 每步往返`——所有杠杆都是在压其中某个乘数。

**与其它模块的深度联动。**
- **× durable execution**:[[34 Agent 部署与持久化执行|Agent 部署与持久化执行]] 的崩溃重放"不重花已完成调用",本质也是"压重复计算"——只不过省的是崩溃重跑的重复,而非同前缀的重复。
- **× Ralph loop**:[[33 长程任务与自我改进(Ralph loop)|Ralph loop]] 重复读 `TODO.md` + 代码作前缀,**prompt caching 几乎必开**;且无人值守循环的头号风险是失控烧钱,本篇的预算账本/限流是其成本护栏。
- **× ReWOO**:[[11 ReWOO|ReWOO]] 一次性批量规划、减少问大模型的次数,直接压"步数"乘数。

**前沿与进阶(带年份)。**
- **RouteLLM(LMSYS, 2024)**:学习型 LLM 路由的代表工作,训练判别器在保证质量下最大化弱模型承接比例,是"按难度分价位"思路的学术化。
- **Speculative decoding(Leviathan et al. / Chen et al., 2023)**:小模型起草、大模型并行验证,在不损质量下提速,已成 vLLM/TensorRT-LLM 等推理引擎标配;后续 **Medusa、EAGLE(2024)** 等进一步提升验证接受率。
- **Prompt/prefix caching 走向标准化(2024–2026)**:从各家 API 的差异化特性(Anthropic 显式断点、OpenAI 自动)逐步成为生产 agent 的默认开关;vLLM 的 **automatic prefix caching** 让自托管也能享受同等红利。
- **知识蒸馏**(用大模型能力蒸到小模型常驻、大模型兜底)是"压单价"的训练侧手段,延伸阅读可看 LLM 域的压缩主题(剪枝/稀疏化/蒸馏)。

**边界与反模式。**
- **过早优化**:低频原型/一次性脚本别堆 router + 多级缓存,先把功能跑通——过早优化只增复杂度。
- **过度压缩丢信息**:[[21 上下文压缩与卸载|上下文压缩与卸载]] 压过头,模型丢掉决策必需细节,省了 token 却办错事。
- **只看单价不看总账**:见 Q6,是最常见的认知误区。
- **语义缓存滥用**:在强上下文依赖步骤用语义缓存,会复用不该复用的答案——返错答的代价可能远超省的钱。
- **缓存一致性失守**:工具结果缓存不及时失效,用过期数据决策。
