[[16 工具设计与工具层|工具设计与工具层]]（Tool Use 设计模式）研究的是：把真实后端包装成模型能**选对、填对、出错后能纠正**的能力边界。[[15 Function Calling 工具调用|Function Calling]] 解决调用格式；工具设计决定暴露什么、返回什么，以及 runtime 如何拒绝不安全的请求。

## 直觉／生活类比

工具像机场的柜台，而不是一扇直通跑道的门。柜台名要清楚（`get_order_status`），表格字段要少而明确，柜员回复要告诉旅客下一步；最关键的是，安检与登机资格由机场系统核验，而不是由旅客在表格里写「我是机长」。

所以一个好工具同时有两份契约：给模型的**描述／schema 契约**，以及给后端的**身份／权限／状态契约**。后者不能由 description、tool annotation 或 `strict: true` 代替。

## 小数字手算

一次查询若回传 $240$ 个 token 的完整订单，但模型下一步只需要状态和 ETA 的 $40$ 个 token；在 12 次调用的任务中：

$$
240\times12=2880,\qquad 40\times12=480,\qquad 2880-480=2400
$$

因此本次任务少带入 $2400$ token，比例为 $2400/2880\approx83.3\%$。这里的 $240$ 和 $40$ 应来自实际 trace，而不是把「字节数 ÷ 4」当成通用 token 公式。

## 公式推导

设工具回传 $r_i$ 个 token，模型真正需要的字段回传 $s_i$ 个 token，则工具结果的上下文负担是：

$$
C_{\text{result}}=\sum_{i=1}^{n}r_i,
\qquad
C_{\text{minimal}}=\sum_{i=1}^{n}s_i,
\qquad
\Delta C=\sum_{i=1}^{n}(r_i-s_i)
$$

但减 token 不能删掉完成下一步所需的语义。正确目标是最小化 $C$，同时保持任务所需事实 $F$：$\min C\;\text{s.t.}\;F_{\text{next step}}\subseteq\text{result}$。工具 schema 也一样：更严格的输入形状降低解析歧义，却不会推出「这个会话有权读取这个资源」。

## 可运行代码：❌ 万能入口 vs ✅ 明确工具＋runtime 策略

```python
# ❌ 能运行，但把选择、校验和权限都藏进自由文本 action/data。
def naive_execute(action: str, data: dict) -> dict:
    return {"ok": True, "action": action, "data": data}

print(naive_execute("delete_order", {"order_id": "ORD-9", "actor": "admin"}))
# 没有可信会话、资源归属、状态机或审计；“admin”只是模型生成的字符串。
```

```python
# ✅ 纯标准库，可直接运行：模型可见参数与可信会话上下文严格分开。
from __future__ import annotations

ORDERS = {
    "ORD-7": {"owner": "user-1", "status": "shipped", "eta": "2026-07-20", "address": "不回传"},
}

GET_ORDER_STATUS_SCHEMA = {
    "type": "object",
    "properties": {"order_id": {"type": "string", "description": "订单号，例如 ORD-7"}},
    "required": ["order_id"],
    "additionalProperties": False,
}

def get_order_status(arguments: dict, session_user_id: str) -> dict:
    # 真实 runtime：未知字段、类型、授权和状态都在后端重验。
    if set(arguments) != {"order_id"} or not isinstance(arguments["order_id"], str):
        return {"ok": False, "error": "order_id 必须是唯一的字符串字段"}
    order = ORDERS.get(arguments["order_id"])
    if order is None:
        return {"ok": False, "error": "订单不存在；请核对订单号"}
    if order["owner"] != session_user_id:
        return {"ok": False, "error": "无权读取该订单"}
    # 高信号、稳定、最小的模型结果；地址仍留在受控后端。
    return {"ok": True, "status": order["status"], "eta": order["eta"]}

assert get_order_status({"order_id": "ORD-7"}, "user-1")["status"] == "shipped"
assert get_order_status({"order_id": "ORD-7"}, "user-2")["ok"] is False
assert get_order_status({"order_id": "ORD-7", "actor": "user-1"}, "user-1")["ok"] is False
print("runtime 校验通过")
```

把 `GET_ORDER_STATUS_SCHEMA` 放进 provider 的 function/tool 定义时，description 要包含「做什么、何时用、何时不用、参数含义与限制」；复杂嵌套参数再补 schema-validated examples。工具输出应优先返回模型下一步所需的稳定 ID 和高信号字段。 [Anthropic Define tools（检索于 2026-07-17）](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)

## 面试高频
> 面试地图：[[Agent 面试题库]]

**Q：为什么不用一个 `execute(action, params)`？** 它把工具选择、参数格式和权限边界塞进一个自由文本入口，模型难选、后端难审计。只有当动作真的共享同一个明确状态机时才合并；否则应按用户意图给动词＋对象命名的工具。

**Q：工具 description 应写什么？** 写能力、触发条件、非适用条件、每个参数的意义和返回限制；只写「处理订单」无法消除工具间歧义。

**Q：怎样既省 token 又不丢信息？** 默认回高信号摘要和稳定 ID；需要详情时用下一次受控读取。用真实任务 trace 比较任务成功率和 token，不能只看返回体变短。

## 关键事实

- 工具描述是模型选择工具和填写参数的重要输入；Anthropic 的当前指南要求说明做什么、何时用／不用、参数语义和限制，并建议复杂输入提供经过 schema 验证的 examples。 [Anthropic Define tools（检索于 2026-07-17）](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- 工具结果应以高信号字段和稳定标识为主；冗长返回会消耗上下文并增加模型抽取重点的难度。 [Anthropic Define tools（检索于 2026-07-17）](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- JSON Schema／`strict: true` 约束的是调用形状；runtime 仍须从可信会话取得主体，检查资源归属、业务状态、限额和审批。 [OpenAI Function calling（检索于 2026-07-17）](https://developers.openai.com/api/docs/guides/function-calling)
- MCP 的 `readOnlyHint`、`idempotentHint` 等 annotation 是提示而非授权依据；来自不可信 server 时 client 不应据此做安全决策。 [MCP Schema Reference 2025-11-25（检索于 2026-07-17）](https://modelcontextprotocol.io/specification/2025-11-25/schema)
- 工具数变大时，先改善命名、描述和粒度，再用 [[18 工具检索与动态加载|工具检索与动态加载]] 限制候选集；工具定义不是越多越好。 [Anthropic Define tools（检索于 2026-07-17）](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) [OpenAI Tool search（检索于 2026-07-17）](https://developers.openai.com/api/docs/guides/tools-tool-search)
