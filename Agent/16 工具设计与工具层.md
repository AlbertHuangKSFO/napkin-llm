[[16 工具设计与工具层|工具设计与工具层]] 的核心命题:**一个 agent 拿到的工具集,就是它能力的边界**——它能做什么、不能做什么、做得好不好,几乎全由工具的设计与暴露方式决定。模型再强,工具烂,agent 也烂。

这是 [[15 Function Calling 工具调用|Function Calling 工具调用]] 的上层议题:Function Calling 解决「怎么把工具喂给模型、怎么执行」,工具设计解决「**喂什么样的工具、怎么组织它们**」。前者是机制,后者是工程与产品判断,而后者往往才是 agent 成败的分水岭。

## 本质:工具集 = 能力边界

把 agent 想成一个被关在房间里、只能通过几个「按钮」与外界交互的智能体。它有多聪明决定了它怎么用这些按钮,但**有哪些按钮、每个按钮干什么、按错了会不会有反馈**,完全由你设计。

- 没给它「查数据库」的工具,它就**永远查不了库**——再聪明也变不出来。
- 给了它一个 `description` 含糊的工具,它**不知道何时该按**,要么漏按要么乱按。
- 给了它一个返回 2KB 无关 JSON 的工具,它的**上下文被噪声塞满**,后续推理变差(见 [[20 上下文工程|上下文工程]])。
- 给了它一个报错只说「Error 500」的工具,它**无从纠正**,只能放弃。

所以工具设计不是「实现完功能顺手包一下」的收尾活,而是**塑造 agent 行为的第一杠杆**。Anthropic、OpenAI 在 agent 工程实践里反复强调同一句话:**写工具要像写给模型用的 API,而模型是一个会读文档、但没法问你问题、且上下文有限的「初级工程师」**——它只能靠你给的 name/description/schema/错误信息来推断一切。

## 好工具的设计原则

![[工具设计与工具层-好坏对比.svg]]

**1. 命名清晰(动词 + 对象)**。`get_order_status` 而非 `do_stuff` / `helper`。模型用 `name` 做第一层筛选,名字本身就该自解释。

**2. 描述写「何时用」,不只写「是什么」**。`description` 是模型决定**用不用、什么时候用**的唯一依据(见 [[15 Function Calling 工具调用|Function Calling 工具调用]])。好的描述会写明**触发条件**:「当用户询问订单是否发货、到哪了、预计何时到达时调用」。差的只写「处理订单」——模型不知道边界,要么漏调要么把无关请求也往这塞。

**3. 参数 schema 紧凑而明确**。每个参数给 `type`、`description`、必要时 `enum` 限定取值、用 `required` 标必填、在描述里给**格式示例**(`order_id 形如 'ORD-12345'`)。避免一个 `data: string` 的自由文本黑洞——那等于把解析负担全压给模型,极易填错。

**4. 返回体 token-efficient(只回模型需要的)**。工具返回**不是给人看的完整数据,是给模型推理用的**。一个查订单工具回 `{status, eta}` 两个字段就够,不要把整条订单(地址、支付流水、商品明细…)2KB 全塞回去——那既烧 token,又用无关信息**污染上下文**、干扰后续推理。需要时让模型再调细节工具。这是 [[20 上下文工程|上下文工程]] 在工具层的体现。

**5. 错误信息可读且可恢复**。报错要让模型**读懂并能据此纠正**:不是 `Error 500`,而是 `order_id 'X' 不存在,正确格式需带 'ORD-' 前缀,例如 'ORD-12345'`。这样模型回灌读到后能**改参数重试**,形成自愈循环(机制见 [[15 Function Calling 工具调用|Function Calling 工具调用]] 的错误回灌、思想同 [[13 Reflection 与 Reflexion|Reflection 与 Reflexion]])。好错误信息是 agent 鲁棒性最便宜的来源之一。

**6. 幂等与最小权限(安全)**。写类工具尽量**幂等**(重复调用结果一致,防模型重试时副作用叠加)。每个工具只给**完成它所需的最小权限**——查询工具就别给删除权;文件工具限定可访问目录。模型给的参数**不可信**,要校验、要[[24 沙箱、最小权限与人审闸门|沙箱]]。

**7. 控制工具数量,避免选择困难**。工具一多(几十上百),模型**选择困难**、还吃光上下文。对策:合并粒度过细的工具、按场景**分层/按需加载**(只在相关阶段暴露相关工具)、用 [[17 MCP 模型上下文协议|MCP 模型上下文协议]] 动态发现而非一次性全塞。「工具越多越强」是反直觉的错觉——往往是越精简越准。

**8. 工具粒度匹配模型的「一步」**。一个工具最好对应模型决策里的一个自然动作。太粗(一个工具干十件事、靠 `data` 里塞 flag 区分)模型难控;太细(每个字段一个工具)又要太多轮往返。

## 工具层(tool layer):agent 与外部世界之间的那层

![[工具设计与工具层.svg]]

「工具层」是 agent 推理与真实后端之间的**适配层**:它把异构的后端——[[17 MCP 模型上下文协议|MCP 模型上下文协议]] server、REST/原生 API、本地函数/脚本——**统一抹平成同一种「带 schema 的工具」抽象**,让 agent 只需面对「一组工具」,不关心背后是什么。

它通常承担这些职责:
- **统一暴露**:把 MCP server 的 tools、第三方 REST API、本地 Python 函数,都转成 [[15 Function Calling 工具调用|Function Calling 工具调用]] 认识的 schema 形态。
- **发现(discovery)**:运行时列出有哪些工具可用、按需把相关子集注入上下文。
- **鉴权 / 限流 / 校验 / 沙箱**:模型给的参数在这层被校验、危险调用被拦截、外部凭证在这层管理(模型看不到密钥)。
- **裁剪返回**:把后端的冗长响应裁成 token-efficient 的形态再回灌(原则 4 的落地点)。

**今天工具层常由 [[17 MCP 模型上下文协议|MCP 模型上下文协议]] 的 client 实现**:MCP client 连上一个或多个 MCP server,把它们暴露的工具发现出来、统一成工具列表交给 agent。这也是 [[23 Agent Harness 概览|Agent Harness 概览]] 里的核心组件之一——harness = 模型循环 + 上下文管理 + **工具层**。把工具层抽出来的好处:换后端(本地函数→远程 MCP server)对 agent 透明,agent 代码不用改。

## 坏 schema → 改好(可跑对比)

```python
# ❌ 坏工具:名字模糊、描述没说何时用、参数是自由文本、无校验
bad = {
    "name": "do_stuff",
    "description": "处理订单相关的事",
    "parameters": {
        "type": "object",
        "properties": {"data": {"type": "string"}},   # 黑洞:模型不知道塞什么
        "required": ["data"]
    }
}

# ✅ 好工具:动词+对象命名、描述写清触发条件、参数明确带示例与枚举
good = {
    "name": "get_order_status",
    "description": ("按订单号查询订单状态。"
                    "当用户询问『订单到哪了 / 是否已发货 / 预计何时送达』时调用。"
                    "只读查询,不修改任何数据。"),
    "parameters": {
        "type": "object",
        "properties": {
            "order_id": {
                "type": "string",
                "description": "订单号,形如 'ORD-12345'(必须带 ORD- 前缀)"
            }
        },
        "required": ["order_id"]
    }
}

# 执行函数:返回精简(只回模型要用的)、错误可读可恢复、最小权限(只读)
def get_order_status(order_id: str):
    if not order_id.startswith("ORD-"):                       # 校验
        return {"error": f"order_id '{order_id}' 格式错误,需带 'ORD-' 前缀,如 'ORD-12345'"}
    row = db.query_readonly("SELECT status, eta FROM orders WHERE id=?", order_id)  # 只读
    if row is None:
        return {"error": f"订单 '{order_id}' 不存在,请核对订单号"}     # 可恢复的错误
    return {"status": row.status, "eta": row.eta}              # 精简:不回整条订单
```

差别全在「**模型视角**」:好工具让模型一眼知道**何时调、怎么填、错了怎么改**,返回还不污染上下文;坏工具把这些负担全甩给模型,于是频繁失败、烧 token。

## 好工具 vs 坏工具对比表

| 维度 | 坏工具 | 好工具 | 为什么 |
|---|---|---|---|
| 命名 | `do_stuff` / `helper` | `get_order_status` | 模型靠名字第一层筛选 |
| 描述 | 「处理订单」 | 「用户问订单到哪了/是否发货时调」 | 描述是模型判断**何时用**的唯一依据 |
| 参数 | `data: string` 自由文本 | `order_id: string`(带格式示例 + required) | 紧凑明确才填得对 |
| 返回体 | 整条订单 2KB | `{status, eta}` 两字段 | token-efficient,不污染上下文 |
| 错误 | `Error 500` | 「格式需带 ORD- 前缀,如 ORD-12345」 | 可读可恢复 → 模型自纠 |
| 权限 | 全表读写 | 只读、最小权限 | 安全 + 幂等 |
| 数量 | 一股脑塞 80 个 | 精简 / 分层按需加载 | 太多致选择困难、吃上下文 |

## 何时用 / 坑 / 反模式

**坑**:
- **把内部实现照搬成工具**:内部 API 是给程序员用的,字段全、报错是错误码;直接暴露给模型,模型读不懂。要**重新为模型设计**一层。
- **返回体不裁剪**:最常见的 token 杀手,也是上下文污染主因。
- **错误吞掉或不可读**:抹掉了 agent 自愈的可能。
- **工具爆炸**:见原则 7,「工具越多越好」是反模式。
- **危险工具无护栏**:`run_shell` / `eval_code` / `delete_file` 这类必须[[24 沙箱、最小权限与人审闸门|沙箱 + 最小权限 + 人类确认门槛]](否则即 [[15 Tool Misuse 与意外代码执行|Tool Misuse]])。

**反模式**:
- 用一个万能工具 `execute(action, params)` 靠 `action` 字段分发——等于把工具选择从 schema 层(模型擅长)推回到参数层(模型易错)。
- 工具返回「给人看的话术」(`"亲,您的订单正在路上哦~"`)而非结构化事实——模型要的是 `{status:"shipped"}`,不是营销文案。

**何时该重新设计工具而非加更多工具**:当 agent 频繁选错工具 / 填错参数 / 在上下文里迷失,**首先怀疑工具设计**,而不是去换更强的模型或加更多工具。改 description、裁返回体、合并工具,往往比换模型见效快得多。

## 关键事实

- **工具集 = agent 的能力边界**;工具设计是塑造 agent 行为的**第一杠杆**,常比换模型更决定成败。
- 八条原则:**清晰命名 / 描述写「何时用」/ 参数紧凑明确 / 返回 token-efficient / 错误可读可恢复 / 幂等最小权限 / 控制数量防选择困难 / 粒度匹配一步**。
- 写工具要把模型当「**会读文档但不能提问、上下文有限的初级工程师**」——它只能靠你给的 name/description/schema/错误信息推断一切。
- **返回体只回模型需要的**:既省 token 又防 [[20 上下文工程|上下文工程]] 意义上的污染。
- **错误也要可读可恢复**:这是 agent 自愈(自纠重试)最便宜的来源,机制接 [[15 Function Calling 工具调用|Function Calling 工具调用]] 的错误回灌、思想同 [[13 Reflection 与 Reflexion|Reflection 与 Reflexion]]。
- **工具层**是 agent 与外部世界之间的适配层,把 MCP server / REST API / 本地函数统一成「带 schema 的工具」,**今天常由 [[17 MCP 模型上下文协议|MCP 模型上下文协议]] 的 client 实现**,是 [[23 Agent Harness 概览|Agent Harness 概览]] 的核心组件。
- agent 表现差时**先查工具设计**(description、返回体、工具数量),再考虑换模型。

## 主流开源实现 / Python 库

- **`modelcontextprotocol/python-sdk`**(pip `mcp`):官方 MCP SDK,把工具层标准化成 server/client——**今天构建可复用工具层的事实标准**,首选。
- **`ComposioHQ/composio`**(pip `composio`):托管工具集,1000+ 预置 toolkit(GitHub/Slack/Notion…),代管 OAuth/鉴权/限流,还带 tool search 与上下文管理——**不想自己写一堆集成时首选**。
- **`pydantic/pydantic-ai`** 的 tools:用 Python 函数 + 类型注解直接声明工具,自动生成 schema,贴合「把工具当 API 写」的理念。
- **`langchain` tools**(pip `langchain`):`@tool` 装饰器 + 海量现成 Toolkit,生态最广但抽象偏重。
- 当下首选:自建标准工具层用 `mcp`;要现成第三方集成与托管鉴权用 `composio`;轻量类型化工具用 `pydantic-ai`。

## 工业界实践

### 谁在认真做工具设计:第一手实践来源

- **Anthropic《Writing tools for agents》/《Building effective agents》**:反复强调「把工具当写给模型用的 API」「返回 token-efficient」「错误可读可恢复」——本笔记八原则的主要出处。
- **OpenAI Function Calling / Agents SDK best practices**:强调 description 写触发条件、参数 enum/required、控制工具数量。
- **Cursor / Claude Code / Devin 等代码 Agent**:工具集设计直接决定能力——它们普遍只暴露**少而精**的核心工具(读文件、改文件、跑命令、搜代码),而非几百个细粒度 API,印证「工具越精简越准」。

### 工具层在生产里的真实形态

| 后端类型 | 接入方式 | 工具层职责 |
|---|---|---|
| 本地 Python 函数 | `@tool` 装饰器 / 类型注解自动生成 schema | 直接暴露 |
| 第三方 REST API | 手写 wrapper 或 `composio` 托管 | 鉴权(代管 OAuth/密钥)、限流、裁剪返回 |
| 数据库 | 只读查询工具 + 参数化(防注入) | 最小权限、SQL 校验、结果裁剪 |
| [[17 MCP 模型上下文协议|MCP]] server | MCP client 连接、动态发现 | 统一成 schema、按需注入 |
| Shell / 代码执行 | 沙箱内执行 | 沙箱、白名单、人审闸门 |

**今天工具层常由 [[17 MCP 模型上下文协议|MCP]] client 实现**:连一个或多个 MCP server、发现其工具、统一成工具列表交给 Agent;换后端(本地函数→远程 MCP server)对 Agent 透明。它是 [[23 Agent Harness 概览|Agent Harness 概览]] 的核心组件(harness = 模型循环 + 上下文管理 + 工具层)。

### 规模化:工具一多怎么办(关键工程难题)

当工具达几十上百个,「全塞进一次请求」会致选择困难 + 吃光上下文。生产对策(详见 [[18 工具检索与动态加载|工具检索与动态加载]]):
- **分层暴露**:按场景/阶段只暴露相关工具子集(如「检索阶段」只给搜索类工具)。
- **工具检索(tool RAG)**:对工具 description 建向量索引,运行时按用户意图**检索 top-k 工具**动态注入,而非全量。
- **工具分组 / 命名空间**:`github_*`、`slack_*` 分组,先选组再选工具(MCP server 天然是分组单位)。
- **元工具(meta-tool)**:用一个 `search_tools` 工具让 Agent 自己查有哪些工具——把工具发现也变成工具调用。

### 返回体裁剪的工程手段(原则 4 落地)

- **字段白名单**:只回 `{status, eta}`,丢弃地址/支付流水/明细。
- **分页 + 摘要**:大列表只回前 N 条 + 总数 + 「调 X 工具看更多」。
- **引用而非内容**:大文档/大结果返回 **handle/id**,模型需要时再调细节工具取——即上下文卸载(见 [[21 上下文压缩与卸载|上下文压缩与卸载]])。
- **截断 + 提示**:超长返回截断并标注「已截断,共 N 条」。

### 踩坑

- **把内部实现照搬成工具**:内部 API 字段全、报错是错误码,模型读不懂——必须**重新为模型设计**一层。
- **返回体不裁剪**:最常见的 token 杀手 + 上下文污染主因。
- **错误吞掉或不可读**:抹掉 Agent 自愈可能。
- **危险工具无护栏**:`run_shell`/`eval_code`/`delete_file` 必须沙箱 + 最小权限 + 人审确认。
- **万能工具 `execute(action, params)`**:靠 `action` 字段分发,把工具选择从 schema 层(模型擅长)推回参数层(模型易错),是经典反模式。

## 面试高频

**Q1:为什么说「工具集 = Agent 的能力边界」?**
标准答:Agent 只能通过工具与外界交互——没给查库工具就永远查不了库,模型再聪明也变不出来;description 含糊它不知何时按;返回体冗长它上下文被噪声塞满推理变差;错误不可读它无从纠正只能放弃。所以工具设计是**塑造 Agent 行为的第一杠杆**,常比换更强的模型更决定成败。

**Q2:好工具的设计原则有哪些?**
标准答(八条):① **命名清晰**(动词+对象,`get_order_status` 而非 `do_stuff`);② **描述写「何时用」**(触发条件,不只写「是什么」);③ **参数 schema 紧凑明确**(type/description/enum/required + 格式示例,避免 `data:string` 黑洞);④ **返回 token-efficient**(只回模型需要的字段,不污染上下文);⑤ **错误可读可恢复**(不是 `Error 500`,而是「需带 ORD- 前缀,如 ORD-12345」);⑥ **幂等 + 最小权限**(查询工具别给删除权);⑦ **控制数量防选择困难**(合并/分层/按需加载);⑧ **粒度匹配模型一步**(不太粗不太细)。
- **记忆锚**:把模型当「**会读文档但不能提问、上下文有限的初级工程师**」,它只能靠你给的 name/description/schema/错误信息推断一切。

**Q3:工具返回为什么不能把完整数据全塞回去?**
标准答:工具返回**不是给人看的完整数据,是给模型推理用的**。把整条订单 2KB 全回会:① 烧 token;② 用无关信息**污染上下文**、干扰后续推理(见 [[20 上下文工程|上下文工程]])。应只回 `{status, eta}`,需要细节时让模型再调细节工具——这是上下文工程在工具层的体现。

**Q4:工具太多导致选择困难怎么解?** 合并粒度过细的工具、按场景**分层/按需加载**(只在相关阶段暴露相关工具)、对工具 description 做**向量检索**动态注入 top-k、用 [[17 MCP 模型上下文协议|MCP]] 动态发现而非一次性全塞。「工具越多越强」是反直觉的错觉——往往越精简越准(详见 [[18 工具检索与动态加载|工具检索与动态加载]])。

**Q5(陷阱):Agent 频繁选错工具/填错参数,第一步该做什么?** **先怀疑工具设计**(改 description、裁返回体、合并工具),而不是先去换更强的模型或加更多工具。改工具往往比换模型见效快得多。

**Q6:什么是「工具层」?它和 Function Calling、MCP 的关系?**
标准答:[[15 Function Calling 工具调用|Function Calling]] 解决「怎么把工具喂给模型、怎么执行」(机制);**工具设计**解决「喂什么样的工具、怎么组织」(工程/产品判断)。**工具层**是 Agent 推理与真实后端之间的适配层,把 MCP server / REST API / 本地函数统一抹平成「带 schema 的工具」,并承担发现、鉴权、限流、校验、沙箱、裁剪返回等职责;今天常由 [[17 MCP 模型上下文协议|MCP]] client 实现,是 [[23 Agent Harness 概览|Agent Harness 概览]] 的核心组件。

**Q7(反模式):用一个万能工具 `execute(action, params)` 好不好?** 不好。靠 `action` 字段分发等于把工具选择从 **schema 层**(模型擅长——靠 name/description 选)推回到**参数层**(模型易错——要在自由文本里编对 action)。同理,工具返回「给人看的话术」(「亲,订单在路上哦~」)而非结构化事实(`{status:"shipped"}`)也是反模式。

## 知识拓展

- **谱系定位**:工具设计是 [[15 Function Calling 工具调用|Function Calling]] 的**上层议题**(机制 vs 工程);返回裁剪接 [[20 上下文工程|上下文工程]] 与 [[21 上下文压缩与卸载|上下文压缩与卸载]];错误可恢复思想同 [[13 Reflection 与 Reflexion|Reflection 与 Reflexion]];工具太多接 [[18 工具检索与动态加载|工具检索与动态加载]];工具层标准化接 [[17 MCP 模型上下文协议|MCP]];整体是 [[23 Agent Harness 概览|Agent Harness 概览]] 的一部分。
- **延伸主题**:
  - **MCP 生态(2024-11 起)**:把「工具暴露」从私有 SDK 升级为开放协议,让工具可跨 Agent/客户端复用,是工具层标准化的里程碑(见 [[17 MCP 模型上下文协议|MCP 模型上下文协议]])。
  - **托管工具平台**:`composio`(1000+ 预置 toolkit、代管 OAuth)、LangChain Toolkits、各家 Agents SDK 内置工具——「不想自己写一堆集成」的工业选择。
  - **工具调用评测**:Berkeley Function-Calling Leaderboard、ToolBench/ToolLLM(Qin et al., 2023)、Gorilla(Patil et al., 2023)衡量「选对工具 + 填对参数」的能力,反向指导工具 schema 怎么写模型才用得对。
  - **安全维度**:危险工具(shell/eval/delete)需沙箱 + 最小权限 + 人审闸门;不当暴露会导致工具滥用与意外代码执行(本笔记已链接到对应安全笔记);也是 prompt injection 经由工具放大的入口。
- **边界 / 反模式**:① 把内部实现照搬成工具;② 返回体不裁剪;③ 错误吞掉或不可读;④ 工具爆炸;⑤ 危险工具无护栏;⑥ 万能 `execute` 工具;⑦ 工具返回营销话术而非结构化事实;⑧ Agent 表现差时先换模型而非先查工具设计。
