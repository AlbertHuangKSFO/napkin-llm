[[21 上下文压缩与卸载|上下文压缩与卸载]] 的本质是:上下文窗是**有限的 token 预算**,而**长历史 + 大工具结果**会迅速把它撑爆——贴一个完整网页、一份上万行日志、一个几千行的 JSON,单次工具返回就能吃掉大半窗口。这篇讲**具体的手段**:怎么把这些东西压小、或干脆挪出上下文。

它和 [[20 上下文工程|上下文工程]] 是「手段层 vs 策略层」的关系:[[20 上下文工程|上下文工程]] 回答「这一轮该放什么」的取舍原则,本篇回答「具体怎么把放不下的东西压下去/搬出去」的操作。它也是 [[19 Agent 记忆系统|Agent 记忆系统]] 的执行细节——记忆系统管「存哪、怎么回来」,压缩与卸载就是那个「存」和「回来」的具体动作。和 [[18 工具检索与动态加载|工具检索与动态加载]] 互补:那个压**工具定义**,这个压**历史和工具返回**。

![[上下文压缩与卸载.png]]

## 本质:撑爆窗口的两个来源

长程 agent 跑着跑着撞窗,几乎总是这两样在膨胀:

1. **长历史**:几十轮 ReAct,每轮的 Thought / Action / Observation 累积,旧轮次越堆越多。
2. **大工具结果**(更凶):一次 `fetch_url` 返回整页 HTML(几万 token)、一次 `read_logs` 返回一万行日志、一次 API 调用返回嵌套很深的大 JSON。**单次返回**就能把预算打穿。

为什么非治不可?三重硬约束(同 [[20 上下文工程|上下文工程]]):**容量有限**(塞满就崩,后续步骤没空间)、**越长越贵越慢**(每轮重发,token×单价,注意力平方复杂度)、**越长越笨**(lost-in-the-middle,关键指令被大段日志淹没)。一个反直觉但关键的点:**贴进去的大内容,90% 模型这一步根本用不上**——它只需要日志里报错那三行、JSON 里那两个字段。把整坨贴进来纯属浪费预算。这就是压缩与卸载的全部动机:**只留这一步真正要用的,其余压掉或挪走**。

## 机制:压缩与卸载的几把手

按「信息损失从大到小、保真从低到高」排,六种手段:

### 1. 截断与窗口滑动(truncation / sliding window)
最糙:超预算就丢。只留最近 N 轮、或把单个工具返回截到前 X 字符。最省 token、零额外开销,但**硬丢信息**——被截掉的报错可能正是关键。适合「确定旧内容不再需要」时。

### 2. 摘要压缩(summarization)
不丢,**压成 summary 再留**。两个粒度:
- **对旧轮次**:每隔几轮把历史浓缩成「做了什么、得了什么结论、还差什么」。
- **对大工具结果**:工具一返回大内容,先用一次小模型调用把它摘成几句再进上下文。

比截断温和,保住脉络丢了细节。代价:**不可逆**(原文没了)、每次摘要要**额外一次模型调用**。

### 3. 截断 + 滚动摘要 = compaction(压实)
摘要的「触发式」升级,是当前 agent 框架(Claude Code 等)的主力:**监控 token 占用,接近阈值(常 ~80%)时触发一次 compaction**,把到目前为止的历史(尤其冗长 Observation)压成结构化摘要(保留关键决策、结论、待办、踩过的坑),替换原始历史,只留最近几轮原文。压完占用骤降,任务可**无限延续**不撞窗。详见 [[20 上下文工程|上下文工程]] 的 compaction 节。

### 4. 结构化抽取(structured extraction)
比摘要更精准:**不让模型自由概括,而是按预定义 schema 只抽出要的字段**。一个大 JSON 返回,只抽 `status` 和 `id` 两个字段进上下文,其余丢弃;一页 HTML 只抽正文。比摘要省调用(可以是规则/代码而非模型)、且**确定性强**(不会被模型自由发挥丢错东西)。适合工具返回结构已知的场景。

### 5. 卸载到文件系统(filesystem-as-context,「给地图不给手册」)
最彻底、且常是最优:**大内容根本不进上下文,写到外部文件,上下文里只留路径 + 一句目录/摘要**。模型需要某段时,**主动调工具(read/grep)把那一小段读回来**。

类比:你不背整本手册,只记「手册在书架第三格」,要用时去翻。一份 1 万行日志、一个 50 页 PDF、整个代码库——不塞进上下文,落在文件系统里;上下文只留「文件在 `/data/run.log`,结构如下…」。这正是 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 的用武之地。三大好处:① 上下文极省,只放当前活跃那一小片;② 信息**无损**留外部(不像摘要丢细节);③ 天然适配 [[23 Agent Harness 概览|Agent Harness 概览]] 的文件工具。Anthropic 的 memory tool / context editing 走的就是这条路。

![[上下文压缩与卸载-卸载检索.png]]

### 6. Sub-agent 隔离(把脏活丢给隔离上下文的子 agent)
不是压内容,而是**换个地方处理**:把会产生大量中间垃圾的任务(翻 50 个网页、读整个目录、跑一堆探索)丢给一个**独立上下文**的子 agent,让它在自己的窗口里折腾,**只把最终结论回传**给主 agent。主上下文从头到尾干净,中间的大工具结果全留在子 agent 那边、用完即弃。这是 [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]] 的核心价值之一——context forking 让脏活的上下文污染被隔离。

> 一句话区分:**截断=直接丢;摘要/compaction=压缩着留;结构化抽取=只留要的字段;卸载到文件=移出去留路径(无损);sub-agent=换个上下文处理只回结论**。优先级通常:能卸载就卸载(无损)> 结构化抽取/摘要(有损但保脉络)> 截断(硬丢)。

## 与 KV-Cache 的张力(最该懂的取舍)

压缩有个隐藏代价,和 [[102 KV-Cache|KV-Cache]] 直接冲突。[[102 KV-Cache|KV-Cache]] 的省钱前提是**前缀逐字不变**才能命中缓存。而:

- **摘要 / compaction 改写了历史** → 前缀变了 → 那次压缩后,被改段的 KV-Cache 必然失效、重算变贵。所以 compaction 是「**用一次昂贵的缓存失效,换之后长期的低占用**」——合算但有即时成本,别频繁触发(设滞回:压到比如 50% 才停,避免在阈值边界反复抖动)。
- **每轮动态插不同的摘要/检索结果到中段** → 反复破坏缓存。对策:压缩动作**批量、低频**,改动尽量发生在上下文尾部而非中段。
- **卸载到文件反而护缓存**:上下文里只留稳定的「路径+索引」,常驻内容小且不变,前缀稳定,缓存命中好。这是卸载相对摘要的又一隐性优势。

一句话:**频繁改前缀=烧钱**。压缩省了 token 占用,但若做得太碎,省下的 token 还不够赔上缓存失效——要在「压小占用」和「保前缀稳定」之间权衡。这条和 [[35 Agent 成本与延迟优化|Agent 成本与延迟优化]] 强相关。

## 可跑的最小实现(伪码)

工具结果超阈值 → 自动摘要 / 卸载:

```python
THRESHOLD = 2000   # token,超过就处理

def estimate_tokens(text):
    return len(text) // 3                       # 粗估,生产用 tokenizer

def handle_tool_result(result, tool_name, llm, fs):
    """工具返回太大时:能结构化抽取就抽,否则卸载到文件,兜底才摘要。"""
    if estimate_tokens(result) < THRESHOLD:
        return result                            # 小,直接进上下文

    # 路线 A:结构已知 → 结构化抽取(确定性最强,无模型调用)
    if tool_name in EXTRACTORS:
        return EXTRACTORS[tool_name](result)     # 只留要的字段

    # 路线 B:大且非结构化 → 卸载到文件,上下文只留路径+目录(无损,首选)
    if estimate_tokens(result) > THRESHOLD * 5:
        path = fs.write(f"results/{tool_name}_{uid()}.txt", result)
        head = result[:300]
        return (f"[结果过大已卸载] 路径: {path}\n"
                f"预览(前300字): {head}\n"
                f"需要细节时用 read_file/grep 按需取回。")

    # 路线 C:中等大小 → 摘要压缩(有损但保脉络)
    return "[结果摘要] " + llm(f"把这段工具返回压成3句话,保留关键事实:\n{result}")

# 主循环里:每次工具返回都先过这道闸
def agent_loop(messages, tools, llm, fs):
    while not done(messages):
        call = llm_step(messages, llm)
        raw = tools[call.name](**call.args)
        slim = handle_tool_result(raw, call.name, llm, fs)   # 压/卸载
        messages.append({"role": "tool", "content": slim})
        messages = maybe_compact(messages, llm)              # 历史侧再压实
```

要点:① **优先级:抽取 > 卸载 > 摘要**——能确定性抽就别让模型摘,能无损卸载就别有损压;② 卸载后**必须留可检索的回路**(路径 + 怎么取),否则信息等于丢了;③ 历史侧(compaction)和工具返回侧(本函数)两条线都要管;④ 阈值触发,别每次都压(摘要要花调用、还破 [[102 KV-Cache|KV-Cache]])。

## 何时用 / 坑

**该上的场景**:任何长程 agent(几十步以上)、工具会返回大内容的 agent(爬虫、日志分析、代码 agent)、对成本/延迟敏感的生产系统、多智能体里给每个 sub-agent 精确投喂([[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]])。

**坑**:
- **压过头丢关键信息**:摘要/compaction 太激进,把后续要用的细节压没了,且**不可逆**。对策:摘要 prompt 明确保留项;关键事实优先**卸载**(无损)而非摘要。
- **卸载后没留回路**:把大内容写文件了,但上下文里的「地图」(路径/目录/摘要)不准或没说清怎么取 → 模型读不到对的文件,反而绕远路。**索引质量决定成败**。
- **忽视 KV-Cache 烧钱**:每轮微调、频繁压缩改前缀,缓存反复失效,账单暴涨却没察觉。压缩要批量、低频。
- **摘要触发抖动**:阈值卡太死,边界反复触发压缩,白花调用。设滞回。
- **结构化抽取抽错字段**:schema 没覆盖到偶发但关键的字段(比如错误码),被抽掉了。对错误/异常路径要保守,宁可多留。
- **sub-agent 回传太简**:子 agent 只回一句结论,主 agent 想追问细节却拿不到(子上下文已弃)。对策:让子 agent 把详情也落盘,回传里带路径。
- **lost-in-the-middle 没根治**:压完总量小了,但若还是把次要内容堆在中段,关键信息照样被淹。少而精 > 多而杂。

## 关键事实

- 撑爆窗口的两大来源:**长历史** + **大工具结果**(贴整页网页/万行日志/大 JSON,单次就能打穿预算)。
- 六把手,按保真排:**截断(硬丢)< 摘要/compaction(压缩着留)< 结构化抽取(只留要的字段)< 卸载到文件(无损留路径)≈ sub-agent 隔离(换上下文只回结论)**。
- **优先级:能卸载就卸载(无损)> 抽取/摘要(有损保脉络)> 截断(硬丢)**。LLMLingua 是「token 级激进压缩」的特例。
- **卸载到文件(给地图不给手册)** 常是最优:上下文只留路径+目录,用 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 按需读回——最省、无损、还护 [[102 KV-Cache|KV-Cache]]。
- 与 [[102 KV-Cache|KV-Cache]] 的张力:摘要/compaction **改写历史 → 缓存失效**,是「一次性贵换长期省」;卸载因前缀稳定反而护缓存。频繁改前缀=烧钱。
- 它是 [[20 上下文工程|上下文工程]] 的手段层、[[19 Agent 记忆系统|Agent 记忆系统]] 的执行细节,和 [[18 工具检索与动态加载|工具检索与动态加载]] 互补(那压工具定义,这压历史和返回),共同服务 [[35 Agent 成本与延迟优化|Agent 成本与延迟优化]]。

## 工业界实践

**谁在压、压什么**:几乎所有长程 agent 产品都把「压缩+卸载」做成了基础设施层,但侧重不同。

- **Anthropic 路线(卸载优先)**:2025-09-29 上线 **memory tool**(beta,客户端执行——模型发 `memory` 工具调用、你的应用在本地落盘,存哪由你控)+ **context editing**(自动清理过期 tool_result)。配合 Claude Agent SDK 内置 **compaction**(接近窗口自动压历史)。哲学是「给地图不给手册」:大内容写文件、上下文只留路径,这与 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 的 grep/read 回取天然一对。
- **LangChain/LangGraph 路线(摘要为主)**:`trim_messages`(截断/滑窗)+ `langmem` 的 `SummarizationNode`/`summarize_messages`(滚动摘要替换旧消息,并把已有摘要往下传播)。生产里常把 `SummarizationNode` 挂在图的入口,超阈值自动压。
- **OpenAI/Codex 路线**:Agents SDK 的 session 把历史存在 context window 之外的持久 session log,需要时回灌——本质也是卸载。

**典型生产架构与数据流**:工具返回 → 入闸函数判大小 → ①结构化抽取(规则,零模型调用,确定性最强)→ ②卸载到对象存储/文件系统(S3 / 本地 fs / vault,上下文只留 `s3://bucket/run_xxx.log` + 300 字预览)→ ③兜底摘要(一次小模型调用)。历史侧单独跑一条 compaction 线,滞回触发(压到 ~50% 才停,避免阈值抖动)。

**规模化与成本/延迟权衡**:
- 摘要/compaction 每触发一次 = 一次额外推理 + **一段 [[102 KV-Cache|KV-Cache]] 失效重算**。所以是「一次性贵换长期省」,务必批量、低频、改动尽量在上下文尾部。
- 卸载到文件**几乎零模型成本**且护缓存(前缀稳定),是大内容的首选;代价是多一次 read/grep 的工具往返延迟。
- **LLMLingua-2**(ACL'24,arXiv 2403.12968)把压缩建模成「抽取式 token 分类」,从 GPT-4 蒸馏监督信号,2-5× 压缩、比上代快 3-6×、端到端加速 1.6-2.9×;已集成进 LangChain / LlamaIndex。适合对 prompt token 极致敏感、又不能丢太多语义的场景。

**可观测运维**:埋点每轮 `context_tokens`、`compaction 次数`、`卸载命中率`(卸载后又被 read 回来的比例——太低说明白卸了,太高说明该留在上下文)、`摘要丢信息导致的重试率`。这些接 [[38 Agent 评估与可观测性|Agent 评估与可观测性]] 的 trace。

**踩坑与最佳实践**:① 卸载必须留**可检索回路**(路径+目录+怎么取),索引质量决定成败;② 对错误码/异常路径,结构化抽取要**保守宁多留**;③ sub-agent 回传别只回一句,把详情也落盘、回传带路径;④ 压缩 prompt 显式写「必须保留:决策、待办、踩过的坑、关键数字」。

## 面试高频

- **Q:agent 跑长了上下文爆窗,你有哪些手段?优先级怎么排?**
  A:六把手按保真度排——截断(硬丢)< 摘要/compaction(压着留)< 结构化抽取(只留要的字段)< 卸载到文件(无损留路径)≈ sub-agent 隔离(换上下文只回结论)。优先级:**能无损卸载就卸载 > 确定性抽取/有损摘要 > 截断硬丢**。追问「为什么卸载优先」→ 无损 + 极省 + 护缓存。
- **Q:compaction 和摘要什么关系?何时触发?**
  A:compaction 是摘要的「触发式工程化」——监控 token 占用,接近阈值(常 ~80%)压一次,把历史压成结构化摘要替换原文、只留最近几轮。陷阱追问:**为什么不每轮都压?** 因为每次压都破 [[102 KV-Cache|KV-Cache]] + 花一次调用,要滞回低频。
- **Q:压缩和 KV-Cache 的张力?**(高频陷阱)
  A:KV-Cache 命中要求前缀逐字不变;摘要/compaction 改写历史 → 前缀变 → 缓存失效重算。所以 compaction 是「一次性贵换长期省」;**卸载到文件反而护缓存**(只留稳定路径)。误区:以为压缩纯赚——压太碎,省的 token 还不够赔缓存失效。
- **Q:结构化抽取 vs 摘要,各自适合什么?**
  A:抽取按 schema 只取已知字段,确定性强、可用代码零调用,适合工具返回结构已知;摘要靠模型自由概括,适合脉络比细节重要的非结构化大段。陷阱:抽取漏了偶发但关键字段(错误码)就丢了——异常路径要保守。
- **Q:「给地图不给手册」是什么意思?**
  A:filesystem-as-context——大内容不进上下文,写外部文件,上下文只留路径+目录,模型按需 read/grep 取回。无损、省、护缓存,是 [[19 Agent 记忆系统|Agent 记忆系统]] 与 [[23 Agent Harness 概览|Agent Harness 概览]] 文件工具的交汇点。

## 知识拓展

- **进阶方向**:从「被动压」到「主动管」——agent 自己决定哪些该留在上下文、哪些卸载(meta-cognition),与 [[20 上下文工程|上下文工程]] 的策略层融合。
- **相关前沿(带年份)**:LLMLingua / LongLLMLingua(EMNLP'23,后者缓解 lost-in-the-middle)/ LLMLingua-2(ACL'24,抽取式、更快);MemGPT(2023,虚拟内存分页换出,见 [[19 Agent 记忆系统|Agent 记忆系统]]);RetrievalAttention(2024-09,KV-cache 卸载 + 向量检索加速长上下文推理)。
- **边界与反模式**:① 压过头丢关键细节且**不可逆**——关键事实优先卸载而非摘要;② 卸载没留回路 = 等于丢;③ 频繁微调前缀烧缓存;④ 总量压小了但仍把次要内容堆中段,lost-in-the-middle 没根治,少而精 > 多而杂。
- **本域关联**:它是 [[20 上下文工程|上下文工程]] 的手段层、[[19 Agent 记忆系统|Agent 记忆系统]] 的执行细节,与 [[18 工具检索与动态加载|工具检索与动态加载]] 互补(那压工具定义,这压历史与返回);卸载后的取回是 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 的用武之地;隔离脏活靠 [[22 多智能体系统|多智能体系统]] / [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]];整体目标服务 [[35 Agent 成本与延迟优化|Agent 成本与延迟优化]]。
