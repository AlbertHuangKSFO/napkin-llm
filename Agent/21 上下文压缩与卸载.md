[[21 上下文压缩与卸载|上下文压缩与卸载]] 的本质：把有限的上下文窗口当作一笔预算；历史、网页和工具输出不能都随身携带，必须保留当前决策所需的高信号信息，并把可复取的原件留在外部。

## 直觉：带工作摘要，不背整座档案馆

排查一次线上故障时，工程师不会把一年日志打印出来带进会议室；他带「当前错误、已排除原因、下一步」三行摘要，原始日志仍放在可查询的系统里。Agent 也一样：**上下文是会议桌，文件/对象存储/数据库是档案馆**。把档案馆搬上桌会淹没目标；只有摘要却找不回原件，又会在追问时失忆。

这和 [[20 上下文工程|上下文工程]] 的关系是「策略与执行」：前者决定该让什么信息在场，本篇实现压缩、持久化和再取回；外部原件的定位与回读可由 [[24 Agentic Search：grep vs 向量检索|Agentic Search]] 完成。

## 小数字手算：何时该压，何时该卸载

设上下文预算为 $B=10{,}000$ token，系统提示和当前任务占 $B_0=2{,}000$，连续三次工具返回分别为 $r=(1{,}000,5{,}000,4{,}000)$。若全部原样加入：

$$
B_{\text{used}}=B_0+\sum_i r_i
=2{,}000+1{,}000+5{,}000+4{,}000
=12{,}000>B
$$

假设保留最近结果的 $1{,}000$ token，把前两项写入文件，并留下 $300$ token 的结构化地图：

$$
B_{\text{after}}=2{,}000+1{,}000+300=3{,}300
$$

节省 $12{,}000-3{,}300=8{,}700$ token，同时原始 $6{,}000$ token 仍可按路径再读。数字只是预算示例，不是通用触发阈值；真正阈值应由模型窗口、工具延迟和任务的可逆性决定。

## 推导：从「删内容」到「保留可恢复状态」

把 agent 状态写成 $S=(H,A)$：$H$ 是对模型可见的历史，$A$ 是外部 artifact（文件、对象存储、数据库记录）。目标不是最小化 $|H|$，而是在预算约束下最大化下一步的有效信息：

$$
\max_{H',A'}\;U(H',A')
\quad\text{s.t.}\quad |H'|\le B
$$

四种动作的差别在于是否还能从 $A$ 恢复：

- **截断**：$H'\leftarrow\operatorname{tail}(H)$。最快，但被删内容不可恢复。
- **摘要/compaction**：$H'\leftarrow\operatorname{summary}(H)$。保留脉络，但模型摘要是有损变换。
- **结构化抽取**：$H'\leftarrow\operatorname{project}(x,\text{schema})$。已知 JSON、诊断字段等场景可确定性地只留所需列。
- **卸载**：$A'\leftarrow A\cup\{(id,x)\}$，$H'\leftarrow H\cup\{(id,\text{摘要},\text{检索方法})\}$。原件不进窗口，必要时用 $id$ 再取。

[Anthropic 的 context engineering（2025-09-29）](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)把 compaction、结构化笔记和 sub-agent 隔离列为长程任务的互补手段；它特别提醒：摘要提示先追求召回，再消除多余信息。不要把「能压缩」误读成「应该删除原始证据」。

## 可运行代码：先外存，再把检索回路放回上下文

❌ 朴素做法把完整结果直接塞回消息；一次大日志就会污染后续每一步。

```python
def naive_tool_message(result: str) -> str:
    return result  # 大 HTML、日志、JSON 全部进入上下文
```

✅ 下面的纯 Python 示例把大结果写进临时目录，只返回稳定的引用、长度和预览。生产环境应换成受权限控制的 artifact store，并记录内容哈希与访问审计。

```python
from pathlib import Path
from tempfile import TemporaryDirectory

LIMIT = 80

def contextualize(result: str, store: Path, key: str) -> str:
    if len(result) <= LIMIT:
        return result
    path = store / f"{key}.txt"
    path.write_text(result, encoding="utf-8")
    preview = result[:40].replace("\n", " ")
    return f"[已卸载 id={key} bytes={len(result)} preview={preview!r}; 用 read(id) 按需回读]"

with TemporaryDirectory() as tmp:
    message = contextualize("error=E42\n" * 30, Path(tmp), "tool-001")
    assert "id=tool-001" in message
    assert (Path(tmp) / "tool-001.txt").read_text(encoding="utf-8").startswith("error=E42")
    print(message)
```

代码的关键不是 `80` 这个演示阈值，而是回传里包含可验证的 `id`、预览和取回动作；否则「卸载」只是难以发现的丢失。

## 长程任务的选型卡

- 工具输出小、下一步马上要用：原样保留。
- 返回结构稳定，且只需要少数字段：先结构化抽取；错误码和异常分支要保守保留。
- 需要连续对话脉络：在接近预算时做高召回 compaction，并保留最近原文。
- 日志、代码库、网页、实验产物：先卸载，保留 `id + 摘要 + 如何检索`。
- 探索面很广、主线只需结论：让 [[26 Sub-agents 与 Agent Teams|sub-agent]] 在独立上下文调查，并交付可复查 artifact，而不只回一句结论。

⚠️ **compaction 不等于 session reset。** 前者是在同一工作流中以摘要替换旧历史；后者让新会话从结构化交接物恢复。Anthropic 在其长程应用 harness 文章（2026-03-24）也明确区分两者：[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)。

## 面试高频
> 面试地图：[[Agent 面试题库]]

**问：压缩、卸载和记忆系统怎样分工？**

答：压缩改变当前 $H$，常有损；卸载把原件移入外部 $A$ 并留可寻址地图；[[19 Agent 记忆系统|记忆系统]]则规定 artifact 如何索引、保留、授权和跨会话回收。可靠系统同时记录「结论」和「证据位置」。

**问：为什么不每轮都摘要？**

答：摘要会增加一次模型调用，并可能抹掉稍后才显得重要的细节。应以预算、里程碑或大结果为触发条件；若原始内容可外存，优先保留可回读路径。

**问：sub-agent 只传摘要是否足够？**

答：不总是。摘要适合主线协调；可验证的代码、报告和数据应落为 artifact，主 agent 传引用和验收结果，避免多次转述造成的「传话损失」。
