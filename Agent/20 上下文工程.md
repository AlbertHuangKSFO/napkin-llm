[[20 上下文工程|上下文工程]] 的本质是:上下文窗是**有限且昂贵的预算**,工程的全部目标就是「每一轮都把最该在的信息放进去、把其余的移出去」——它不是写好一句 prompt,而是动态管理模型每一步看到的整个信息环境。

它是 [[19 Agent 记忆系统|Agent 记忆系统]] 的另一面:记忆系统管「放不下的东西存哪、怎么回来」,上下文工程管「这一轮上下文窗里到底放什么」。对一个跑长程任务的 agent 来说,上下文工程做得好不好,直接决定它能不能撑过几十步而不迷失、不爆预算。

## 本质:从 prompt engineering 到 context engineering

早期大家谈的是 **prompt engineering**——怎么把一句话写得让模型听话。但 agent 时代问题变了:模型一轮一轮地跑,上下文里堆着系统指令、几十轮对话、一堆工具返回、检索回灌的记忆……prompt 不再是「写一次」的静态文本,而是**每一步都要重新组装的动态信息流**。于是焦点从「怎么措辞」转向「**这一轮该让模型看到什么、不看到什么**」。这就是 context engineering。

**Prompt engineering vs Context engineering 一句话**:前者是**静态地把一句话写好**(措辞、few-shot、格式),后者是**每一轮动态决定整个信息环境放什么**(历史、记忆、工具返回的去留)——一个调「怎么说」,一个调「这步该看见什么」。

为什么是「预算」这个词最贴切?因为上下文窗有三重硬约束,全都是钱和性能:

- **容量有限**:几万到几百万 token,塞满就崩。
- **越长越贵越慢**:token 数直接乘单价,且注意力是平方复杂度,长上下文延迟陡增。
- **越长越笨**:lost-in-the-middle——上下文太长,中段信息被模型忽略,关键指令被淹没。塞得多 ≠ 效果好,**信噪比**才是关键。

所以上下文工程的核心动作就一个:**在固定预算里做取舍**。把当下真正需要的放进去(检索回灌、保留近期),把暂时不需要的移出去(裁剪、压缩、换出到外部),并尽量让前缀稳定以省下 [[102 KV-Cache|KV-Cache]] 的钱。

## 机制:管理上下文的几把刀

把候选信息(system 指令、对话历史、检索/记忆回灌、工具定义、工具返回)送进一个「调度器」,按相关度排序后,在预算内决定每一项的去留。常用技术从轻到重:

### 1. 裁剪 / 过滤(trimming)
最简单:超预算就丢。常见策略是**滑动窗口**——只保留最近 N 轮,更早的直接扔。或按相关度过滤:工具返回里只留有用字段,删掉冗长的原始 JSON。代价是**硬丢信息**,早期的关键决策可能被误删。

### 2. 滚动摘要(rolling summary)
不直接丢,而是把旧内容**压成摘要**再保留。每隔几轮,把这几轮对话浓缩成「做了什么、得到什么结论、还差什么」几句话,用摘要替换原文。比裁剪温和——保住了脉络,只丢了细节。代价:摘要**不可逆**且可能丢关键细节,且每次摘要要额外调一次模型。

### 3. Compaction(压实)
滚动摘要的「触发式」升级,是当前 agent 框架(如 Claude Code)的主力机制。

![[上下文工程-compaction对比.png]]

机制:**监控上下文 token 占用,当接近阈值(常设 ~80%)时,触发一次 compaction**——把到目前为止的历史(尤其冗长的工具返回、旧 Observation)压成一段结构化摘要(保留关键决策、结论、待办、踩过的坑),用它替换原始历史,只把最近几轮保留原文。压完上下文占用骤降,腾出预算继续往下做,任务因此可以**无限延续**而不撞窗。它和 [[19 Agent 记忆系统|Agent 记忆系统]] 里 MemGPT 的「换出」是同一思想:接近 RAM 上限就压缩+外移。

### 4. Filesystem-as-context(「给地图,不给手册」)
最彻底的思路:**大内容根本不进上下文,存到外部文件,上下文里只放索引/路径**。

类比:你不会把整本操作手册背进脑子,而是记住「手册在书架第三格」,需要时去翻。agent 同理——一个 50 页的 PDF、一份 1 万行的日志、整个代码库,**不塞进上下文**,而是落在文件系统里;上下文里只留一句「文件在 `/data/report.pdf`,目录结构如下…」。模型需要某段内容时,**主动调工具(读文件/grep)把那一小段读回来**。这正是 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 的用武之地:与其把全库 embedding 后语义检索,不如让 agent 像人一样 `grep`/`ls`/`read` 按需取。好处:① 上下文极省,只放当前活跃的那一小片;② 信息**无损**地留在外部(不像摘要会丢细节);③ 天然适配 [[23 Agent Harness 概览|Agent Harness 概览]] 的文件工具。

> 一句话区分四把刀:**裁剪 = 直接丢;摘要/compaction = 压缩着留;filesystem-as-context = 移出去留路径**。优先级通常是:能外置就外置(无损)> 压缩(有损但保脉络)> 裁剪(硬丢)。

## 与 KV-Cache 的关系:前缀稳定是省钱命门

这是上下文工程里最反直觉、也最值钱的一条。

[[102 KV-Cache|KV-Cache]] 的原理:模型对一段 token 算过的 K/V 可以缓存复用,**只要前缀逐字不变**。agent 每轮把全上下文重发给模型,如果前缀(system 指令 + 早期历史)和上一轮**完全一致**,这部分就直接命中缓存——不重算、计费还大幅打折(命中部分常只收约 1/10 价)。

推论,全是钱:

- **system 指令、工具定义放最前面且别动**。每轮重写系统提示(哪怕只改个时间戳)会让**整段缓存从改动点起全部失效**,后面所有 token 重算。
- **历史尽量只追加,不改写**。在上下文中段插入/删除/重排内容,会让插入点之后的缓存全废。
- **compaction 的隐藏代价**:它**改写了历史**→前缀变了→那次压缩后的几轮 KV-Cache 必然失效、变贵。所以 compaction 是「用一次昂贵的缓存失效,换之后长期的低 token 占用」,是笔合算但有即时成本的交易。
- **动态检索回灌要小心位置**。每轮把不同的检索结果插进上下文中段,会反复破坏缓存。把回灌内容放在相对固定的位置、或批量稳定下来,能护住命中率。

一句话:**频繁改前缀 = 烧钱**。上下文工程在「装更相关的信息」和「保前缀稳定省钱」之间反复权衡。

## 可跑的最小实现:compaction 触发

```python
def estimate_tokens(messages):
    return sum(len(m["content"]) for m in messages) // 3   # 粗估,生产用 tokenizer

def maybe_compact(messages, llm, limit, threshold=0.8, keep_recent=4):
    """接近阈值就把旧历史压成摘要,保留 system 与最近几轮。"""
    if estimate_tokens(messages) < limit * threshold:
        return messages                      # 预算够,不动

    system = messages[0]                      # system 永远保留在最前(护 KV-Cache)
    recent = messages[-keep_recent:]          # 最近几轮保原文(还在活跃使用)
    old = messages[1:-keep_recent]            # 中间这段被压缩

    summary = llm(
        "把下面这段 agent 工作历史压成结构化摘要,"
        "保留:关键决策、已得结论、待办事项、踩过的坑;丢弃冗长的原始工具返回。\n\n"
        + "\n".join(f'{m["role"]}: {m["content"]}' for m in old)
    )
    # 用一条摘要消息替换掉整段旧历史
    return [system, {"role": "system", "content": f"[历史摘要]\n{summary}"}, *recent]

# 主循环里每步调用
def agent_loop(messages, llm, limit):
    while not done(messages):
        messages = maybe_compact(messages, llm, limit)   # 先压实,再继续
        messages.append(llm_step(messages, llm))
```

要点:① 阈值触发,不是每轮都压(压缩本身要花一次模型调用 + 破坏缓存);② **system 永远留在最前不动**,护住 [[102 KV-Cache|KV-Cache]];③ 最近几轮保原文(它们还在被活跃引用),只压更早的;④ 摘要 prompt 明确「留什么、丢什么」,否则模型乱压会丢关键信息。

## 对比:几种上下文管理技术

| 技术 | 信息损失 | 省 token | 护 KV-Cache | 适合 |
|---|---|---|---|---|
| 裁剪/滑窗 | 硬丢(高) | 高 | 一般(改了中段) | 早期内容确实不再需要 |
| 滚动摘要 | 有损(中) | 高 | 差(频繁改写) | 对话型、脉络比细节重要 |
| Compaction | 有损(中) | 很高 | 差但一次性 | 长程 agent、接近窗口时 |
| Filesystem-as-context | **无损** | **极高** | 好(上下文里只放稳定索引) | 大文档/代码库/日志,按需读 |
| 只追加不改写 | 无 | 低 | **最好** | 想最大化缓存命中、控成本 |

## 何时用 / 坑

**该重视上下文工程的场景**:任何长程 agent(几十步以上)、要处理大文档/代码库的 agent、对成本/延迟敏感的生产系统、多智能体里给每个 sub-agent 精确投喂上下文([[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]] 靠隔离上下文降噪)。

**坑**:
- **压过头丢关键信息**:摘要/compaction 太激进,把后续要用的细节压没了。对策:摘要 prompt 明确保留项、关键事实考虑外置而非压缩。
- **为省 token 误删指令**:把 system 里的约束、安全规则当历史裁掉,agent 行为失控。system 区永远保护。
- **忽视 KV-Cache 烧钱**:每轮微调系统提示、动态插检索结果到中段,缓存反复失效,账单暴涨却没意识到。
- **filesystem-as-context 的索引失真**:给模型的「地图」(目录/摘要)不准,它就读不到对的文件,反而绕远路。索引质量决定成败。
- **lost-in-the-middle**:塞太多「看似相关」的内容,真正关键的被淹在中段。少而精 > 多而杂。
- **摘要触发抖动**:阈值卡得太死,在边界反复触发压缩,白花调用。设个滞回(压到比如 50% 才停)。

## 关键事实

- 上下文工程 = **在有限且昂贵的 token 预算里,每一轮决定放什么、留什么、出什么**;焦点从「怎么措辞」转到「让模型看到什么」。
- 三重约束:容量有限、越长越贵越慢、越长越笨(lost-in-the-middle)。**信噪比 > 信息量**。
- 四把刀:**裁剪(硬丢)< 摘要/compaction(压缩着留)< filesystem-as-context(移外部留路径,无损)**;优先外置。
- **Compaction**:接近阈值(~80%)时把历史压成结构化摘要再继续,让长程任务不撞窗;代价是改写历史 → [[102 KV-Cache|KV-Cache]] 失效。
- **Filesystem-as-context**(「给地图不给手册」):大内容存外部,上下文只放索引,按需用 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 读回——最省且无损。
- **前缀稳定 = 省钱**:system/工具定义放最前且别动、历史尽量只追加,最大化 [[102 KV-Cache|KV-Cache]] 命中;频繁改前缀是烧钱。
- 它与 [[19 Agent 记忆系统|Agent 记忆系统]] 一体两面,是 [[23 Agent Harness 概览|Agent Harness 概览]] 的核心职责,也是 [[25 Agent Skills(SKILL.md)|Agent Skills(SKILL.md)]](按需加载技能,不常驻上下文)背后的同一逻辑。

## 主流开源实现 / Python 库

具体的压缩/外移落地手段见配套笔记 [[21 上下文压缩与卸载|上下文压缩与卸载]];这里只列工具。

- **`microsoft/LLMLingua`**(pip `llmlingua`,EMNLP'23/ACL'24,2026 仍活跃):用小模型给每个 token 打重要性分、丢低分 token,可达约 20x prompt 压缩、精度损失小;已集成进 LangChain(`LLMLinguaCompressor` + `ContextualCompressionRetriever`)与 LlamaIndex。**做有损 prompt/检索内容压缩的首选**。
- **LangChain `trim_messages` / 摘要链**(pip `langchain`):`trim_messages` 做滑窗裁剪(本节「裁剪」那把刀),配 summarization 链做滚动摘要——框架内最顺手的轻量上下文管理。
- **Claude context editing / memory tool**(`anthropic` SDK):平台侧自动按阈值压实/外移上下文,对应本节的 compaction + filesystem-as-context,接 Anthropic 时几乎零成本拿到。

## 工业界实践

上下文工程是 2025 年生产 agent 的「头号工程问题」——不是写好一句 prompt,而是把上下文管理当成系统设计的核心。两个最权威的生产案例:**Manus** 和 **Anthropic Claude Code**。

### Manus 的六条原则(生产 agent 的圣经)

Manus(Peak Ji,2025-07 博客《Context Engineering for AI Agents》)把整套 agent 框架**重写了五次**,每次都为了更好地塑造上下文。一个任务平均约 50 次工具调用,沉淀出六条原则:

1. **围绕 KV-Cache 设计**:cache 命中率是生产 agent **最重要的单一指标**。保持 prompt 前缀逐字稳定(**别放精确时间戳**这类每轮变的东西)、上下文只追加不改写、需要时显式标 cache breakpoint。
2. **遮蔽而非移除工具(mask, don't remove)**:不同阶段需要不同工具,但**别动态增删工具定义**(会破前缀缓存 + 让指向已删工具的历史动作变悬空)。改用 **logits masking**——工具定义全留,在解码时屏蔽掉当前不该用的工具的 token。这和 [[18 工具检索与动态加载|工具检索与动态加载]] 的「按阶段批量切换」是同一矛盾的两种解法。
3. **用文件系统当上下文(filesystem-as-context)**:大内容外置到文件,上下文只留路径/索引,模型按需读回——无损且极省。
4. **通过复述操纵注意力(recitation)**:Manus 反复重写一个 `todo.md` 并勾掉已完成项,**把全局目标不断「念」到上下文末尾**,推进模型的近期注意力,对抗长任务里的 lost-in-the-middle 和目标漂移。
5. **保留错误(keep the wrong stuff in)**:**别擦掉失败和报错**。把失败动作 + stack trace 留在上下文里,模型「看到」失败会隐式更新先验、不再重犯。擦掉错误反而让它学不到。
6. **别被少样本带偏(avoid few-shot ruts)**:上下文里清一色的同构示例会让模型机械重复某种模式,要适度引入多样性。

这六条里,1/3 直接对应本笔记的「KV-Cache 命门」和「filesystem-as-context」,4/5/6 是文字层面更细的注意力管理。

### Anthropic Claude Code:把 cache miss 当生产事故

Anthropic 工程团队披露:**prompt caching 驱动了 Claude Code 的每一个主要设计决策**,工程师把 **cache 命中率下降当作生产事故(production incident)** 来处理。这印证了本笔记「前缀稳定 = 省钱命门」不是理论——命中部分常只收约 1/10 价,频繁改前缀 = 直接烧钱。平台侧提供 **context editing + memory tool**(按阈值自动压实/外移),对应本笔记的 compaction + filesystem-as-context,接 Anthropic 栈几乎零成本拿到。

### 落地手段与运维

```text
[候选信息: system / 历史 / 检索回灌 / 工具定义 / 工具返回]
        ▼ 调度器(按相关度排序, 预算内取舍)
   能外置就外置(filesystem, 无损) > 压缩(compaction, 有损保脉络) > 裁剪(硬丢)
        ▼ 全程护前缀: system/工具定义放最前不动, 历史只追加
   [监控] token 占用 / cache 命中率(掉了当事故) / compaction 触发频率
```

- **compaction 触发**:监控 token 占用,接近阈值(常 ~80%)触发一次,把历史压成结构化摘要(留关键决策/结论/待办/踩过的坑)再继续,让长程任务不撞窗。设**滞回**(压到比如 50% 才停)避免边界抖动反复白花调用。
- **可观测**:把「token 占用、cache 命中率、compaction 次数、平均上下文长度」做成看板,cache 命中率掉了优先排查(联动 [[35 Agent 成本与延迟优化|Agent 成本与延迟优化]] 与 [[38 Agent 评估与可观测性|Agent 评估与可观测性]])。

## 面试高频

**Q1:context engineering 和 prompt engineering 什么区别?**
prompt engineering 是「怎么把**一句话**写得让模型听话」(静态文本,写一次)。但 agent 一轮一轮跑,上下文堆着 system 指令、几十轮对话、一堆工具返回、检索回灌的记忆——prompt 变成**每一步都要重新组装的动态信息流**。context engineering 的焦点从「**怎么措辞**」转到「**这一轮该让模型看到什么、不看到什么**」。
- 一句话:prompt engineering 管措辞,context engineering 管**信息环境的动态管理**。

**Q2:为什么说上下文窗是「预算」?有哪三重约束?**
因为三重硬约束全是钱和性能:① **容量有限**(几万到几百万 token,塞满就崩);② **越长越贵越慢**(token 乘单价,注意力平方复杂度,长上下文延迟陡增);③ **越长越笨**(lost-in-the-middle,中段信息被忽略)。所以核心结论:**信噪比 > 信息量**,塞得多 ≠ 效果好。

**Q3:管理上下文有哪几把刀?优先级怎么排?**
四把刀按信息损失从重到轻:**裁剪/滑窗(硬丢)< 滚动摘要/compaction(压缩着留,有损保脉络)< filesystem-as-context(移外部留路径,无损)**。优先级:**能外置就外置(无损)> 压缩(有损但保脉络)> 裁剪(硬丢)**。区分:裁剪=直接丢;摘要/compaction=压缩着留;filesystem-as-context=移出去留路径。

**Q4:什么是 compaction?它的隐藏代价是什么?**
compaction = 监控上下文 token,接近阈值(~80%)时把历史(尤其冗长工具返回、旧 Observation)压成结构化摘要(留关键决策/结论/待办/坑),用它替换原始历史、只保留最近几轮原文,腾出预算让任务**无限延续**而不撞窗。**隐藏代价:它改写了历史 → 前缀变了 → 那次压缩后的 KV-Cache 必然失效、变贵**。所以 compaction 是「用一次昂贵的缓存失效,换之后长期的低 token 占用」的合算交易。

**Q5:上下文工程和 KV-Cache 是什么关系?(最高频)**
**前缀稳定 = 省钱命门**。KV-Cache 只要前缀逐字不变就能命中(命中部分常只收约 1/10 价)。推论全是钱:① **system 指令/工具定义放最前且别动**(改个时间戳都会让整段缓存从改动点起全失效);② **历史尽量只追加不改写**(中段插入/删除/重排会让插入点后缓存全废);③ compaction 改写历史必然破缓存;④ 动态检索回灌别插中段、放固定位置。一句话:**频繁改前缀 = 烧钱**,上下文工程在「装更相关信息」和「保前缀稳定」之间反复权衡。
- 陷阱:这题答不出 KV-Cache 这层就只停留在「省 token」的表面;能讲到「Anthropic 把 cache miss 当生产事故」是顶配。

**Q6:filesystem-as-context 是什么?好处?**
「给地图,不给手册」——大内容(50 页 PDF、1 万行日志、整个代码库)**根本不进上下文**,落在文件系统里,上下文只留索引/路径;模型需要某段时**主动调工具(read/grep)**把那一小段读回来。好处:① 上下文极省;② 信息**无损**留外部(不像摘要丢细节);③ 天然适配文件工具。对应 [[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 的「让 agent 像人一样按需取」。

**Q7:上下文工程有哪些坑?**
压过头丢关键信息(摘要太激进)、为省 token 误删 system 指令(行为失控,**system 区永远保护**)、忽视 KV-Cache 烧钱、filesystem 的索引失真(地图不准就读不到对的文件)、lost-in-the-middle(塞太多「看似相关」的)、摘要触发抖动(没设滞回在边界反复压缩)。

## 知识拓展

- **它与记忆系统一体两面**:[[19 Agent 记忆系统|Agent 记忆系统]] 管「放不下的存哪、怎么回来」,上下文工程管「这一轮放什么」。**working memory 的管理 = 上下文工程**;两者一起决定 agent 的「记性」和长程能力。
- **它是 Agent Harness 的核心职责**:[[23 Agent Harness 概览|Agent Harness 概览]] 每轮重新组装上下文,上下文工程就是这层的主逻辑;[[25 Agent Skills(SKILL.md)|Agent Skills(SKILL.md)]] 的「按需加载技能、不常驻上下文」是同一逻辑;[[18 工具检索与动态加载|工具检索与动态加载]] 是同一逻辑作用在「工具定义」上。
- **多智能体即「上下文隔离」**:[[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]] 给每个 sub-agent 精确投喂上下文、彼此隔离降噪,本质是上下文工程的一种架构手段(Manus 六原则里的 context isolation)。
- **具体压缩/外移落地手段**见配套笔记 [[21 上下文压缩与卸载|上下文压缩与卸载]]——本篇讲「为什么/什么时候」,那篇讲「怎么压、怎么卸」。
- **前沿与边界**:`LLMLingua`(微软,EMNLP'23/ACL'24)用小模型给 token 打重要性分、丢低分 token,可达 ~20x prompt 压缩、精度损失小,是有损压缩的代表。趋势是压缩/外移能力**下沉进平台**(Anthropic context editing、memory tool)——应用层越来越不用自己手搓。开放问题:摘要不可逆地丢细节 vs filesystem 无损但索引可能失真,二者权衡仍无银弹;长上下文模型(百万 token)并没消灭上下文工程,反而让「越长越笨/越长越贵」更突出。
- **反模式**:把「上下文越大越好」当真(信噪比才是关键);每轮微调 system prompt(烧缓存);把错误/失败从上下文擦干净(模型学不到,违反 Manus「keep the wrong stuff in」);摘要 prompt 不写清「留什么丢什么」(模型乱压丢关键信息)。
