[[30 A2A 协议|A2A 协议]]（Agent2Agent）规定独立 agent 应如何声明能力、接收任务并返回任务状态/产物，使异构框架之间能以黑盒方式协作。它是 agent↔agent 的互操作协议；[[17 MCP 模型上下文协议|MCP]] 则主要解决 agent↔工具/数据，两者可以同用。

## 直觉 / 生活类比

把 A2A 想成跨公司的外包接口：服务商递出能力名片（Agent Card），委托方交付一个可跟踪任务（Task），服务商再交付文档、文件或结构化结果（Artifact）。委托方不需要知道对方内部用什么模型、提示词或工具，但仍必须确认它是谁、可授权什么数据、任务失败如何处理。

没有统一合同，$N$ 个组织的 agent 往往需要为每个合作对象另写请求格式、错误码、流式行为和鉴权适配。A2A 把“双方都实现同一协议”作为公共边界；它**不**负责决定谁应该调用谁、任务应如何拆分或结果是否可信——这些仍属于 [[07 Orchestrator-Workers|编排]] 与安全策略。

## 小数字手算

有 $N=6$ 个组织且任意两方都要互通。若每条连接是私有适配，潜在组合数为：

$$
\binom{6}{2}=\frac{6\times5}{2}=15
$$

若每个组织各实现一套兼容的 A2A server/client 边界，实施责任可按 $2N=12$ 个端点能力计划，而不是为 $15$ 种双边格式分别维护代码。这个数字不是承诺“集成工作必然更少”——身份、授权、语义映射与运维仍是每个合作关系的成本；它只量化协议对**传输与消息格式**组合爆炸的缓解。

## 公式推导

设 Agent Card 为 $C$，请求消息为 $m$，任务状态为 $z_t$，产物集合为 $A$。下面是**常见任务路径，不是完整状态机**：

$$
(C,m)\xrightarrow{\operatorname{SendMessage}}\operatorname{Task}(\texttt{submitted})
\rightarrow\texttt{working}\rightarrow\texttt{completed}\;(\text{可携带 }A)
$$

`input-required` 与 `auth-required` 是需要补充输入或授权的中断状态，满足条件后可继续；`rejected` 是终态，另有 `failed`、`canceled` 等终止结果。因而 “completed → Artifact” 只是一种有效完成结果，不能把 Artifact 当作每个 task 必有的通用终点。

协议能标准化消息、任务和状态，却不能推出业务正确性：

$$
\operatorname{A2A\ compatible}\;\not\Rightarrow\;
\operatorname{authorized}\;\not\Rightarrow\;
\operatorname{trustworthy\ output}
$$

因此接收端要把 Card、消息、artifact 和状态都当成外部不可信输入，独立执行鉴权、schema 验证、最小权限与审计。官方 samples 也明确提醒不要未经清洗地把外部 Card/消息写入 LLM prompt。[官方 samples](https://github.com/a2aproject/a2a-samples)

跨 agent 风险传播见 [[AI 安全/18 Agent 间通信安全与级联失败]]。

## 可运行代码 / 配置

官方 Python SDK 明确实现 A2A **1.0**，并同时列出 JSON-RPC、gRPC、HTTP+JSON/REST 的 client/server 支持。最快的可运行起点是官方 Helloworld sample（两个终端）：

```bash
# 终端 1：启动 A2A server
git clone https://github.com/a2aproject/a2a-samples.git
cd a2a-samples/samples/python/agents/helloworld
uv run .

# 终端 2：向它发送任务
cd a2a-samples/samples/python/agents/helloworld
uv run test_client.py
```

下面是 HTTP+JSON binding 的请求形状；端点、认证令牌和 `messageId` 应由实际部署提供：

```bash
# ❌ 不要以 Agent Card 的 name/description 当作身份或授权依据。
# ✅ 版本、服务端点与认证按 Card 的接口/安全方案及本地策略处理。
curl -X POST 'https://agent.example.com/message:send' \
  -H 'A2A-Version: 1.0' \
  -H 'Content-Type: application/a2a+json' \
  -H 'Authorization: Bearer REPLACE_ME' \
  --data '{"message":{"role":"ROLE_USER","messageId":"replace-me","parts":[{"text":"请生成摘要"}]}}'
```

这里的 `1.0` 是协议协商值；正式规范版本为 `1.0.0`。JSON-RPC、gRPC、HTTP+JSON/REST 是 **v1.0** 的三种标准 binding，不应再写成“仅 JSON-RPC 后来新增 gRPC”。[官方 Python SDK compatibility](https://github.com/a2aproject/a2a-python)

## 面试高频
> 面试地图：[[Agent 面试题库]]

**Q：A2A 与 MCP 如何分工？**

答：A2A 面向自主 agent 间的发现、任务与产物交换；MCP 面向模型/agent 接入工具、资源与数据。一个远程 A2A agent 完全可在内部使用 MCP；协议层不替代业务编排。

**Q：A2A v1.0.0 的 binding 与签名是什么？**

答：正式规范的标准 binding 是 JSON-RPC、gRPC、HTTP+JSON/REST。Agent Card 可带**可选 JWS**签名，签名格式遵循 RFC 7515，进行的是密钥材料上的密码学校验；它**不是域名证书签名**，也不自动授予对方数据或工具权限。

**Q：为什么“拿到 Agent Card”不等于可以信任？**

答：Card 只帮助描述接口与能力。仍要验证 transport/authentication、安全方案、JWS（若本地策略要求且 Card 提供）、调用方权限、输入/输出 schema 与审计记录；对方产物还可能包含提示注入或错误信息。

## 关键事实

- **现行官方 `latest` 正式规范为 A2A `1.0.0`**；协议协商示例使用 `1.0`。核心操作独立于 binding，规范列出 JSON-RPC、gRPC、HTTP+JSON/REST 三种标准 binding。[A2A Specification 1.0.0](https://a2a-protocol.org/latest/specification/)
- **JWS 是可选的 Agent Card 签名机制**：规范采用 RFC 7515 的 JSON Web Signature，并要求在签名时使用规范化 JSON；它不是“域名证书签名”。[v1.0 更新说明](https://a2a-protocol.org/latest/whats-new-v1/)
- **A2A 只标准化互操作，不保证安全或质量**：外部 agent 的 Card、message、artifact 均应当作不可信输入，结合 [[18 Agent 间通信安全与级联失败|通信安全]]、最小权限与 trace 审计。
- **实现口径要锁版本**：官方 Python SDK 说明实现规范 `1.0` 并保留 `0.3` compatibility；部署应记录 spec、SDK、binding 与认证策略。[SDK，2026](https://github.com/a2aproject/a2a-python)
