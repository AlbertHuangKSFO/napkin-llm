[[30 A2A 协议|A2A 协议]](Agent2Agent Protocol)是一套**让不同厂商、不同框架造出来的 agent 能互相发现、互相委派任务的开放协议**:一个 agent 把自己包装成「可被远程调用的服务」,用标准化的 **Agent Card** 对外宣告能力,别的 agent 读到 Card 就能向它发起 **task**、流式拿回 **artifact(产物)**。一句话——**A2A 之于 agent,就像 HTTP 之于网站**:它定义的是「agent 与 agent 之间怎么对话」的通用语,而不关心对方内部是怎么实现的。

它和 [[17 MCP 模型上下文协议|MCP 模型上下文协议]] 是**正交互补**的两层,这是理解 A2A 最快的切入点:MCP 解决的是「**一个 agent 怎么接外部工具/数据**」(纵向:agent↔工具),A2A 解决的是「**多个 agent 怎么互相协作**」(横向:agent↔agent)。同一个 agent 完全可以一边用 MCP 接 GitHub、数据库这些工具,一边把自己当成一个 A2A 远程 agent 暴露给别的 agent 调用。两者不冲突、各管一头,业界常把它们放在一起讲「MCP + A2A 是 agent 互联网的两根基础协议」。

![[A2A 协议.svg]]

## 本质:消灭「多 agent 协作的私有对接」

回想 [[17 MCP 模型上下文协议|MCP 模型上下文协议]] 解决的痛点是「N 个应用 × M 个工具」的集成爆炸。A2A 解决的是**同构但发生在更高一层的问题**:当一个复杂任务需要多个 agent 配合(一个负责检索、一个负责写代码、一个负责审校),而这些 agent 来自不同团队、不同厂商、用不同框架(LangGraph、CrewAI、Google ADK、自研……)写成时,**它们之间怎么对话?**

没有标准协议时,每接一个外部 agent 就要为这对组合写一份私有适配:对方的输入格式、鉴权方式、流式协议、错误语义全都不一样。这是 [[22 多智能体系统|多智能体系统]] 走向「跨组织、跨厂商」时的真实障碍——内部多 agent 还能共享一套代码,**一旦跨边界,私有对接立刻爆炸**。

A2A 的洞见和 MCP 完全一致:**定一个标准协议,把两两私有对接变成「各连一次标准口」**。每个 agent 只要实现一次 A2A 服务端(暴露 Agent Card + 接受 task),就能被**所有** A2A 客户端调用;每个 agent 只要实现一次 A2A 客户端,就能调用**所有** A2A 远程 agent。关键设计原则是 **opaque(黑盒)**:A2A 让 agent 互通,但**不要求对方暴露内部的提示词、工具、记忆、模型权重**——你只需要知道它「能做什么、怎么调、返回什么」,内部实现对你是黑盒。这一点对企业很重要:协作不等于把家底交出去。

## 机制:Agent Card 发现 → task 生命周期 → artifact 流式

![[A2A 协议-Agent Card 与 task 生命周期.svg]]

A2A 的交互分三步,每一步都有明确的协议原语:

**① 发现:Agent Card(能力名片)**
每个 A2A agent 在一个**约定路径**(`/.well-known/agent-card.json`,沿用 well-known URI 惯例)上暴露一份 JSON,叫 **Agent Card**。它声明:
- `name` / `description`:这个 agent 是谁、做什么;
- `url`:A2A 服务端点;
- `skills`:它能做的一组技能(每个有 `id`、`description`、示例),这是客户端做路由选择的依据,概念上类似 [[16 工具设计与工具层|工具设计与工具层]] 里给工具写的描述,只是粒度是「整个 agent 的能力」;
- `capabilities`:支持哪些协议特性(`streaming` 流式、`pushNotifications` 推送回调等);
- `securitySchemes`:鉴权方式(OAuth2、API Key、OIDC……)。
客户端 agent 想委派任务时,先拉对方的 Agent Card,根据 `skills` 判断「这个远程 agent 能不能干这活」,再决定调谁。**v1.2 起 Agent Card 支持加密签名**(用域名证书签名),用来验证「这张名片确实来自声称的那个组织」,防伪造。

**② 发起 task:message/send 与 message/stream**
客户端通过 JSON-RPC 调用远程 agent 的方法:
- `message/send`:发一条消息(`role` + `parts`,part 可以是文本、文件、结构化数据),同步等结果;
- `message/stream`:同样发消息,但用 **SSE(Server-Sent Events)流式**接收——远程 agent 一边干一边推状态更新和中间产物,适合长程任务(参见 [[33 长程任务与自我改进(Ralph loop)|长程任务与自我改进(Ralph loop)]] 那类一跑很久的活)。
返回里带一个 **`taskId`**:A2A 把一次委派建模成一个有状态的 **Task** 对象,后续可以用 `tasks/get` 查、`tasks/cancel` 取消。

**③ Task 生命周期与 artifact**
Task 是一个状态机,典型流转:
- `submitted`(已提交)→ `working`(执行中)→ `completed`(完成,返回产物);
- 中途可能进 `input-required`(远程 agent 需要客户端补充信息,比如缺参数、需要确认——这正是把 Human-in-the-Loop 或「上游 agent 补料」编进协议),补完回到 `working`;
- 异常终态:`failed` / `canceled` / `rejected`。
最终产物叫 **Artifact**——可以是文本、文件、或结构化 JSON。流式模式下 artifact 可以增量推送(写一段推一段),非流式则在 `completed` 时一次返回。

**传输与底座**:A2A 基于 **JSON-RPC 2.0 over HTTP(S)**,流式用 SSE;新版也支持 gRPC 传输。它刻意复用 Web 既有的鉴权、TLS、well-known 等基础设施,降低落地成本——这与 MCP「复用 JSON-RPC」的工程哲学一脉相承。

## 可跑的最小实现

**服务端(暴露一个 A2A agent,Python SDK 伪码)**:

```python
# pip install a2a-sdk
from a2a.server.apps import A2AStarletteApplication
from a2a.server.request_handlers import DefaultRequestHandler
from a2a.types import AgentCard, AgentSkill, AgentCapabilities

skill = AgentSkill(
    id="research",
    name="深度调研",
    description="给定主题,联网检索并产出带引用的报告",
    examples=["调研一下 2026 年 A2A 的采用情况"],
)
card = AgentCard(
    name="ResearchAgent",
    description="一个会做深度调研的远程 agent",
    url="https://my-host/a2a",
    version="1.0",
    capabilities=AgentCapabilities(streaming=True),
    skills=[skill],
)

class MyExecutor:  # 真正干活的逻辑
    async def execute(self, context, event_queue):
        # context.message 是客户端发来的 task 输入
        # 内部可以是一个完整的 agent(用 MCP 接工具、跑 ReAct 循环……)
        result = await run_my_agent(context.message)
        await event_queue.enqueue_artifact(result)  # 推回产物

handler = DefaultRequestHandler(agent_executor=MyExecutor())
app = A2AStarletteApplication(agent_card=card, http_handler=handler)
# 用 uvicorn 跑起来,Agent Card 自动挂在 /.well-known/agent-card.json
```

**客户端(发现并调用一个远程 agent,伪码)**:

```python
from a2a.client import A2AClient

# ① 发现:拉对方的 Agent Card
client = await A2AClient.from_url("https://remote-host/a2a")
print(client.agent_card.skills)   # 看看它能做什么

# ② 发起 task,流式接收
async for event in client.send_message_streaming(
        message={"role": "user", "parts": [{"text": "调研 2026 A2A 采用情况"}]}):
    if event.is_status_update():
        print("状态:", event.status.state)   # working / input-required / completed
    if event.is_artifact():
        print("产物:", event.artifact)        # 增量产物
```

关键点:**服务端的 `MyExecutor` 内部往往本身就是一个完整 agent**——它可以用 [[17 MCP 模型上下文协议|MCP 模型上下文协议]] 接工具、跑 [[09 ReAct|ReAct]] 循环、有自己的 [[19 Agent 记忆系统|Agent 记忆系统]]。A2A 只负责把这个 agent「服务化」并和外界对话,内部怎么实现完全黑盒。

## 对比:A2A vs MCP(同一张图的两根轴)

| 维度    | MCP 模型上下文协议                 | A2A 协议                              |
| ----- | --------------------------- | ----------------------------------- |
| 连接谁   | agent ↔ **工具/数据**(纵向)       | agent ↔ **agent**(横向)               |
| 解决的爆炸 | N 应用 × M 工具                 | 跨厂商 agent 两两私有对接                    |
| 核心原语  | Tools / Resources / Prompts | Agent Card / Task / Artifact        |
| 发现机制  | `tools/list` 等列举能力          | Agent Card(well-known JSON)         |
| 对端是什么 | 一个**能力提供者**(无自主性)           | 一个**自主 agent**(会推理、有状态)             |
| 交互形态  | 一问一答的工具调用                   | 有生命周期的 task(可长程、可流式、可要补输入)          |
| 黑盒性   | server 暴露明确的工具接口            | **刻意黑盒**:不暴露内部提示/工具/权重              |
| 发起方   | Anthropic(2024-11)          | Google(2025-04),后捐 Linux Foundation |

记忆口诀:**MCP 让 agent「拿到工具」,A2A 让 agent「找到同伴」**。一个智能体系统([[22 多智能体系统|多智能体系统]])里两者常同时出现——内部子 agent 之间也可以用 A2A 通信,但 A2A 的真正价值在**跨组织/跨厂商**那一刀。

## 何时用 A2A / 何时不用(及坑)

**该用**:
- 要调用**别的团队/厂商**造的 agent,且不想(或拿不到)对方源码——黑盒互通正是 A2A 的主场;
- 构建**跨框架**的智能体系统:一个 LangGraph agent 想委派给一个 CrewAI agent;
- 需要**长程、异步、流式**的 agent 间委派(task 生命周期 + SSE 天然支持)。

**未必用**:
- **同进程、同框架的内部子 agent**——直接函数调用 / 框架原生的 [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]] 机制更轻,套 A2A 是过度工程。A2A 的开销(HTTP、序列化、鉴权、发现)只有跨进程/跨边界时才划算。
- 你需要的是**接工具**而不是「接另一个会推理的 agent」——那是 [[17 MCP 模型上下文协议|MCP 模型上下文协议]] 的活,别拿 A2A 硬套。

**坑**:
- **A2A 不替你做编排**。它只定义「两个 agent 怎么对话」,**谁调谁、按什么顺序、失败怎么补**这些 [[07 Orchestrator-Workers|Orchestrator-Workers]] 式的编排逻辑还得你自己写——A2A 是通信层,不是编排层。
- **信任与鉴权是真问题**。把任务委派给外部 agent,意味着把权限和数据递出去;Agent Card 签名只解决「名片防伪」,**对端会不会乱用工具、会不会被 [[05 Prompt Injection 提示注入|Prompt Injection]] 劫持**仍需你在权限护栏层面自己兜(参见 [[18 Agent 间通信安全与级联失败|Agent 间通信安全]]、[[14 Excessive Agency 与 Goal Hijack|过度代理]])。黑盒互通是双刃剑。
- **能力发现 ≠ 能力可信**。Agent Card 里写「我会做 X」是对方的自我声明,实际能不能做好、稳不稳定,得靠你自己评估(参见 [[38 Agent 评估与可观测性|Agent 评估与可观测性]])。
- **协议年轻、还在演进**。从 2025-04 到 2026 已从 Python 单 SDK 走到五语言、v1.2,接口和最佳实践仍在变,生产落地要锁版本。

## 关键事实速记

- A2A = **Agent2Agent**,Google 2025-04 发布,2025-06 捐 Linux Foundation,Apache 2.0,2026 已 v1.2、150+ 组织、五语言 SDK。
- 三大原语:**Agent Card**(发现)、**Task**(有状态的委派,带生命周期状态机)、**Artifact**(产物)。
- 底座:**JSON-RPC 2.0 over HTTP(S)**,流式用 **SSE**,新增 gRPC;Agent Card 挂在 `/.well-known/agent-card.json`。
- 与 MCP 正交:**MCP=agent↔工具,A2A=agent↔agent**,常同时使用。
- 设计哲学:**opaque(黑盒)互通**——能协作但不暴露内部实现。

## 工业界实践

**① 一周年成绩单(2026-04):从规范走进生产。** Linux Foundation 在 A2A 满一年时公布:**支持组织超 150 家**,已**深度集成进 Google、Microsoft、AWS 三大云**,并出现**跨行业的生产部署**——供应链、金融、保险、IT 运维等垂直领域用 A2A 协调"跨工具、跨厂商、跨环境"的自治系统。换句话说,A2A 已过了"概念验证"阶段,进入企业实际编排多 agent 的工程期。

**② 协议格局:A2A 不是孤岛,而是"agent 互联网"标准簇的一员。** 工业界理解 A2A 要放进一张更大的协议地图里:
- **MCP**(Anthropic,2024-11):纵向,agent↔工具/数据。与 A2A 正交互补(本篇主线)。
- **A2A**(Google→Linux Foundation):横向,agent↔agent 跨组织协作。
- **AG-UI**(Agent-User Interaction Protocol):agent↔前端用户界面的标准事件流(把 agent 的状态/中间产物/需补输入实时推给 UI),补的是"人机交互层"——A2A 管 agent 间,AG-UI 管 agent 与人。
- **AGNTCY**(Cisco 发起,2025 捐 Linux Foundation):更上层的**开放多 agent 基础设施**——统一 discovery、identity、messaging、observability,**显式声明与 A2A 和 MCP 互操作**。可理解为"给多 agent 系统配的目录服务 + 身份 + 可观测底座"。
- 行业正走向**收敛**:MCP 接工具、A2A 接同伴、AG-UI 接人、AGNTCY 提供发现/身份/观测,四者拼成完整的互操作栈。面试若问"除了 A2A 还有哪些 agent 协议",能说出这张图就到位。

**③ 典型企业落地架构。** 一个跨厂商工作流(如保险理赔):一个 orchestrator agent(可能是 ADK/LangGraph 写的)读各远程 agent 的 Agent Card 做能力路由 → 用 `message/stream` 把子任务流式委派给"文档抽取 agent(厂商 A)""欺诈检测 agent(厂商 B)""定价 agent(内部)" → 各 agent 内部用 **MCP** 接自己的数据库/工具、跑自己的 [[09 ReAct|ReAct]] 循环(对外**黑盒**)→ artifact 流式回灌,遇 `input-required` 触发人工确认(或经 AG-UI 推到坐席界面)。编排逻辑(谁先谁后、失败补偿)由 orchestrator 自己写——**A2A 只是通信层,不替你编排**。

**④ 安全与运维(企业最在意的一刀)。** 跨组织委派 = 把权限和数据递出去,这是 A2A 生产化最敏感处:
- **Agent Card 签名(v1.2)**:用域名证书签名,验"名片确实来自声称的组织",防伪造;但**只解决名片防伪,不解决对端行为可信**。
- **鉴权下沉到 Web 既有设施**:`securitySchemes` 走 OAuth2 / OIDC / API Key,复用企业现成的 IdP。
- **最小权限 + 护栏**:对端可能被 [[05 Prompt Injection 提示注入|Prompt Injection]] 劫持去乱用工具,需在权限层兜(见 [[18 Agent 间通信安全与级联失败|Agent 间通信安全]]、[[14 Excessive Agency 与 Goal Hijack|过度代理]])。
- **可观测**:task 有生命周期状态机(submitted→working→completed/failed),天然可观测;生产上把每个 task 的状态流转、artifact、跨 agent 调用链接入 trace(见 [[38 Agent 评估与可观测性|Agent 评估与可观测性]]),否则跨厂商出问题无从定位责任。
- **版本锁定**:协议从 2025-04 到 2026 已走到五语言 SDK、v1.2,接口仍在演进,生产要锁 SDK 与协议版本。

```yaml
# Agent Card 关键字段(/.well-known/agent-card.json,生产视角)
name: "ClaimsExtractor"
url: "https://vendor-a.example.com/a2a"
version: "1.2"
capabilities: { streaming: true, pushNotifications: true }
securitySchemes:                 # 复用企业 IdP
  oauth2: { flows: { clientCredentials: { tokenUrl: "..." } } }
skills:
  - id: "extract_claim"
    description: "从理赔 PDF 抽取结构化字段"
    examples: ["抽取这份车险理赔单的关键信息"]
signature: "<域名证书签名>"        # v1.2:验名片来源真实性
```

## 面试高频

**Q1:A2A 和 MCP 什么关系?(几乎必问)**
标准答:**正交互补的两层**——MCP 解决 agent↔**工具/数据**(纵向,N 应用×M 工具的集成爆炸),A2A 解决 agent↔**agent**(横向,跨厂商两两私有对接爆炸)。口诀:**MCP 让 agent 拿到工具,A2A 让 agent 找到同伴**。同一 agent 可同时是 MCP 客户端(接工具)和 A2A 服务端(被别的 agent 调)。追问"对端的本质区别":MCP 对端是无自主性的能力提供者(一问一答),A2A 对端是会推理、有状态的自主 agent(有生命周期 task)。

**Q2:A2A 的三大核心原语?**
答:**Agent Card**(发现——well-known JSON 声明能力/端点/鉴权)、**Task**(有状态委派,带生命周期状态机 submitted→working→completed,中途可 input-required)、**Artifact**(产物——文本/文件/结构化 JSON,流式可增量推)。追问底座:**JSON-RPC 2.0 over HTTP(S),流式用 SSE,新增 gRPC**;Agent Card 挂 `/.well-known/agent-card.json`。

**Q3:为什么要"opaque(黑盒)"设计?**
答:A2A 让 agent 互通但**不要求暴露内部提示词/工具/记忆/模型权重**。原因:企业协作≠把家底交出去,你只需知道对方"能做什么、怎么调、返回什么"。这是 A2A 能跨组织落地的前提——同时也是双刃剑(见 Q5)。

**Q4:什么时候**不**该用 A2A?**
答:① 同进程/同框架的内部子 agent——直接函数调用或框架原生 [[26 Sub-agents 与 Agent Teams|Sub-agents]] 更轻,套 A2A 是过度工程(HTTP/序列化/鉴权/发现的开销只在跨边界才划算);② 你要的是"接工具"而非"接另一个会推理的 agent"——那是 MCP 的活。陷阱:有人认为"内部多 agent 也该上 A2A 统一"——开销不值。

**Q5(陷阱):有了 Agent Card 签名,委派给外部 agent 就安全了吗?**
答:**不**。签名只验"名片来自声称的组织"(防伪造名片),**不保证对端行为可信**——对端可能能力名不副实、可能被 Prompt Injection 劫持去滥用权限、可能泄露你递过去的数据。需在权限护栏层自己兜:最小权限、输出校验、审计。能力发现 ≠ 能力可信。

**Q6:A2A 帮你做编排吗?**
答:**不做**。A2A 只定义"两个 agent 怎么对话",谁调谁、按什么顺序、失败怎么补这些 [[07 Orchestrator-Workers|Orchestrator-Workers]] 式编排逻辑要你自己写。A2A 是**通信层不是编排层**——这是常见误解,务必区分。

## 知识拓展

- **协议收敛趋势(2026)**:业界普遍认为 MCP + A2A + AG-UI + AGNTCY 正拼成完整互操作栈,且在向更统一的治理收敛(Linux Foundation 把 A2A 和 AGNTCY 都收入 Agentic AI 治理)。关注点从"协议之争"转向"如何组合"。
- **AG-UI 值得单独记**:补的是 A2A/MCP 不管的"agent↔人界面"层——把 agent 的状态更新、中间 artifact、`input-required` 标准化成前端可消费的事件流,让任意框架的 agent 接任意前端。与 A2A 的 task 生命周期天然契合(input-required → 经 AG-UI 推给用户补料)。
- **与长程任务的契合**:A2A 的 task 生命周期 + SSE 流式 + `pushNotifications` 回调,天然适配 [[33 长程任务与自我改进(Ralph loop)|长程任务]] 那类一跑很久、需异步回调的委派——客户端发起后断开,远程 agent 跑完用 push 通知。
- **边界 / 反模式**:① 用 A2A 接工具(应用 MCP);② 内部子 agent 强行 A2A 化(过度工程);③ 信任 Agent Card 自我声明的能力而不评估(能力发现≠可信);④ 不锁版本(协议演进快,接口会变);⑤ 把编排逻辑寄希望于协议(A2A 不编排)。
