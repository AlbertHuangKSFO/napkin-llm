[[22 多智能体系统|多智能体系统]] 的本质是:把一个大任务**拆给多个各有分工、各持独立上下文的 agent 协作完成**——当一个 agent 单凭一条上下文、一套工具搞不定时,用「分而治之 + 角色专精」换取规模、并行和质量,代价是协调成本与级联错误的风险。

它把 [[07 Orchestrator-Workers|Orchestrator-Workers]] 这类单 agent 的工作流模式,放大成「多个独立 agent 实例之间」的协作;在 agent harness 层面,它的具体落地形态就是 [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]]。

## 本质:为什么要多个 agent

一个单 agent([[03 Agent 核心循环|Agent 核心循环]])已经很强了——它能规划、调工具、反思。那为什么还要多体?因为单 agent 有几个天花板:

1. **上下文会爆 / 会脏**。一个 agent 干一件大事,几十步下来上下文塞满了各种子任务的中间产物,信噪比崩了([[20 上下文工程|上下文工程]] 救不过来)。拆成多个 sub-agent,每个只管自己那摊、各持**干净聚焦的上下文**,主 agent 只收汇总结果——这是多体最被低估、却最实在的好处:**上下文隔离即降噪**。
2. **角色需要专精**。「写代码的」和「审代码的」该带不同的 system prompt、不同的工具、甚至不同的模型。捏在一个 agent 里,指令会互相打架;拆开,各自的 procedural memory([[19 Agent 记忆系统|Agent 记忆系统]])才干净。
3. **要并行省时间**。三个互不依赖的子任务(查三个数据源),单 agent 只能串行,多体可以**同时跑**,墙钟时间近乎除以 3。
4. **要多视角提质量**。让两个 agent 辩论、或一个生成一个批判([[08 Evaluator-Optimizer|Evaluator-Optimizer]] 的多体版),往往比单 agent 自说自话更靠谱。

但**多体不是默认选项**。它带来成本翻倍、协调开销、级联错误、调试困难。**先问:单 agent 配上子任务工具能不能搞定?能,就别上多体。** 这是 Anthropic、LangChain 等反复强调的纪律——简单优先。

**盈亏平衡手算**。多体「省时间但烧 token」,值不值要算。设 3 个子任务互不依赖,单 agent 串行墙钟 $= t_1+t_2+t_3 \approx 3T$;3 个 worker 并行,墙钟 $\approx \max(t_i) \approx T$——**墙钟近乎除以 3**。但 token 反向:3 个 worker 各跑各的上下文,token $\approx 3\times$ 单 agent(Anthropic Research 实测更夸张,达 $\sim15\times$,因为还有 lead 规划 + 汇总 + 引用核对的额外开销)。所以盈亏平衡点是:**当「快 3 倍的墙钟」值的钱 > 「多花 3~15 倍的 token」时才划算**——这只在一次答对值很多钱的高价值任务(法务尽调、文献综述)成立;消费级 Q&A 吸收不了这个乘数。Anthropic 内部评测里「Opus 4 lead + Sonnet 4 subagent」比单 agent Opus 4 高 $90.2\%$,且 $\sim80\%$ 的性能方差由 token 用量解释——这正说明:**多体的增益本质是「拿更多 token 预算 + 上下文隔离」换来的,不是凭空更聪明**。

## 机制:四种拓扑

多体的差异主要在**拓扑**——谁指挥谁、消息怎么流。

![[多智能体系统.png]]

### 1. Supervisor-Worker(主管-工人,最常用)
一个 **supervisor**(主管)agent 负责:理解总任务 → 拆成子任务 → 派给若干 **worker** agent → 收集各 worker 的结果 → 汇总成最终答案。worker 之间**互不通信**,只对主管负责。

这是 [[07 Orchestrator-Workers|Orchestrator-Workers]] 工作流模式的「多 agent 实例」版:那里 orchestrator 和 worker 是同一程序里的角色,这里是各自独立、各持上下文的真 agent。主管的核心动作其实是一次 [[05 Routing|Routing]]——根据子任务把活分给对的 worker。绝大多数生产多体系统(含 [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]])都是这个结构,因为它**有中心、好控、好调试**:出错能定位到哪个 worker,主管能重试。

### 2. Peer-to-Peer(对等)
**无中心**,agent 之间对等互发消息,通过协商/辩论/接力达成一致。没有谁是主管,谁该接下一棒由消息内容和规则决定。

优点:灵活,适合开放式协作(比如多 agent 辩论、角色扮演模拟)。缺点很致命:**容易失控、难收敛**——可能无限互相甩消息、达不成一致、或陷入礼貌性死循环。需要强约束(轮数上限、终止条件、仲裁者)才稳。生产里用得少,研究/模拟里多。

### 3. Planner-Executor(规划者-执行者)
一个 **planner** 专门做规划——把任务拆成有序步骤清单(蓝图);一个或多个 **executor** 负责按步骤逐个执行;执行遇到偏差就回报 planner 重规划。

这其实是把单 agent 的 [[10 Plan-and-Execute|Plan-and-Execute]] 拆成两个独立 agent:规划和执行**职责分离**,各自上下文干净。好处是 planner 可以用强模型只管想、executor 用便宜模型只管做,省钱;坏处是规划-执行之间的交接如果设计不好,会反复来回。

### 4. Hierarchical(分层)
supervisor-worker 的递归版:一个**顶层主管**指挥若干**中层主管**,每个中层主管又各带一队 worker。任务层层分解,像公司组织架构。适合**超大、可深度分解**的任务(比如「写一份完整研究报告」→分章节主管→各章节再分小节 worker)。代价:层数越多,协调和级联错误越严重。

## 通信与共享状态

agent 之间怎么传信息,是多体的另一个设计核心:

- **消息传递(message passing)**:agent A 把结果作为消息发给 agent B。简单直接,但每次传递都要把内容塞进对方上下文——传得多、传得长,token 成本和噪音都涨。
- **共享状态 / 黑板(shared state / blackboard)**:所有 agent 读写一块公共状态(一个共享的 dict、一个文件、一个数据库)。LangGraph 的 state、CrewAI 的共享记忆都是这思路。好处:不必把一切塞进消息,谁要谁去读(配合 filesystem-as-context,见 [[20 上下文工程|上下文工程]]);坏处:**并发写冲突、状态不一致**——两个并行 agent 同时改一块状态,谁覆盖谁?
- **传摘要而非全文**:agent 间通信传**结论/摘要**,而非原始全过程。这既省 token 又护住各自上下文的干净——sub-agent 内部跑了 20 步,只把最终 3 句话交回主管。这正是 [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]] 的关键设计:子 agent 的上下文不污染主 agent。

## 可跑的最小实现:supervisor 路由

```python
WORKERS = {
    "researcher": {"sys": "你只负责检索与查证,返回事实要点", "tools": [web_search]},
    "coder":      {"sys": "你只负责写代码,返回可运行片段",   "tools": [run_code]},
    "writer":     {"sys": "你只负责把要点写成通顺文字",       "tools": []},
}

def supervisor(task, llm, max_rounds=6):
    scratch = f"总任务:{task}\n已完成的子结果:\n"
    for _ in range(max_rounds):
        # 主管做一次路由决策:派给谁、子任务是什么,或宣布完成
        decision = llm(
            "你是主管。根据总任务与已有子结果,决定:"
            "要么输出 ROUTE:<worker名>|<子任务>,要么输出 DONE:<最终答案>。\n"
            f"可用 worker:{list(WORKERS)}\n{scratch}"
        )
        if decision.startswith("DONE:"):
            return decision[5:]                       # 汇总完成,返回
        _, body = decision.split("ROUTE:", 1)
        name, subtask = body.split("|", 1)
        w = WORKERS[name.strip()]
        # 关键:每个 worker 用「干净上下文」执行(只见自己的子任务,不见主管全历史)
        result = run_agent(w["sys"], subtask.strip(), w["tools"], llm)
        # 只把「摘要结果」回灌给主管,不回灌 worker 的全过程(护上下文)
        scratch += f"- [{name.strip()}] {subtask.strip()} → {result}\n"
    return "达到最大轮数仍未完成"
```

要点:① 主管的决策本质是 [[05 Routing|Routing]](派给谁)+ 终止判断(DONE);② 每个 worker 用**独立干净的上下文**执行,看不到主管的全历史——这是上下文隔离;③ 只把 worker 的**摘要结果**回灌主管,worker 内部 20 步过程不污染主管上下文;④ `max_rounds` 是必备护栏,防止无限派活。

## 对比:四种拓扑

| 拓扑 | 有无中心 | 通信 | 好控/好调试 | 适合 | 主要风险 |
|---|---|---|---|---|---|
| Supervisor-Worker | 有(主管) | worker 只对主管 | ★★★ | 绝大多数生产任务 | 主管成瓶颈 |
| Peer-to-Peer | 无 | 对等互发 | ★ | 辩论/模拟/开放协作 | 不收敛、失控 |
| Planner-Executor | 有(规划者) | 规划↔执行 | ★★ | 步骤可预排的长任务 | 交接来回 |
| Hierarchical | 多层主管 | 层层上下 | ★★ | 超大可深分解任务 | 级联错误放大 |

## 何时用 / 坑

**该上多体**:任务能**清晰分解**为子任务、各子任务需要**不同专精**(工具/指令/模型)、子任务**可并行**值得省时间、或单个上下文**装不下**(用隔离降噪)、需要**多视角**辩论提质量。

**不该上**:任务本质是串行的、子任务间强耦合(拆开后反复来回还不如不拆)、或单 agent 配几个工具就能干净利落搞定。**为多而多是反模式。**

**坑**:
- **成本翻倍甚至更多**:N 个 agent 各跑各的,token 和延迟都涨;peer-to-peer 互发消息更会失控膨胀。多体要先算账。
- **级联错误**:上游 agent 给出错误结果,下游全建立在错的之上,错误被放大。需要在交接点设校验([[08 Evaluator-Optimizer|Evaluator-Optimizer]])。
- **协调开销吃掉收益**:派活、通信、汇总本身要花模型调用;子任务太小,协调成本比干活还贵。拆得别太细。
- **状态不一致**:并行 agent 读写共享状态产生冲突,或各持过时副本。需要明确的状态所有权和同步机制。
- **上下文污染**:把 worker 的全过程回灌给主管,主管上下文迅速变脏。**只传摘要**(见 [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]])。
- **难调试**:多条轨迹交织,出错难定位。supervisor-worker 这类有中心的拓扑明显更好查——这是它成为主流的重要原因。

## 关键事实

- 多体的本质:**大任务拆给多个各有分工、各持独立上下文的 agent**;最实在的好处常是**上下文隔离降噪**,而非「更聪明」。
- **多体不是默认选项**:先问单 agent 能否搞定,不能再上。为多而多是反模式,纪律是简单优先。
- 四种拓扑:**supervisor-worker(有中心、最常用、好调试)/ peer-to-peer(无中心、易失控)/ planner-executor(规划执行分离)/ hierarchical(分层、超大任务)**。
- supervisor 的核心动作是 [[05 Routing|Routing]];它是 [[07 Orchestrator-Workers|Orchestrator-Workers]] 工作流模式的「多 agent 实例」版;planner-executor 是 [[10 Plan-and-Execute|Plan-and-Execute]] 的两体拆分。
- 通信靠**消息传递**或**共享状态/黑板**;关键纪律:**agent 间只传摘要不传全过程**,护住各自上下文。
- 代价:成本翻倍、级联错误、协调开销、状态不一致、难调试。落到 harness 层就是 [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]];选框架看 [[37 Agent 框架对比|Agent 框架对比]]。

## 主流开源实现 / Python 库

- **`langchain-ai/langgraph`**(pip `langgraph`):把多体显式建成有向图(节点/边/共享 state),控制力最强,supervisor / hierarchical 拓扑都能精确表达——**要可控、好调试的生产多体首选**。
- **`crewAIInc/crewAI`**(pip `crewai`):以「crew + role + task」声明式组队,44K+ star、上手最快,适合团队速度优先。
- **`ag2ai/ag2`**(pip `ag2`,⚠️ 原 `microsoft/autogen` 社区分支独立出来、原名 AutoGen v0.2 一脉;Microsoft 另维护 v0.4+ 重写版):对话式多 agent、辩论/协商研究场景见长。
- **`openai/openai-agents-python`**(pip `openai-agents`,2025-03 发布,取代实验性 Swarm):核心抽象是 **handoff**——agent 显式把控制权连同上下文交给另一个,轻量贴近 OpenAI 栈。
- 当下首选:要控制力 `langgraph`;要快速组队 `crewai`;对话式研究 `ag2`;OpenAI 原生轻量 `openai-agents`。

## 工业界实践

**最有代表性的生产案例:Anthropic 的 Research(多 agent 深度研究)**。它是教科书级的 supervisor-worker:一个 **lead researcher** 规划 → 并行起 3-5 个**专精 subagent**(各持独立上下文、各自探索问题的一个侧面)→ lead 汇总,再单独跑一遍 **citation(引用核对)pass**。两个必须记住的数字:① **token 用量约是普通 chat 的 ~15×**;② 内部评测里「Opus 4 做 lead + Sonnet 4 做 subagent」的多体配置**比单 agent Opus 4 高 90.2%**。Anthropic 还总结:**约 80% 的性能方差来自 token 用量**——而 subagent 的并行 + 各自独立窗口,本身就是一种压缩(每个只把最重要的 token 浓缩回 lead)。这把本篇「上下文隔离即降噪」的论点落到了真实数据上。

**经济学边界**:~15× 的成本只有**高价值任务**才扛得住——法务尽调、竞品情报、生物医学文献综述这类一次答对值很多钱的场景。消费级 Q&A 吸收不了这个乘数,**就该用单 agent**。这正对应本篇纪律:多体不是默认选项。

**行业的两派之争(面试爱问)**:
- **Anthropic「How we built our multi-agent research system」(2025-06)**:多体能赢,关键在并行 + 上下文隔离 + 充足 token 预算。
- **Cognition(Devin 团队)「Don't Build Multi-Agents」(Walden Yan,2025-06)**:naive 多体很脆——subagent 之间互不知道对方在干什么,决策会冲突;主张「context engineering」,尽量传完整上下文、谨慎拆分。
- **看似对立,实则一致**:不是意识形态之争,是「选对工具」——任务能干净分解、可并行、需专精就上多体;强耦合、需要共享全程上下文的就别拆。两篇都在说:**拆分的代价是上下文共享变难**,只在收益盖过这代价时才拆。

**典型落地框架与定位**:`langgraph`(把多体建成有向图 + 共享 state,控制力/可调试性最强,生产首选)、`crewai`(crew+role+task 声明式,上手最快)、`ag2`(对话式辩论/协商)、`openai-agents`(handoff 显式移交控制权 + 上下文,轻量贴 OpenAI 栈)。harness 层落地见 [[26 Sub-agents 与 Agent Teams|Sub-agents 与 Agent Teams]]。

**规模化与成本/延迟权衡**:墙钟时间靠**并行**近乎除以 worker 数,但 token 成本随 agent 数线性甚至超线性涨(peer-to-peer 互发消息会失控膨胀)。控成本三招:① subagent 用便宜模型(Sonnet/Haiku)、lead 用强模型;② 只传摘要不传全过程;③ 限 worker 数 + `max_rounds` 护栏。

**可观测运维**:多条轨迹交织,**必须**给每个 agent 打标做分布式 trace(谁派给谁、各花多少 token、哪一步出错),否则无法定位。supervisor-worker 有中心、好定位,是它成主流的重要原因。接 [[38 Agent 评估与可观测性|Agent 评估与可观测性]]。

## 面试高频

- **Q:什么时候该上多智能体,什么时候不该?**
  A:该上——任务可清晰分解、子任务需不同专精(工具/指令/模型)、可并行省时、或单上下文装不下(隔离降噪)、需多视角辩论。不该上——本质串行、子任务强耦合、单 agent 配几个工具就能搞定。**为多而多是反模式,纪律是简单优先。**
- **Q:多 agent 最被低估的好处是什么?**(高频)
  A:**不是「更聪明」,而是上下文隔离即降噪**——每个 sub-agent 各持干净聚焦的上下文,中间垃圾不污染主 agent。Anthropic Research 的 ~80% 性能方差来自 token 用量,正源于此。
- **Q:四种拓扑分别是?哪种最常用、为什么?**
  A:supervisor-worker(有中心、最常用)/ peer-to-peer(无中心、易失控不收敛)/ planner-executor(规划执行分离)/ hierarchical(分层、超大任务)。supervisor-worker 最常用,因为**有中心、好控、好调试**(出错能定位到哪个 worker)。
- **Q:supervisor 的核心动作本质是什么?**
  A:一次 [[05 Routing|Routing]](根据子任务派给对的 worker)+ 终止判断。它是 [[07 Orchestrator-Workers|Orchestrator-Workers]] 的「多 agent 实例」版;planner-executor 是 [[10 Plan-and-Execute|Plan-and-Execute]] 的两体拆分。
- **Q:agent 之间怎么通信?有什么坑?**
  A:消息传递 vs 共享状态/黑板(LangGraph state、CrewAI 共享记忆)。关键纪律:**只传摘要不传全过程**,护各自上下文。坑:共享状态的**并发写冲突/状态不一致**——并行 agent 同改一块,谁覆盖谁?需明确状态所有权与同步。
- **Q:多体的主要风险?**(陷阱:别只说成本)
  A:成本翻倍、**级联错误**(上游错下游全建在错上,需在交接点设 [[08 Evaluator-Optimizer|Evaluator-Optimizer]] 校验)、协调开销吃掉收益(拆太细)、状态不一致、难调试。
- **Q:Anthropic 和 Cognition 在多体上为什么「打架」?**
  A:Anthropic 证明多体能赢(并行+隔离+token 预算),Cognition 警告 naive 多体脆(上下文不共享、决策冲突)。本质不矛盾:**拆分代价是上下文共享变难,只在收益盖过代价时才拆**。

## 知识拓展

- **进阶方向**:从静态拓扑到**动态组队**(运行时按任务难度决定起几个 worker、用什么模型);从纯并行到**辩论/投票**(多 agent debate 提质量,2023-2024 多篇研究);A2A 跨厂商 agent 互操作见 [[30 A2A 协议|A2A 协议]]。
