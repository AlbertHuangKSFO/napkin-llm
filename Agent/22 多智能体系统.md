[[22 多智能体系统|多智能体系统]] 的本质：把一个目标拆成边界清晰、可独立验证的子任务，由协调者分配并汇总；它扩大的是搜索宽度、工具吞吐和上下文隔离，不是让多个模型「天然更聪明」。

## 直觉：主治医生与并行会诊

复杂病例里，主治医生不会让五位专家各自「把病人治好」；他把影像、用药、病理等互不重叠的问题分给相应专家，要求统一的报告格式，再对矛盾证据作最终决策。多智能体中的 orchestrator 是主治，worker 是专家，artifact/验收规则是病历。没有任务边界和汇总协议，五位专家只是把同一份检查重复看五次。

它是 [[07 Orchestrator-Workers|Orchestrator-Workers]] 的动态化实现：由模型根据中间发现继续分解；若步骤强依赖、共享同一可变状态，则先用单 agent 或显式工作流，别为「多」而多。

## 小数字手算：并行只在可并行部分上加速

三个独立检索任务每个需 $t=10$ 秒，合并与调度开销 $o=2$ 秒。串行时间：

$$
T_{\text{serial}}=3\times10=30\text{ s}
$$

若三者真能并行：

$$
T_{\text{parallel}}=\max(10,10,10)+2=12\text{ s},\qquad
S=\frac{30}{12}=2.5
$$

若三个任务都必须读写同一份未加锁的计划，实际还要等待、重试和冲突解决；当 $o\ge20$ 秒时，$S\le1$。因此先问「结果能否独立产生、能否独立验收」，而不是先数 agent。

成本同样相加。以 token 预算单位为例，协调者 $2$、三个 worker 各 $4$、汇总 $2$，则：

$$
C=2+3\times4+2=16
$$

这是架构预算算例，不是任何产品的普适倍数或性能承诺。

## 推导：什么时候拆分值得

设任务集合为 $V$，依赖边为 $E$。仅当子任务间没有未解决依赖时，才可进入并行批次：

$$
\operatorname{ready}(v)\iff \forall (u,v)\in E,\;u\text{ 已交付并通过验收}
$$

协调器需要为每个 $v$ 明确五件事：目标、允许工具/数据范围、预算与停止条件、artifact 格式、验收器。返回对象不是「我觉得完成了」，而是：

$$
a_v=(\text{claim},\text{evidence},\text{location},\text{checks},\text{open risks})
$$

这样合并者可以比较证据、重新运行检查，或只重派失败分支。共享状态则应由事务、锁、版本号或单一写者管理；把冲突留给语言模型临场协调，无法给出一致性保证。

[Anthropic 的生产复盘（2025-06-13）](https://www.anthropic.com/engineering/multi-agent-research-system)把其 Research 实现为 orchestrator-worker：适合广度优先、多个独立方向的研究；同一篇文章也指出，强共享上下文或相互依赖多的任务（其举例包括许多编码任务）并不适合当前多 agent。文中出现的评测百分比和 token 比例只属于其模型、提示、任务集和对照设置，不能外推为通用收益。

## 可运行代码：先声明独立边界，再并行

❌ 朴素做法把相同大目标广播给所有 worker，容易重复搜索且难合并。

```python
tasks = ["研究这个主题", "研究这个主题", "研究这个主题"]
```

✅ 此最小示例用独立输入、结构化交付和 `asyncio.gather` 并发；现实系统还应限制并发、超时、重试和权限。

```python
import asyncio

async def worker(scope: str) -> dict:
    await asyncio.sleep(0)  # 代表独立 I/O 或工具调用
    return {"scope": scope, "claim": f"{scope} 已检查", "evidence": [f"artifact://{scope}"]}

async def orchestrate() -> list[dict]:
    scopes = ["接口契约", "失败路径", "回归测试"]
    reports = await asyncio.gather(*(worker(scope) for scope in scopes))
    assert {r["scope"] for r in reports} == set(scopes)
    assert all(r["evidence"] for r in reports)
    return reports

print(asyncio.run(orchestrate()))
```

并行 API 只解决等待重叠；任务是否真的独立、证据是否足够、写操作是否冲突，仍是系统设计责任。

## 运行契约：避免三类常见失败

- **重复劳动**：给每个 worker 不同的范围和排除项；协调者在交付前去重，而不是靠「你们别重复」的泛泛提示。
- **传话失真**：大结果写入文件、数据库或对象存储，回传 artifact 引用和关键结论。该模式与 [[21 上下文压缩与卸载|上下文压缩与卸载]] 相连。
- **提前宣告成功**：验收器检查外部结果，而非只读 worker 的自然语言。代码任务看测试、构建产物和 diff；研究任务看主张—来源对应关系。

⚠️ **specialist 不是魔法角色。** 「测试 agent」「安全 agent」只有在工具、上下文、验收 rubric 或职责边界确有不同的时候才值得拆开；否则一个清晰 prompt 的单 agent 往往更便宜、也更容易调试。

## 面试高频
> 面试地图：[[Agent 面试题库]]

**问：多 agent 何时优于单 agent？**

答：当任务可以拆成低依赖、可并行验证的分支，且价值覆盖额外 token、协调和失败处理成本时。例如多源研究、互不相干的批量审计。强共享状态、细粒度顺序依赖、低价值小任务优先单 agent。

**问：orchestrator 的最小职责是什么？**

答：分解、授权、预算、调度、汇总和验收。它不该吞掉所有中间文本；应让 worker 产出可引用 artifact，并在失败时只重派相应分支。

**问：如何评估多 agent？**

答：至少测最终正确性/安全性、延迟、token 与工具成本、重复率、失败恢复率。不要只比较一条「最佳轨迹」；随机性要求多次 trial，并以同一任务集和预算对比单 agent 基线。

## 关键事实

- [Anthropic，2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system)：其 Research 功能采用 lead agent 协调并行 sub-agent 的模式，专门面向开放式、多方向研究；同时列出协调、可靠性、成本和强依赖任务的限制。
- [Anthropic，2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：将 sub-agent 描述为隔离深度探索上下文、只回传浓缩结果的一种策略，适用性取决于任务特征。
- [Anthropic，2026-01-09](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：对会改写环境的 agent，应衡量最终外部状态并保留完整 trace；这同样适用于 orchestrator 的分支验收。
