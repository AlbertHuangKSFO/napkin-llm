[[24 Agentic Search：grep vs 向量检索|Agentic Search：grep vs 向量检索]] 戳破一个反直觉的现实:**2026 年的编码 agent 普遍放弃向量库,改用 grep / find / read 迭代搜索**。原因不是向量检索不行,而是 **agentic search 是模型自主规划多步搜索、每步之间带推理**(形成假设→用工具验证→跨文件追因果链),而非单次匹配——在这种范式下,精确、零索引、永不陈旧的 grep 往往比语义检索更香。

## 本质:agentic search 不是「搜一次」,是「边搜边想」
传统检索(包括向量检索)的心智模型是:**一个 query 进去,一批结果出来,结束**。它是单跳(single-shot)的——把问题向量化,去库里找最相似的 top-k,返回。

agentic search 的心智模型完全不同:**模型像个侦探,搜索是一连串带推理的动作**。它先形成一个假设(「鉴权逻辑大概在 `auth/` 目录」),用工具去验证(`grep -r "authenticate"`),读命中的文件看上下文,据此**精化假设**(「原来调用方在 `middleware.py`」),再发起下一轮搜索……如此循环,直到把因果链追清楚。**关键在「每步之间带推理」**:每一次 grep 不是孤立的匹配,而是基于上一步观察做出的、有目的的下一步。

![[Agentic Search：grep vs 向量检索.svg]]

这就是为什么它叫 **agentic** search 而不是 semantic search:主语是 agent(模型自主决定搜什么、怎么搜、何时停),搜索只是它手里的一连串工具调用。这本质上是 [[03 Agent 核心循环|Agent 核心循环]] 的「思考→行动→观察」落在「检索」这个具体任务上的产物——每一轮 grep/read 都是一次「行动」,读到的结果是「观察」,据此再「思考」下一步。

## 机制:迭代搜索环怎么转
拆开看,一轮典型的 agentic search 是这样转的:

1. **形成假设**:模型读懂问题(「这个超时配置在哪生效?」),基于对代码库常识的先验,猜一个起点。
2. **用工具验证**:发起 `grep`/`glob`——精确字面匹配。比如 `grep -rn "timeout" --include=*.py`。这一步**精确**:命中就是命中,没有「相似度 0.83」的模糊。
3. **读上下文(read)**:对命中点,用 `read` 看周围几十行,理解它在干什么、被谁调用。
4. **精化假设、跨文件追链**:发现这个 `timeout` 是从环境变量读的 → 新假设:「那环境变量在哪设的?」→ 回到第 2 步,换关键词再 grep。这一步是 agentic 的灵魂:**它在跨文件追一条因果链**,而不是停在第一个命中点。
5. **收敛或继续**:信息够了就给答案/动手改;不够就继续循环。模型自己判断何时停——这正是 [[03 Agent 核心循环|Agent 核心循环]] 的终止判断。

整个过程里,**没有索引、没有 embedding、没有向量库**。工具就是操作系统级的 `grep`/`find`/`read`,模型用自然的多步推理把它们串起来。这也呼应 [[16 工具设计与工具层|工具设计与工具层]]:给 agent 一组**可组合的原子工具**(grep + glob + read),往往比给它一个黑箱的「语义搜索」工具更强,因为模型能自己编排。

## 为什么编码场景 grep 更香
编码是 agentic search 最先「抛弃向量库」的领域,原因很具体:

- **精确**:代码是精确的符号系统。函数名 `getUserById` 就是 `getUserById`,grep 它要么命中要么不命中,没有歧义。向量检索给你「语义相似」,但你要找的往往是**那一个确切的标识符**,相似没用。
- **零索引**:grep 即查即用,不需要预先建索引。clone 下来一个新仓库,第一秒就能搜。向量检索得先把全库 embedding 一遍、建库,这在 CI、临时仓库、私有代码里都是负担。
- **无陈旧**:代码每分钟都在改。向量索引一旦建好,代码一改它就**陈旧**了——你搜到的可能是已删除的旧函数。grep 永远搜的是**当前磁盘上的真实内容**,不存在陈旧问题。这是编码场景最致命的一点:agent 改了文件后,下一次 grep 立刻看到新状态。
- **可组合**:`grep` 能和 `glob`(限定文件范围)、管道、正则组合,模型可以非常精细地控制搜什么。语义搜索是个黑箱,不可组合。
- **token 可控**:grep 只返回命中行(可加 `-A/-B` 控制上下文行数),token 开销小且可预测。向量检索常返回整块 chunk,容易把无关内容塞进上下文,加剧 [[20 上下文工程|上下文工程]] 的压力。

一句话:**在一个「内容精确、频繁变更、即开即用」的环境里,grep 的每一个特性都正中要害,而向量检索的每一个代价都被放大**。

## 向量检索何时仍然有用
但别走极端——这不是「向量检索死了」,而是「分场景」。向量检索在这些情况下仍不可替代:

- **模糊语义查询**:当你不知道确切关键词,只知道「意思」。比如在一个产品文档库里问「怎么处理用户退订」,文档里可能写的是「cancellation flow」「取消订阅」——字面词对不上,但语义相近。这时 [[04 Embedding 与向量数据库|Embedding]] + [[04 Embedding 与向量数据库|向量数据库]] 的语义召回就是刚需。
- **超大库、自然语言为主**:几十万篇文档、客服记录、知识库——这些是自然语言(不是精确符号),且大到没法 grep 全扫。这正是 [[RAG]] 的主场。
- **跨语言/同义召回**:用户用中文问,文档是英文;或同一概念有多种叫法。向量空间能跨越这些表面差异。

判断口诀:**内容是「精确符号」(代码、API、标识符)→ 偏 grep;内容是「模糊语义」(自然语言文档)→ 偏向量。**

## 混合策略与关键数据
最强的往往是**混合**:用向量做粗召回(找到「大概相关」的区域),再用 grep 做精筛(在区域内精确定位)。这吸收了两者长处——语义负责召回率,grep 负责精确度。

![[Agentic Search：grep vs 向量检索-三法对比.svg]]

这里有个非此即彼必须保真的关键事实:**Cursor 的研究显示语义搜索 + grep 比纯 grep 回答代码库问题准确率高 12.5%,在 1000+ 文件的库上提升最大**。

注意这个结论的精确含义,别误读成「向量检索吊打 grep」:它说的是**「语义搜索 + grep」**(混合)对比**「纯 grep」**——也就是在 grep 之上**叠加**语义召回能带来 12.5% 的准确率提升,且**库越大(1000+ 文件)提升越大**。这恰恰印证了上面的判断:在小到中等的库里,纯 grep 迭代已经很够;但当库大到 grep 的「选对关键词」越来越难、需要语义来兜召回时,混合才显出价值。换句话说,grep 是地基,语义是在大库上锦上添花的那一层。

## 可跑最小示例(agentic search 的循环)
下面这段伪代码体现「每步带推理」的迭代本质——对比一下单跳向量检索:

```python
# Agentic search:多步、带推理、用 grep/read 迭代
def agentic_search(question, repo):
    hypothesis = llm(f"针对问题猜一个搜索起点(关键词+目录):{question}")
    findings = []
    for _ in range(MAX_STEPS):                  # 多步循环
        hits = grep(hypothesis.keyword, path=hypothesis.dir)  # 精确、零索引、不陈旧
        for h in top(hits):
            ctx = read(h.file, around=h.line)   # 读命中点上下文
            findings.append(ctx)
        # 关键:基于观察精化假设,跨文件追因果链
        decision = llm(f"已知:{findings}\n问题:{question}\n够答了吗?不够给下一步搜索。")
        if decision.done:
            return llm(f"基于 {findings} 回答:{question}")
        hypothesis = decision.next_search        # 换关键词/换目录,再来一轮
    return llm(f"基于 {findings} 尽力回答:{question}")

# 对比:单跳向量检索——一个 query 进,top-k 出,结束
def vector_search(question, index):
    qv = embed(question)
    chunks = index.topk(qv, k=8)                 # 没有"下一步",没有推理迭代
    return llm(f"基于 {chunks} 回答:{question}")
```

差别一目了然:`agentic_search` 有 `for` 循环、有 `精化假设`、有 `够了吗` 的自主判断;`vector_search` 是一锤子买卖。这也是为什么 agentic search 能力上限更高——它把「检索」从一次匹配,变成了一段可推理的探索。

## 对比表:grep 迭代 vs 向量检索 vs 混合
| 维度 | grep / glob 迭代 | 向量检索 | 混合 |
|---|---|---|---|
| 精确度 | 高(字面精确) | 中(语义相似,不精确) | 高(语义召回 + grep 精筛) |
| 语义理解 | 无(只字面) | 强(懂同义/模糊) | 强 |
| 索引成本 | 零(即查即用) | 高(需建/维护索引) | 高(仍需索引) |
| 陈旧风险 | 无(永远查当前内容) | 有(代码一改即过时) | 有(索引部分会陈旧) |
| token 开销 | 小且可控(只回命中行) | 中(常回整块 chunk) | 中 |
| 适用规模 | 小到大(编码场景默认) | 超大、自然语言库 | 大库,需语义兜召回 |
| 典型场景 | 代码库探索、改 bug | 文档 [[RAG]]、模糊问答 | 1000+ 文件大库代码问答 |

## 何时用 / 坑
- **何时用 grep 迭代**:编码、配置、日志这类**精确符号 + 频繁变更**的内容。这是编码 agent 的默认搜索方式,也是最稳的起点。
- **何时上向量/混合**:内容是**自然语言**、库**超大**、查询**模糊**;或代码库大到 grep 选关键词困难(此时混合,享受那 12.5%)。
- **坑一:盲目给 agent 上向量库**。在代码场景,建索引、维护陈旧、召回不精确的代价常常超过收益——先试纯 grep 迭代,不够再叠语义。
- **坑二:把 agentic search 当单跳用**。如果你只让模型搜一次就答,你丢掉了它最大的优势(多步推理追链)。要给它循环、给它「再搜一次」的工具和预算。
- **坑三:工具不可组合**。给 agent 一个黑箱「搜索」工具,不如给它 grep+glob+read 一组原子工具——见 [[16 工具设计与工具层|工具设计与工具层]],可组合性是 agentic search 的前提。
- **坑四:不管 token**。迭代搜索每轮都往上下文塞内容,容易爆。用 grep 的上下文行数控制、及时摘要,配合 [[20 上下文工程|上下文工程]]。
- **坑五:误读 Cursor 数据**。那 12.5% 是「语义 + grep」相对「纯 grep」,不是「向量 > grep」;且大库收益最大、小库未必。别拿它当「必须上向量库」的依据。

## 2026 关键事实
- **2026 年的编码 agent 普遍放弃向量库,改用 grep / find / read 迭代搜索**。
- **agentic search = 模型自主规划多步搜索,每步之间带推理**(形成假设→用工具验证→跨文件追因果链),而非单次匹配。
- 关键数据:**Cursor 的研究显示语义搜索 + grep 比纯 grep 回答代码库问题准确率高 12.5%,在 1000+ 文件的库上提升最大**。
- grep 在编码场景的五大优势:**精确、零索引、无陈旧、可组合、token 可控**。
- 向量检索仍有用的场景:**模糊语义查询、超大自然语言库**——这是 [[RAG]] 的主场;混合策略(语义召回 + grep 精筛)是大库的更优解。
- 关联:agentic search 是 [[03 Agent 核心循环|Agent 核心循环]] 落在检索任务上的体现;依赖 [[16 工具设计与工具层|工具设计与工具层]] 的可组合原子工具;与 [[36 Agentic RAG|Agentic RAG]](让 agent 自主决定检索)同源;受 [[20 上下文工程|上下文工程]] 的 token 约束。跨域概念见 [[RAG]]、[[04 Embedding 与向量数据库|Embedding]]、[[04 Embedding 与向量数据库|向量数据库]]、[[08 混合检索 Hybrid Search|混合检索]]。

## 工业界实践

**谁这么干**:2025-2026 真正在写/调代码的 agent——**Claude Code、Cursor、Devin**——大多不为代码库起向量库,而是跑 grep、读文件树、调 find、按名取文件。其中 **Claude Code 押注极简**:不建索引、不做 embedding,纯 grep + read + 文件树 + 跟 import 链(像有经验的工程师那样找代码)。

**Claude Code 抛弃 RAG 的四条理由(面试常问,务必记牢)**:① **Security**——存在某处的索引就是攻击目标;② **Privacy**——专有代码的 embedding 会泄露信息;③ **Staleness**——session 开始时建的索引,第一个文件一改就陈旧;④ **Reliability**——每多一个系统就多一个故障点。这四条加上「精确、零索引、无陈旧、可组合、token 可控」五大优势,构成了编码场景偏 grep 的完整论证。

**Cursor 的另一条路(语义索引)**:把仓库切 chunk → embedding → 语义检索,是把 RAG 用在代码上。有数据支撑其价值:**embedding 搜索相比裸 grep 减少约 40% token**,**AST-based 检索可砍约 74% token**;语义搜索让「浪费的读取」降到约 1/8。但 grep 与 grep+semantic 都倾向「找到更少文件但相关函数占比更高」,grep+semantic 召回与纯 grep 接近、个别场景反而略差——印证「小到中库纯 grep 够,大库才靠语义兜召回」。

**混合的工程形态**:**Claude Context** 是一个 MCP server,把代码库索引进 **Milvus / Zilliz Cloud**,让任意 MCP-aware agent 跑 **BM25 + 稠密向量的混合检索**,而不是把整目录塞进 prompt。这是「向量粗召回 + grep/读取精筛」落到 [[17 MCP 模型上下文协议|MCP 模型上下文协议]] 上的现成件。

**典型数据流(纯 grep 迭代)**:形成假设(关键词+目录)→ `grep -rn`/`glob` 精确匹配 → `read` 命中点上下文(`-A/-B` 控行数)→ 精化假设、跨文件追因果链 → 收敛或再来一轮。全程零索引、零 embedding、查的永远是当前磁盘真实内容——agent 改完文件,下一次 grep 立刻看到新状态。

**规模化与成本/延迟权衡**:grep 即查即用、token 只回命中行(小且可控),但**选错关键词**会多绕几轮;大库(1000+ 文件)选词越来越难,此时叠语义兜召回。延迟上 grep 是本地系统调用、极快;向量检索省 token 但要维护索引 + 承担陈旧风险。

**踩坑与最佳实践**:① 工具要**可组合**(grep+glob+read 原子工具 > 黑箱「搜索」),见 [[16 工具设计与工具层|工具设计与工具层]];② 给足循环预算别当单跳用;③ 控 token——grep 上下文行数 + 及时摘要(配 [[21 上下文压缩与卸载|上下文压缩与卸载]]);④ 大库再上混合,别一上来就建向量库。

## 面试高频

- **Q:为什么 2026 的编码 agent 普遍放弃向量库改用 grep?**
  A:代码是**精确符号系统 + 频繁变更 + 即开即用**——grep 的五大特性正中要害:精确(标识符要么命中要么不命中)、零索引、无陈旧(永远查当前磁盘)、可组合、token 可控。加上 Claude Code 抛弃 RAG 的四理由:Security / Privacy / Staleness / Reliability。
- **Q:agentic search 和普通(向量)检索的本质区别?**(高频)
  A:向量检索是**单跳**(一个 query → top-k → 结束);agentic search 是**模型自主规划的多步搜索,每步之间带推理**(形成假设→工具验证→读上下文→精化假设→跨文件追因果链)。它是 [[03 Agent 核心循环|Agent 核心循环]] 落在检索上的产物。
- **Q:那向量检索是不是死了?**(陷阱)
  A:没有,分场景。内容是**精确符号**(代码/API/标识符)→ 偏 grep;内容是**模糊语义**(自然语言文档、超大库、跨语言同义召回)→ 偏向量,这是 [[RAG]] 主场。口诀:精确符号偏 grep,模糊语义偏向量。
- **Q:Cursor 那个 12.5% 数据怎么解读?**(必考陷阱)
  A:它是「**语义搜索 + grep(混合)**」相对「**纯 grep**」高 12.5%,**不是**「向量 > grep」;且**库越大(1000+ 文件)提升越大**。结论:grep 是地基,语义是大库上锦上添花的那层,别拿它当「必须上向量库」的依据。
- **Q:为什么给 agent 一组原子工具比给一个黑箱「搜索」工具强?**
  A:可组合性是 agentic search 的前提——grep+glob+read 能让模型精细编排(限范围、控行数、跟链),黑箱不可组合、不可控。见 [[16 工具设计与工具层|工具设计与工具层]]。
- **Q:把 agentic search 当单跳用会丢什么?**
  A:丢掉它最大的优势——多步推理追因果链。要给它循环、给「再搜一次」的工具和 token 预算。

## 知识拓展

- **进阶方向**:**混合分层检索**(向量/BM25 粗召回 → grep/AST 精筛 → read 验证);AST/符号级检索(按语法树而非字面,token 更省);把检索决策交给 agent 自主编排即 [[36 Agentic RAG|Agentic RAG]]。
