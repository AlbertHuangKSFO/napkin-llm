[[010 显存墙与 LLM 推理的本质约束|显存墙]](memory wall)指硬件算力(FLOPS)的增速长期远超内存带宽的增速,二者裂成「剪刀差」;后果是 LLM 自回归 decode 受带宽限而非算力限——推理本质是一场「把权重从 HBM 搬到计算单元」的搬运游戏。

## 直觉:厨房里不是炉子不够快,是配菜送不上来
把 GPU 想成一个超快的炒锅(算力),但备菜区到炉灶的传送带(HBM 带宽)跟不上。炉子每秒能炒 100 份,传送带每秒只送 10 份料 → 炉子有 90% 时间空烧等料。decode 每生成一个 token,都要把整个模型权重「整盘端过来」过一遍炉子,却只翻炒几下就出锅。瓶颈永远在传送带,不在炒锅。堆更猛的炒锅(更多 FLOPS)毫无意义。

## 小数字例子:decode 吞吐被带宽锁死
70B 模型 fp16 权重 140GB,单流 decode(batch=1):每生成 1 token 必须把 140GB 权重整读一遍。
- **H200(4.8 TB/s)**:上限 ≈ 4800/140 ≈ **34 tok/s**。
- **B200(8 TB/s)**:≈ 8000/140 ≈ **57 tok/s**。
- 此时算力几乎全闲——这就是 [[004 算力 vs 带宽：Roofline 与算术强度|Roofline]] 里「带宽限」区。
**破局靠提算术强度**:batch=32 时,140GB 权重读一次服务 32 个请求,每请求摊到的带宽成本降 32×,吞吐随之逼近算力上限。所以「连续批处理(continuous batching)」是推理引擎的核心优化(见 [[LLM/076 显存占用估算(参数、梯度、优化器、激活、KV)|显存估算]] 系列后续)。

## 原理:算术强度与 Roofline
单次 matmul 的算术强度 $I = \dfrac{\text{FLOPs}}{\text{Bytes from HBM}}$。decode 阶段(batch 小)矩阵乘退化为矩阵×向量,$I$ 极低:

$$\text{decode 吞吐} \approx \min\!\left(\frac{\text{峰值 FLOPS}}{\text{每 token FLOPs}},\; \frac{\text{HBM 带宽}}{\text{每 token 读字节}}\right)$$

当 $I < $ 硬件的「脊点」算术强度(峰值 FLOPS ÷ 带宽,H 系约 200+ FLOP/Byte),系统落在带宽限一侧,$\text{吞吐} = \text{带宽} / \text{读字节}$,与 FLOPS 无关。memory wall 让脊点逐代右移,decode 越来越难离开带宽限区。

## 为什么 prefill 和 decode 命运不同

| 阶段 | 并行度 | 算术强度 | 受限于 |
|---|---|---|---|
| Prefill(处理 prompt) | 一次过所有 token,矩阵×矩阵 | 高 | 算力(compute-bound) |
| Decode(逐 token 生成) | 一次一个 token,矩阵×向量 | 极低 | **带宽(memory-bound)** |

![[hw-010prefill与decode命运.svg]]

这解释了诸多设计:**量化**(int4 把权重读字节减 4× → 吞吐 4×)、**MoE**(每 token 只激活部分专家,少读权重)、**KV-Cache 压缩 / PagedAttention**(KV 也要每步整读,压它就提速)、**投机解码**(一次验证多 token 摊带宽)。全都是冲着「少搬字节 / 多复用」去的。

## 代码/配置:别在带宽限场景堆算力

```python
# ❌ 误以为「换更高 FLOPS 的卡 / 开 FP8 算力」就能让单流生成更快
# 单请求 batch=1 时,decode 是带宽限,FLOPS/算力精度几乎不影响 tok/s
llm = LLM(model="llama-70b", dtype="float16", max_num_seqs=1)   # 浪费

# ✅ 三招对症「带宽限」:
# 1) 加大并发,摊薄每 token 的权重读取(continuous batching)
llm = LLM(model="llama-70b", max_num_seqs=256)        # batch 大 → 算术强度上升
# 2) 量化权重,直接减少每 token 读字节
llm = LLM(model="llama-70b", quantization="awq")      # int4 权重读量 ÷4
# 3) KV 也要省:PagedAttention + KV 量化,减少每步 KV 读取
llm = LLM(model="llama-70b", kv_cache_dtype="fp8")
```

## 面试高频
- **为什么说 LLM 推理是 memory-bound?** 自回归 decode 每生成 1 token 要把全部权重(和 KV-Cache)从 HBM 整读一遍,却只做极少算术 → 算术强度极低,GPU 算力闲置,等带宽。瓶颈是 TB/s 不是 PFLOPS。
- **什么是显存墙(memory wall)?** 算力增速远超带宽增速(2012→2022 FLOPS ×80、带宽 ×17)的长期剪刀差;导致越来越多工作负载(尤其 decode)困在带宽限一侧。
- **prefill 和 decode 为什么瓶颈不同?** prefill 一次处理整段 prompt,矩阵×矩阵、算术强度高、compute-bound;decode 一次一个 token、矩阵×向量、算术强度低、memory-bound。
- **既然 decode 带宽限,怎么提吞吐?** 不靠堆算力,靠:① 加 batch(摊薄权重读取)② 量化(减读字节)③ KV 压缩 / MoE(少搬数据)④ 投机解码(一次摊多 token)。
- **为什么新卡都比 TB/s?** 因为决定 decode 吞吐的是 HBM 带宽:单流上限 ≈ 带宽 ÷ 每 token 读字节;FLOPS 再高也搬不快数据。

## 关键事实(2025–2026)
- **剪刀差数据**:2012→2022,NVIDIA GPU FLOPS 约 ×80,HBM 带宽仅约 ×17,缺口持续扩大(memory wall)。
- **decode 单流吞吐公式**:≈ HBM 带宽 ÷ 每 token 需读字节(权重 + KV)。70B fp16 在 H200(4.8 TB/s)约 34 tok/s,B200(8 TB/s)约 57 tok/s。
- **当代带宽**:H200 4.8 TB/s、MI300X 5.3 TB/s、B200 ~8 TB/s——业界已转向以带宽而非 FLOPS 作为推理芯片核心指标。
- **本质结论**:LLM 推理是「搬权重」游戏;batching、量化、MoE、KV 压缩、投机解码全是为了「少搬字节、多复用」,绕开显存墙。
