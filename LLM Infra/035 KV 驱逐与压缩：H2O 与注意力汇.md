[[035 KV 驱逐与压缩：H2O 与注意力汇]] 是一类**把 KV-Cache 的「序列长度 T」这一维压成近似定长**的方法:解码时不再保留全部历史 token 的 KV,而是按某种重要性准则**驱逐(evict)** 一部分,只留下「真正还有用」的。两条代表线:**H2O**(Heavy-Hitter Oracle,按累计注意力分留「重击者」)和 **StreamingLLM**(保留最前几个「注意力汇」+ 近期滑窗)。它和 [[LLM/103 KV-Cache 优化：GQA、量化、驱逐与前缀共享|KV 优化]] 里「驱逐」一栏对应,是把 [[015 KV-Cache 的显存账(逐层手算)|KV 显存账]] 里的 T 维直接砍掉,与 [[036 KV 分层 offload：GPU、CPU、SSD(LMCache)|无损 offload]] 形成「有损省显存 vs 无损搬走」的互补。

## 直觉类比
KV-Cache 像你写长文时桌上摊开的**所有草稿纸**:每写一句都要扫一遍全部草稿。纸越堆越高,桌子(显存)迟早放不下。驱逐就是**定期清桌**——但不能乱扔:① 最前面那几张「封面/提纲」必须留(后文每句都要瞄一眼它,这就是**注意力汇**);② 被反复引用的几张关键草稿留着(**重击者**);③ 手边最近几张留着(**近窗**);中间没人看的就扔。清完桌面始终保持差不多大,而不是无限堆高。

## 小数字例子
设上下文 8192 token,每 token KV 占约 0.5 MB(某模型某层折算)。全量保留 ≈ 4 GB/层级预算。
- **H2O 留 20%**:只保 ~1638 个高分 token 的 KV → 显存降到约 **1/5**,batch 可放大,论文报告吞吐相对 FlexGen 最高约 **3×**(相对 DeepSpeed/HF 可达 ~29×)。
- **StreamingLLM**:留前 **4** 个 sink + 滑窗(如 2044)= 2048 个 KV,无论生成到第几百万 token,KV **恒定** 2048 个 → 支持 **400 万 token** 流式,相对「滑窗重算」基线最高 **22.2×** 加速。
关键观察:朴素滑窗若把最前 4 个也淘汰,困惑度会**爆炸**——因为丢掉了 softmax 的「泄洪口」。

## 原理:注意力汇与重击者
**注意力汇(attention sink)**:训练好的 decoder-only 模型(Llama、Mistral、Falcon、Pythia 都如此),深层里后面每个 token 都把大量注意力质量倒给**最前 1~4 个 token**,哪怕它们语义为空。原因是 softmax 必须把权重归一到和为 1,当某个 query 对当前所有 token 都「不太想看」时,多余的注意力质量需要一个**默认倾倒处**,前几位天然充当了这个角色:

$$
\sum_{j=1}^{t}\text{softmax}(s_{tj})=1,\qquad s_{tj}=\frac{q_t k_j^\top}{\sqrt{d}}
$$

一旦把承接这部分质量的 sink 的 KV 驱逐掉,剩余权重被迫重新归一化,分布剧烈偏移 → 掉点。所以 **StreamingLLM 的处方 = 永久保留前 K 个 sink(常 K=4)+ 滑动近窗**。

**H2O** 则换个准则:把每个 token 历史**累计注意力得分**当重要性,留 top-K「重击者」+ 近窗。它把驱逐建模成一个**动态子模(submodular)** 问题并给出近似保证。

$$
\text{score}(j)=\sum_{t>j}\text{softmax}(s_{tj}),\quad \text{保留}\ \underset{j}{\text{top-}K}\ \text{score}(j)\ \cup\ \text{近窗}
$$

## 配置 / 代码
```python
# StreamingLLM 思路:KV-Cache = 固定 sink + 滑动窗口(伪代码)
class StreamingKVCache:
    def __init__(self, n_sink=4, window=2044):
        self.n_sink, self.window = n_sink, window
        self.keys, self.vals = [], []   # 每元素是一层一头的 KV

    def append(self, k, v):
        self.keys.append(k); self.vals.append(v)
        # 超长时:只保留 [前 n_sink 个] + [最近 window 个],中间整体丢弃
        if len(self.keys) > self.n_sink + self.window:
            keep = self.keys[:self.n_sink] + self.keys[-self.window:]
            keepv = self.vals[:self.n_sink] + self.vals[-self.window:]
            self.keys, self.vals = keep, keepv
        return self.keys, self.vals
```

```text
✅ 留前 4 个 sink + 近窗(StreamingLLM)/ 留累计高分重击者(H2O)→ KV 近似定长且基本不掉点
```

## 面试高频
- **KV 驱逐省的是哪一维?** 序列长度 T。GQA 省头数 H、量化省每元素字节、前缀共享去重,驱逐则让 KV 不再随 T 线性增长。
- **什么是注意力汇,为什么不能丢?** 后面 token 把大量注意力质量倒给最前几位(即使语义空),因为 softmax 要归一、需要「泄洪口」;丢掉它们权重重归一化剧变,困惑度爆。
- **H2O 和 StreamingLLM 区别?** H2O 按**累计注意力分**留重击者(适合一般生成、有理论保证);StreamingLLM 固定留**前 K 个 sink + 滑窗**(主打无限长流式、免微调)。
- **驱逐有什么代价?** 被丢的 token 永久消失,长程**精确召回**(如大海捞针 needle-in-haystack)可能掉点;故常与无损 offload 互补、或对近窗精确、远端才压缩。
- **为什么这俩免微调?** 都是推理期 KV 管理策略,不改权重;StreamingLLM 让有限窗训练的模型直接泛化到极长序列。

## 关键事实
- **H2O**(Heavy-Hitter Oracle),Zhang et al. **2023**(NeurIPS 2023,arXiv 2306.14048):按累计注意力分留 top-K 重击者 + 近窗;留 20% 时吞吐相对基线最高约 3×(对 DeepSpeed/HF 达 ~29×)。
- **StreamingLLM**,Xiao et al. **2023**(ICLR 2024,arXiv 2309.17453,mit-han-lab):保留前 4 个 attention sink + 滑窗,支持 **400 万 token** 稳定流式,vs 滑窗重算最高 **22.2×**,免微调。
- 注意力汇现象在 Llama / Mistral / Falcon / Pythia 普遍存在;前 1~4 位承接溢出注意力质量。
- 与 [[LLM/107 长上下文推理：YaRN、位置插值与 StreamingLLM|StreamingLLM]](长上下文域)同源;与 [[036 KV 分层 offload：GPU、CPU、SSD(LMCache)|分层 offload]] 互补(有损压缩 vs 无损搬走)。
- 通用配方:**永久 sink + 高分重击者 + 近期滑窗**;工程常配「近窗精确 + 远端驱逐」分段。
