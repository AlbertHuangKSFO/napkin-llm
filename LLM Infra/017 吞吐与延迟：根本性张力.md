[[017 吞吐与延迟：根本性张力|吞吐与延迟张力]]是 LLM 服务最核心的工程取舍:**系统吞吐(throughput)**和**单请求延迟(latency)**沿一条帕累托前沿此消彼长,无法同时最优。根因在 [[016 batch 如何改变算术强度|batch 改变算术强度]]——提高 batch/并发能摊薄权重搬运、把 [[014 Decode 阶段：访存受限|访存受限]]的 decode 推向算力饱和,从而拉高总吞吐;但同一份显存带宽被更多请求瓜分,每个请求的 [[018 TTFT、TPOT、ITL 与 goodput：服务指标定义|TPOT]] 反而变长。服务系统的任务,就是在不破延迟 SLO 的前提下尽量右移取最大吞吐——这正是 goodput 优化的本质。

## 直觉

把 GPU 想成一条**固定带宽的传送带**。

- 想让**每个用户体验最快**(低延迟)→ 让传送带专心服务他一个 → 利用率低、总产出小。
- 想让**总产出最大**(高吞吐)→ 把尽量多请求塞上传送带一起跑 → 每个人都要等别人、人均变慢。

这不是工程没做好,而是**物理约束**:总带宽固定,人均速度 ≈ 总带宽 / 并发数。多服务一个人,人均必然慢一点。两者是同一资源的两种切法,天然对立。

类比餐厅:一个厨师(GPU),要么专心给一桌出菜快(低延迟、翻台率低),要么同时炒十桌的菜涨翻台率(高吞吐、每桌等更久)。老板的活是在"客人能忍的上菜时间(SLO)"内,塞最多的桌子。

## 例子

Llama 70B,H100,decode 阶段(沿 batch 滑动):

| batch | 单请求 TPOT | 系统吞吐 | 体验 |
|---|---|---|---|
| 1 | ≈ 42 ms/tok(≈24 tok/s) | ≈ 24 tok/s | 单人最快,机器最闲 |
| 16 | ≈ 45 ms/tok | ≈ 350 tok/s | 几乎不损延迟,吞吐 ×15 |
| 128 | ≈ 70 ms/tok | ≈ 1800 tok/s | 吞吐高,单请求开始变慢 |
| 512 | ≈ 200 ms/tok | ≈ 2500 tok/s | 吞吐封顶,延迟明显恶化 |

- batch 1→16:吞吐暴涨而 TPOT 几乎不动(还在 memory-bound 黄金区,见 [[016 batch 如何改变算术强度|batch]])——这是"几乎免费"的吞吐。
- batch 越过转折点后:吞吐增速放缓,TPOT 却快速上升——再塞请求是拿延迟换吞吐。
- 若 SLO 要求 TPOT &lt; 50 ms,则 batch 只能开到约 16–32,**这就是 SLO 给吞吐设的天花板**。

## 原理

设总有效带宽 $\beta$,每请求每 token 需搬字节 $m$(权重摊薄后 + 自己的 KV),并发 $B$:

$$
\text{TPOT}(B) \approx \frac{m_\text{weight}/B + m_\text{kv}}{\beta_\text{eff}}\cdot\frac{1}{?}\ \Longrightarrow\ \text{系统吞吐}=\frac{B}{\text{TPOT}(B)}
$$

更直观地:在 memory-bound 区,**系统吞吐 ≈ 带宽 / 单 token 字节**(几乎与 $B$ 无关地接近上限),而单请求速度 = 系统吞吐 / $B$ → $B$ 越大单请求越慢。两者乘积受同一带宽约束:

$$
\underbrace{\text{吞吐}}_{B/\text{TPOT}}\ \times\ \underbrace{\text{单请求延迟}}_{\text{TPOT}} = B \quad(\text{受带宽与 } B^* \text{ 封顶})
$$

帕累托前沿:沿 batch 移动,(吞吐↑, 延迟↑) 单调权衡,**不存在同时压低两者的点**。可行区由延迟 SLO 切出上界,前沿与 SLO 线的交点 = goodput 最大点(见 [[018 TTFT、TPOT、ITL 与 goodput：服务指标定义|goodput]])。

## 代码

扫 batch 描出帕累托前沿,并在给定 SLO 下选最优 batch:

```python
def pareto(throughput_fn, tpot_fn, batches=(1,2,4,8,16,32,64,128,256)):
    pts = [(B, tpot_fn(B), throughput_fn(B)) for B in batches]
    return pts  # 每点 (batch, TPOT_ms, sys_tok_s)；连起来就是前沿

def best_batch_under_slo(pts, tpot_slo_ms):
    # ✅ 在不破 TPOT SLO 的点里，取系统吞吐最大的那个
    feasible = [(B, t, thr) for (B, t, thr) in pts if t <= tpot_slo_ms]
    if not feasible:
        raise ValueError("没有 batch 能满足 SLO，需加卡/换更高带宽")
    return max(feasible, key=lambda r: r[2])   # 吞吐最大的可行点

# ❌ 错误：一味把 batch 调到最大求吞吐，违反延迟 SLO，用户体验崩、goodput 反降
# ✅ 正确：在 SLO 约束下沿前沿取最右可行点 —— 这才是 goodput 最优
```

`❌` 只盯系统吞吐把 batch 拉满,会击穿延迟 SLO,真正达标的请求(goodput)反而变少;`✅` 在 SLO 约束内沿帕累托前沿取最右点。

## 面试高频

- **Q:为什么吞吐和延迟不能两全?** 总带宽固定,系统吞吐 ÷ 并发 = 单请求速度;多服务一个请求,人均必然变慢,二者是同一资源的对立切法。
- **Q:那 batch 1→16 为什么看似两全(吞吐涨延迟几乎不变)?** 此时还在 memory-bound 黄金区,权重搬运被摊薄、算力本就闲——是"补利用率",越过转折点后才开始真正以延迟换吞吐。
- **Q:服务系统优化的目标到底是什么?** 不是裸吞吐,而是 **goodput**:在 TTFT/TPOT SLO 内的最大达标吞吐 = 帕累托前沿与 SLO 线的交点。
- **Q:怎么打破这条前沿(而非沿它移动)?** 换更高带宽硬件、量化/GQA 减搬运、投机解码、PD 分离(让 prefill 不抢 decode 带宽)——这些是把前沿整体外推,不同于沿前沿取舍。

## 关键事实

- 系统吞吐与单请求延迟构成**帕累托前沿**,batch/并发是沿前沿移动的滑块——这是 LLM 服务最根本的取舍(2023 起业界共识)。
- memory-bound 黄金区(小 batch)能近似免费涨吞吐;越过转折批量 $B^*$ 后必须以 TPOT 上升为代价(见 [[016 batch 如何改变算术强度|batch]])。
- 正确优化目标是 **goodput**(SLO 内达标吞吐),DistServe(2024)指出盲目最大化裸吞吐会压低 goodput,故主张 prefill/decode 分离。
