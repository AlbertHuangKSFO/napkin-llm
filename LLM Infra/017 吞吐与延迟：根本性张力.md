[[017 吞吐与延迟：根本性张力|吞吐与延迟张力]]是 LLM 服务最核心的工程取舍:系统吞吐(throughput)与单请求延迟(latency)常在受控资源下形成帕累托关系，但不是恒等式。小 batch 区间可因权重复用同时改善吞吐与设备利用率；再提高并发则会碰到 KV/attention、计算、collective 和排队。服务系统的任务是以 [[018 TTFT、TPOT、ITL 与 goodput：服务指标定义|TTFT、TPOT、ITL]] SLO 为约束，最大化达标吞吐(goodput)，而不是用一个孤立 batch 数追求裸 tok/s。

## 直觉

把 GPU 想成一条**固定带宽的传送带**。

- 想让**每个用户体验最快**(低延迟)→ 让传送带专心服务他一个 → 利用率低、总产出小。
- 想让**总产出最大**(高吞吐)→ 把尽量多请求塞上传送带一起跑 → 每个人都要等别人、人均变慢。

这不只是一个"总带宽 / 并发"的除法。请求在队列里的等待、共享权重、每序列 KV、计算和跨卡通信都同时存在。先把闲置的计算资源用起来时，吞吐可涨而服务时间几乎不变；排队和非共享成本开始主导后，更多并发才会让尾延迟明显恶化。

类比餐厅:一个厨师(GPU),要么专心给一桌出菜快(低延迟、翻台率低),要么同时炒十桌的菜涨翻台率(高吞吐、每桌等更久)。老板的活是在"客人能忍的上菜时间(SLO)"内,塞最多的桌子。

## 例子

用刻意简化的**单位示例**看一轮 decode。设一次 step 的共享权重流量 $W=100$ GB、每个活跃序列的 KV/激活流量 $K(S)=1$ GB、有效带宽 $BW_{\rm eff}=100$ GB/s；再设计算项 $F(B,S)/P_{\rm eff}$ 与 collective 分别由 profile 给出。若 $t_{\rm queue}=0.2$ s:

| batch $B$ | $t_{\rm mem}=(W+B K)/BW_{\rm eff}$ | 假定最大资源项 | $t_{\rm step}$ | 系统吞吐 $B/t_{\rm step}$ |
|---|---|---|---|---|
| 1 | $1.01$ s | $\max(1.01,0.8,0.1)=1.01$ s | $1.21$ s | $0.83$ tok/s |
| 16 | $1.16$ s | $\max(1.16,1.0,0.1)=1.16$ s | $1.36$ s | $11.76$ tok/s |
| 128 | $2.28$ s | $\max(2.28,2.0,0.2)=2.28$ s | $2.48$ s | $51.61$ tok/s |

这个手算不是 Llama 或 H100 基准，而是说明：$W$ 可被 batch 摊薄、$BK(S)$ 与计算/队列却会增长。因此吞吐能先升，单请求每步服务时间也可能已经升。生产中必须把该表替换为指定模型、GPU、dtype、上下文长度、并行和到达率下的采样数据。

## 原理

设 $W$ 为一次 decode step 中可被活跃请求共享的权重/常量流量，$K(S)$ 为一个上下文长度 $S$ 的请求在该步不可共享的 KV/激活流量，$F(B,S)$ 为该步 FLOPs，$BW_{\rm eff}$、$P_{\rm eff}$ 为 profile 得到的有效带宽与算力，$t_{\rm collective}$ 为并行通信，$t_{\rm queue}$ 为本请求在服务前的等待。保守的服务时间下界模型是:

$$
t_{\rm step}(B,S)\gtrsim \max\!\left(
\frac{W+B\cdot K(S)}{BW_{\rm eff}},\quad
\frac{F(B,S)}{P_{\rm eff}},\quad
t_{\rm collective}
\right)+t_{\rm queue}
$$

若一次 step 对 $B$ 个请求各生成一个 token，则在稳定态:

$$
\text{系统吞吐}\approx \frac{B}{t_{\rm step}},\qquad
\text{TPOT}_{\rm service}\approx t_{\rm step},\qquad
\text{ITL}\approx t_{\rm queue}+t_{\rm step}
$$

TTFT 还包括请求等待、prompt prefill 与首 token 的服务时间。上式不是排队论精确解，也不能推出"吞吐与 batch 无关"或"延迟必然按 $B$ 线性上升"；它是提醒你把共享项、非共享项和排队项分开量。可行区由 TTFT/TPOT SLO 切出，达标吞吐才是 goodput。

## 代码

扫 batch 描出帕累托前沿,并在给定 SLO 下选最优 batch:

```python
def measure_candidates(throughput_fn, tpot_fn, batches=(1,2,4,8,16,32,64,128,256)):
    pts = [(B, tpot_fn(B), throughput_fn(B)) for B in batches]
    return pts  # 每点 (batch, TPOT_ms, sys_tok_s)；还应带上 queue、ITL、显存和 P95/P99

def best_batch_under_slo(pts, tpot_slo_ms):
    # ✅ 在不破 TPOT SLO 的点里，取系统吞吐最大的那个
    feasible = [(B, t, thr) for (B, t, thr) in pts if t <= tpot_slo_ms]
    if not feasible:
        raise ValueError("没有 batch 能满足 SLO，需加卡/换更高带宽")
    return max(feasible, key=lambda r: r[2])   # 吞吐最大的可行点

# ❌ 错误：一味把 batch 调到最大求吞吐，违反延迟 SLO，用户体验崩、goodput 反降
# ✅ 正确：在 SLO 约束下，从实测的达标点取系统吞吐最大的那个
```

`❌` 只盯系统吞吐把 batch 拉满，或用虚构的固定 TPOT 表配参数；`✅` 对候选 batch 实测 $t_{\rm step}$、queue、TTFT、TPOT、ITL、显存与 SLO，再在达标点选吞吐最大者。

## 面试高频

- **Q:写出服务时间模型，并解释每一项。** A:用 $t_{\rm step}\gtrsim\max((W+BK(S))/BW_{\rm eff},F(B,S)/P_{\rm eff},t_{\rm collective})+t_{\rm queue}$。$W$ 是可共享权重流量，$K(S)$ 是每序列的上下文相关流量，第二项是计算，第三项是并行通信，最后一项是排队。然后再从 $B/t_{\rm step}$ 推系统吞吐，不能反过来把吞吐除以 batch 当作完整用户体验。
- **Q:为什么 batch 1→16 可能看似两全?** A:共享权重被摊薄、设备此前有闲置，吞吐可先快速升；但这不是保证。要检查 KV、attention、通信和队列是否已让 TPOT/ITL 变差。
- **Q:服务系统优化的目标到底是什么?** 不是裸吞吐,而是 **goodput**:在 TTFT/TPOT SLO 内的最大达标吞吐 = 帕累托前沿与 SLO 线的交点。
- **Q:怎么打破受控前沿(而非只沿它移动)?** 换更高带宽硬件、量化/GQA 减搬运、投机解码、PD 分离(让 prefill 不抢 decode 资源)都可能外推前沿；仍要以同一模型、负载和 SLO 的端到端试验验证。

## 关键事实

- 吞吐与延迟必须按同一模型、GPU、dtype、上下文分布、并行策略与到达率采样；没有这些条件的固定 tok/s、TPOT 或"最佳 batch"不具有可迁移性。模型化可参考 Orca(Yu et al., OSDI 2022) 与 vLLM(Kwon et al., SOSP 2023)。
- 正确优化目标是 **goodput**(SLO 内达标吞吐)。DistServe(Zhong et al., OSDI 2024)把 prefill/decode 分离用于减少互相干扰，但其收益仍依赖部署配置和负载。
