[[001 LLM 推理的系统视角：从一次请求到一张卡|推理系统视角]] 是把"一个 prompt 进来、一串 token 吐出"看成一条横跨调度、引擎、数值、硬件四层的流水线,核心是认清 **prefill 受算力限、decode 受带宽限**这一对主要矛盾。

把一次推理想成餐厅出餐:**prefill 是一次性把整桌食材并行下锅**(吃灶台火力 = 算力),**decode 是之后一道一道端菜,每端一道都得跑回冷库把全部库存翻一遍**(吃跑腿速度 = [[003 GPU 内存层级：HBM、L2、SRAM、寄存器|HBM 带宽]])。一张请求的延迟 = 第一道菜上桌时间(TTFT,由 prefill 决定)+ 后续每道菜的间隔(TPOT,由 decode 决定)。

具体走一遍 70B 模型、用户发 1000 token、生成 200 token 的请求(单张 [[006 GPU 代际：A100 到 H100、H200、B200、GB200|H100]],权重 FP16 共 140GB,显存账见 [[LLM/076 显存占用估算(参数、梯度、优化器、激活、KV)|显存估算]]):
- **Tokenize**:1000 字符级文本 → ~1000 个 token id,CPU 上 μs 级,可忽略。
- **Prefill**:1000 个 token 一次性过 80 层,算 QKV/FFN 大矩阵乘。约 $2 \times P \times T_{in} = 2 \times 70\text{e}9 \times 1000 = 1.4\times10^{14}$ FLOPs;H100 FP16 dense ~989 TFLOPS,理想 $1.4\text{e}14 / 9.89\text{e}14 \approx 0.14$ s。这就是 TTFT 量级(算力受限)。
- **写 [[LLM/102 KV-Cache|KV-Cache]]**:1000 个 token × 80 层 × 2(K、V),存进 HBM,供后续 decode 复用。
- **Decode**:每生成 1 个 token,要把 140GB 权重 + 当前 KV 从 HBM 读一遍。单 token ≈ $140 / 3350 \approx 42$ ms → 200 个 token ≈ 8.4 s。**这才是大头**,且几乎纯带宽活(算力闲置)。
- **Detokenize + 流式返回**:每出一个 token 立刻 detokenize 推给客户端(SSE 流),用户先看到字、不必等全部生成完。

![[hw-001四层流水线受限维度.svg]]

原理:Transformer 解码是**自回归**的,第 $t$ 个 token 依赖前 $t-1$ 个。所以:
$$\text{Prefill: 一次算 } T_{in} \text{ 个 token,可并行} \quad\Rightarrow\quad \text{算力受限}$$
$$\text{Decode: 一次只算 1 个 token,串行 } T_{out} \text{ 步} \quad\Rightarrow\quad \text{带宽受限}$$
单步 decode 的[[004 算力 vs 带宽：Roofline 与算术强度|算术强度]] $I = \text{FLOPs}/\text{Bytes} \approx \frac{2P}{2P} = 1$(FP16 下每个权重读 2 字节、做 2 次浮点),远低于 H100 脊点 ~297,所以死贴 [[004 算力 vs 带宽：Roofline 与算术强度|Roofline]] 的斜屋顶。这也解释了 batching、[[LLM/102 KV-Cache|KV-Cache]] 量化、continuous batching 这些系统优化为何全围着 decode 转——把多条请求的 decode 拼到一起,**摊薄每次权重搬运**,提升有效算术强度。

![[hw-推理全链路系统分层.svg]]

最小可运行的"延迟账"脚本,把上面的手算变成代码:

```python
# ✅ 用 Roofline 思路估 decode 上限:decode 是 memory-bound
P = 70e9                     # 参数量
bytes_per_param = 2         # FP16
weight_bytes = P * bytes_per_param          # 140 GB
HBM_BW = 3.35e12            # H100 HBM3 带宽 B/s

t_per_token = weight_bytes / HBM_BW         # 仅权重搬运下限
print(f"decode 单 token ≈ {t_per_token*1e3:.1f} ms")     # ≈ 41.8 ms
print(f"单请求上限 ≈ {1/t_per_token:.1f} token/s")        # ≈ 23.9 tok/s

# ❌ 常见误区:用算力(FLOPs/峰值)估 decode
flops_per_token = 2 * P                      # 1.4e11
t_compute = flops_per_token / 989e12         # ≈ 0.14 ms —— 严重低估真实耗时
# 错在 decode 根本不是 compute-bound,瓶颈在 HBM 带宽不在 Tensor Core
```

输出与手算一致:decode 单 token ~42ms,而错误的算力估法只给 0.14ms,**差 ~300 倍**——这正是 prefill 与 decode 受限维度不同的直接体现。

## 面试高频
- **Q:一次 LLM 请求从输入到输出经历哪些阶段?** A:tokenize → prefill(并行处理全部输入,填好 KV-Cache)→ decode 自回归循环(逐 token,每步读全权重+全 KV,追加新 KV)→ detokenize → 流式返回。陷阱:把 prefill 和 decode 混为一谈;二者受限维度不同(算力 vs 带宽)。
- **Q:为什么 decode 比 prefill 慢这么多?** A:prefill 一次并行算 $T_{in}$ 个 token,算术强度高、吃满 Tensor Core;decode 每步只算 1 个 token 却要把整个模型权重从 HBM 读一遍,算术强度 ≈1,被带宽卡死。陷阱:回答"因为要生成很多 token"——那只是 decode 步数多,关键是**每步**就慢。
- **Q:TTFT 和 TPOT 分别由什么决定?** A:TTFT(首 token 延迟)≈ tokenize + prefill,主要随输入长度和算力变;TPOT(token 间隔)≈ 单步 decode,主要随模型大小和 HBM 带宽变。陷阱:以为加大 batch 能降 TTFT——加 batch 主要提吞吐和摊薄 decode,对单请求 TTFT 帮助有限。

## 关键事实
- H100 SXM5:80GB HBM3、3.35 TB/s 带宽、132 个 SM、FP16 Tensor ~989 TFLOPS(dense)。来源:NVIDIA H100 Datasheet / Hopper Architecture Whitepaper(2022–2024)。
- 推理含 prefill(prompt 并行编码)与 decode(自回归逐 token)两阶段,是 vLLM/TensorRT-LLM/SGLang 等引擎调度的基本单位。来源:vLLM PagedAttention 论文(Kwon et al., SOSP 2023, arXiv:2309.06180)。
- 单步 decode 算术强度 ≈1 FLOP/Byte,远低于 H100 FP16 脊点 ~297,故 memory-bound。来源:Roofline 模型(Williams et al., CACM 2009)。
