[[041 连续批处理：迭代级调度内幕|迭代级调度内幕]]拆解 [[LLM/105 连续批处理 continuous batching|连续批处理]] 每一步到底发生了什么。所谓**迭代级调度(iteration-level scheduling)**,就是把"调度"这个动作插进**每两次 forward 之间**:一步 = 一次 forward = running batch 里每个请求各前进一个 token;步与步之间,调度器做三件事——**退出**(本步产出 EOS 或达上限的请求移出、释放 KV)、**补位**(从 waiting 队列按 KV 预算准入新请求填空槽)、**混批**(prefill 与 [[014 Decode 阶段：访存受限|decode]] 共存同一 batch)。相比 [[040 静态批、动态批与连续批|静态批]]的请求级调度,它把空槽即时回填,让 GPU 持续满载。这是 Orca selective batching 的工程内核。

## 直觉

把它想成**一张每秒重排一次的牌桌**,庄家(调度器)在每一手牌(每一步)之间做三个动作:

1. **收牌**:这一手有人亮牌结束(出了 EOS),把他请下桌,空出座位。
2. **发牌**:从候场名单里叫人入座,但要看桌上还有没有筹码(KV 显存)够他玩。
3. **混局**:新入座的人要先"读规则"(prefill 整段 prompt),老玩家继续"出牌"(decode 一个 token)——这两种动作被塞进同一手牌一起算。

难点在第 3 步:prefill 是又宽又大的矩阵乘,decode 是细长的向量乘,**形状完全不同**却要同批。Orca 的答案是 **selective batching**:只对形状一致的算子(如 FFN 的大 GEMM)合批,对 attention 这种逐请求序列长度不同的算子**拆开逐请求算**,算完再拼回去。

**生活类比**:连续批处理像一辆**不等坐满才发车的公交**(GPU),4 个座位,每到一站(每一步)就重排一次。第 t 站:A、B、C 坐着、各往前坐一格(decode 各出 1 token),还空 1 座。第 t+1 站:A 到站了(出了 EOS)立刻下车让座、退票(释放 KV),空出 2 座。第 t+2 站:站台上排队的 D、E **马上补座**(准入)——但上车前要看车上还有没有筹码够坐(KV 显存够不够)。这样座位**永远是满的**,司机(GPU)不空跑。妙处在「混局」:新上车的 D 要先**读规则**(prefill,把整段 prompt 一次性过一遍,又宽又大的矩阵乘),老乘客 B、C 照常**出牌**(decode,各出 1 token,细长的向量乘)——两类乘客被塞进同一手牌一起算,这就是混批。形状不一样怎么一起算?selective batching:形状一致的 FFN 大矩阵乘合批,逐请求长度不一的 attention 拆开单算再拼回。注意带 prefill 那两步会被大行李拖慢,同车 decode 的 ITL 出现尖刺——这就是后面 chunked prefill 要治的 stall。

## 例子

running batch 容量 4,某时刻装着 A、B、C(都在 decode),D、E 在 waiting:

- **step t**:batch = {A_dec, B_dec, C_dec, 空}。跑一步,各出一个 token。
- **step t+1**:A 这步产出 EOS → 调度器**退出 A**,释放 A 的 KV 块。现在有 2 个空槽。
- **step t+2**:调度器查 waiting,D 需要的 KV 块 ≤ 空闲块 → **准入 D**。D 第一步走 prefill(把它整段 prompt 一次性过网络填 KV)。batch = {D_prefill, B_dec, C_dec, 空}。
- **step t+3**:E 也准入。batch = {D_dec, E_prefill, B_dec, C_dec}——**一个 batch 里同时有 prefill(E)和 decode(D/B/C)**,这就是混批。
- 之后 D、E 转入 decode,槽位始终满载。

注意 step t+2、t+3 那两步里混进了 prefill:它们的单步耗时会比纯 decode 步长(prefill 大 GEMM 拖慢),同批 decode 的 ITL 出现尖刺——这正是 [[043 prefill、decode 干扰与 stall|generation stall]] 的来源,引出 [[042 chunked prefill：切块融合|chunked prefill]]。

## 原理

设第 $k$ 步的 running 集合为 $R_k$,token 预算 $C$(max_num_batched_tokens),每请求本步贡献 token 数 $n_i$(decode 贡献 1,prefill 贡献其 chunk 长度)。迭代级调度的不变式:

$$
\sum_{i\in R_k} n_i \le C,\qquad \sum_{i\in R_k}\text{kv}(i) \le M_\text{KV}
$$

即**每步 token 数受预算 $C$ 约束、总 KV 占用受显存 $M_\text{KV}$ 约束**。状态转移:

$$
R_{k+1} = \big(R_k \setminus \text{Done}_k\big)\ \cup\ \text{Admit}_k,\quad \text{Admit}_k \subseteq \text{Waiting},\ \text{受上面两约束}
$$

**selective batching** 让混批可行:对 FFN/投影等算子,把 $\sum n_i$ 个 token 拼成一个大矩阵合批(摊薄权重搬运);对 attention,因每请求序列长不同,**逐请求**调用(各自的 Q 乘各自的 KV),无法合并但开销小。这样既享受了合批的算术强度提升(见 [[016 batch 如何改变算术强度|batch 改变算术强度]]),又绕开了 attention 形状不齐的障碍。

## 代码

迭代级调度主循环(贴近 vLLM 的 `schedule()` + `step()` 结构):

```python
def engine_loop(scheduler):
    while scheduler.has_unfinished():
        # ---- schedule(): 决定这一步跑哪些请求 ----
        batch = []
        token_budget = MAX_NUM_BATCHED_TOKENS
        # ✅ 先排已在 running 的 decode（每个只占 1 token，便宜，优先保证它们不 stall）
        for req in scheduler.running:
            if token_budget >= 1:
                batch.append(req.as_decode()); token_budget -= 1
        # ✅ 再用剩余预算准入 waiting 的 prefill；放不下就 chunk（见 042）
        while scheduler.waiting and token_budget > 0 and scheduler.kv_can_fit(scheduler.waiting[0]):
            req = scheduler.waiting.popleft()
            chunk = min(req.prompt_len, token_budget)   # ✅ 超预算就切块
            batch.append(req.as_prefill(chunk)); token_budget -= chunk
            scheduler.running.append(req)

        # ---- step(): 一次 forward，全 batch 各前进 ----
        outputs = model_forward(batch)                  # selective batching 在 model 内部

        # ---- 步后处理：退出完成的，释放 KV ----
        for req in list(scheduler.running):
            if req.finished():                          # EOS 或达 max_tokens
                scheduler.running.remove(req); scheduler.free_kv(req)

# ❌ 错误：把 schedule 放到循环外只算一次 —— 退化成静态批，完成的请求占着槽位不放
```

`❌` 把调度移出每步循环就退回请求级、丢掉连续批全部收益;`✅` 调度必须嵌在每两次 forward 之间,且**先保 decode、再补 prefill**(decode 便宜且关乎在飞请求的 SLO)。

## 面试高频

- **Q:迭代级调度每步具体做哪三件事?** 退出本步完成的请求并释放 KV、从 waiting 按 KV 预算准入新请求补空槽、把 prefill 与 decode 混在同一 batch。
- **Q:prefill 和 decode 形状完全不同,怎么混进一个 batch?** selective batching:对形状一致的算子(FFN/投影)合批,对序列长不齐的 attention 逐请求单独算,再拼回。这是 Orca 的关键工程贡献。
- **Q:为什么调度时通常先排 decode 再排 prefill?** decode 每请求只贡献 1 token、极便宜,且关乎在飞请求的 TPOT/SLO;先占满 decode 再用剩余 token 预算放 prefill,能最小化对在飞请求的干扰(vLLM V1 默认 decode 优先)。
- **Q:一步里塞太多 prefill 会怎样?** 单步耗时被 prefill 大 GEMM 拉长,同批 decode 出现 [[043 prefill、decode 干扰与 stall|generation stall]],TPOT 尖刺;解法是 [[042 chunked prefill：切块融合|chunked prefill]] 用 token 预算钳住单步长度。

## 关键事实

- **iteration-level scheduling** 与 **selective batching** 是 Orca(Yu et al., OSDI 2022)的两大核心机制,二者配合才让"每步重组 + prefill/decode 混批"在 Transformer 上可行。
- vLLM 的实现里,调度的硬约束是**两个预算**:每步 token 数 ≤ `max_num_batched_tokens`,以及总 KV 块 ≤ 显存可用块;装不下就触发 [[045 抢占：重计算 vs swap|抢占]]。
- vLLM **V1(2025)** 默认开启 chunked prefill 并**优先调度 decode**:先把所有待处理 decode 合批,再用剩余 token 预算放 prefill,放不下自动切块。
