[[095 从单进程到集群：服务架构演进]]讲的是:把一个 LLM 从"`python -m vllm` 跑在一张卡上的玩具"一路推到"跨节点分布式集群、声明式编排、按负载自动扩缩"的完整演进路径,以及每一步是被什么瓶颈逼出来的。它是 [[LLM Infra]] 这条线的开篇——后面的 [[096 Kubernetes 上部署 LLM：基本盘|K8s 部署]]、[[097 KServe：模型生命周期与 LLMInferenceService|KServe]]、[[098 llm-d：K8s 原生分布式推理|llm-d]]、[[099 Ray Serve：Python 优先的编排|Ray Serve]] 都是这条演进线上的不同落点。

## 类比
像一家面馆扩张。**单进程**=一个厨师一口锅,自己接单自己煮,锅坏了整店歇业。**多副本+网关**=开三口锅,门口站个领位员(负载均衡)把客人均分。**智能路由**=领位员记得"这桌刚才点过的高汤已经在 2 号锅熬着了",就把续单也分给 2 号锅,省一次熬汤([[100 推理网关与智能路由(cache-aware)|cache-aware]] 复用 KV)。**分布式调度**=一道大菜单口锅做不了,拆成"备料档口"和"出餐档口"流水线协作([[048 为何分离 prefill 与 decode|PD 分离]]),还有总调度盯着全店把人手在档口间动态调配。

## 小数字例子
一张 H100(80GB)单进程跑 Llama-3-8B,假设峰值 ~2000 tok/s、并发上限 ~30。
- 单进程:QPS 一过阈值,队列爆,[[018 TTFT、TPOT、ITL 与 goodput：服务指标定义|TTFT]] 从 200ms 飙到 5s。
- 4 副本 + 轮询网关:理论 4×,但多轮对话每次都换副本→前缀全部重算,实际有效吞吐可能只 ~2.5×。
- 4 副本 + cache-aware:同会话粘住同副本,前缀缓存命中率从 ~0% 升到 60%+,有效吞吐回到 ~3.8×。

![[orch-095路由有效吞吐.png]]

## 原理:四个阶段与各自瓶颈
1. **单进程**:引擎+HTTP 同进程。瓶颈=单点故障、并发无上限保护、扩不动。
2. **多副本+网关**:无状态横向扩展,LB 做 round-robin/least-conn。瓶颈=分发不感知 KV-Cache,跨副本重算前缀;副本数靠人手调。
3. **智能路由网关**:网关变成"懂推理"的调度器,按 KV 命中、队列深度、负载选副本([[038 KV-aware 路由与跨引擎复用|KV-aware 路由]])。瓶颈=单副本=单引擎,大模型/长上下文撑不住;prefill 与 decode 仍挤同一引擎互相 stall。
4. **分布式调度**:控制面声明式管理,PD 解耦成独立池、跨节点 TP/EP、KV 分层 offload、按 SLO 自动扩缩。这就是 KServe LLMInferenceService、llm-d、Ray Serve LLM 这一代的战场。

贯穿四阶段的不变张力:[[017 吞吐与延迟：根本性张力|吞吐 vs 延迟]]、利用率 vs SLO。每一层本质都是把"调度决策"上移到更全局的视角——决策粒度从请求级→副本级→节点级→KV-block 级越走越细。

## 代码:演进的两端对比
```yaml
# ❌ ① 单进程:一条命令,无副本/无健康检查/无扩缩,挂了就全挂
# vllm serve meta-llama/Llama-3-8B --port 8000
```
```yaml
# ✅ ④ 声明式编排:副本、健康探针、资源、自动扩缩交给控制面
apiVersion: apps/v1
kind: Deployment
metadata: { name: llama3-vllm }
spec:
  replicas: 4                      # 横向扩展由编排器管,不再手起进程
  selector: { matchLabels: { app: llama3 } }
  template:
    metadata: { labels: { app: llama3 } }
    spec:
      containers:
      - name: vllm
        image: vllm/vllm-openai:latest
        args: ["--model","meta-llama/Llama-3-8B","--port","8000"]
        resources:
          limits: { nvidia.com/gpu: 1 }   # GPU 当可调度资源
        readinessProbe:                    # 模型加载完才进 LB(见 096)
          httpGet: { path: /health, port: 8000 }
          initialDelaySeconds: 120
---
# 上层再叠:智能路由网关(③)+ HPA/KEDA 自动扩缩 + PD 解耦池(④)
```
要点:从"人肉起进程"到"声明期望状态、控制面收敛",副本数、健康、扩缩、路由全部变成可声明、可观测、可自愈的对象。

## 面试高频
- **画出 LLM 服务从单机到集群的演进,每步说出瓶颈与解法。** 单点/无并发保护→多副本;均匀分发浪费 KV→cache-aware 路由;PD 互相 stall + 大模型放不下→PD 解耦 + 跨节点并行 + 声明式编排。
- **为什么 LB 用 round-robin 对 LLM 不够好?** LLM 有大量可复用的 KV-Cache 状态,轮询把同会话打散导致前缀重算;要 cache-aware/会话亲和。
- **什么时候才"必须"上分布式调度?** 模型超单节点显存、需要 PD 独立扩缩、需要按 SLO 自动配比时;小模型单副本能扛就别过度工程。
- **演进里"调度决策上移"指什么?** 决策粒度从请求级逐步细化到 KV-block 级,且从引擎内部上移到全局控制面。

## 关键事实
- 这代 K8s 原生 LLM 编排栈(KServe LLMInferenceService、llm-d、Ray Serve LLM)在 2025 年成形;llm-d 2025-05 由 Red Hat、Google Cloud、IBM、CoreWeave、NVIDIA 发起,2026 年进入 CNCF;KServe 2025-11 成为 CNCF incubating 项目。
- 演进的核心驱动力一直是同一对:吞吐/利用率 与 延迟/SLO 的张力,以及大模型显存超出单节点。
- 「智能路由 + PD 解耦 + 自动扩缩」是 2025–2026 生产级 LLM 服务的事实标配组合,而非单一框架专利。
