[[125 多卡 TP 部署 70B 模型]]:把 [[057 张量并行推理：延迟换显存|张量并行推理]] 落成命令——单卡装不下 70B,用 `--tensor-parallel-size 4` 把每层权重切到 4 张卡,靠 [[008 片内互联：NVLink、NVSwitch、NVLink-C2C|NVLink]] 做每层 [[058 TP 的通信：每层 all-reduce 与 NVLink 依赖|all-reduce]],配 `--gpu-memory-utilization` 调显存,把 70B 跑起来。

## ① 类比:四个人合抬一张巨型桌子

一张 70B 的「桌子」一个人(单卡 80GB)抬不动——光 BF16 权重就 ~140GB。**TP 让 4 个人各抬一角**:每张卡只存 1/4 的权重,但每算完一层都要**碰一下头对齐**(all-reduce 同步部分和)。碰头走 NVLink(快)还是 PCIe(慢)决定了这桌子抬得稳不稳——所以**TP 强依赖 NVLink**。

## ② 起 70B:一条命令

```bash
# 4 卡 TP 起 Llama-3.1-70B(BF16 ~140GB,4×80GB 刚好)
vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.92 \
  --max-model-len 8192 \
  --port 8000
```

`-tp 4` 必须 ≤ 可见 GPU 数,且**整除注意力头数**(70B 是 64 头,4/8 都行)。

## ③ 原理:TP 怎么切、通信卡在哪

**1. 切权重,不切层数。** TP 把每个 [[022 GEMM：cuBLAS、CUTLASS 与 Tensor Core 利用率|GEMM]] 的权重矩阵按列/行切到各卡:attention 的 QKV/O、MLP 的 up/down 都切。每卡只存 1/N 权重和 1/N 的 [[015 KV-Cache 的显存账(逐层手算)|KV-Cache]]。

**2. 每层两次 all-reduce。** attention 后、MLP 后各一次 all-reduce 把部分和拼回完整激活([[067 all-reduce 算法：ring、tree 与 SHARP|ring/tree all-reduce]])。一层走两次,几十层累积 → 通信量大 → **必须 NVLink**,跨 PCIe/跨节点会让 TP 退化。

**3. 延迟换显存。** 4 卡 TP 把单 token 延迟降低(算力 ×4)但引入通信开销;它的本质是「用通信换出装得下大模型的显存」(详见 [[057 张量并行推理：延迟换显存|TP 的权衡]])。TP 通常**限单节点内**(NVLink 域),跨节点上 [[059 流水线并行推理：micro-batch 与气泡|PP]]。

## ④ 起前检查:NVLink 与显存

```bash
# 1. 看互联:NV# 表示 NVLink 连接,PIX/PHB/SYS 表示走 PCIe(慢)
nvidia-smi topo -m
#        GPU0  GPU1  GPU2  GPU3
# GPU0    X    NV18  NV18  NV18      <- 全 NVLink,适合 TP
# GPU1   NV18   X    NV18  NV18

# 2. 起服务时实时看四卡显存是否均匀爬升
watch -n1 nvidia-smi

# 3. 显存预算手算(BF16):
#    权重 70B×2B = 140GB / 4卡 = 35GB/卡
#    剩 80-35 ≈ 45GB/卡 给 KV+激活 → 决定并发上限
```

若 `topo -m` 看到 TP 组内是 `SYS`/`PHB`(走 PCIe),延迟会暴涨——换卡或换拓扑。

## ⑤ 完整脚本:Docker 多卡 + 多节点提示

```bash
# Docker 4 卡 TP
docker run --runtime nvidia --gpus all --ipc=host \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  --env "HF_TOKEN=$HF_TOKEN" \
  -p 8000:8000 \
  vllm/vllm-openai:latest \
  --model meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.92
```

```bash
# 单节点放不下(如 405B / 8卡不够)→ TP×PP 跨节点,靠 Ray
# 节点内 TP=8,跨 2 节点 PP=2
vllm serve meta-llama/Llama-3.1-405B-Instruct \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 2 \
  --distributed-executor-backend ray
```

❌ 反模式:`-tp 8` 但只有 4 卡,或 TP 跨没有 NVLink 的卡;或 `-tp` 不整除注意力头数 → 启动报错。
✅ 正解:`-tp` = 节点内 NVLink 互联的卡数且整除头数;**TP 留在单节点 NVLink 域内**,跨节点用 PP。

## 面试高频

- **「为什么 70B 必须多卡,TP 解决了什么?」** BF16 ~140GB 超单卡 80GB;TP 把每层权重+KV 切到 N 卡,每卡只放 1/N,用通信换显存。
- **「TP 为什么强依赖 NVLink?」** 每层两次 all-reduce,几十层累积通信量巨大,走 PCIe/跨节点带宽不够会让 TP 严重退化;NVLink 才撑得住。
- **「TP 和 PP 怎么选/组合?」** TP 切单层、通信密集→限单节点 NVLink 域;PP 切层段、通信稀疏→适合跨节点。大模型常 TP(节点内)×PP(跨节点)。
- **「`-tp 4` 有什么约束?」** ≤ 可见 GPU 数,且整除注意力头数;否则启动失败。
- **「怎么验证多卡起对了?」** `nvidia-smi topo -m` 确认 NVLink;`watch nvidia-smi` 看各卡显存均匀爬升。

## 关键事实

- `--tensor-parallel-size N`:N 整除注意力头数、≤ 可见 GPU 数;70B BF16 ≈140GB,4×80GB 刚好。
- TP 每层两次 all-reduce → 强依赖 NVLink,通常限单节点;跨节点上 `--pipeline-parallel-size`。
- `nvidia-smi topo -m`:`NV#`=NVLink(好),`SYS/PHB/PIX`=PCIe(差)。
- 多节点需 `--distributed-executor-backend ray`。
- `--gpu-memory-utilization 0.92` 常用;剩余显存决定 KV 池与并发。
