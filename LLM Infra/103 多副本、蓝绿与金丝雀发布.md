[[103 多副本、蓝绿与金丝雀发布]]:模型也要升级——换新版权重、换微调、换引擎配置。可推理服务有 [[060 数据并行与副本扩展|多副本]]、模型又重又贵,直接全量替换风险极高。这一篇讲生产里怎么**灰度切换模型版本**:金丝雀(按比例渐进切流)、蓝绿(整批切换 + 秒级回滚)、A/B(对比两版质量),以及回滚。它紧接 [[100 推理网关与智能路由(cache-aware)|推理网关]](切流量靠网关)、[[101 自动扩缩：HPA、KEDA、scale-to-zero 与冷启动|自动扩缩]](新版要先扩出副本预热)。在 [[097 KServe：模型生命周期与 LLMInferenceService|KServe]] 里,这些能力由 `canaryTrafficPercent` 等字段原生支持。

## ① 类比:换厨师班子

餐厅要换主厨菜谱。**金丝雀**:先让新菜谱做 5% 的桌,客人反馈好再扩到 25%、100%——出问题只影响一小撮人。**蓝绿**:后厨预备一整套新班子(Green)满员待命,前厅指针「啪」一下从旧班子(Blue)切到新班子,出问题指针再切回去,秒级回滚——但代价是同时养两套班子。**A/B**:不是为了上线,而是同时跑两版菜谱,科学对比哪版客人更满意。对 LLM 而言,「换班子」最贵的地方是:新模型的 GPU 副本要重新拉起、预热,旧 KV-Cache 全作废。

## ② 小数字例子:金丝雀阶梯与蓝绿成本

**金丝雀阶梯。** 假设服务 20 个 v1 副本承全量。上 v2:
- 先扩 1 个 v2 副本,网关分 **5%** 流量给它;观察 30 min 错误率/P99/质量。
- 没问题 → 25%(扩到 5 个 v2,缩 v1)→ 50% → 100%。每步都能监控、随时停。
- 出问题:把 `canaryTrafficPercent` 调回 0,流量瞬间全回 v1,**只波及过那 5% 的请求**。

**蓝绿成本。** v1 用 20 张 H100。蓝绿要 Green 也满载 20 张预热好 → **切换窗口内占 40 张卡**。模型大、卡贵,所以蓝绿对 LLM 常只用于关键模型 + 短窗口;否则双倍 GPU 成本吃不消。

## ③ 原理:三种策略 + LLM 特有的坑

**1. 金丝雀(canary)。** 同时在线 v1/v2,**按比例**把流量从 v1 渐迁到 v2。优点:省资源(只多几个 v2 副本)、爆炸半径小、可随时停;缺点:切换期两版本并存,回滚是「降比例」而非瞬切。KServe 用 `canaryTrafficPercent` 在新旧 revision 间按百分比切流。

**2. 蓝绿(blue-green)。** 两套完整环境:Blue(v1 在线)+ Green(v2 预热满载、0 流量)。验证 Green 没问题后,**流量指针一刀切** Blue→Green;出问题指针切回 Blue,**秒级回滚**。优点:回滚最干脆、切换瞬时;缺点:切换窗口内**双倍副本 = 双倍 GPU**,对 LLM 很贵。

**3. A/B 测试。** 目的不同——不是为了安全上线,而是**对比两版的业务/质量指标**(答案质量、用户偏好、转化)。按用户分桶而非纯比例,长期并行收集统计显著的对比;常和 [[112 人评、LLM-as-judge 与 Arena|LLM-as-judge / Arena]] 类评估配合。

**4. LLM 特有的坑。**
- **缓存失效**:换模型版本 = 旧版的 KV-Cache、[[032 前缀缓存：RadixAttention 树结构|前缀缓存]] 全作废,切换瞬间命中率掉 0,TTFT 抖一下(见 [[033 自动前缀缓存的命中与失效|APC 失效]])。
- **预热成本**:新副本要经历 [[101 自动扩缩：HPA、KEDA、scale-to-zero 与冷启动|冷启动]](搬权重进显存,分钟级),不能「秒上线」——金丝雀/蓝绿都得先把 v2 副本拉起预热好再切流。
- **质量回归难自动判**:错误率/延迟可自动监控,但「答案变差了」往往要人评或 LLM-as-judge,金丝雀阶段要带上质量看板,不能只看 5xx。
- **输出契约兼容**:新模型若改了 tool-calling 格式或 stop token,可能悄悄破坏下游解析——灰度时要校验输出结构,不只看是否报错。

## ④ 配置:KServe 金丝雀切流

```yaml
# KServe:canaryTrafficPercent 给新 revision 按比例切流
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata: { name: llama3-chat }
spec:
  predictor:
    canaryTrafficPercent: 10        # 新版本先接 10% 流量,其余仍走稳定版
    model:
      modelFormat: { name: vLLM }
      storageUri: s3://models/llama3-v2   # v2 权重;改回旧 URI 即回滚
      resources:
        limits: { nvidia.com/gpu: 1 }
```

```yaml
# 蓝绿:两套 Deployment + 一个 Service selector 切指针(秒级回滚)
apiVersion: v1
kind: Service
metadata: { name: llm-svc }
spec:
  selector:
    app: llm
    version: green                  # 改成 blue 即瞬切回滚;但 blue/green 副本需同时在线
```

❌ 反模式:① 直接 `kubectl set image` 全量滚动替换模型——新模型有质量回归/格式不兼容时,全量用户中招,且没有干净的回滚点。② 金丝雀只盯 5xx 错误率——LLM 的回归常是「答案变差」,5xx 全绿但质量崩了。③ 切流时忘了 v2 还在冷启动——把流量打给没预热好的副本,TTFT 爆。

✅ 正解:**金丝雀**(5%→25%→100%,带质量看板 + 自动回滚阈值)做日常模型升级,省 GPU;**蓝绿**留给关键模型 + 需秒级回滚的场景(接受双倍 GPU 的短窗口);切流前确保 v2 副本已扩出并预热;监控同时覆盖错误率、延迟、**输出质量与格式契约**。

## 面试高频

- **「金丝雀和蓝绿区别、各自取舍?」** 金丝雀按比例渐进切流,省资源、爆炸半径小,但回滚是降比例;蓝绿整批切换、秒级回滚最干脆,但切换窗口要双倍副本(LLM 贵)。
- **「模型发布和普通微服务发布有什么不同?」** ① 副本贵且重,蓝绿双倍 GPU 成本高;② 新副本要冷启动预热(搬权重)不能秒上线;③ 换版本让 KV/前缀缓存全失效,切换瞬间 TTFT 抖;④ 回归常是质量下降,光看 5xx 发现不了。
- **「金丝雀阶段监控什么?」** 错误率、P99 延迟/TTFT,以及 LLM 特有的输出质量(人评/LLM-as-judge)和输出格式契约(tool-calling、stop token)。
- **「A/B 和金丝雀的目的区别?」** 金丝雀是为安全上线(渐进降风险);A/B 是为对比两版业务/质量指标做决策,按用户分桶长期并行。
- **「KServe 怎么做灰度?」** `canaryTrafficPercent` 在新旧 revision 间按百分比切流,Knative 创建新 revision,改回旧 storageUri / 调回 0% 即回滚。

## 关键事实

- **金丝雀**:按比例渐进切流(如 5%→25%→100%),省资源、爆炸半径小,回滚=降比例;KServe 用 `canaryTrafficPercent`。
- **蓝绿**:Blue 在线 + Green 预热满载,指针一刀切 + 秒级回滚;代价是切换窗口双倍副本/双倍 GPU。
- **A/B**:目的是对比两版质量/业务指标(非安全上线),按用户分桶,常配 LLM-as-judge / Arena。
- **LLM 特有坑**:换版本使 KV/前缀缓存全失效(TTFT 抖)、新副本需冷启动预热(分钟级)、质量回归难自动判、输出格式契约需校验。
- KServe 2025 走 GenAI-first(LLMInferenceService),原生支持 traffic splitting / canary / blue-green;2025-11 成为 CNCF 孵化项目。
