[[122 端侧与边缘部署：量化、蒸馏与移动推理]] 把推理从数据中心搬到**手机、笔记本、IoT、边缘盒子**上跑。动机很硬:**隐私**(数据不出设备)、**离线/弱网可用**、**低延迟**(无网络往返)、**零云成本**(不占云 GPU)。但端侧硬约束也很硬——内存只有几 GB、功耗发热受限、算力带宽远低于数据中心 GPU。所以核心套路是**先把大模型压小**:**量化**(FP16 → 4-bit / 混合精度)+ **蒸馏**(大模型教出 3B 级小模型)+ 剪枝,叠加可缩小 10–20×;再用 **llama.cpp / MLC-LLM / ExecuTorch / 移动 NPU** 把压好的权重跑起来。它直接复用 [[092 llama.cpp、GGUF：CPU 与端侧|llama.cpp]] 的 GGUF/CPU 推理能力,与 [[121 机密推理与隐私：TEE、加密简述|机密推理]] 是两条隐私路线(「数据不出端」vs「云端飞地」),也关系 [[110 成本与 TCO：每百万 token 成本怎么算|成本 TCO]](端侧边际推理近乎免费)。常见生产形态是**端云协同**:端上小模型兜底、难例按难度路由到云端大模型。

## 直觉类比
云端大模型像**一座中央厨房**:设备齐全、什么菜都能做,但你每点一道都得下单、等配送(网络往返、云成本、数据外发)。端侧部署像**给你家配一台压缩版料理机**:体积小、功能砍过(小模型、量化有损),但**就在厨房台面上、断网也能用、食材不出家门(隐私)、即点即做(低延迟)**。量化像**把高清菜谱压成缩略图**——文件小了、占内存少了,细节略糊但够用;蒸馏像**老师傅把毕生手艺浓缩成一本傻瓜速成手册**交给学徒(小模型),学徒做不了满汉全席,但家常菜稳稳拿下。难菜?再下单给中央厨房(端云协同)。

## 小数字例子
以 **Llama 3.2 3B** 上安卓为例:
- **量化**:4-bit 后训练量化(PTQ)实测模型体积**缩约 68.66%**,从而塞进普通安卓手机的内存预算,得以本地跑起来。
- **压缩组合**:量化 + 剪枝 + 蒸馏叠加常得 **10–20× 更小**,同时保住原精度的 **90–95%**——这是端侧能跑且还可用的关键平衡点。
- **量化精度账**:7B 模型 FP16 约 14 GB;4-bit 约 $7\text{B}\times0.5\,\text{B/参}\approx3.5$ GB,再加 KV 与激活,刚好够中高端手机内存周转。
- **能耗**:面向移动 NPU 的 MobileQuant 用 8-bit 激活,报告能耗最多降 **~50%**——端侧「电量/发热」和「内存」一样是一等约束。

## 原理:量化、蒸馏与端侧约束
**量化**把权重从高精度($b_{\text{hi}}$ 位,如 16)降到低精度($b_{\text{lo}}$ 位,如 4),内存与带宽近似按位宽比缩小:

$$
\text{Mem} \approx N_{\text{params}}\times \frac{b_{\text{lo}}}{8}\ \text{bytes},\qquad
\text{压缩比}\approx \frac{b_{\text{hi}}}{b_{\text{lo}}}
$$

对称量化把浮点 $w$ 映到整数:$w_q=\mathrm{round}(w/s)$,$s=\frac{\max|w|}{2^{b-1}-1}$;反量化 $\hat w=s\cdot w_q$,误差来自舍入。**蒸馏**让小学生模型 $p_S$ 拟合大教师 $p_T$ 的软标签,典型损失:

$$
\mathcal{L}=\alpha\, T^2\,\mathrm{KL}\!\big(p_T^{(T)}\,\Vert\,p_S^{(T)}\big)+(1-\alpha)\,\mathrm{CE}(y,p_S)
$$

端侧三大约束:**内存**(几 GB,放不下大权重 + KV)、**功耗/发热**(持续推理掉电、降频)、**算力/带宽**(远低于数据中心)。所以「先压再跑」是必然,而压缩**有损**——小模型能力上限本就低于云端大模型,这是端侧的根本取舍。2025 趋势:从单一 4-bit 转向**混合精度**,贴合具体移动芯片(骁龙 8 Gen 4、天玑 9400、Apple A18),并把 8-bit 激活喂给**移动 NPU**省能耗。

## 配置 / 代码
```bash
# llama.cpp:把模型量化成 GGUF 4-bit,在端侧 CPU/NPU 跑
# 1) 转 GGUF 并 4-bit 量化(体积约缩到 FP16 的 1/4 上下)
python convert_hf_to_gguf.py ./Llama-3.2-3B --outfile model-f16.gguf
./llama-quantize model-f16.gguf model-q4.gguf Q4_K_M   # 4-bit 混合,端侧主流档

# 2) 本地推理:无需联网、数据不出设备
./llama-cli -m model-q4.gguf -p "总结这段会议纪要" -t 4   # CPU 4 线程
```

```python
# MLC-LLM:把量化模型编译到目标端(Apple/移动 GPU/NPU),离线运行
# mlc_llm compile Llama-3.2-3B-q4f16 --device metal -o dist/
from mlc_llm import MLCEngine
engine = MLCEngine(model="dist/Llama-3.2-3B-q4f16")   # 本地、离线
print(engine.chat("帮我写条回复，别联网"))             # 端云协同:难例再上云大模型
```

## 面试高频
- **为什么要端侧部署,值什么?** 隐私(数据不出设备)、离线/弱网可用、低延迟(无网络往返)、零云成本(端侧边际推理近乎免费);代价是模型能力上限与精度受限。
- **端侧三大硬约束是什么?** 内存(几 GB,放不下大权重 + KV)、功耗/发热(持续推理掉电、降频)、算力/带宽(远低于数据中心 GPU);外加模型文件得能装进 App/下载。
- **怎么把大模型塞进手机?** 量化(FP16 → 4-bit/混合精度,按位宽比缩内存)+ 蒸馏(大模型软标签教出小模型)+ 剪枝,叠加 10–20× 缩小、保 90–95% 精度;再选端侧运行时跑。
- **主流端侧运行时各擅长什么?** llama.cpp/GGUF:CPU 为主、依赖极少、笔记本/树莓派/安卓通吃;MLC-LLM:编译到各端 GPU(Apple Silicon/移动);ExecuTorch:PyTorch 移动端(2025-10 1.0 GA);移动 NPU(骁龙/天玑/Apple)用 8-bit 激活省能耗。
- **量化和蒸馏区别?** 量化降数值精度(同结构、改位宽)直接省内存/带宽;蒸馏换更小结构的新模型、用大模型软标签训练;二者常叠用,蒸馏决定「多小」、量化决定「多省」。
- **端侧 vs 机密推理,隐私上怎么选?** 端侧 = 数据根本不出设备(要离线/极致隐私、且模型能压到端上);机密推理 = 数据上云但在 GPU 飞地内加密计算(要大模型/弹性算力)。常见折中是端云协同:端上兜底 + 难例上云。

## 关键事实
- 量化实测:**Llama 3.2 3B** 经 4-bit 后训练量化体积**缩约 68.66%**,得以在标准安卓设备本地运行;量化+剪枝+蒸馏叠加常得 **10–20× 更小**、保 **90–95% 精度**。
- 运行时(2025–2026):**llama.cpp**(GGML/GGUF,CPU 优先、依赖极少,笔记本/树莓派/安卓)仍是无 GPU 端侧首选;**MLC-LLM**(编译到 Apple Silicon/移动 GPU);**ExecuTorch**(Meta,**2025-10 1.0 GA** 标志生产就绪);**ONNX Runtime Mobile**。
- 量化趋势:2024 以 **Q4_K_M** 4-bit 为标准;2025 转向**混合精度**,贴合骁龙 8 Gen 4、天玑 9400、Apple A18 等移动芯片;**MobileQuant** 联合优化权重变换与激活范围、8-bit 激活面向**移动 NPU**,报告能耗最多降 **~50%**。
- 端侧三约束:内存、功耗/发热、算力带宽;压缩有损 → 小模型能力上限低于云端大模型,故常用**端云协同**(端上兜底 + 难例上云)。
