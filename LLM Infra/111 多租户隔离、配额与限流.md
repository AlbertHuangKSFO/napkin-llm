这是 [[LLM Infra]] 域把「一池 GPU 安全卖给很多人」的工程问题。**多租户(multi-tenancy)**=多个租户(用户/团队/API key)共享同一套推理引擎与 GPU 池,靠**配额 + 限流 + 优先级**把它们彼此隔开,既不浪费(每人独占太贵)又不互相拖垮。核心矛盾:共享省钱,但共享意味着一个租户能用光大家的资源——这就是要解决的**噪声邻居(noisy neighbor)**问题。它直接关系 [[105 SLO、SLA 设计：为推理定指标|SLO 设计]](按租户分级 SLA)、调度里的优先级与公平,以及 [[110 成本与 TCO：每百万 token 成本怎么算|每百万 token 成本]](提利用率靠拼租户)。

类比:合租公寓的水电。一个房间(租户)开着热水猛用,会让别人没热水(共享 GPU/KV 被占满)。解决办法不是给每人单独装一套锅炉(独占实例,太贵),而是给每户**装表 + 配额**(TPM/RPM 限额),并约定**高峰优先级**(付费房客先用热水)。装表必须按**用水量(token)** 而非**开关次数(请求数)**,否则一次长时间用水算不出来。

小数字:网关给租户 A 配 TPM=100k(每分钟 10 万 token)、RPM=600。某用户一次发 8k 输入 + 期望 2k 输出 ≈ 10k token,理论上 1 分钟最多放 10 次这种长请求($100\text{k}/10\text{k}=10$),即便他 RPM 还没到 600 也会被 TPM 先卡住。反过来若只设 RPM,租户灌 1 个 100k token 的超长上下文只算「1 次请求」,却能吃满共享 KV 显存——**RPM 防不住长请求,必须用 TPM**。

$$
\text{令牌桶}:\ \text{tokens}\mathrel{+}=r\cdot\Delta t,\quad \text{tokens}\le B;\qquad
\text{准入当且仅当}\ \text{tokens}\ge \text{cost}_{\text{req}}
$$

补充速率 $r$=TPM(稳态预算)、桶容量 $B$=允许的突发量。难点在 LLM 的 $\text{cost}_{\text{req}}$ 事前未知:输出长度要生成完才知道。实践做法是**输入 token 先扣、输出 token 按实际补扣**,用滚动窗口或内存原子计数维护每租户用量。隔离分两层:**入口层**(网关 RPM/TPM/优先级,把超额挡在 GPU 之外、返回 429)+ **引擎层**(调度器的优先级、抢占、per-tenant KV 显存配额防饥饿)。SLA 关键租户可上**硬隔离**——独立实例或 MIG 分区,贵但彻底。

```yaml
# AI 网关:分层配额(每个 virtual key 独立 RPM/TPM/优先级)
tenants:
  - key: team-a-prod
    rpm: 600
    tpm: 100000          # 主预算:按 token 计,防长请求噪声邻居
    priority: high       # 高峰可抢占低优先
    kv_quota_gb: 12      # 引擎层:限制该租户占用的 KV 显存
  - key: team-b-free
    rpm: 60
    tpm: 10000
    priority: low
    on_exceed: reject_429   # 超额返回 429 Too Many Requests
```

```text
❌ 只设 RPM(每分钟请求数)做限流
   → 噪声邻居灌 1 个 100k-token 超长上下文 = "1 次请求",吃满共享 KV,
     其他租户 TTFT 飙升,RPM 计数却毫无察觉
✅ 以 TPM(token/分钟)为主预算 + RPM 兜底短请求 + 引擎层 KV 配额
   → 资源真正按用量隔离;事前扣输入 token,事后补扣输出 token
```

## 面试高频
- **为什么限流要用 TPM 而不是只用 RPM?** RPM 把长短请求一视同仁,一个超长上下文算 1 次却占满资源;TPM 按 token 计才真实反映 GPU 负载。RPM 用来兜底「大量极短请求」的开销。
- **噪声邻居是什么、怎么防?** 一个租户耗尽共享资源(KV 显存/batch 槽)拖垮他人。防:TPM 限流 + per-tenant KV 配额 + 优先级/公平调度。
- **LLM 限流难在哪?** 输出长度事前未知,$\text{cost}_{\text{req}}$ 算不准 → 输入先扣、输出完成补扣,滚动窗口维护用量。
- **软隔离 vs 硬隔离?** 软=同引擎内靠优先级/配额(省钱、会互相影响);硬=独立实例/MIG 分区(贵、彻底,给 SLA 关键租户)。
- **优先级与公平怎么平衡?** 高优先可抢占低优先,但要设最低保障/老化(aging)防低优先租户饥饿。

## 关键事实
- 限流主维度是 **TPM**(token/分钟),RPM 作为短请求的次级护栏(**2025–2026**,TrueFoundry/Hivenet)。
- 网关给每个 user/team/API key/virtual key 独立 TPM、RPM、预算,防单租户拖垮共享基建(**2025**)。
- 噪声邻居:高量长上下文租户可耗尽共享部署的速率/GPU 容量,触发他人 429 与高延迟。
- token 感知限流:输入 token 提前计数、输出 token 完成后归因;用滚动窗口或内存原子计数实现。
- 厂商自带限流粒度粗、不可配,企业级多租户需自建网关层(**2025**,agentgateway)。
