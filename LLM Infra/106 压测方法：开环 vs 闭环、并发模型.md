[[106 压测方法：开环 vs 闭环、并发模型|压测方法]]决定了你测出的延迟数字是真是假。核心是两种**负载模型(workload model)**:**闭环(closed-loop)** 固定并发 N——N 个虚拟用户,每个收到响应才发下一个;**开环(open-loop)** 固定到达率 λ——按 λ req/s 持续注入,不管前一个回没回。关键反直觉:**用闭环去压一个生产中是开环的服务,会因「协调省略(coordinated omission)」严重低估尾延迟**。原理是:服务一卡顿,闭环客户端跟着等、不再发新请求,卡顿期那些「本该到达却没发」的请求从未被计入,p99 被算成接近 p50。研究表明这能让 p99 被低估 25 倍以上。生产真实流量是开环的(用户不会因为你慢就不来),所以**验 SLO、测尾延迟、找雪崩拐点必须用开环**;闭环只适合测最大吞吐/容量上限。配合 warmup(预热,排除冷启动/JIT/缓存未命中的偏差)才有可比结果。这直接服务于 [[105 SLO、SLA 设计：为推理定指标|SLO 设计]]和 [[047 准入控制与排队论：队列长度到延迟|排队论]]揭示的过载行为,数字口径与 [[107 基准：MLPerf Inference 与 InferenceMAX|基准]]相通。

## 直觉

**生活类比**:测一个办事窗口。**闭环 = 固定 50 个人排队**,一个办完才放下一个进门(收到响应才发下一个);**开环 = 不管里面多挤,每秒固定来 50 人**(真实流量,用户不会因为你慢就不来)。现在窗口卡死 **5 秒**,其余时间每人 **1ms**。闭环里这 5 秒**只有几个人在等**,门外想来的人因为进不去**根本没被记账**——客户端"自带刹车",卡顿被人数自动盖住,算出 **p99 ≈ 1ms**(谎报)。这就是**协调省略(coordinated omission)**:系统最卡的那段恰恰是发请求最少的那段,最糟的样本被系统性漏采。开环里这 5 秒**照常涌进 ~500 人**全堆队里,每人真实等了 0~5 秒、一个不漏,**p99 ≈ 4900ms**(真相)。**同一场卡顿,闭环把 p99 测低几十倍(≥25×)**——验 SLO 必须用开环,否则会误判"达标";闭环只配测"最多扛多少人"。

![[obs-106类比排队办事.svg]]

把压测想成**往水池注水测排水能力**。

- **闭环 = 用固定数量的水桶来回舀**:N 个桶,一个倒完(收到响应)再去接下一桶。如果排水口堵了(服务变慢),你舀水的人就在那干等——**注水速度自动跟着排水变慢**。结果:水池永远不会真正溢出,你看不到「堵到什么程度会淹」。
- **开环 = 水龙头按固定流量一直开着**:不管排水快慢,λ 升/秒持续灌。排水一慢,水位立刻上涨、溢出——**真实暴露过载和尾延迟**,就像生产里用户流量不会因为你慢就停。

「协调省略」就是闭环那个**自带刹车**的副作用:系统最卡的那段时间,恰恰是发请求最少的时间,于是最糟糕的延迟样本被系统性地漏采,p99 被美化。

## 例子

服务能力 μ = 100 req/s。某段时间服务卡顿 5 秒(全停),其余正常 1ms。

**闭环(10 个 VU)**:卡顿期 10 个 VU 全卡住等待,不发新请求。这 5 秒只有 10 个请求在等。
- 报告:绝大多数请求 1ms,只有 10 个慢 → **p99 算出来 ≈ 1ms**(谎报)。

**开环(λ=100 req/s)**:卡顿 5 秒内**照常到达 ~500 个请求**全部堆积排队。
- 报告:这 500 个请求等待 0~5s,p99 真实反映 → **p99 ≈ 4900ms**(真相)。

| | 闭环 | 开环 |
|---|---|---|
| 控制量 | 并发 N | 到达率 λ |
| 卡顿期到达请求 | **变少**(自带刹车) | **照常到达**(无刹车) |
| coordinated omission | **有**,低估尾延迟 | 无 |
| λ>μ 行为 | 永远追得上(伪稳态) | 队列无限增长(真过载) |
| 适合 | 测最大吞吐/容量 | 验 SLO、测尾延迟、找拐点 |

研究结论:闭环对开环服务的 **p99 可低估至少 25×**。差一个量级,SLO 验收会得出完全相反的结论。

## 原理

**闭环吞吐**受 Little's Law 约束:并发 $N$、平均延迟 $R$,则达成的吞吐

$$
X = \frac{N}{R}
$$

——延迟 $R$ 一变大,吞吐 $X$ 自动下降,到达率被系统反压「钳住」,这正是 coordinated omission 的数学根源。

**开环**则把到达过程与服务过程**解耦**:到达率 $\lambda$ 外生(常用泊松到达),与服务快慢无关。当 $\lambda > \mu$,队列长度

$$
L(t) \approx (\lambda - \mu)\, t \;\to\; \infty
$$

线性发散——真实复现 [[047 准入控制与排队论：队列长度到延迟|排队论]]里 ρ→1 的延迟爆炸。闭环里 $\lambda$ 永远等于 $X \le \mu$,**结构上无法过载**,所以测不出雪崩点。

**协调省略校正**:若必须用闭环工具,可对每个迟到的样本**回填**它「本应发起」的那些请求的等待时间(按预期发送间隔补样本),把被省略的尾部补回来——`wrk2`、HdrHistogram 即据此修正。

**warmup**:头部若干请求/秒数据丢弃,排除模型 load、CUDA graph 捕获、JIT 编译、prefix cache 未命中、autoscaler 未到位等冷启动偏差,使稳态测量可比。

## 代码

开环负载发生器(异步、固定到达率、不被响应反压):

```python
import asyncio, time, random, numpy as np

async def open_loop(send, rate, duration, warmup=10):
    """固定到达率 λ=rate;泊松间隔;不等响应即发下一个 → 无 coordinated omission"""
    lat = []
    t_end = time.perf_counter() + duration
    async def one():
        t0 = time.perf_counter()
        await send()                       # 发一个请求,记录端到端延迟
        lat.append((t0, time.perf_counter() - t0))
    tasks = []
    while time.perf_counter() < t_end:
        tasks.append(asyncio.create_task(one()))   # ✅ 立即起任务,不 await,故不被服务变慢反压
        await asyncio.sleep(random.expovariate(rate))  # 泊松到达间隔
    await asyncio.gather(*tasks)
    # 丢弃 warmup 秒,再算分位
    t0 = lat[0][0] + warmup
    steady = [d for (ts, d) in lat if ts >= t0]
    return np.percentile(steady, [50, 95, 99, 99.9]) * 1000  # ms

# ❌ 反模式:闭环——收到响应才发下一个,服务一卡就自动少发 → 漏采尾部 → p99 失真
async def closed_loop_BAD(send, concurrency, duration):
    async def worker(deadline):
        while time.perf_counter() < deadline:
            await send()                   # 阻塞等响应;慢了就少发 → coordinated omission
    end = time.perf_counter() + duration
    await asyncio.gather(*[worker(end) for _ in range(concurrency)])
```

`❌` 闭环对开环服务低估 p99 可达 25×,SLO 验收会误判「达标」;`✅` 开环按外生到达率注入、不被响应反压,真实暴露排队与尾延迟,再叠 warmup 排冷启动偏差。实务工具:开环用 `wrk2`/`k6`(open model)/`vllm bench serve --request-rate`,闭环仅用于摸容量上限。

## 面试高频

- **Q:开环和闭环压测的区别?** 闭环固定并发 N(收到响应才发下一个),开环固定到达率 λ(按时刻表持续发、不管前一个回没回)。前者到达率被服务反压,后者解耦。
- **Q:什么是协调省略(coordinated omission),为什么危险?** 闭环里服务卡顿时客户端跟着等、少发请求,卡顿期的样本被系统性漏采,p99 被算成接近 p50;对开环服务可低估尾延迟 25×,导致 SLO 验收误判。
- **Q:验证生产 SLO 该用哪种?** 开环。生产真实流量是开环的(用户不因你慢而停),只有开环能真实暴露排队、尾延迟和雪崩拐点;闭环只适合测最大吞吐/容量上限。
- **Q:闭环为什么测不出过载?** 由 Little's Law,闭环吞吐 X=N/R,到达率恒 ≤ μ,结构上无法让 λ>μ,队列不会无限增长,测不到 ρ→1 的延迟爆炸点。
- **Q:warmup 为什么必要?** 排除模型 load、CUDA graph 捕获、JIT、prefix cache 未命中、autoscaler 未就绪等冷启动偏差,只统计稳态,保证结果可比。
- **Q:必须用闭环工具(如 ab/wrk)怎么办?** 用支持 coordinated omission 校正的工具(wrk2 / HdrHistogram),按预期发送间隔回填被省略的尾部样本;否则尾延迟不可信。

## 关键事实

- **闭环测开环服务会触发协调省略**,p99 可被低估 ≥ 25×(Tene/HdrHistogram、Brooker 等多篇论证);生产流量本质开环,验 SLO 必须用开环负载模型。
- **开环 = 固定到达率(常泊松),闭环 = 固定并发**;开环在 λ>μ 时队列线性发散、能复现雪崩拐点,闭环吞吐恒 X=N/R ≤ μ,测不出过载——k6、Locust、Artillery 等 2025 工具均显式提供 open/closed 两种模式。
- **主流压测工具**:开环 `wrk2`、`k6`(open model)、`vllm bench serve --request-rate`;协调省略校正靠 wrk2 / HdrHistogram;warmup 丢弃头部样本是稳态测量的标准前置(2025–2026 通行做法)。
