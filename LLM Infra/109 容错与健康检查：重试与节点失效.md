[[109 容错与健康检查：重试与节点失效|容错与健康检查]]是让推理服务在 GPU 掉卡、节点失效、瞬时过载下仍守住 [[105 SLO、SLA 设计：为推理定指标|SLO]]的工程。核心是三道防线:**健康检查**(K8s 的 liveness/readiness/startup 三种探针,职责正交)、**请求重试**(幂等 + 退避 + 熔断)、**节点失效迁移与优雅降级**。关键反直觉有两条:其一,**liveness 和 readiness 职责完全不同**——readiness 控「是否给它发流量」(没就绪/过载就摘出负载均衡),liveness 控「是否重启它」(卡死才重启);把过载当 liveness 失败会触发**误杀重启风暴**。其二,**大模型慢启动(load 权重 + 编译 kernel 数分钟)必须用 startup 探针保护**,否则 liveness 在启动期就判死,陷入 CrashLoop 永远起不来。重试必须只重幂等/可重试错误并带退避抖动,否则**重试风暴会打垮正在恢复的服务**;流式已吐 token 的请求重试 = 重复输出,要靠幂等键去重。超时要分层设(connect/首 token/整体)。这与 [[047 准入控制与排队论：队列长度到延迟|排队论]]的过载保护、[[108 监控：GPU 利用率、KV 占用、排队、p99|监控指标]]的 readiness 信号协同,在 [[054 PD 配比与独立扩缩|PD 配比]]这类解耦架构里还要按角色各设健康检查。

## 直觉

把容错想成**餐厅应对突发状况**。

- **readiness(就绪牌)= 门口的「正在备餐」牌**:厨房还在 load 食材或忙不过来,就翻牌让领位**不带客人进来**;好了再翻回。它**控流量,不杀人**。
- **liveness(心跳)= 看厨师是否昏倒**:真卡死(死锁)才叫救护车(重启)。陷阱:厨师只是手慢(过载),你却当他昏倒一脚踹走重新招人——**误杀**,越踹越乱。
- **startup(开业宽限)= 新店装修期别催**:大模型开业要装修几分钟,这期间别用「心跳」标准判死,否则永远开不了张(CrashLoop)。
- **重试 = 菜上错了重做**:但只重做「可重做」的(上错/超时),不重做「客人主动取消/违规点单」;而且别一窝蜂重做(重试风暴)压垮后厨,要排队错峰(退避 + 抖动)。

## 例子

某 K8s 上的 vLLM 部署,探针配置与一次故障处置:

| 探针 | 检查什么 | 配置 | 失败动作 |
|---|---|---|---|
| **startup** | 模型 load + kernel 编译完没 | `failureThreshold=60, period=10s`(给 10 分钟) | 仍在启动,**不判死** |
| **readiness** | 能否接新请求(KV 有余量、未过载) | `period=5s, timeout=2s` | 摘出负载均衡,**不重启** |
| **liveness** | 进程是否卡死 | `period=15s, failureThreshold=3` | 重启 Pod |

**故障旅程**(一次 GPU ECC 错):
1. 节点 A 的 GPU 报 ECC 错,引擎 readiness 转 fail → **负载均衡摘掉 A,不再发新流量**。
2. A 上**在途的请求会丢**(KV 在显存里,无法迁移)→ 靠**客户端带幂等键重试**。
3. 重试请求**退避 200ms + 抖动**后路由到健康节点 B;B 重新 prefill 该请求。
4. 调度器在健康节点重建 A 的副本,容量恢复。
5. 若所有大模型副本都不可用 → **优雅降级**:返回小模型结果 / 缓存 / 排队 + 友好提示,而非直接 500。

- **量化**:无 startup 探针时,模型 load 需 6 分钟而 liveness `failureThreshold×period=45s` 就判死 → **CrashLoop,永远起不来**;加 startup(10 分钟窗口)后正常启动。
- **重试风暴对照**:1000 个并发请求同时撞上 A 失效,若**无退避同时重试** → 瞬间 1000 QPS 砸向 B,B 也被打垮(级联);带**指数退避 + 抖动**后,重试在 0~2s 内摊开,B 平稳吸收。

## 原理

**三探针职责正交**:

$$
\text{readiness fail} \Rightarrow \text{摘流量(不杀)},\quad
\text{liveness fail} \Rightarrow \text{重启},\quad
\text{startup 未过} \Rightarrow \text{暂停前两者}
$$

把过载/依赖未就绪错挂到 readiness(可恢复、不重启),把死锁挂到 liveness。混用会误杀。

**重试的数学——退避 + 抖动**避免「惊群同步」。指数退避第 $k$ 次等待:

$$
t_k = \min(\text{cap},\ \text{base}\cdot 2^{k})\cdot U(0,1) \quad(\text{full jitter})
$$

抖动项 $U(0,1)$ 打散同步重试,把瞬时洪峰摊平,防止 [[047 准入控制与排队论：队列长度到延迟|过载]]雪崩。

**重试预算**:全局限制重试占比(如 ≤ 总请求 10%),配**熔断器**:滑动窗口失败率超阈则「断开」,直接快速失败一段时间,给坏节点喘息:

$$
\text{失败率}_{[t-w,t]} > \theta \Rightarrow \text{OPEN(快速失败)} \to \text{半开探测} \to \text{CLOSE}
$$

**幂等性**:仅当请求可安全重放才重试。LLM 流式响应一旦吐出 token 再重试会**重复输出**,需用**幂等键(idempotency key)**让服务端去重/续传,或对已开始流式的请求**不重试**。

**超时三层**:connect 超时、首 token(TTFT)超时、整体超时;无超时则坏节点会**永久占用**客户端连接,拖垮上游(级联故障)。

**节点失效**:GPU 显存里的 KV **不可迁移**,在途请求只能丢 + 客户端重试;[[054 PD 配比与独立扩缩|PD 分离]]架构下 prefill/decode 节点独立失效,需各自健康检查 + KV 传输失败兜底。优雅退出:收到 SIGTERM 先转 readiness=fail 摘流量、排空在途、再关闭,避免滚动发布丢请求。

## 代码

健康检查端点 + 带退避/幂等/熔断的客户端重试:

```python
# 服务端:liveness 简单、readiness 全面但快
@app.get("/livez")          # ✅ 只看进程活着 → 别在这做重活,否则慢响应被误判死锁
def livez(): return {"ok": True}

@app.get("/readyz")         # ✅ 全面:模型加载完 + 未过载 + KV 有余量
def readyz():
    if not model_loaded: return Response(status_code=503)        # 启动期 → 摘流量(配 startup)
    if kv_usage() > 0.95 or waiting() > MAX_Q:                   # 过载 → 摘流量,但不该触发重启
        return Response(status_code=503)
    return {"ready": True}

# 客户端:只重可重试错、退避+抖动、幂等键、熔断
import random, time
def call_with_retry(send, payload, key, max_retry=3, base=0.2, cap=2.0):
    for k in range(max_retry + 1):
        try:
            return send(payload, idempotency_key=key, timeout=(1.0, 5.0))  # connect/整体超时分层
        except RetryableError:                       # 503 / 超时 / 连接断
            if k == max_retry: raise
            time.sleep(min(cap, base * 2**k) * random.random())  # ✅ full jitter,防重试风暴
        except NonRetryableError:                    # ❌ 400 参数错 / 内容安全拒绝
            raise                                    # 不重试,重试也没用

# ❌ 反模式:无退避、无幂等、什么错都重试
def call_BAD(send, payload):
    for _ in range(5):
        try: return send(payload)
        except Exception: continue   # 立即重试 → 1000 客户端同步重试打垮恢复中的服务;
                                      # 流式已吐 token 的重试 → 重复输出;400 重试纯浪费
```

`❌` 无退避的「什么错都立即重试」会制造重试风暴打垮恢复中的节点、对流式请求造成重复输出、对 400 类错误做无谓重试;`✅` 只重幂等/可重试错、full jitter 退避、带幂等键、配熔断与分层超时,并用 readiness(摘流量)而非 liveness(重启)处理过载,才能在失效中平稳迁移、不放大故障。

## 面试高频

- **Q:liveness 和 readiness 探针区别?** readiness 控「是否给它发流量」(没就绪/过载就摘出 LB,不重启);liveness 控「是否重启」(卡死才重启)。过载该走 readiness,误挂 liveness 会触发误杀重启风暴。
- **Q:大模型为什么需要 startup 探针?** load 权重 + 编译 kernel 可能数分钟,若 liveness 在启动期就按常规阈值判死会 CrashLoop 永远起不来;startup 给足启动窗口,通过后才启用另两个探针。
- **Q:重试要注意什么?** 只重可重试错(超时/503/连接断),不重 400/内容拒绝;退避 + 抖动(full jitter)防重试风暴;带幂等键防重复;配重试预算与熔断;分层超时。
- **Q:LLM 流式请求能重试吗?** 已吐 token 的请求重试会重复输出;要么不重试,要么靠幂等键让服务端去重/续传。未开始流式的可安全重试。
- **Q:节点/GPU 失效怎么处理?** readiness 转 fail 摘流量,调度器在健康节点重建副本;显存里的 KV 不可迁移,在途请求丢失靠客户端重试到新副本;PD 分离架构需各角色独立健康检查。
- **Q:什么是优雅降级和优雅退出?** 降级:主模型不可用时退到小模型/缓存/排队而非直接 500。退出:收 SIGTERM 先转 readiness=fail 摘流量、排空在途请求再关闭,避免滚动发布丢请求。

## 关键事实

- **K8s 三探针职责正交**:readiness(控流量,过载/依赖未就绪走这里,不重启)、liveness(控重启,仅卡死)、startup(保护慢启动);LLM 服务因模型 load + kernel 编译耗时数分钟,必须配 startup 否则 CrashLoop(2025–2026 标准实践)。
- **重试必须幂等 + 退避抖动 + 熔断 + 重试预算**:full jitter 退避防惊群重试风暴;熔断器(失败率超阈 OPEN→半开→CLOSE)给坏节点喘息;流式已吐 token 的请求重试会重复输出,需幂等键去重。
- **节点失效时显存 KV 不可迁移**,在途请求丢失靠客户端重试到健康副本;优雅退出(SIGTERM→摘流量→排空→关闭)避免滚动发布丢请求;生产配优雅降级(降级到小模型/缓存)与分层超时(connect/首 token/整体)防级联故障。
