[[033 自动前缀缓存的命中与失效|自动前缀缓存的命中与失效]]讲 vLLM 的 **automatic prefix caching**:对每个**满 block** 算一个 **hash**(由"前缀 hash + 块内 tokens + 可选 LoRA/多模态/salt"组成),进全局 hash 表;新请求同 hash 的 block **直接复用物理块、跳过 prefill**(命中),否则正常算并写入(未命中);显存满则 LRU **驱逐**冷块(失效),前缀改一个 token 则后续 block hash 全变而失效。它是 [[032 前缀缓存：RadixAttention 树结构|前缀缓存]]的 vLLM 实现路线——**不建树、块彼此独立**,靠 hash 表自动共享,是 [[LLM/103 KV-Cache 优化：GQA、量化、驱逐与前缀共享|KV 优化]]里最省心的一档。

## 直觉

SGLang 用树,vLLM 走另一条路:**给每个满 block 发一个指纹(hash)**。指纹包含"我之前所有 token 的 hash"(链式),所以**同样的前缀必然得到同样的指纹**。所有物理块进一张全局 hash 表;新请求把自己的 block 逐个算指纹去查表,查到就**复用那块物理 KV、连 prefill 都省了**,查不到才真算。好处是**块之间完全独立、无需维护树**,分配/释放各管各的;命中是"自动"的——你不用声明哪段是前缀,hash 一样就共享。

## 例子

system prompt 占 2 个满 block(`h0,h1`),user 问题占第 3 个满 block(`h2`)+ 半块(不缓存):
- **第一个请求**:`h0,h1,h2` 都未命中 → 全算 prefill,写入缓存。
- **第二个请求(同 system prompt、不同问题)**:`h0,h1` 命中 → 跳过这 2 块的 prefill,直接复用物理 KV;`h2` 因问题不同而变,未命中 → 只算它。
- **若把请求 ID 放进 system prompt 开头**:`h0` 就变了,链式导致 `h1,h2` 全变 → **命中率归零**。

命中率随负载与共享度变;高共享场景(同 system prompt 批量、多轮对话)可达很高。

## 原理

block hash 链式定义(第 $i$ 个满块):

$$
\text{hash}_i = H\big(\text{hash}_{i-1},\ \text{tokens}_i,\ \text{extra}\big)
$$

`extra` 含 LoRA ID、多模态输入 hash、cache salt(多租户隔离)。链式保证**前缀任一 token 变 → 其后所有块 hash 变 → 全失效**(这是"失效"的主因之一,另一个是 LRU 驱逐)。命中省的是**那些块的 prefill 计算**与**KV 显存**(同物理块共享)。半块(未填满)**不缓存**——hash 只对满块算。vLLM v0.11 起默认 hash 用 **sha256**(早期默认 hash 不保证无碰撞),可经 `--prefix-caching-hash-algo` 切换。

## 代码

```python
from vllm import LLM
llm = LLM(
    model="meta-llama/Meta-Llama-3-8B-Instruct",
    enable_prefix_caching=True,    # ✅ 开自动前缀缓存（V1 引擎默认即开）
    # prefix_caching_hash_algo="sha256"   # v0.11 起默认 sha256 防碰撞
)

# ✅ 固定内容前置、变动内容后置 —— 最大化前缀命中
SYSTEM = "You are a helpful assistant.\n" + LONG_FEW_SHOT   # 跨请求不变 → 命中
prompts = [SYSTEM + f"\nUser: {q}\nAssistant:" for q in questions]
out = llm.generate(prompts)        # 公共前缀块只 prefill 一次，其余请求命中复用

# ❌ 反例 1：变动字段放前缀最前 → 链式 hash 全变 → 命中率 0
#   bad = f"[req={uuid4()}] " + SYSTEM + ...      # 每条 h0 就不同
# ❌ 反例 2：以为命中是永久的 —— 显存压力下冷块被 LRU 驱逐，下次同前缀仍要重算
```

`❌` 两个高频坑:**(1)** 把 UUID/时间戳塞进前缀头 → 命中率归零;**(2)** 把命中当永久——它是**机会性**的,显存一紧张冷块就被 LRU 驱逐,前缀缓存只减计算/显存,不保证一定命中。

## 面试高频

- **vLLM 自动前缀缓存怎么实现?** 对每个**满 block** 算链式 hash(前缀 hash+块内 tokens+extra),进全局 hash 表;同 hash 复用物理块、跳过 prefill。**不建树、块独立**。
- **和 RadixAttention 区别?** 同目标(共享前缀),vLLM 用 **hash 表**(块独立、各自分配释放),SGLang 用 **radix 树**(显式前缀路径)。
- **hash 里有什么、为何?** 前缀 hash(链式保证前缀一致性)+ 块内 tokens + LoRA/多模态/salt(隔离多租户、避免错误共享)。
- **何时失效?** (1)前缀任一 token 变 → 链式后续全失效;(2)显存满 LRU 驱逐冷块;(3)半块本就不缓存。
- **何时受益?** 长 system prompt、few-shot、多轮对话、批量同模板;变动内容务必后置。
- **命中是永久的吗?** 不,**机会性**——LRU 随时可驱逐;只减计算/显存,不保证命中。
- **hash 碰撞风险?** 早期默认 hash 不保证无碰撞;v0.11 起默认 **sha256** 修复。

## 关键事实

- vLLM **automatic prefix caching**:满 block 链式 hash → 全局 hash 表 → 同 hash 复用物理块、跳过 prefill;`enable_prefix_caching`(V1 引擎默认开启)。
- 块**彼此独立**、无树结构,可单独分配/释放;hash 含 tokens + LoRA ID + 多模态 hash + cache salt(多租户隔离)。
- 失效三因:前缀 token 改动(链式连锁)、LRU 驱逐、半块不缓存;**v0.11 起默认 sha256** 防碰撞(`--prefix-caching-hash-algo`)。
- 与 [[032 前缀缓存：RadixAttention 树结构|RadixAttention]] 同目标不同实现;建在 [[030 PagedAttention 深入：KV 当虚拟内存|分页 block]] 之上,不改注意力数学。
