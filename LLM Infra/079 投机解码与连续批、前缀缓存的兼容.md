[[079 投机解码与连续批、前缀缓存的兼容|投机解码的系统兼容性]] 决定它能否真正落进生产引擎。结论先行:[[073 投机解码系统：draft-verify 全流程|投机解码]] 与 [[032 前缀缓存：RadixAttention 树结构|前缀缓存]]、[[042 chunked prefill：切块融合|chunked prefill]]、[[030 PagedAttention 深入：KV 当虚拟内存|PagedAttention]] **正交可叠加**(各治不同阶段或资源);但与 [[041 连续批处理：迭代级调度内幕|连续批处理]] 是**此消彼长**的关系——**batch 越大,投机收益越低**。根因在 [[078 接受率、草稿长度与收益分析|收益分析]] 的 roofline 约束:投机靠 [[014 Decode 阶段：访存受限|decode 访存受限]] 时的闲置算力"白嫖";一旦 batch 大到逼近 [[004 算力 vs 带宽：Roofline 与算术强度|算力屋顶]],闲置算力消失,验证 k 个 token 不再免费,反而和正常请求**抢算力**。所以生产实践是:**低并发/低延迟开投机,高并发/高吞吐自适应降草稿长甚至关闭**。这是投机解码能不能上线的最关键工程判断。

## 直觉

投机解码像"高速公路空车道时多拉几个乘客"——decode 阶段算力这条车道大量空着(访存受限),顺手验证几个草稿 token 几乎不占额外时间,白赚。

但连续批处理是"把更多车塞上同一条道":batch 一大,算力车道就被正常请求填满了。这时你再想"顺手多拉草稿乘客",已经没有空位——草稿验证要和真实请求**抢同一份算力**,不但不白赚,还可能**拖慢大家**。

而前缀缓存、chunked prefill、PagedAttention 是另一套设施:前缀缓存省的是"进城前那段路"(prefill),投机省的是"城里走走停停"(decode),两段不冲突,收益相乘。PagedAttention 是停车场管理(KV 分页),投机的树状候选只是多停了几辆"候选车",停车场照样管得了——但拒绝时要记得**把多停的车开走(回滚多写的 KV 块)**。

## 例子

同一 EAGLE-3 + Llama-8B 部署,随 batch 变化的典型加速(示意趋势):

| batch | decode 算力占用 | 投机净加速 | 说明 |
|---|---|---|---|
| 1 | ~5% | **~3×** | 算力大量闲置,验证全白嫖 |
| 8 | ~30% | ~2× | 仍有闲置,收益可观 |
| 32 | ~70% | ~1.3× | 闲置变少,边际收益下降 |
| 128 | ~100% | **~1× 或更低** | 算力打满,验证抢资源,投机失效甚至负优化 |

所以同一套权重,**低 QPS 时段开投机抢低延迟,高 QPS 时段关投机保吞吐**。SGLang/vLLM 的自适应投机正是据 batch / 接受率在线调 num_steps、topk,batch 大时自动缩草稿。

## 原理

**与连续批:此消彼长(roofline)**。设单步算力屋顶利用率为 $u(B)$($B$ 为 batch)。投机的额外算力开销被吸收的前提是 $u(B)<1$(有闲置);当 $u(B)\to 1$,验证 $k$ 个 token 的额外 FLOP 不再免费,单步时间从 $\approx T$ 变成 $\approx (1+\text{开销})T$,净加速 $\frac{g(k)}{1+\text{开销}}\to$ 失效:

$$
\text{投机增益}\ \propto\ \big(1-u(B)\big)\quad\Rightarrow\quad B\uparrow \;\Rightarrow\; u(B)\uparrow \;\Rightarrow\; \text{增益}\downarrow
$$

**与前缀缓存:正交相乘**。前缀缓存省 [[013 Prefill 阶段：计算受限|prefill]] 重算,投机省 decode 步数,作用在不同阶段,端到端加速近似相乘。草稿器还能复用同一前缀的 KV,不冲突。

**与 PagedAttention / 树状验证:需协调但兼容**。EAGLE/Medusa 的树状候选要在 KV cache 里管理**多个分支**——靠分页 KV 天然支持(每分支占若干 block)。关键工程细节:验证后**只保留被接受路径,其余分支的 KV block 必须回滚释放**,否则 KV 泄漏。chunked prefill 与投机作用阶段不同(prefill vs decode),共存无碍。

**何时关**:高并发吞吐优先、batch 持续大、或接受率被任务拉低(OOD 输入)时,投机净收益 ≤ 1,应自适应缩 $k$ 或关闭。

## 面试高频

- **Q:投机解码和连续批处理为什么此消彼长?** 投机靠 decode 闲置算力白嫖;batch 大时算力逼近屋顶、闲置消失,验证额外 FLOP 与真实请求抢算力,收益 $\propto (1-u(B))$ 趋零甚至变负。
- **Q:和前缀缓存冲突吗?** 不冲突,正交。前缀缓存省 prefill、投机省 decode,作用阶段不同,端到端加速相乘。
- **Q:树状验证怎么和 PagedAttention 配合?** 多个候选分支各占若干 KV block(分页天然支持);验证后只留被接受路径,**其余分支 KV 必须回滚释放**,否则显存泄漏。
- **Q:什么时候应该关闭投机解码?** 高并发/大 batch/吞吐优先,或接受率被 OOD 输入拉低时——净加速 ≤1,应自适应缩 $k$ 或关。
- **Q:生产里怎么动态决策?** 按当前 batch 大小 / 在线接受率自适应调 num_steps、topk(SGLang/vLLM 支持);低负载开大草稿抢延迟,高负载缩草稿保吞吐。

## 关键事实

- 兼容性总表:**前缀缓存 / chunked prefill / PagedAttention 正交可叠加**;**连续批处理此消彼长**(batch↑ → 收益↓)。
- roofline 约束:投机增益 $\propto (1-u(B))$,$u(B)$ 为算力屋顶利用率;**大 batch 算力受限,投机收益蒸发**,这是部署核心取舍。
- 工程细节:树状候选靠分页 KV 管多分支,验证后须**回滚未接受分支的 KV block**;草稿/验证可复用前缀缓存 KV。
- 现状(2025):vLLM、SGLang 均支持投机 + prefix caching + continuous batching 共存,并提供**按负载自适应**调草稿长/topk(高 QPS 自动缩或关),低延迟场景固定开 EAGLE-3。
