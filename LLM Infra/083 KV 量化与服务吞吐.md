[[083 KV 量化与服务吞吐|KV 量化与服务吞吐]]从**吞吐视角**讲量化三处里的第三处:把 [[LLM/102 KV-Cache|KV-Cache]] 用 **FP8/INT8** 存,省下的 KV 显存直接换成**更大 batch 或更长上下文**,从而提吞吐。部署细节回链 [[034 KV 量化部署：FP8、INT8 KV|KV 量化部署]],KV 优化全景回链 [[LLM/103 KV-Cache 优化：GQA、量化、驱逐与前缀共享|KV 优化]]。与权重/激活量化([[080 服务量化总览：W、A、KV 三处|三处量化]])**正交**,可独立叠加。

## 直觉

吞吐为什么靠"省 KV"来提?因为 [[014 Decode 阶段：访存受限|decode 是访存受限]],提吞吐的核心手段是**增大 batch**(见 [[016 batch 如何改变算术强度|batch 改变算术强度]]),而 batch 上限往往**卡在 KV 显存**——每多一路并发就多一份 KV。把 KV 从 2 字节压到 1 字节,**同样显存能塞 2× 的 KV**,于是 batch 翻倍、吞吐随之上去;或者把这份空间留给单条请求,跑**更长上下文**。类比:决定餐厅翻台率的不是厨房算力,而是大堂能摆几桌(KV 显存);KV 量化就是把桌子换小,同样面积多摆一倍客人。注意——量化**只动 KV 的存储**,注意力计算时仍反量化回高精度做 $qk$,数学不变。

## 例子

80GB H100,Llama-3 70B(GQA,8 KV 头),权重等占 ~40GB,剩 ~40GB 给 KV:

- **BF16 KV**:32k 上下文每序列 KV **10GB** → 约 **4 路**并发。
- **FP8 KV**(1 字节):每序列 **5GB** → 约 **8 路**(2×),或单序列上下文翻到 **64k**。
- 实测吞吐:FP8 KV 把可分配 KV 空间约翻倍,在 KV 受限的高并发场景吞吐显著上升;非 KV 受限时收益小。
- 精度:FP8 E4M3 KV 多数任务掉点可忽略;**长上下文/长生成**可能积累误差,需评测。

## 原理

KV 显存账(出自 [[015 KV-Cache 的显存账(逐层手算)|KV 显存账]]):

$$
M_{KV}=2\,L\,H_{kv}\,d_h\,S\,B\cdot b_{KV}
$$

KV 量化只动最后那个**每元素字节 $b_{KV}$**:BF16 的 $b=2$ → FP8/INT8 的 $b=1$,$M_{KV}$ 直接减半。这和 **GQA** 完全正交——GQA 减的是 $H_{kv}$(KV 头数,如 64→8,省 8×),量化减的是 $b_{KV}$(省 2×),**两者相乘 = 16× KV 缩减**,互不冲突(见图)。格式选择:**FP8 E4M3**(浮点指数位耐离群,vLLM 默认且**当前只支持 FP8 KV**)、**INT8**(TensorRT-LLM 支持,需更细 scale)、**INT4/KIVI**(4× 省但长序列易掉点,研究态)。掉点缓解:per-token/per-head scale、对 attention sink 的前几个 token 保留高精度。

## 代码

```bash
# vLLM:KV 用 FP8 E4M3(与权重量化正交,可同时开)
vllm serve meta-llama/Llama-3-70B \
     --quantization fp8 \
     --kv-cache-dtype fp8_e4m3 \
     --max-model-len 65536      # 省下的 KV 空间换更长上下文

# 校准 KV scale(静态),否则用默认动态 scale
# --calculate-kv-scales 让引擎在线统计 per-tensor scale
```

❌ 误区:以为 KV 量化能直接加速注意力计算(像激活量化加速 GEMM 那样)。
✅ 正解:KV 量化的吞吐收益**间接来自省显存 → 增大 batch**;注意力仍在反量化后的高精度域算,$qk$ 数学不变。收益只在 **KV 受限**时显现,KV 不是瓶颈时几乎无感。

## 面试高频

- **Q:KV 量化怎么提吞吐?** 省 KV 显存 → 同显存塞更大 batch → decode 访存受限下吞吐随 batch 上升;或换更长上下文。
- **Q:KV 量化和 GQA 冲突吗?** 不冲突,正交。GQA 减 KV 头数,量化减每元素字节,相乘叠加(如 8×2=16× 缩减)。
- **Q:为什么 KV 量化不直接加速计算?** 它只压存储,注意力计算时反量化回高精度,数学不变;收益是"省显存换 batch",不是"算得更快"。
- **Q:KV 量化的精度风险在哪?** 长上下文/长生成时误差积累;attention sink 的前几个 token 敏感,常保留高精度。

## 关键事实

- 2025:vLLM KV 量化**仅支持 FP8**(E4M3/E5M2),INT8 KV 在排期(issue 讨论中);TensorRT-LLM 支持 FP8/INT8 KV。
- FP8 KV 约让可分配 KV 空间翻倍 → 2× batch 或 2× 上下文;多数任务近无损。
- 与 GQA、[[030 PagedAttention 深入：KV 当虚拟内存|PagedAttention]]、[[032 前缀缓存：RadixAttention 树结构|前缀缓存]] 全部正交可叠加。
- INT4 KV(KIVI 等)4× 省但长序列掉点明显,2025 仍偏研究态。
