[[120 语义缓存与响应复用]] 解决一个朴素观察:线上请求里有大量**语义重复**——同一个问题被无数人用不同措辞问。**语义缓存(semantic cache)**把每条 prompt 用 embedding 编成向量,新请求来时去向量库做**最近邻检索**,若与某条历史 prompt 的相似度超过阈值,就**直接复用那条历史的整段答案**,完全跳过模型前向。代表实现是 **GPTCache**。它与 [[032 前缀缓存：RadixAttention 树结构|前缀缓存]] 是两回事:前缀缓存复用的是共享 token 前缀的 KV-Cache(仍要跑模型,只省重复 prefill),要求 token 完全相同;语义缓存复用的是**整段答案文本**,只要语义近似就命中,二者正交可叠用。它是 [[100 推理网关与智能路由(cache-aware)|推理网关]]、[[110 成本与 TCO：每百万 token 成本怎么算|成本 TCO]] 的重要省钱杠杆,在 [[RAG/01 什么是 RAG|RAG]] 问答系统里也常用来缓存高频问;但带来命中阈值与**语义错配**的风险,用错会返陈旧或张冠李戴的答案,触及 [[AI 安全/AI 安全|AI 安全]] 关切。

## 直觉类比
语义缓存像**客服的「话术速查本」**:不同客户问「怎么退款」「退款流程是啥」「我想退货」其实是同一意图,客服不必每次重新组织语言、直接翻到那一页念。代价是这本速查本得**判断「够不够像」**:翻太松,把「2024 年退款政策」当成「2025 年退款政策」念了——错配翻车;翻太严,稍微换个说法就翻不到、只好重新现编(漏命中、省不下功夫)。而前缀缓存更像**背诵开头一模一样的稿子时省下重读开头的力气**:要求开头逐字相同,且还是得把后面讲完(仍跑模型)。

## 小数字例子
设缓存命中省一次 LLM 调用:命中返回 **3–8 ms**,未命中走模型 **500–2000 ms**;某 API 单次调用计 **$0.002**。
- 日均 100 万次请求,语义命中率 **40%** → 40 万次不调模型,省 $40\text{万}\times0.002=\$800/\text{天}$,且这 40 万次时延从约 1 s 降到毫秒级。
- **阈值取舍**:余弦相似度阈值 $\tau=0.85$ 时命中率高但误命中多;调到 $\tau=0.95$ 误命中骤降但命中率掉到 ~25%。
- **错配代价**:「公司 2024 营收多少」与「公司 2025 营收多少」cosine 可达 0.92,若 $\tau=0.85$ 会误命中、返成去年数字——一次错配可能比省下的几百刀代价大得多。

## 原理:近邻检索 + 阈值判定
把 prompt $x$ 编码为向量 $\mathbf{e}(x)$,缓存里存着历史 $(\mathbf{e}_i, a_i)$(向量、答案)。新请求 $q$ 检索最相似的历史项,按**余弦相似度**与阈值 $\tau$ 决定命中:

$$
i^\star=\arg\max_i \cos\!\big(\mathbf{e}(q),\mathbf{e}_i\big),\qquad
\cos(\mathbf u,\mathbf v)=\frac{\mathbf u\cdot\mathbf v}{\lVert\mathbf u\rVert\,\lVert\mathbf v\rVert}
$$

$$
\text{hit} \iff \cos\!\big(\mathbf{e}(q),\mathbf{e}_{i^\star}\big)\ge \tau \;\Rightarrow\; \text{return } a_{i^\star}
$$

阈值 $\tau$ 是**精度/召回的旋钮**:$\tau\uparrow$ 误命中(false hit)少但命中率低;$\tau\downarrow$ 反之。难点在于**不同类查询在嵌入空间的密度不同**——代码类词汇受限、聚得紧,口语开放问分布稀疏,单一全局 $\tau$ 难两全;2025 的 **vCache** 等用在线学习为每条缓存项估计逐项阈值。此外答案有**时效/个性化**,需 TTL 过期与主动失效,否则返陈旧答案。期望省下成本可写作 $\text{命中率}\times(\text{单次模型成本})-\text{embedding 与检索开销}$。

## 配置 / 代码
```python
# GPTCache 式语义缓存:embedding + 向量检索 + 阈值
from gptcache import Cache
from gptcache.embedding import Onnx
from gptcache.manager import manager_factory
from gptcache.similarity_evaluation import SearchDistanceEvaluation

cache = Cache()
emb = Onnx()                                          # prompt → 向量
cache.init(
    embedding_func=emb.to_embeddings,
    data_manager=manager_factory("sqlite,faiss", vector_params={"dimension": emb.dimension}),
    similarity_evaluation=SearchDistanceEvaluation(),  # 相似度判命中
    # 阈值由 evaluation/eviction 配置:越严越防错配
)

def ask(prompt, ttl=3600):
    hit = cache.get(prompt)            # 近邻检索 + 阈值
    if hit is not None:
        return hit                     # 命中:复用整答,3–8 ms,不调模型
    answer = llm(prompt)               # 未命中:正常生成
    cache.put(prompt, answer, ttl=ttl) # 写回 + 过期时间
    return answer
```

## 面试高频
- **语义缓存和前缀缓存有什么区别?** 语义缓存复用「整段答案文本」、语义近似即命中、完全跳过模型;前缀缓存(RadixAttention)复用共享前缀的 KV-Cache、要求 token 逐字相同、仍跑模型只省重复 prefill。二者正交,可同时上。
- **命中怎么判定?阈值怎么取舍?** prompt 嵌成向量做最近邻检索,余弦相似度 ≥ 阈值 τ 即命中返缓存答。τ 高:误命中少、命中率低;τ 低:反之。是精度/召回旋钮。
- **为什么单一全局阈值不好?** 不同类查询在嵌入空间密度不同(代码类聚得紧、口语类稀疏),一个 τ 对两类都不优;2025 趋势是逐项/按类自适应阈值(如 vCache 在线学习)。
- **最大的风险是什么?** 语义错配:相似但答案应不同的查询(2024 vs 2025、不同用户)被误命中,返错答;时效/个性化答案不过期则陈旧。宁可漏命中也别返错。
- **什么场景收益最大,什么场景别用?** FAQ、搜索式短问、客服话术等高重复+答案稳定场景省钱省时延最多;强时效、强个性化、需精确事实的查询应禁用或加严阈值 + TTL + 主动失效。
- **省下多少成本怎么估?** ≈ 命中率 × 单次模型调用成本 − embedding 与向量检索开销;命中还把这部分请求时延从数百毫秒降到几毫秒。

## 关键事实
- **GPTCache**(zilliztech)是语义缓存代表实现:embedding 编码 + 向量库(如 FAISS/Milvus)最近邻 + 固定相似度阈值判命中;命中返回约 **3–8 ms**,未命中走模型约 **500–2000 ms**。
- 工程上语义缓存对「高重复短中等 prompt」(搜索查询、助手调用)最有效;业界报告在合适负载上可显著降本(如某些场景 API 账单降约 60%)与降时延。
- **2025–2026 研究热点**:单一全局阈值在不同查询密度上表现差,vCache 等用在线学习为每条缓存项估计逐项最优阈值;另有按任务类型动态调阈、集成多 embedding 提升命中质量的工作。
- 与 [[032 前缀缓存：RadixAttention 树结构|前缀缓存]] 正交:前者复用整答跳过模型,后者复用 KV 仍跑模型;生产中常叠用并由 [[100 推理网关与智能路由(cache-aware)|推理网关]] 统一调度。
- 安全/正确性关切:语义缓存被研究为 [[RAG/01 什么是 RAG|RAG]] 系统的对抗攻击面(投毒/缓存中毒),时效与个性化场景须谨慎,见 [[AI 安全/AI 安全|AI 安全]]。
