[[054 PD 配比与独立扩缩|PD 配比]]是 [[048 为何分离 prefill 与 decode|PD 分离]] 落地后的运维核心:[[013 Prefill 阶段：计算受限|Prefill]] 实例数与 [[014 Decode 阶段：访存受限|Decode]] 实例数的比例(记作 **xPyD**,如 1P1D、3P1D、1P3D),应随**负载形态**动态调整,并支持两类实例**独立扩缩**——谁是瓶颈就加谁,不必整机扩。配比取决于流量的输入/输出长度比(ISL:OSL):长 prompt 短输出偏 prefill,短 prompt 长输出偏 decode。这是把 [[018 TTFT、TPOT、ITL 与 goodput：服务指标定义|goodput]] 维持在峰值的关键调参,由 [[052 NVIDIA Dynamo：分布式推理框架与 SLO Planner|Dynamo]] 的 SLO Planner 等做闭环。

## 直觉

聚合系统像一辆固定座位的车:想多拉货只能换更大的车(整机扩)。PD 分离像把"装货工(prefill)"和"司机(decode)"分开雇——订单里要装的多就多招装货工,要送的远就多派司机,各招各的。理想配比≈两阶段的**总耗时之比**:如果一批流量里 prefill 总共要花的卡时是 decode 的 3 倍,那就配 ~3 个 prefill 实例对 1 个 decode 实例(3P1D),让两条线**同时跑满、互不积压**。

反直觉:**配比不是常数**。早高峰可能长文档摘要多(prefill 重),晚上闲聊多(decode 重),固定配比总有一头空转、另一头排队 → 必须随负载实时漂移。

## 例子

按 ISL:OSL 选配比(直观账):

- **短 prompt、长输出**(如开放式聊天,ISL=256、OSL=1024):decode 是瓶颈 → 偏 decode,如 **1P3D**(1 个 prefill 喂 3 个 decode)。
- **长 prompt、短输出**(如长文档抽取,ISL=8k、OSL=64):prefill 是瓶颈 → 偏 prefill,如 **3P1D**。
- 独立扩缩例子:监控发现 decode 队列堆积、TPOT 逼近 SLO,而 prefill 卡利用率仅 40% → 只**加 decode 实例**(或从 prefill 借),把 2P2D 调到 1P3D,无需买整套新机。
- 配比估算:设单条请求 prefill 耗 $t_p=200$ ms、decode 耗 $t_d=1000$ ms(逐 token 累计),则稳态下 prefill:decode 实例数 ≈ $t_p:t_d=1:5$ → 约 1P5D 才能让两端吞吐匹配。

## 原理

稳态下要让两池吞吐匹配(无一端积压),实例数比应等于单请求在两阶段的耗时比:

$$
\frac{n_p}{n_d} \approx \frac{\bar t_{\text{prefill}}}{\bar t_{\text{decode}}}
= \frac{L_{\text{in}} / r_p}{(L_{\text{out}}-1)\cdot \text{TPOT}}
$$

$L_{\text{in}}$ 越大(长 prompt)→ $\bar t_{\text{prefill}}$ 越大 → $n_p/n_d$ 越大(偏 prefill);$L_{\text{out}}$ 越大(长输出)→ 偏 decode。由于 $L_{\text{in}}, L_{\text{out}}$ 随流量变,最优配比是个**动态量**;闭环控制器持续测两池的队列/利用率,调 $(n_p,n_d)$ 使:

$$
\max\ \text{Goodput}\quad\text{s.t.}\quad n_p+n_d\le G,\ \text{两池均不积压}
$$

## 代码

xPyD 的声明 + 按负载动态调比:

```python
# ❌ 固定配比:写死 1P1D,流量形态一变就一端空转、一端排队
# cluster = deploy(prefill=1, decode=1)

# ✅ xPyD + 独立扩缩:按 ISL:OSL 与队列动态调
def target_ratio(isl, osl, tpot, r_prefill):
    t_p = isl / r_prefill               # prefill 耗时 ∝ 输入长度
    t_d = (osl - 1) * tpot              # decode 耗时 ∝ 输出长度
    return t_p / t_d                    # n_p : n_d 目标比

def autoscale(metrics, G):
    # metrics: 两池队列长度/利用率;G: GPU 预算
    if metrics.decode_queue > THRESH and metrics.prefill_util < 0.5:
        scale_decode(+1)                # ✅ 只加瓶颈侧,不整机扩
    if metrics.prefill_queue > THRESH and metrics.decode_util < 0.5:
        scale_prefill(+1)
# Dynamo SLO Planner / DOPD 即此类闭环:按 TTFT/ITL 与负载实时调 (n_p, n_d)
```

`❌` 固定 1P1D 在偏态流量下必有一池空转、另一池积压,goodput 掉;`✅` 按 ISL:OSL 估目标比、按队列独立扩缩瓶颈侧,两池同时跑满。

## 面试高频

- **Q:xPyD 是什么?怎么定 x 和 y?** x 个 prefill 实例配 y 个 decode 实例;比例 ≈ 单请求 prefill 耗时 : decode 耗时,由流量的 ISL:OSL 决定——长 prompt 偏 prefill(如 3P1D),长输出偏 decode(如 1P3D)。
- **Q:为什么 PD 分离能独立扩缩?物理隔离后,prefill 与 decode 是两类独立实例,谁是瓶颈就只扩谁,不必像聚合系统那样整机扩,省卡。
- **Q:配比为什么必须动态?** 流量的输入/输出长度比随时间变(白天长文档、晚上闲聊),固定配比总有一端空转;闭环控制器按队列/SLO 实时调。
- **Q:配比失衡会怎样?** 偏少的一侧成瓶颈、队列积压,其 SLO(TTFT 或 TPOT)超标,goodput 下降;另一侧空转浪费卡。
- **Q:谁来做动态配比?** Dynamo 的 **SLO Planner**、研究系统 **DOPD** 等,基于负载监控做闭环扩缩。

## 关键事实

- **xPyD** = x 个 prefill 实例 + y 个 decode 实例;**1P1D** 是最小单元;比例由流量 **ISL:OSL** 与各阶段耗时决定,随负载**动态漂移**。
- 独立扩缩是 PD 分离相对聚合的关键运维优势:**按瓶颈侧扩**而非整机扩,提升卡利用率与 goodput。
- 动态配比由控制器闭环实现:**Dynamo SLO Planner**(2025)按 TTFT/ITL 调;研究系统如 **DOPD** 按实时负载求最优 P/D 比。vLLM 社区的 P2P-NCCL xPyD 实现(2025)受 Dynamo 启发支持动态加 worker。
