[[046 优先级、公平性与饥饿|优先级与饥饿]]处理 [[044 调度器设计：waiting、running 队列与抢占|调度器]]里"谁先服务"这道策略题。最简单的 **FCFS**(先到先服务)最公平,但长请求堵在队头会造成**队头阻塞**;**优先级调度**让 SLO 严的请求(P0 交互)插队保延迟,代价是**饥饿(starvation)**——高优先源源不断时,低优先(P2 批量/长请求)可能永远排不上。这里的根本张力是**公平性 vs 吞吐 vs SLO**:最短优先(SJF)吞吐最优但饿死长请求,FCFS 公平但损吞吐,SLO 分级 + 老化(aging)是工程折中。理解它,才能在多租户、混合负载下不让某类请求被牺牲。

## 直觉

把调度想成**医院急诊分诊**:

- **FCFS(挂号顺序看)**:绝对公平,但一个复杂病例(长请求)占住医生半天,后面急症(短交互请求)干等——**队头阻塞**,平均等待变长。
- **优先级(按病情轻重)**:心梗(P0,严 SLO)立刻进,擦伤(P2)往后排——救了急症,但如果急症一个接一个来,擦伤的病人**永远轮不到 = 饥饿**。
- **老化(aging)**:擦伤等久了,分诊级别**自动往上提**,等到一定时间必被叫号——给低优先一个"保底翻身"机会,防饿死。
- **配额/加权公平**:给每个科室(优先级/租户)分配保底接诊份额,高优先抢不走全部资源。

工程现实:既要保 P0 的 SLO(优先级),又不能让 P2 饿死(老化),还要护住总吞吐(配额)——三者同时拿捏。

## 例子

三级队列,GPU 每步能服务的容量有限:
- **P0 交互**:严 TTFT SLO(< 500 ms),持续每秒来 8 个。
- **P1 标准**:松一些。
- **P2 批量**:含一个超长请求 g(输出 8000 token),SLO 极松。

**纯优先级调度**:P0 持续涌入 → 调度器永远先满足 P0 → P1 偶尔、**P2 的 g 永远排不到**(饥饿)。运行一小时,g 仍未开始 → 用户投诉"任务卡死"。

**加老化**:g 在 waiting 里每等 1 分钟,有效优先级 +1。等了 10 分钟后它的有效优先级超过新来的 P0 → 被强制准入。代价:那一刻 P0 的 TTFT 略升,但 g 不再饿死。

**加配额**:规定 P2 至少占 10% 的 running 槽位。则 g 从一开始就有保底份额,稳步推进,P0 仍占 90% 保 SLO。

数字感受:无老化时 g 的等待 = ∞(饿死);加老化后 g 最坏等待 = 老化阈值(如 10 min);加 10% 配额后 g 持续推进、端到端可预测。**这就是公平性机制把"无界等待"变成"有界等待"的价值**。

## 原理

设请求 $i$ 基础优先级 $p_i$、已等待时间 $w_i$,**有效优先级**(带老化):

$$
p_i^\text{eff}(t) = p_i + \alpha\, w_i(t)
$$

$\alpha$ 是老化速率:$\alpha=0$ 退化为纯优先级(可能饿死),$\alpha\to\infty$ 退化为近似 FCFS(老化主导)。调度每步选 $p_i^\text{eff}$ 最高者。**最坏等待有界**:

$$
w_i^\max \le \frac{p_\max - p_i}{\alpha}
$$

即任何请求等到老化把它顶过最高优先级就必被服务——这是防饥饿的数学保证。

**公平性 vs 吞吐**:平均响应时间 $\bar W$ 在 **SJF(最短优先)** 下最小(经典排队论结论),但 SJF 下长请求 $w$ 无界(饿死);**FCFS** 下 $\bar W$ 较大但无饥饿。SLO 分级是按 deadline 紧迫度(类 EDF)排序,在两者间取折中:既压低紧急请求延迟,又用配额/老化给非紧急请求保底。

抢占时的公平:victim 选择应优先抢**低优先级**请求(而非长请求),否则长请求被反复抢占恢复、永远跑不完——这把 [[045 抢占：重计算 vs swap|抢占]]与公平性耦合在一起。

## 代码

带老化的优先级调度,避免饥饿:

```python
import time

def effective_priority(req, alpha=1.0):
    wait = time.time() - req.arrival_time
    # ✅ 有效优先级 = 基础优先级 + 老化项；等越久越优先，防饿死
    return req.base_priority + alpha * wait

def pick_next(waiting, alpha=1.0):
    # 选有效优先级最高者（数值越大越先）
    return max(waiting, key=lambda r: effective_priority(r, alpha))

def pick_victim(running):
    # ✅ 抢占时优先踢「低优先级 + 最晚到达」者，保护高优先与老请求
    return min(running, key=lambda r: (r.base_priority, -r.arrival_time))

# ❌ 反模式 1：纯优先级、无老化
def pick_next_naive(waiting):
    return max(waiting, key=lambda r: r.base_priority)  # 高优先持续涌入 → 低优先饿死

# ❌ 反模式 2：抢占总挑「最大 KV 占用」者
def pick_victim_naive(running):
    return max(running, key=lambda r: r.kv_blocks)      # 长请求被反复抢占，永不完成
```

`❌` 纯优先级无老化会饿死低优先;`❌` 抢占总挑最大 KV(往往是长请求)会让长请求反复被踢、永不完成。`✅` 用老化给等待请求保底、抢占优先挑低优先级而非长请求。生产中还会叠加**配额/加权公平**给每级保底份额。

## 面试高频

- **Q:FCFS 有什么问题?** 公平且无饥饿,但长请求堵在队头造成队头阻塞,短请求/交互请求被迫等待,平均延迟和尾延迟变差。
- **Q:优先级调度引入什么新问题,怎么解?** 饥饿——高优先源源不断时低优先永不被服务;解法是老化(等待越久优先级越升,把最坏等待变有界)+ 配额(每级保底份额)。
- **Q:为什么不直接用 SJF(最短优先)?它吞吐最优。** SJF 平均响应时间最优,但长请求被无限期推迟、饿死;且 LLM 输出长度事先未知,真 SJF 不可实现(只能用 prompt 长度等近似)。
- **Q:多租户/SLO 分级怎么调度?** 按 deadline 紧迫度分级(类 EDF/SLO-aware),P0 交互保严 TTFT,P2 批量松 SLO;用老化 + 配额防低优先饿死,同时护吞吐。
- **Q:抢占和公平性怎么耦合?** victim 应优先选低优先级而非最大 KV;若总抢长请求,长请求反复恢复永不完成,等于另一种饥饿。

## 关键事实

- 调度策略谱系:**FCFS**(公平、防饥饿、损吞吐)↔ **SJF/最短优先**(吞吐与平均延迟最优、饿死长请求)↔ **优先级/SLO 分级**(保紧急 SLO、需防饥饿)。
- **饥饿**的标准缓解手段是**老化(aging)**:有效优先级随等待时间上升,使最坏等待有界 $\le (p_\max-p_i)/\alpha$;再叠加**配额/加权公平**给每级保底。
- vLLM 默认 **FCFS**,并提供 **priority 调度**(`scheduling_policy="priority"`)按用户指定优先级排序;生产多租户系统(截至 2025)普遍在其上加 SLO 分级与公平/配额逻辑以平衡延迟、吞吐与饥饿。
