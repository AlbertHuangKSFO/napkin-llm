[[055 聚合还是解耦：决策与权衡|聚合还是解耦]]是部署时的根本抉择:把 [[013 Prefill 阶段：计算受限|Prefill]] 与 [[014 Decode 阶段：访存受限|Decode]] 放同一张卡(**聚合 aggregated**,靠 [[LLM/106 chunked prefill 与 prefill、decode 解耦|chunked prefill]] 缓解干扰),还是物理分到不同 GPU 池([[048 为何分离 prefill 与 decode|解耦 disaggregated]])?答案不是非此即彼:**高负载 + 严 SLO + 规模足够大**时解耦赢(各自调优、独立扩缩,[[018 TTFT、TPOT、ITL 与 goodput：服务指标定义|goodput]] 高);**小规模 / 低负载**时聚合赢(无 [[053 KV 传输：NIXL、点对点与带宽|KV 传输]]、运维简单、更省卡)。前沿是统一视角(如 TaiChi),按负载在两者间平滑切换——聚合与解耦是连续谱,不是开关。

## 直觉

解耦像开两家专门店(只做早餐 / 只做晚餐),效率高但要两套房租、两班人马、还得在两店间运货(KV);聚合像一家全天候小馆,一个厨房全包,省事省租金,但高峰时备餐和上菜互相挤。**小店开两家专门店是亏的**——租金和运货成本压垮那点效率收益;**大连锁拆专门店才划算**——规模摊薄固定成本,专业分工的收益才显出来。

决策的本质是权衡:解耦买来"无干扰 + 独立扩缩",代价是"KV 跨节点传输 + 高速网 + 调度复杂度";规模和 SLO 严苛度决定这笔买卖是否划算。

## 例子

几个典型判断:

- **小团队自部署一个 13B,QPS 个位数,SLO 宽松**:聚合(单卡 + chunked prefill)。解耦要的 RDMA 网、双池运维不值得,KV 传输开销反而拖累。
- **大规模在线服务,QPS 上千,P90 TTFT<200ms 且 TPOT<50ms**:解耦。两阶段干扰在严 SLO 下无法忍,DistServe 类分离把 goodput 抬数倍。
- **长上下文为主(文档/代码,prompt 数千 token)**:解耦 + KVCache 复用([[051 Mooncake：KVCache 中心解耦架构|Mooncake]] 式)收益最大,prefill 重且可跨请求复用。
- **流量在闲忙间剧烈波动**:统一框架(TaiChi 思路),闲时退化为聚合省卡,忙时切解耦扛 SLO,避免为峰值常驻两套池。

## 原理

设解耦相对聚合的净收益:

$$
\Delta = \underbrace{\big(\text{goodput}_{\text{disagg}} - \text{goodput}_{\text{agg}}\big)}_{\text{无干扰}+\text{独立扩缩,随负载/SLO 严苛度}\uparrow}
\;-\;
\underbrace{\big(\text{cost}_{\text{transfer}} + \text{cost}_{\text{ops}} + \text{cost}_{\text{net}}\big)}_{\text{KV 传输}+\text{运维}+\text{高速网,近似固定}}
$$

第一项随**负载、SLO 严苛度、规模**增长(干扰在高负载/严 SLO 下代价剧增,规模摊薄分工成本);第二项近似固定门槛(一旦上了 RDMA 网与双池)。于是存在一个**临界规模/负载**:低于它 $\Delta<0$ 选聚合,高于它 $\Delta>0$ 选解耦。统一框架让系统沿负载在 $\Delta$ 的两侧自动切换,而非静态二选一。

## 代码

按负载/SLO 选模式的决策逻辑(可作为统一框架的策略层):

```python
# ❌ 教条:无脑全上解耦,小流量时被 KV 传输 + 双池运维拖累、更贵
# mode = "disaggregated"   # always

# ✅ 按规模/负载/SLO 决策,甚至随负载动态切换
def choose_mode(qps, slo_tight, isl, fast_network, scale_gpus):
    if not fast_network or scale_gpus < THRESH_GPUS:
        return "aggregated"            # 无高速网或规模小 → 聚合 + chunked prefill
    if slo_tight and (qps > THRESH_QPS or isl > THRESH_LONG):
        return "disaggregated"         # ✅ 高负载/长 prompt/严 SLO → 解耦
    return "aggregated"

# TaiChi 式统一:闲时聚合省卡,忙时切解耦扛 SLO(连续谱,非开关)
mode = choose_mode(qps=current_qps(), slo_tight=True, isl=avg_isl(),
                   fast_network=has_rdma(), scale_gpus=cluster_size())
```

`❌` 不看规模一律解耦,小流量时 KV 传输与双池运维成本压过收益、反而更贵更复杂;`✅` 按高速网/规模/负载/SLO 决策,理想下随负载在聚合↔解耦间平滑切换。

## 面试高频

- **Q:什么时候该解耦,什么时候该聚合?** 高负载 + 严 SLO + 规模够大 → 解耦(无干扰、独立扩缩、goodput 高);小规模 / 低负载 / 无高速网 → 聚合(无 KV 传输、运维简单、更省卡)。
- **Q:解耦相对聚合的代价有哪些?** KV 跨节点传输 + 必需的高速网(RDMA/IB)+ 配比/路由/扩缩的调度复杂度;小流量时这些固定成本压过收益。
- **Q:chunked prefill 和 PD 解耦是竞争还是互补?** chunked prefill 是聚合下的"软隔离"(切片插队缓解干扰),PD 解耦是"硬隔离"(物理分卡);聚合系统常用 chunked prefill,达不到要求再上解耦。
- **Q:有没有不二选一的方案?** 有,统一视角(如 TaiChi):同框架按负载在聚合/解耦间平滑切换,把二者看作连续谱,闲时省卡、忙时扛 SLO。
- **Q:一句话决策依据?** 看解耦净收益 $\Delta$ = (goodput 提升) − (KV 传输 + 运维 + 高速网成本);存在临界规模/负载,过了才解耦。

## 关键事实

- 决策不是开关而是**连续谱**:聚合(+chunked prefill)↔ 解耦,临界点由**规模、负载、SLO 严苛度、是否有高速网**共同决定。
- 解耦的固定门槛:**KV 传输 + RDMA/IB 高速网 + 双池运维复杂度**;低于临界规模时聚合更划算。
- 代表系统沿谱分布:聚合(vLLM/SGLang 默认 + chunked prefill)→ 解耦(DistServe、Splitwise、[[051 Mooncake：KVCache 中心解耦架构|Mooncake]]、[[052 NVIDIA Dynamo：分布式推理框架与 SLO Planner|Dynamo]])→ 统一切换(TaiChi 类,2024–2025)。大规模严 SLO 部署(含 [[062 Wide-EP：DeepSeek、Kimi 在 H100、H200 上的部署|Wide-EP]])几乎都走解耦。
