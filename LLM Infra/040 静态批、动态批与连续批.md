[[040 静态批、动态批与连续批|批处理三态]]是 LLM 服务吞吐的第一道分水岭:**调度粒度**决定一切。**静态批(static batch)**和**动态批(dynamic batch)**都在**请求级(request-level)** 调度——一批请求一起进、一起出;而[[LLM/105 连续批处理 continuous batching|连续批处理]](continuous / in-flight batching)在**迭代级(iteration-level)** 调度——每跑完一步(一次 forward)就重组 batch,谁完成谁立即退、谁在等立即补。正因 [[014 Decode 阶段：访存受限|decode]] 是逐 token 的长尾过程(不同请求输出长度差几十倍),请求级批处理会被最长的请求拖住产生**木桶效应**,而连续批把空槽即时回填,吞吐常比静态批高数倍。这是 Orca(Yu 2022)奠定、如今 [[LLM/105 连续批处理 continuous batching|vLLM]]/TensorRT-LLM/TGI 全员标配的技术。

## 直觉

把 GPU 想成一辆**班车**。

- **静态批**:发车前必须坐满固定人数,且**所有人到同一终点站才许下车**,中途想下的也得陪到底。短途乘客(短输出请求)白白陪长途乘客(长输出)空耗——这就是木桶效应,座位利用率低。
- **动态批**:发车更灵活(凑够一小窗口的乘客就发,不死等满员),但**还是到站才整车清空**——缓解了"等满员"的排队延迟,没解决"陪到底"的空耗。
- **连续批**:这是辆**随时上下客的公交**——每到一站(每一步)就让到站的人下车,候车的人立即补上空座,车永远满载且没人陪跑。

关键洞察:LLM 请求的"行程长度"(输出 token 数)**事先不知道且差异巨大**,所以"到站才清空整车"的代价极高,必须做到迭代级的随上随下。

## 例子

4 个请求,输出长度 5 / 5 / 5 / 100 token,decode 每步 40 ms,batch 容量 4:

**静态批**:整批必须等最长的 100 步全部跑完才释放 → 总耗时 = 100 步 × 40 ms = 4000 ms。其中三个短请求第 5 步就该完成,却被迫陪跑 95 步。
- 有效产出 = 5+5+5+100 = 115 token;空转格 = 4×100 − 115 = 285 格。
- **批利用率 = 115 / 400 ≈ 29%**(GPU 七成在空转长尾)。

**连续批**:三个短请求第 5 步完成即退,空出的 3 个槽位立即被等待队列里的新请求填上。100 步里这 3 个槽位可以接力服务 ~60 个短请求。
- 同样 4000 ms 内,有效产出从 115 token 涨到 ~400+ token(槽位几乎全程满载)。
- **批利用率 ≈ 95%+**,吞吐相对静态批 **×3 以上**。

这就是 Orca 报告"至多 36.9× 吞吐"的来源——长尾越严重、请求长度越参差,连续批赢得越多。

## 原理

设 batch 内请求输出长度 $\{L_i\}$,decode 每步耗时 $t$。

**静态批**完成整批耗时由最长者决定:

$$
T_\text{static} = t \cdot \max_i L_i,\qquad \text{批利用率} = \frac{\sum_i L_i}{B\cdot \max_i L_i}
$$

长度方差越大,$\sum_i L_i \ll B\max_i L_i$,利用率越低 → 木桶效应。

**连续批**让每个槽位独立流转,稳态下吞吐逼近"槽位满载":

$$
\text{吞吐}_\text{cont} \approx \frac{B}{t}\ (\text{tok/s}),\qquad \text{加速比} \approx \frac{B\cdot\max_i L_i}{\sum_i L_i}
$$

加速比正是静态批利用率的倒数——静态批越浪费,连续批提升越大。注意连续批不改变单步算力(同样受 [[017 吞吐与延迟：根本性张力|吞吐延迟张力]]约束),它消除的是**调度层面的空转**,而非物理瓶颈。

## 代码

对比请求级(静态)与迭代级(连续)调度循环:

```python
# ❌ 静态批:请求级调度，整批等齐才释放
def static_batch_serve(batch):
    while any(not r.done for r in batch):
        step(batch)                 # 一步：全 batch 各前进一个 token
    return batch                    # 短请求被迫陪跑到 max(L_i)，槽位空转

# ✅ 连续批：迭代级调度，每步重组 running batch
def continuous_serve(waiting, max_batch):
    running = []
    while waiting or running:
        # 1) 退出本步完成的请求，释放其 KV 块
        running = [r for r in running if not r.done]
        # 2) 用 waiting 里的新请求补满空槽（受 KV 预算约束）
        while waiting and len(running) < max_batch and kv_can_fit(waiting[0]):
            running.append(waiting.pop(0))   # 新请求先 prefill 再转 decode
        # 3) 跑一步：prefill 与 decode 可混在同一 batch
        step(running)
```

`❌` 静态批的 `while any(...)` 把整批锁死到最长请求,短请求完成后槽位空转;`✅` 连续批每步先剔除已完成、再从 waiting 回填,槽位几乎全程满载——这就是迭代级调度的全部魔法。详见 [[041 连续批处理：迭代级调度内幕|迭代级调度内幕]]。

## 面试高频

- **Q:静态批和连续批最本质的区别是什么?** 调度粒度:静态批是请求级(一批一起进一起出),连续批是迭代级(每步重组,完成即退、新请求即补)。区别不在算力,在能否回收空槽。
- **Q:动态批(dynamic batching)算连续批吗?** 不算。动态批(如 Triton 的 dynamic batcher)只是放宽"凑批"时机减少等待,仍是请求级、整批同退;它解决吞不满的问题,不解决长尾陪跑。
- **Q:连续批为什么能比静态批快几倍而不是几成?** 因为 LLM 输出长度方差极大且事先未知,静态批的利用率可能只有 20–30%,连续批把它拉到 90%+,加速比 = 利用率倒数。
- **Q:连续批有什么代价?** 每步重组有调度开销;prefill 与 decode 混批时,长 prefill 会拉长同批 decode 的 ITL(见 [[043 prefill、decode 干扰与 stall|PD 干扰]]),由此引出 [[042 chunked prefill：切块融合|chunked prefill]] 与 [[048 为何分离 prefill 与 decode|PD 分离]]。

## 关键事实

- **连续批处理**由 Orca(Yu et al., OSDI 2022)首次系统化提出,核心是 **iteration-level scheduling + selective batching**,报告至多 **36.9× 吞吐**提升。
- 截至 2025,连续批是所有主流推理框架(**vLLM、TensorRT-LLM、TGI、SGLang**)的默认且不可关闭的基础调度策略。
- 静态批利用率 ≈ $\sum L_i /(B\max L_i)$,在输出长度高方差的真实流量下常仅 20–40%;连续批把它拉到 90%+,这正是数倍吞吐差的来源。
