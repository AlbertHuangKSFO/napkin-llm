[[118 函数调用与工具服务化]] 是**把 [[Agent/15 Function Calling 工具调用|Function Calling]] 落到推理服务侧的那一层**:请求带上 `tools` 的 JSON schema,引擎用 [[114 结构化输出：guided decoding 与 XGrammar|guided decoding]] **约束生成**出合法的工具调用,再用**模型特定的 tool parser** 把文本里的调用抽成结构化对象,交给上层并行执行;工具结果作为 tool message **回灌**继续生成。一句话:**结构化输出 + 解析 + 并行工具 + 回灌循环**。引擎(vLLM/SGLang)只负责「生成合法调用 + 解析」;真正的执行、编排、记忆、重试在 Agent 层——这正是 [[Agent/03 Agent 核心循环|Agent 核心循环]] 的服务侧承载。它和 [[Agent/16 工具设计与工具层|工具层]] 对接,底层复用 [[114 结构化输出：guided decoding 与 XGrammar|XGrammar/Outlines]] 的约束解码基础设施。

## 直觉类比
模型像个**只会说话、不会动手的专家**:你问它「上海多少度」,它不能自己查,只能**写一张工单**——「请调用 get_weather,参数 {city:'上海'}」。工具服务化就是把这套「写工单」标准化:① 给专家一份**可用工具清单**(schema);② 用约束解码逼它把工单写成**结构合法**的格式(绝不写错字段);③ 前台(parser)把工单**读出来**;④ 后勤(Agent runtime)**并行去办**这些工单(还要管超时、办砸了重试);⑤ 把办事结果**塞回**给专家,让它据此说出最终答案或再开下一张工单。

## 小数字例子
一次「订机票并查天气」请求,带 2 个工具 schema:
- `tool_choice="required"`:引擎用约束解码**保证**产出至少一个合法调用,而非自由文本。
- 模型一次响应里给出 **2 个 tool_calls**(`search_flight(...)`、`get_weather(...)`)→ Agent runtime **并行**下发,墙钟时延 ≈ max(两者) 而非 sum。
- 其中 `get_weather` 超时(>3s):指数退避**重试 2 次**仍失败 → 返回结构化错误,模型读到后改口「天气服务暂不可用」而非崩溃。回灌的 tool message 长这样(`content` 里塞一段错误 JSON,而非抛异常):

```json
{
  "role": "tool",
  "tool_call_id": "call_get_weather_01",
  "name": "get_weather",
  "content": "{\"ok\": false, \"error\": \"timeout\", \"detail\": \"upstream 3s exceeded; retried 2x\", \"retryable\": true}"
}
```

模型把这段读进上下文,据 `"ok": false` 与 `"error"` 字段决定降级措辞或换路,而不会因为缺结果而幻觉编造天气。成功时则是 `{"ok": true, "city": "上海", "temp_c": 19}`——成功/失败**同一套结构**,模型只需看 `ok` 分支。
- 两个结果作为 tool message 追加 → 模型据此生成最终回答,或发起下一轮调用(多步循环)。

## 原理:约束生成 + 解析 + 回灌
设工具集 $\mathcal{T}=\{t_1,\dots,t_n\}$,每个工具有参数 schema $S_i$。服务侧把工具调用建模为「输出必须匹配某个 $S_i$」的**结构化输出**问题——直接复用 guided decoding:每步对 logits 加文法掩码,使输出必为合法 `{"name": t_i, "arguments": <匹配 S_i 的 JSON>}`。生成完由 **tool parser** $\Pi$ 抽取结构化调用:

$$
\text{calls} = \Pi(\text{output}),\quad
\Pi:\ \text{文本}\ \to\ \{(t_i,\ \text{args}_i)\}_{i}
$$

$\Pi$ 是**模型相关**的:不同模型用不同标记(Qwen3 用 XML 标签、GLM-4 用专用 marker、Llama/Mistral 各有格式)——这带来 **M×N 的解析器维护成本**(M 模型 × N 引擎)。执行后,结果 $r_i$ 作为 tool message 回灌,进入下一轮自回归:

$$
\text{context}_{k+1} = \text{context}_k \,\Vert\, \{(t_i,\text{args}_i,r_i)\}\ \Rightarrow\ \text{续写或再调用}
$$

## 配置 / 代码
```python
# vLLM:OpenAI 兼容工具调用(服务侧)
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="-")
# 启动:vllm serve Qwen/Qwen2.5-7B-Instruct \
#        --enable-auto-tool-choice --tool-call-parser hermes

tools = [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询城市天气",
    "parameters": {
      "type": "object",
      "properties": {"city": {"type": "string"}},
      "required": ["city"],
    },
  },
}]

resp = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user", "content": "上海现在天气怎么样?"}],
    tools=tools,
    tool_choice="required",          # 约束解码:必产出合法调用
    parallel_tool_calls=True,        # 允许一次多个工具
)
# resp.choices[0].message.tool_calls → 已被 parser 解析成结构化对象
# 上层:并行执行 → 把结果以 role="tool" 追加 → 再请求一次续写
```

```text
❌ 不约束、靠 prompt 求模型「输出 JSON 调用」→ 偶发格式错/多说话/漏字段 → parser 抽不出 → 整轮 Agent 卡死;且工具无超时重试,一个慢工具拖垮全链
✅ tool_choice=required + guided decoding 保证合法调用;模型专属 parser 稳定抽取;并行工具 + 超时/退避重试/结构化错误兜底 → 健壮可观测
```

## 面试高频
- **服务侧的 function calling 本质是什么?** 一个结构化输出问题——「输出必须匹配某工具参数 schema」;`tool_choice=required` 时引擎用 guided decoding 强制产出合法调用。
- **tool parser 为什么是模型相关的?** 不同模型把调用编码成不同标记(XML 标签 / 专用 marker / JSON);引擎需为每个模型实现专属 parser,带来 M×N 维护成本。
- **并行工具调用怎么提速?** 一次响应可含多个 tool_calls,Agent runtime 并发执行,墙钟时延 ≈ max 而非 sum;需注意工具间无依赖才能并行。
- **服务侧要哪些工程护栏?** 工具超时、指数退避重试、幂等性、限流、把失败**结构化**返回给模型(让它能读懂并重试或换路),以及可观测(trace 每次调用)。
- **引擎和 Agent 层分工?** 引擎:生成合法调用 + 解析;Agent 层:执行、编排、记忆、多步循环、错误恢复。引擎不执行工具。
- **它和结构化输出什么关系?** 共用同一套约束解码基础设施([[114 结构化输出：guided decoding 与 XGrammar|XGrammar/Outlines]]);工具调用是结构化输出的一个特例(schema = 工具参数)。

## 关键事实
- vLLM 工具调用(2025):`--enable-auto-tool-choice` + `--tool-call-parser`;内置 parser 含 hermes、llama3_json、mistral 等;`tool_choice="required"` 用结构化输出保证合法调用;支持 `parallel_tool_calls`。
- 不同模型格式不一:Qwen3 用 XML 标签、GLM-4 用专用 marker;社区称之为 grammar/parser 维护的 **M×N 问题**。
- SGLang(2025)同样内置 tool schema / tool call parser / function call parser;二者「结构化输出 + 工具调用联用」仍在持续完善(vLLM #16313 等)。
- 底层复用约束解码:见 [[114 结构化输出：guided decoding 与 XGrammar|guided decoding]];工具调用 = schema 为工具参数的结构化输出。
