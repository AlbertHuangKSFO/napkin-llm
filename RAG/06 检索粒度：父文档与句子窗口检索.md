[[06 检索粒度：父文档与句子窗口检索|检索粒度：父文档与句子窗口检索]] 的核心洞见只有一句:**用来 embedding 检索的粒度,和喂给 LLM 的粒度,不必相同——更不该相同。** 用**小块**做精准召回(向量不被稀释,相似度突出),命中后**扩展成大块**(父段/句子窗口)给 LLM 足够上下文。这套打法叫 **small-to-big**,是对 [[03 分块策略 Chunking|分块策略 Chunking]] 那个「块大召回不准、块小丢上下文」根本矛盾的最直接破解。

## 本质:解耦「embed 粒度」与「喂 LLM 粒度」

回顾 [[03 分块策略 Chunking|分块策略 Chunking]] 的死结:
- **块切大** → 一个向量糊了多个主题,query 来了相似度不突出 → **召回不准**。
- **块切小** → embedding 精准、召回准,但一个 chunk 装不下完整论述 → **LLM 拿到的上下文不够,答不好**。

Naive RAG 用**同一个粒度**同时干两件事(既拿去 embed 又拿去喂 LLM),于是被迫在两个相反方向上妥协,怎么切都不对。

small-to-big 的破法是**把这两件事拆开**:
1. **检索阶段**:索引并 embedding **小块**(句子 / 小段)——保证召回精准。
2. **喂给阶段**:小块命中后,不直接把小块喂 LLM,而是顺着一个**映射**找到它对应的**大块**(父段落 / 周围句子窗口),把大块喂给 LLM——保证上下文充足。

「small」负责找得准,「big」负责答得好,各取所长。这是 [[02 Naive RAG 与失败模式|Naive RAG 与失败模式]] 里「召回到了却答不全」的标准解药。

## 机制:三种 small-to-big 实现

### 1. Parent-Document Retriever(父文档检索,LangChain)
建库时把每个文档先切成**大父块**(如整段、整节),再把每个父块切成**小子块**;**只对子块做 embedding 入库**,同时记录「子块 → 父块」的归属。检索时拿 query 匹配**子块**(精准),命中后**返回该子块所属的整个父块**给 LLM。一句话:**embed 子块,返回父块**。

### 2. Sentence-Window Retrieval(句子窗口检索,LlamaIndex)
更细的粒度:把文档切成**单句**,**每句单独 embedding** 入库,同时给每句存好它在原文的位置。检索时匹配到**最相关的那一句**(极精准),返回时把这句**前后各扩展 N 句**(window,如 ±3 句)拼成一个窗口喂给 LLM。命中点是句,喂出去的是「句 + 邻句上下文」。一句话:**embed 单句,返回句±N 句窗口**。

### 3. Auto-merging Retriever(自动合并检索,LlamaIndex)
建一棵**层次块树**(大块→中块→小叶块,父子关系明确)。检索时对**叶子小块**做匹配。关键规则:**如果同一个父块下,被命中的子块数量超过阈值**(比如一个父块有 4 个子块,命中了 3 个),就认为「这个父块整体高度相关」,**自动把这些子块合并、返回父块**;否则只返回命中的子块。它在「返回小块还是大块」之间**自适应**——零散命中给小块,密集命中给大块,避免无脑总返回大块带来的冗余。一句话:**命中够密就向上合并成父块**。

三者关系:Parent-Document 是固定的「子→父」两层;Sentence-Window 是「句→邻句窗口」;Auto-merging 是「多层树 + 按命中密度自适应向上合并」,最灵活。

## 可跑最小代码

```python
# small-to-big 骨架:embed 小块,命中后映射回大块(父块/窗口)喂 LLM
def build_index(doc, embed):
    parents = split_into_paragraphs(doc)          # 大父块
    child2parent, child_vecs, children = {}, [], []
    for p in parents:
        for c in split_into_sentences(p):         # 每个父块再切小子块
            child2parent[c] = p                    # 记住 子块→父块 映射
            children.append(c)
            child_vecs.append(embed(c))            # 只 embed 小子块(精准)
    return children, child_vecs, child2parent

def retrieve_small_to_big(query, children, child_vecs, child2parent, embed, k=3):
    qv = embed(query)
    hits = top_k(qv, child_vecs, k)                # ① 用小块召回(准)
    # ② 命中小块 → 映射回父块,去重(避免同一父块重复喂)
    parents = []
    for i in hits:
        p = child2parent[children[i]]
        if p not in parents: parents.append(p)
    return parents                                 # ③ 返回大块给 LLM(上下文足)

# 句子窗口变体:不映射到父块,而是返回命中句 ±N 句
def sentence_window(hit_idx, sentences, n=3):
    lo, hi = max(0, hit_idx-n), min(len(sentences), hit_idx+n+1)
    return "".join(sentences[lo:hi])
# 生产直接用:LangChain ParentDocumentRetriever / LlamaIndex SentenceWindow & AutoMerging
```

## 对比表

| 方法 | embed 粒度 | 返回粒度 | 扩展逻辑 | 框架 |
|---|---|---|---|---|
| Parent-Document | 子块 | 父块 | 固定:子→父 | LangChain |
| Sentence-Window | 单句 | 命中句 ±N 句 | 固定窗口 | LlamaIndex |
| Auto-merging | 叶子块 | 子块 或 父块 | 自适应:命中够密→合并父块 | LlamaIndex |

## 何时用 / 坑

**几乎总该用**:small-to-big 是 RAG 默认就该上的优化,成本低、收益大。只要你的内容里「完整论述跨多句」(技术文档、论文、合同),就该解耦粒度。

**坑**:
- **窗口/父块开太大 → 上下文膨胀**:返回的大块太长,token 暴涨且 lost-in-the-middle 反而拉低生成质量。窗口 N、父块大小要调,配合 [[20 上下文工程|上下文工程]]。
- **同父块重复返回**:多个命中子块映射到同一父块,不去重就把同段喂好几遍,浪费 token。务必按父块去重(代码里那步)。
- **Auto-merging 阈值难调**:合并阈值太低 → 总是返回大块(退化成块切大);太高 → 从不合并(退化成块切小)。要按语料调。
- **元数据/映射要在建库时存好**:「子块→父块」「句→位置」的映射是这套打法的命脉,切块时([[03 分块策略 Chunking|分块策略 Chunking]])就要把它和 metadata 一起落库,后补很麻烦。
- **和 rerank 顺序**:通常先用小块召回 top-k,可以**在小块层面先 [[10 重排序 Reranking|重排序 Reranking]]**(对小块精排更准),再映射成大块喂 LLM;别先扩成大块再 rerank(大块稀释了 rerank 信号)。
- **和进阶索引互补**:small-to-big 在「返回时」补上下文;[[05 进阶索引：Contextual Retrieval、RAPTOR、Late Chunking|进阶索引：Contextual Retrieval、RAPTOR、Late Chunking]] 在「建库时」给小块本身补上下文。两者正交,可叠加(如 Late Chunking 给子块更好的 embedding,再 small-to-big 返回父块)。

## 工业界实践

small-to-big 是生产 RAG 里**性价比最高、几乎默认就该开**的优化之一,因为它不需要额外模型、不增加在线 LLM 调用,只是在建库时多存一份「子块→父块」映射、在检索后多做一步映射扩展。

### 主流框架的现成实现

| 框架 | 组件 | 形态 |
|---|---|---|
| LlamaIndex | `SentenceWindowNodeParser` + `MetadataReplacementPostProcessor` | 单句 embedding,命中后用 metadata 里存的 window 文本替换喂 LLM |
| LlamaIndex | `HierarchicalNodeParser` + `AutoMergingRetriever` | 多层块树,命中够密自动向上合并父块 |
| LangChain | `ParentDocumentRetriever`(配 `InMemoryStore`/Redis 存父块) | 子块入向量库,父块入 docstore,命中子块返回父块 |
| Haystack | `AutoMergingRetriever` + `HierarchicalDocumentSplitter` | 同 LlamaIndex 思路 |

**LlamaIndex 的句子窗口最常被生产采用**,因为它只在 metadata 里塞一段 window 文本,检索后用 `MetadataReplacementPostProcessor` 一键替换,工程量极小且对向量库无侵入(向量库里只存单句向量)。

### 典型生产架构与存储

```
建库:文档 → 切父块(段/节)→ 各父块切子块(句/小段)
      子块 → embedding → 向量库(只存子块向量 + 子块上携带的 parent_id metadata)
      父块 → docstore(KV: parent_id → 父块全文,放 Redis / Postgres / 向量库的 payload)
检索:query → 召回 top-k 子块 → 取 parent_id 去重 → 从 docstore 拉父块 → 喂 LLM
```

关键工程决策:**子块→父块映射存哪**。两种主流做法——① 把 `parent_id` 直接存进子块的 metadata(向量库 payload),父块全文另存 KV 库;② 父块全文直接冗余进每个子块的 metadata(省一次 KV 查询,但存储翻倍)。中小规模常用 ②,大规模用 ① 避免冗余。

### 规模化、延迟与成本

- **延迟**:在线几乎零额外开销——多的只是「子块命中后查 docstore 取父块」这一步 KV 查询(毫秒级)。比 [[07 查询变换 Query Transformation|查询变换 Query Transformation]] / Contextual Retrieval 那种要加在线 LLM 调用的方案轻得多。
- **token 成本**:返回父块比返回子块喂给 LLM 的 token 更多,父块越大越贵,且过大会触发 lost-in-the-middle。所以**父块/窗口大小是核心调参**,不是越大越好。
- **去重是省钱关键**:多个命中子块常映射到同一父块,不去重就把同一段喂好几遍,既浪费 token 又稀释信号。

### 与重排的顺序(生产强约定)

**先在小块层 [[10 重排序 Reranking|重排序 Reranking]],再映射成父块喂 LLM**。理由:reranker(cross-encoder)对短、聚焦的文本判别更准;先扩成大父块再 rerank,大块里混入的无关句会稀释 rerank 信号。生产链路通常是:混合召回子块([[08 混合检索 Hybrid Search|混合检索 Hybrid Search]])→ 子块层 rerank → 取 top-n 子块 → 映射去重成父块 → 喂 LLM。

### 评估与可观测

- 用 [[18 RAG 评估|RAG 评估]] 的 Ragas **context recall / context precision** 对比「直接返回命中块」vs「small-to-big 返回父块」:通常 context recall 升(上下文更全)、答案 faithfulness 升,但要盯 context precision 别因父块带入无关句而掉太多——这正是父块大小的权衡点。
- 可观测重点:记录「平均每 query 返回的父块数 / 去重率 / 父块平均 token」,以及 Auto-merging 的「合并触发率」,用来反推阈值和窗口大小是否合理。

## 面试高频

**Q1:为什么 embedding 的粒度和喂给 LLM 的粒度要分开?**
标准答:因为它们的最优粒度相反。embedding 要**小块**才精准(向量不被多主题稀释,召回准);LLM 要**大块**才能拿到完整论述(答得全)。Naive RAG 用同一粒度同时干两件事,被迫在两个相反方向妥协,怎么切都不对。small-to-big 把两件事解耦:小块召回、大块生成,各取所长。
- 追问「具体怎么实现?」→ 建库时存「子块→父块」映射,只 embed 子块,命中后顺映射返回父块。

**Q2:Parent-Document、Sentence-Window、Auto-merging 三者区别?**
标准答:Parent-Document 是固定两层「子块 embed → 返回整个父块」(LangChain);Sentence-Window 是「单句 embed → 返回命中句 ±N 句窗口」,更细(LlamaIndex);Auto-merging 是「多层块树 + 按命中密度自适应」——同一父块下命中的子块数超阈值就向上合并返回父块,否则只返回子块(LlamaIndex),最灵活。
- 追问「Auto-merging 阈值怎么影响行为?」→ 太低总返回大块(退化成块切大),太高从不合并(退化成块切小),要按语料调。

**Q3(顺序陷阱):small-to-big 和 reranking 谁先谁后?**
标准答:**先在小块层 rerank,再扩成父块**。因为 cross-encoder 对短聚焦文本判别更准,先扩大块会稀释 rerank 信号。这是高频陷阱题,答反了说明没理解 rerank 信号的来源。

**Q4:small-to-big 和进阶索引(Contextual Retrieval / Late Chunking)是什么关系?**
标准答:**正交互补**。small-to-big 在「返回时」补上下文(扩成父块),进阶索引在「建库/embedding 时」给小块本身补上下文。可叠加,例如 Late Chunking 给子块更好的 embedding,再 small-to-big 返回父块。陷阱:别答成「二选一」或「谁取代谁」。

**Q5:这套方案有什么坑/什么时候不该用?**
标准答:坑包括——父块/窗口开太大致上下文膨胀 + lost-in-the-middle;同父块不去重浪费 token;映射/元数据没在建库时存好后补麻烦;Auto-merging 阈值难调。基本「内容里完整论述跨多句」就该用;但纯 FAQ、每条答案就一两句、块本身已自足的语料,收益很小。

## 知识拓展

- **small-to-big 的本质是「解耦索引单元与上下文单元」**,这个思想在传统 IR 里早有雏形:passage retrieval 用小段召回、再回溯到所属文档做相关性判断。RAG 把「回溯」从「整篇文档」收窄到「父段/句窗」,在召回精度和上下文充足间取了更好的折中。
- **与上下文工程的连接**:返回的父块大小直接影响进入 LLM 窗口的 token 分布,过大触发 **lost-in-the-middle**(Liu et al. 2023,《Lost in the Middle》,长上下文中间位置信息易被忽略)。所以父块/窗口大小不只是检索参数,也是上下文工程参数,要和 prompt 内证据的排布一起调。
- **Late Chunking × small-to-big 的最佳组合**:Late Chunking([[05 进阶索引：Contextual Retrieval、RAPTOR、Late Chunking|进阶索引]])让子块向量天然携带全文上下文(召回更准),small-to-big 再把命中子块扩成父块(生成更全)——一个治召回、一个治生成,叠加是当前小而强的实践组合。
- **边界与反模式**:① 父块无脑设大是反模式(token 暴涨 + lost-in-the-middle),应按「一个完整论述单元」定父块边界;② 不去重直接喂是反模式;③ 先扩父块再 rerank 是反模式(稀释信号);④ 把映射元数据留到检索时再补是反模式(建库时 [[03 分块策略 Chunking|分块策略 Chunking]] 阶段就要落库)。
- **延伸**:Auto-merging 的「命中密度→自适应粒度」思路,与 [[12 Self-RAG、CRAG 与 Adaptive RAG|Adaptive RAG]] 的「按需调整检索行为」是同一种自适应哲学,只是前者作用在「返回粒度」、后者作用在「是否/如何检索」。

## 关键事实

- 核心:**解耦 embed 粒度与喂 LLM 粒度**——小块精准召回,命中后扩成大块喂足上下文(small-to-big)。
- 直接破解 [[03 分块策略 Chunking|分块策略 Chunking]] 的「块大召回不准 / 块小丢上下文」矛盾,治 [[02 Naive RAG 与失败模式|Naive RAG 与失败模式]] 的「召回到了答不全」。
- 三实现:**Parent-Document**(子块 embed→返回父块,LangChain)、**Sentence-Window**(单句 embed→返回句±N 句,LlamaIndex)、**Auto-merging**(叶块 embed→命中够密则合并返回父块,自适应,LlamaIndex)。
- 命脉是建库时存好「子块→父块 / 句→位置」的**映射 + 元数据**。
- 配套:返回的大块别太大(防上下文膨胀),按父块**去重**,rerank 放在**小块层**做。
- 与 [[05 进阶索引：Contextual Retrieval、RAPTOR、Late Chunking|进阶索引：Contextual Retrieval、RAPTOR、Late Chunking]] 正交:前者「返回时」扩上下文,后者「建库时」给块补上下文,可叠加。
