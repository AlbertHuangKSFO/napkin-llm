[[06 检索粒度：父文档与句子窗口检索|检索粒度：父文档与句子窗口检索]] 是一套**条件化的粒度策略**：用于检索的 child 与交给 LLM 的上下文单元可以不同；是否拆开、扩到多大、在哪一层排序，都要由语料、预算和评测决定。它为 [[03 分块策略 Chunking|分块策略 Chunking]] 的「检索定位」与「回答所需上下文」提供了可比较的两阶段设计，而不是放之四海皆准的默认开关。

## 本质：解耦「索引单元」与「上下文单元」

同一块文本同时承担检索和生成上下文时，容易遇到张力：块变长后可能混入多个主题，块变短后又可能缺少完成答案所需的限定、因果或例外。small-to-big 把它拆为两步：

1. **检索阶段**：以 child（句子或小段）做候选匹配；前提是 child 自身仍保留问题与答案相连的关键信号，不能只剩「它」「该方法」一类失去指代的碎片。
2. **上下文阶段**：命中 child 后，依据 `parent_id` 或句子位置扩成父段、父文档或邻句窗口，再在窗口预算内组装给 LLM 的证据。

这不是「小块一定更准、大块一定更好」的定律。若答案本来就是一条自足 FAQ，直接以该条检索和回答即可；若答案需跨句解释，且 child 仍能表达可检索的命题，父文档或句窗扩展才值得纳入 [[18 RAG 评估|RAG 评估]] 的候选方案。

像查字典：先用精确词条定位，读时再看相邻释义和例句；但若一条词条本身已经给出完整答案，就不必强行翻回整页。关键是让定位单元和阅读单元各自服务问题，而非规定二者必须不同。

## 机制：三种从 child 回到上下文的实现

### 1. Parent-Document Retriever（父文档检索，LangChain Classic）

建库时先确定父单元（整篇、节或段），再将它切为 child；向量库索引 child，同时在 child metadata 保存 `parent_id`，并在 docstore 保存父单元。查询命中 child 后，按 `parent_id` 取回父单元并去重。这就是「**索引 child，返回 parent**」。`LangChain Classic` 的官方 `ParentDocumentRetriever` 参考保留了这种较小块检索、再按 parent ID 返回较大文档的机制；它是 legacy/向后兼容参考，而非当前 LangChain Python 的默认入口。实现时应按已安装的包与版本选择 API，不要把该类名写进版本无关的业务逻辑。

### 2. Sentence-Window Retrieval（句子窗口检索，LlamaIndex）

把文档切成单句，将每个句子作为检索节点，并把相邻句窗口存入 metadata；命中后以窗口文本替换命中句，发送给 LLM。LlamaIndex 的 `SentenceWindowNodeParser` 说明：窗口 metadata 不参与 embedding 或直接展示给 LLM，需在后处理阶段以 metadata-replacement postprocessor 替换。已安装的 LlamaIndex 版本决定该后处理器的确切导入/符号，应以对应版本的句窗指南和 Metadata Replacement API 为准，而不把某个类名当作通用写法。因此它适合「单句能被问题定位、答案却依赖邻句」的文档，而窗口半径应由预算与离线集选择，不应从框架示例直接抄成业务默认值。

### 3. Auto-merging Retriever（自动合并检索，LlamaIndex）

先建立带父子关系的层次节点。检索从叶节点开始；当某父节点下的命中 child 占比超过配置阈值时，检索器用父节点替换这些 child，否则保留较细节点。LlamaIndex 官方实现的判断量就是「当前命中的子节点数 ÷ 父节点子节点总数」，故阈值与层次边界都应被当作待评估变量，而不是通用常数。

三者分别对应固定的 child→parent 映射、命中句→邻句窗口、命中密度驱动的层次合并。它们都要求建库阶段保留父子关系；差别在扩展边界如何决定。

## 小数字手算：去重与句窗边界

父段 $P_A$ 切成 $[c_0,c_1,c_2,c_3]$。一次 child 检索命中 $c_1,c_2$，则扩展前有 2 个候选，映射后为：

$$
\operatorname{unique}(\{parent(c_1),parent(c_2)\})
=\operatorname{unique}(\{P_A,P_A\})=\{P_A\}
$$

最终只交付 1 个父段，避免同一证据重复占用窗口。

句子序列为 $[s_0,s_1,s_2,s_3,s_4]$，命中 $s_2$，选窗口半径 $n=1$。先算边界：$lo=\max(0,2-1)=1$，$hi=\min(5,2+1+1)=4$；再按左闭右开区间取 $[s_1,s_2,s_3]$。结果是 3 句，而非越界地取到 $s_0$ 或 $s_4$。这里的 $n=1$ 仅为手算例子；真实值由问题集、token 预算和答案完整度共同决定。

## 公式：候选、扩展与比较

令 child 集合为 $C$，相关性函数为 $s(q,c)$，则 child-first 的第一步是：

$$
H_C(q)=\operatorname{TopK}_{c\in C}s(q,c)
$$

父文档扩展只改变交付给 LLM 的上下文集合：

$$
E_P(q)=\operatorname{unique}\{parent(c)\mid c\in H_C(q)\}
$$

句窗的上下文为：

$$
W(i,n)=[s_{\max(0,i-n)},\ldots,s_{\min(m,i+n+1)-1}]
$$

但 $H_C\rightarrow E_P$ 不应预设胜过父单元直接排序 $H_P(q)$。在同一离线问题集上，对两条链路比较证据召回、证据精度、答案支持度、窗口 token、检索/重排延迟与 ACL 拒绝率；在约束下选择表现更好的链路，而不是只比较单一相似度分数。

## 可跑最小代码

下面的纯 Python 例子用字符重叠代替 embedding，因而不依赖安装包；它同时跑父单元优先与 child 优先，并演示 child→parent 去重和句窗。生产中只需将 `score`/`rank` 换成 embedding 或 [[10 重排序 Reranking|重排序 Reranking]]，保留同样的 ID、版本与权限检查。

```python
# python3 granularity_demo.py
def tokens(text):
    return set(text.replace("。", "").replace("，", ""))


def score(query, text):
    return len(tokens(query) & tokens(text))


def rank(query, items):
    return sorted(items, key=lambda x: (-score(query, x["text"]), x["id"]))


def build_children(parents):
    children = []
    for parent_id, parent in parents.items():
        for pos, sentence in enumerate(s for s in parent.split("。") if s):
            children.append({"id": f"{parent_id}-{pos}", "parent_id": parent_id,
                             "pos": pos, "text": sentence})
    return children


def parent_first(query, parents, k):
    items = [{"id": pid, "text": text} for pid, text in parents.items()]
    return rank(query, items)[:k]


def child_first_then_expand(query, children, parents, child_k):
    child_hits = rank(query, children)[:child_k]
    parent_ids = list(dict.fromkeys(hit["parent_id"] for hit in child_hits))
    return [{"id": pid, "text": parents[pid]} for pid in parent_ids]


def sentence_window(sentences, hit_idx, radius):
    lo = max(0, hit_idx - radius)
    hi = min(len(sentences), hit_idx + radius + 1)
    return "。".join(sentences[lo:hi])


parents = {
    "p1": "父文档检索先匹配子块。命中后返回父块。",
    "p2": "句子窗口保留命中句。邻句提供必要上下文。",
}
children = build_children(parents)
query = "父块检索"

# ❌ 只把命中 child 原样交给 LLM：可能遗漏限定句
# ✅ 以 child 匹配后，按 parent_id 去重并扩展；同时保留 parent-first 基线
print("parent-first:", [x["id"] for x in parent_first(query, parents, k=1)])
print("child-first:", [x["id"] for x in child_first_then_expand(query, children, parents, child_k=2)])
print("sentence-window:", sentence_window(["s0", "s1", "s2", "s3", "s4"], 2, 1))

assert child_first_then_expand(query, children, parents, child_k=2)[0]["id"] == "p1"
assert sentence_window(["s0", "s1", "s2", "s3", "s4"], 2, 1) == "s1。s2。s3"
```

## 选型卡：先列变量，再做离线对比

| 变量 | 影响与检查 | 可比较的候选 |
|---|---|---|
| 文档结构 | 标题、段落、表格、代码或引用是否构成稳定的父边界；句子切分是否会破坏指代 | 直接父段、child→parent、句窗、层次合并 |
| 答案粒度 | 金标答案是自足原子事实，还是必须连同定义、条件、例外才能成立 | 自足答案保留短块基线；跨句论证比较扩展上下文 |
| 窗口预算 | 给检索证据分到多少 token，及其在 prompt 中的位置 | 改父边界/句窗半径/返回父数，并记录实际 token |
| 召回与重排成本 | child 数量、候选数、重排器的输入长度与在线时延预算 | 父先排、子先排、子排后扩展；比较同等预算下的指标 |
| ACL/版本继承 | child、parent 是否共享同一 `doc_id`、`version_id`、`acl_id`；父文档取回会否越权或串版 | 在两层都过滤/复核权限，版本切换后重建映射，再评测授权与拒绝查询 |
| 离线评测 | 是否有带证据标注且覆盖真实问法、短答与跨句答的问题集 | 对每条链路记录证据召回/精度、答案支持度、token、延迟和失败样例 |

## 重排、权限与评测：没有固定顺序

**先比较父先排与子先排。** 建立相同 query 集、同一窗口预算的两条基线：一条先对父单元做召回/重排，另一条先对 child 做召回/重排再去重扩展。不要从「短文本更聚焦」直接推导出后者必胜。

只有当两个条件同时满足时，才值得优先尝试「child 层重排→扩展父文档」：① child 本身保留足以判断答案相关性的信号；② reranker 的上下文长度或成本使其更适合处理短候选。若 child 丢失主语、限定条件或跨句推理链，或 reranker 需要看完整命题，父先排/父层重排可能更合适。两者均应以离线结果决定。

权限与版本不能只挂在父文档上：child 索引记录至少应带 `doc_id`、`parent_id`、`version_id`、`acl_id`；检索 child 前施加访问过滤，取 parent 时再次校验同一版本与授权。父文档更新、拆分或撤权后，要同步失效或重建其 child 映射，避免旧 child 指向新 parent、或从已撤权父文档扩展出内容。

评测除了答案分数，还应人工抽查「命中的 child 是否含答案信号」「扩展是否补齐而非冲淡证据」「父先排与子先排各自错在哪」。这能把窗口、层次阈值和 rerank 顺序变成可复现的选择，而非经验口号。

## 工程边界与常见坑

- **父块或窗口过大**：会挤占其它证据的预算，并可能让关键信息落在长上下文中不利的位置；从满足一个完整论述所需的最小上下文开始，在离线集中逐步比较。
- **同父块重复交付**：多个 child 命中同一 parent 时必须去重；但去重后也要保留触发 child 与分数，以便诊断为何扩展该父块。
- **child 过短而失去答案信号**：这是 child-first 失败的常见根因。不要仅因句子短就索引；可改为更完整的小段、附带标题/实体，或选父先排。
- **把 Auto-merging 阈值当默认参数**：阈值受层次切分、top-k 和问题分布共同影响，需在评测集上连同父边界一起调。
- **只在一层做 ACL 或版本处理**：可能导致召回虽被过滤、扩展时却拿到不该看的父文档；两层都要校验。
- **只测 child-first**：small-to-big 是候选架构，不是基线替代品；保留父先排比较才能发现扩展收益是否抵得过额外 token 和重排成本。
- **与进阶索引的关系**：[[05 进阶索引：Contextual Retrieval、RAPTOR、Late Chunking|进阶索引：Contextual Retrieval、RAPTOR、Late Chunking]] 可以改变 child 表征，small-to-big 改变返回上下文；能否叠加、在哪个数据集获益，同样由离线评测确认。

## 面试高频

**Q1：为什么检索粒度和喂给 LLM 的粒度可以分开？**

答：二者服务的目标不同：前者用于定位，后者用于支持答案。若短 child 保留足够答案信号、但完整答案跨句，先检索 child 再扩展 parent/窗口是合理候选；若答案自足或 child 丢失语义，则不必拆开。要用父先排与子先排的离线对比决定。

**Q2：Parent-Document、Sentence-Window、Auto-merging 的区别？**

答：Parent-Document 是固定 child→parent 映射；Sentence-Window 是命中句→相邻句窗口；Auto-merging 依据同一父节点下的命中占比向上合并。三者共同依赖可追溯的父子 metadata，但扩展边界不同。

**Q3：small-to-big 和 reranking 谁先？**

答：没有固定顺序。先在同一问题集比较父先排与子先排；当 child 自身能表达答案信号、reranker 又受上下文长度/成本限制时，可尝试 child 层 rerank 后再扩展。若排序判断需要完整命题，则父层排序可能更好。

**Q4：这套方案如何保证权限与版本正确？**

答：child 与 parent 共享并校验 `doc_id`、`version_id`、`acl_id`；检索阶段过滤 child，扩展阶段再次授权并验证版本一致。更新、撤权或重切块时同步重建映射，不能让旧 child 静默指向新父内容。

**Q5：什么时候不该把它当默认方案？**

答：自足短 FAQ、没有稳定父边界、child 易丢失关键指代、或窗口预算很紧时，直接父单元可能更合适。最终看文档结构、答案粒度、预算、重排成本、ACL/版本约束和离线评测，而不是套固定参数。

## 知识拓展

- **small-to-big 的抽象**是「索引单元」与「上下文单元」可以不同。它既可用于段落，也可用于句窗和层次节点；关键不在块大小的绝对值，而在映射能否保留证据关系。
- **与上下文工程的连接**：父块/窗口大小决定证据在 prompt 中的 token 分布。Liu et al.（2023）讨论了长上下文中信息位置对使用效果的影响，因此窗口预算也应和证据排序一起评测。
- **可观测性**：为每次回答保留 `query_id`、命中 child、扩展 parent、去重前后数量、版本、授权决定、窗口 token 与最终答案引用；这样才能定位失败发生在检索、扩展、重排还是权限过滤。
- **反模式**：无条件扩成全文、只存文本不存 parent/version/ACL、将框架示例参数当生产默认、或只证明 child-first 有效而不保留父先排基线，都会让粒度选择失去可证伪性。

## 关键事实

- `LangChain Classic` 官方 `ParentDocumentRetriever` 参考的机制是检索较小 child，再按 parent ID 返回较大 parent；parent 可以是原始文档，也可以是较大的切块。它用于 legacy/向后兼容参考，不是当前 LangChain Python 的默认入口；实际 API 以已安装版本为准。
- LlamaIndex 官方 [SentenceWindowNodeParser 指南](https://developers.llamaindex.ai/python/framework/module_guides/loading/node_parsers/modules/) 说明其将文档切为单句，并在 metadata 存相邻句窗口；配套的 [Metadata Replacement API](https://developers.llamaindex.ai/python/framework-api-reference/postprocessor/metadata_replacement/) 描述替换后处理。已安装的 LlamaIndex 版本决定确切的导入/符号，应查该版本文档，不应断言某一个类名对所有版本通用。
- LlamaIndex 官方 `AutoMergingRetriever` 从向量库取回 child，再尝试向父上下文合并；合并依据命中 child 在父节点所有 child 中的占比与配置阈值。
- 这些实现描述的是机制，不推出「小块必优」「先子后父必优」或任何通用窗口/阈值；实际策略必须比较父先排与子先排，并纳入答案信号、预算、ACL/版本和离线评测。
