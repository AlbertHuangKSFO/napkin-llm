[[17 检索数据治理|检索数据治理]] 的本质是:把 RAG 当成一个 **知识运行时(knowledge runtime)** 来运维——检索质量门、来源验证、访问控制、审计轨迹**一体化编排**,而不是「灌一次向量库就完事」。类比 Kubernetes 管应用:给每一个检索操作都嵌入质量门、来源校验与治理钩子。

它管的是 [[01 什么是 RAG|什么是 RAG]] 从 demo 走向企业生产时冒出来的全部「非算法」问题:权限从哪继承、答案能不能溯源、数据能不能出境、索引怎么增量更新、PII 怎么脱敏、新鲜度怎么保证。这些不解决,RAG 在企业里根本上不了线。

## 本质:RAG 是运行时,不是一次性管线

新手把 RAG 看成「文档 → 切块 → embed → 入库」的**一次性 ETL**。生产视角恰相反:RAG 是一个**长期运行、持续摄入、持续被查询**的系统,数据在变、权限在变、模型在变。所以要按「运行时」治理:

> 类比 **Kubernetes**:它不是「部署一次应用」,而是持续编排——健康检查、滚动更新、资源配额、审计。**knowledge runtime** 同理,给每个检索操作嵌入**质量门 / 来源校验 / 治理**,持续保障。

更接地气的类比:RAG 不是「图书馆开馆那天把书一次性上架就完事」,而是**图书馆的日常运营**——新书要审来源、登记编目(摄入治理),违禁书下架、过期版本换新(增量索引/新鲜度),借阅按读者证权限放行(ACL),还要留借阅流水备查(审计)。ETL 一次性 vs 持续运营的差别,就是「装修完就锁门」和「天天开门、上下架、查证、记流水」的差别。

四件事被编排成一条治理链:**摄入治理 → 检索质量门 → 生成 → 审计/血缘**,外加贯穿全链的横切关注点(权限继承、SSO、数据驻留、provenance)。

## 机制

### 分层治理链

**① 摄入治理(ingestion)**
- **来源验证**:只摄入可信来源,给文档打来源标签(供后续溯源与 [[16 检索安全与访问控制|检索安全与访问控制]] 的投毒防护)。
- **PII 脱敏**:摄入时识别并脱敏个人信息(姓名、身份证、手机号),避免敏感数据进向量库后被检索泄露。
- **权限继承**:从源系统(SharePoint / Confluence / DB)继承 ACL 元数据,**别重造权限**。
- **增量索引 + 数据新鲜度**:源文档更新时只重索引变化部分,保证检索到的是最新版而非陈旧快照。

**② 检索质量门(retrieval quality gate)**
- **相关性阈值**:召回相似度低于阈值的直接丢,宁可少召回也不引噪音(防 [[02 Naive RAG 与失败模式|Naive RAG 与失败模式]]）。
- **重排序**:用 [[10 重排序 Reranking|重排序 Reranking]] 把真正相关的顶上来。
- **ACL 过滤**:按用户权限过滤([[16 检索安全与访问控制|检索安全与访问控制]] 的预过滤)。
- **来源可信度校验**:低可信来源降权或拦截。

**③ 生成**
- **引用归因 + 忠实度校验**:每句答案标来源、校验是否真有据(见 [[11 生成层：引用归因与忠实度|生成层：引用归因与忠实度]]);**越权信息拦截**兜底。

**④ 审计 / 血缘(audit / provenance)**
- **审计日志**:记录谁、何时、查了什么、召回了哪些文档、生成了什么——合规与事后追责必备。
- **血缘 / provenance**:每条答案可**溯源到具体文档**(甚至具体 chunk),回答「这个结论从哪来」。

### 横切关注点(贯穿四层)
- **权限继承**:源系统权限实时同步到检索层。
- **SSO / 身份联邦**:接企业单点登录,统一身份。
- **数据驻留(data residency)**:数据按法规留在指定地域(EU 数据不出欧盟),向量库、索引、日志都要满足——GDPR 等合规硬要求。
- **provenance / 血缘**:全链路可追溯。

### 运维面(keep it healthy）
- **增量索引**:源变更触发局部重建,而非全量重跑。
- **数据新鲜度**:监控「索引落后源多久」,设新鲜度 SLA。
- **index 失效与重建**:embedding 模型升级、schema 变更时,旧索引失效需重建——这是个昂贵且要灰度的运维动作。
- **PII 脱敏**:不只摄入时做,变更时也要复查。

这套东西本质是 [[13 Modular RAG|Modular RAG]] 的「治理模块化」落地,也与 [[38 Agent 评估与可观测性|Agent 评估与可观测性]] 共享同一套可观测性基础设施(日志、追踪、指标)。

## 可跑最小代码

把治理链串成一个可运维的检索运行时:

```python
class KnowledgeRuntime:
    """RAG 即 knowledge runtime:每个操作都过质量门 + 治理钩子"""

    def ingest(self, doc, source):
        verify_source(source)                       # 来源验证(防投毒)
        doc = redact_pii(doc)                        # PII 脱敏
        acl = inherit_permissions(source, doc)       # 从源系统继承权限,别重造
        chunks = chunk(doc)
        for c in chunks:
            c.meta.update(source=source, acl=acl,
                          residency=source.region,   # 数据驻留标记
                          provenance=doc.id)          # 血缘:可溯源
        self.index.upsert_incremental(chunks)        # 增量索引,非全量重跑
        self.freshness.touch(source)                 # 更新数据新鲜度

    def retrieve(self, query, user):
        cands = self.index.search(query, filter=acl_for(user, residency=user.region))  # ACL+驻留预过滤
        cands = [c for c in cands if c.score >= REL_THRESHOLD]   # 质量门:相关性阈值
        cands = rerank(query, cands)                              # 质量门:重排序
        self.audit.log(user, query, [c.provenance for c in cands])  # 审计 + 血缘留痕
        return cands

    def rebuild_if_stale(self, source):
        if self.freshness.lag(source) > SLA or self.embed_model.changed():
            self.index.reindex(source)               # index 失效 → 灰度重建
```

要点:① 治理**嵌进每个操作**(摄入打 ACL/驻留/血缘,检索过质量门 + 审计),不是事后加;② **增量索引**而非全量;③ embedding 模型变更触发 **index 重建**;④ 全链 **provenance** 让答案可溯源。

## 对比表

| 维度 | demo 式 RAG | 企业级知识运行时 |
|---|---|---|
| 心智模型 | 一次性 ETL | **持续运行的 runtime** |
| 权限 | 无 / 重造 | 从源系统继承 + SSO |
| 数据合规 | 不管 | 数据驻留 + PII 脱敏 |
| 可溯源 | 无 | provenance / 血缘到 chunk |
| 审计 | 无 | 全量审计日志 |
| 索引更新 | 全量重跑 | 增量 + 新鲜度 SLA |
| 质量保障 | 召回啥用啥 | 相关性阈值 + 重排序质量门 |

## 何时用 / 坑

**该上(必须)**:任何企业生产 RAG——多用户、有合规要求、数据敏感、源数据持续变化。原型阶段可简化,但**上线前**这套治理是门槛。

**坑**:
- **把它当一次性 ETL**:灌完库不管,数据陈旧、权限错乱、无法审计。必须按 runtime 持续运维。
- **重造权限**:不继承源系统,自己维护一套 ACL,迟早与源端不一致导致泄露。
- **忽视数据驻留**:把 EU 数据 embed 到美区向量库,直接违规。索引、日志、缓存都要落在合规地域。
- **无血缘**:答案出错却查不到来自哪份文档,既无法纠错也无法追责。provenance 要在摄入时就埋好。
- **index 重建被低估**:换 embedding 模型 = 全库重 embed,贵且需灰度,常被规划遗漏。
- **新鲜度无 SLA**:用户拿到的是上周的数据却不自知。要监控并暴露「索引落后多久」。
- **治理与检索两张皮**:治理逻辑游离在检索之外,容易被绕过。要**嵌进检索路径**,像质量门一样强制通过。

## 关键事实

- 本质 = 把 RAG 当 **knowledge runtime**:检索质量门、来源验证、访问控制、审计**一体化编排**(类比 Kubernetes 给每个操作嵌治理)。
- 治理链分层:**摄入治理 → 检索质量门 → 生成 → 审计/血缘**;横切:**权限继承、SSO、数据驻留、provenance**。
- 企业标配:从源系统**继承权限**(别重造)、审计日志、SSO、**数据驻留(data residency)**、血缘可溯源。
- 运维面:**增量索引、数据新鲜度 SLA、index 失效与重建(换 embedding 模型即触发)、PII 脱敏**。
- 心智转变:RAG 不是**一次性 ETL**,是**持续运行的系统**;治理要**嵌进检索路径**而非事后补。
- 与 [[16 检索安全与访问控制|检索安全与访问控制]](访问控制 + 投毒防护)、[[13 Modular RAG|Modular RAG]](模块化编排)、[[38 Agent 评估与可观测性|Agent 评估与可观测性]](共享可观测性)同体系。

## 工业界实践

治理在工业界不是「写一篇规范」,而是落成**可强制、可审计、可回滚**的工程设施。下面按生产关注点展开。

**1)权限继承的两种落地范式**
- **查询时 ACL 过滤(post/pre-filter)**:检索时把用户身份转成元数据过滤条件(`filter: {acl: {$in: user.groups}}`),向量库侧裁掉无权片段。优点是权限实时;缺点是高基数 ACL 会拖慢 ANN(过滤后候选不足要回捞)。**Qdrant/Weaviate/Milvus** 都支持带 payload 过滤的 HNSW,但**过滤选择性极低时(每个 chunk 一套 ACL)性能崩**,需做分区索引或 RBAC 收敛到「角色」而非「个人」。
- **摄入时分库/分 namespace**:按租户/密级建独立 collection,查询只打有权的库。隔离强、性能稳,但库爆炸、跨库检索难。**金融/政企**多用这条(物理隔离更易过审计)。
- 主流产品里 **Glean、Microsoft Copilot(Graph connectors)、Vectara、Elastic** 都把「**实时继承源系统 ACL**」当卖点——SharePoint/Confluence/Jira 权限变更要分钟级同步到检索层,否则离职员工仍能搜到机密。这就是 [[16 检索安全与访问控制|检索安全与访问控制]] 里「权限要在检索层强制」的产品化。

**2)增量索引与 CDC(变更数据捕获)**
- 生产不可能每天全量重 embed(贵且慢)。标准做法是 **CDC**:监听源系统的 webhook/binlog/修改时间戳,只对 diff 的文档重新解析→分块→embed→upsert,并删除已下线文档的旧向量(**软删/tombstone**,避免检索到已删内容)。
- **去重**靠内容哈希(`content_hash`)做幂等 upsert,防止同一文档多版本污染召回。
- 工具:**Airbyte / Fivetran / 自研 connector** 拉数据,**Kafka/Pulsar** 做变更流,**Temporal/Airflow** 编排重索引工作流。

**3)数据新鲜度与 index 重建(reindex)**
- **新鲜度 SLA** 暴露成指标:`freshness_lag = now - last_indexed_at`,超阈值告警。
- **换 embedding 模型 = 全库重 embed**,这是治理里最被低估的成本项。生产做法是**蓝绿索引**:新模型在影子索引上重建,A/B 比对召回质量达标后原子切换,失败可秒级回滚。**别原地覆盖**——重建期间在线流量还在查旧索引。

**4)PII 脱敏与合规**
- 摄入管线插一道 **PII 检测**(`Microsoft Presidio`、`spaCy + 正则`、云厂商 DLP)做识别+脱敏/打标;敏感字段可**加密存储 + 检索时按权限解密**。
- **数据驻留**:EU 数据的向量、索引、日志、LLM 调用都要落在 EU region(GDPR);很多企业因此在每个 region 部署一套独立 RAG 栈。注意**LLM API 出境**也算数据流出——用 Azure OpenAI 的 region 部署或自托管模型规避。

**5)可观测与血缘**
- 全链 **tracing**:用 **OpenTelemetry + Phoenix/LangSmith/Langfuse** 把「query → 召回的 chunk id → rerank 分 → prompt → 答案 → 引用」串成一条 trace,每条答案能反查到具体 chunk 和源文档版本。这与 [[38 Agent 评估与可观测性|Agent 评估与可观测性]] 共享同一套 tracing 基建。
- **审计日志**单独落冷存储(合规要求保留数年),记录 who/when/what/retrieved/generated。

**6)治理即代码(伪配置)**
```yaml
# 把治理规则声明化,管线启动时强制加载(而非散在代码里)
ingestion:
  source_allowlist: [confluence, sharepoint]   # 来源验证
  pii_redaction: { engine: presidio, mode: replace }
  permission: { inherit_from_source: true }     # 继承,别重造
  residency: eu-central-1                        # 数据驻留
retrieval:
  quality_gate: { min_score: 0.32, reranker: cohere-rerank-v3 }
  acl_filter: required                           # 缺 ACL 直接拒绝检索
  audit: { sink: s3://audit-cold, retention_days: 2555 }
reindex:
  trigger: [embed_model_change, schema_change]
  strategy: blue_green                           # 蓝绿,可回滚
  freshness_sla_minutes: 30
```

**常见踩坑**:① ACL 高基数导致过滤后召回不足;② tombstone 漏做,删了的文档还能被搜到(合规事故);③ reindex 原地覆盖导致重建期间召回质量塌方;④ 把 LLM API 出境当成「不算数据流出」而违规;⑤ 治理逻辑游离在检索路径外,被某个新接入的查询入口绕过。

## 面试高频

**Q1:RAG 上生产,除了召回质量,你还要解决哪些「非算法」问题?**
标准答:权限继承(从源系统继承 ACL,别重造)、数据驻留与 PII 合规、增量索引与新鲜度、index 重建(换 embedding 模型)、引用归因与血缘、审计日志、可观测。一句话:把 RAG 当**持续运行的 knowledge runtime**,不是一次性 ETL。
- 追问「权限怎么实时同步?」→ CDC/webhook 监听源系统 ACL 变更,分钟级同步;高基数 ACL 用角色收敛或分 namespace 物理隔离。
- 陷阱:有人答「在 prompt 里告诉 LLM 别泄露无权内容」——**错**,LLM 兜底不可信,必须在**检索层预过滤**,无权片段根本不进上下文。

**Q2:换了 embedding 模型,线上索引怎么办?**
标准答:全库重 embed,用**蓝绿/影子索引**重建,A/B 验证召回不退化后原子切换,可回滚;别原地覆盖。这是被低估的大成本项,要做容量规划和灰度。
- 追问「重建期间在线查询查哪个?」→ 查旧索引,新索引在影子里建好再切。

**Q3:用户删了一份机密文档,RAG 还能搜到吗?怎么防?**
标准答:必须做 **tombstone/软删**——CDC 捕获删除事件,立即从向量库删除对应 chunk 的向量并打删除标记;否则旧向量残留会被检索到,属合规事故。
- 陷阱:只更新源系统、不同步向量库,是最常见的数据泄露路径。

**Q4:GDPR / 数据驻留对 RAG 架构有什么约束?**
标准答:EU 数据的向量库、索引、审计日志、**以及 LLM 调用**都要在 EU region;LLM API 跨境也算数据出境,要用 region 化的托管端点或自托管模型。常见做法是按 region 部署独立 RAG 栈。

**Q5:怎么保证「答案可溯源」?**
标准答:摄入时给每个 chunk 埋 `provenance`(源文档 id + 版本 + 页码/偏移),检索和生成全程透传,引用归因(见 [[11 生成层：引用归因与忠实度|生成层：引用归因与忠实度]])把答案每句话挂到具体 chunk;配合 OpenTelemetry tracing 做完整血缘。

## 知识拓展

- **与 [[16 检索安全与访问控制|检索安全与访问控制]] 的分工**:16 偏「攻防」(访问控制、投毒防护),17 偏「运维治理」(血缘、新鲜度、合规、reindex)。生产里两者是同一套治理链的不同切面,常合并成一个「检索平台团队」owner。
- **数据网格(Data Mesh)思想迁移到 RAG**:把每个领域的知识源当成「数据产品」,由领域团队负责其质量门、ACL、新鲜度 SLA,中央平台只提供编排与可观测——这是大厂内部 RAG 平台(如 Glean、内部 enterprise search)的组织范式。
- **反模式**:① 「灌一次向量库就完事」(把 RAG 当 ETL);② 「LLM 兜底权限」(靠 prompt 防泄露);③ 「全量重索引」(不做增量);④ 「治理两张皮」(治理逻辑不嵌进检索路径,可被绕过);⑤ 「无血缘」(答案出错查不到来源,无法纠错追责)。
- **前沿与边界**:**Agentic RAG**(见 [[36 Agentic RAG|Agentic RAG]])让检索变多轮自主,治理难度上升——每一轮 agent 检索都要过 ACL 和质量门,审计要记录完整轨迹而非单次召回;这与 [[38 Agent 评估与可观测性|Agent 评估与可观测性]] 的多步 tracing 合流。**Confidential Computing / TEE** 正在被探索用于「数据驻留 + 不可信云」场景下的合规检索。
- 本篇是 [[13 Modular RAG|Modular RAG]] 的「治理模块化」落地,与 [[18 RAG 评估|RAG 评估]](质量度量)、[[20 RAG 开源生态全景|RAG 开源生态全景]](工具选型)构成「生产 RAG 三件套」:能度量、能治理、知道用什么轮子。
