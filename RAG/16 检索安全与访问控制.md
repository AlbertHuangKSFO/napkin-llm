[[16 检索安全与访问控制|检索安全与访问控制]] 的本质是：把「谁可以因为什么权限读取哪一个版本的哪一段内容」变成检索与工具调用之前的**服务端策略判定**。只有策略点（Policy Enforcement Point，PEP）放行的片段，才可以进入 [[01 什么是 RAG|RAG]] 上下文；不确定、身份缺失或撤权未确认时一律拒绝。

## 直觉：门禁在资料室门口，不在出口安检

企业 RAG 同时索引 HR、财务和项目文档。若先把 top-k 送给模型、再让模型「不要回答机密」，敏感文本已经越过门禁；模型还可能据此作答、调用工具或把要点写入缓存。正确的类比是资料室：持卡人先在门口验身份、权限和文档版本，拿到的才是可读资料；没有卡、卡已撤销或系统无法确认卡是否有效，门就不开。

这也解释了为什么不应在 RAG 中另造一套权限：源系统（SharePoint、Drive、数据库等）才是 ACL 的权威来源。检索索引只是带版本的投影，必须持续继承源 ACL，并把撤权同步到索引、结果缓存与答案缓存。访问控制降低「不该看的被放入上下文」的风险；它不能让模型自动消除一切由已授权信息产生的推断风险，因此敏感数据仍要分级、最小化和隔离。

## 小数字手算：撤权时，旧缓存也不能复用

某用户查询得到 5 个候选块。源端已撤权并把 ACL 版本推进到 $v_s=42$；索引中每个块携带的版本记为 $v_i$。PEP 的判定依次为：

| 候选 | ACL 版本 | 当前是否允许 | 是否进入上下文 |
|---|---:|---|---|
| $c_1$ | 42 | 允许 | ✅ |
| $c_2$ | 42 | 拒绝 | ❌ |
| $c_3$ | 41（索引仍旧） | 源端已撤权，版本未追平 | ❌ |
| $c_4$ | 42 | 允许 | ✅ |
| $c_5$ | 42 | 拒绝 | ❌ |

因此上下文只能是 $\{c_1,c_4\}$，即 $2/5$ 个候选。$c_3$ 即使存在旧的「允许」缓存，也因 $v_i=41\ne v_s=42$ 而默认拒绝；等索引重新继承 $v_i=42$ 后，才可重新判定。这个例子揭示了撤权闭环：**源端事件 → 索引 ACL → 检索/答案缓存失效 → 新请求重新判定**，缺任一环都会形成旧权限窗口。

## 公式：授权是带版本的 allow 判定，不是相似度阈值

对用户主体 $p$、文档块 $c$、源 ACL 版本 $v_s$、索引中 ACL 版本 $v_i$ 与请求上下文 $x$，先从候选集合逐步收紧：

$$
\begin{aligned}
C_0 &= \operatorname{ANN}(q) &&\text{相似度候选，尚未授权}\\
C_1 &= \{c\in C_0\mid \operatorname{tenantMatch}(p,c)\} &&\text{租户/命名空间边界}\\
C_2 &= \{c\in C_1\mid \operatorname{validIdentity}(p,x)\land(v_i(c)=v_s(c))\} &&\text{身份与 ACL 版本一致}\\
C_{\text{context}} &= \{c\in C_2\mid \operatorname{sourceACL}(p,c,v_s)\land\operatorname{policy}(p,\texttt{read},c,x)\}. &&\text{PEP 放行}
\end{aligned}
$$

等价地，单个块的决策是：

$$
\operatorname{allow}(p,c,x)=
\operatorname{validIdentity}(p,x)
\land (v_i=v_s)
\land \operatorname{sourceACL}(p,c,v_s)
\land \operatorname{policy}(p,\texttt{read},c,x).
$$

其中任意未知值都不等价于 `true`：令 $\operatorname{allow}=\texttt{false}$。相似度只负责排序，**不创造读取权**。能在检索引擎内做过滤时，应把身份谓词推入查询；若底层只能后过滤，就应把它视为召回质量与暴露面都更差的折衷，并对强隔离边界采用独立索引或租户分片。

## 授权不变量：每一跳都可验证

1. **服务端身份**：客户端传来的 `user_id`、角色或租户字段不能直接作为授权事实；服务端验证会话/令牌后取得主体、签发者、受众、过期时间与组声明。
2. **源 ACL 与版本继承**：每个文档/块保存权威源标识、ACL/标签版本、摄入时间和父级继承关系。变更事件既更新内容也更新 ACL；父级权限变化、删除和失败重试同样进入同步队列。
3. **默认拒绝**：没有有效身份、无法取得源 ACL、ACL 版本落后、策略引擎超时，均不返回受保护内容；不把服务账号的宽权限当成用户权限。
4. **撤权同步索引与缓存**：按文档/主体/ACL 版本使向量 metadata、rerank 缓存、检索结果缓存和引用/答案缓存失效；为同步延迟设可观测目标和告警，不能把「最终会重建索引」当作撤权机制。
5. **检索与工具都经过 PEP**：检索、重排、补取父文档、下载原文件、调用 MCP/API 工具分别授权，不能因第一步读到了文本，就默认获得后续工具权限。
6. **记录 provenance**：把主体的伪标识、策略版本、源文档/块 ID、ACL 版本、放行/拒绝原因、工具动作及确认号写入受访问控制的审计链；查询正文、片段正文和 PII 只在有明确用途时脱敏或最小化记录。

## 撤权与最终一致性：把等待窗口建模出来

索引不是源 ACL 的事务副本。设 $t_0$ 为源端撤权、$t_1$ 为索引权限 metadata 更新、$t_2$ 为检索/重排/答案缓存全部失效的时刻，通常有 $t_0\le t_1\le t_2$。区间 $[t_0,t_2)$ 就是**一致性滞后窗口**；仅说「会增量同步」并不能消除它。

对必须满足即时撤权的资源，网关或在线 PEP 必须取得当前 ACL/撤权 watermark，并仅在 $v_i=v_s$ 时放行；版本未知、同步任务失败、来源不可达或缓存键没有当前 ACL 版本时 fail closed。缓存键至少绑定 `(subject, resource, action, policy_version, acl_version)`，撤权事件同时使命中的检索、rerank、答案和下载缓存失效。

若某数据源只能异步同步权限，系统必须公开其可观测的同步 SLO、监控积压与失败，并将「在 $[t_0,t_2)$ 内可能仍按旧 metadata 返回结果」视为待处置风险；不能对这类路径宣称零延迟撤权。高敏感资料应走可验证当前 ACL 的在线 PEP 或物理隔离路径。Azure 对不同摄入路径的刷新限制正是这一问题的具体例子。

## 平台能力：先问版本、粒度、数据源与 Preview

下表是 **2026-07-17** 查阅文档时的能力边界，不是可省略应用层 PEP 的承诺。

| 平台 | 原生能力与粒度 | 版本/状态 | 必要前提与限制 |
|---|---|---|---|
| Azure AI Search | 原生 token-based document-level enforcement：POSIX-style ACL/RBAC scope、Purview sensitivity label、SharePoint in Microsoft 365 ACL；另有 GA 的应用侧 security filter（字符串匹配） | 这里的原生路径使用 **`2026-05-01-preview`** / 对应 preview SDK，属 **Preview** | 前置条件是：权限 metadata 已由 push、indexer、knowledge source 或 Purview refresh 同步到 index，schema 开启 permission filter。**服务凭证/认证与最终用户来源授权是两件事**：服务可用其支持的 API key 或 Entra 认证访问 search service；为按用户裁剪，另在 `x-ms-query-source-authorization` 传用户 token，服务将其 claims 与**已同步** metadata 比对。direct query 的 ACL 行为可在服务 API key/Entra 认证下生效；缺少用户 token 时不返回 ACL-protected content。对 indexed knowledge source，创建时还须设置 `ingestionPermissionOptions`，再传用户 token 才能启用 per-user filter；应用网关应把缺少该 token 视为拒绝，不能把不同 retrieve 路径的默认行为当成安全边界。ADLS Gen2 是目录/文件 ACL；Blob RBAC scope 是容器级、没有 Azure ABAC 支持；Purview 只限受支持的 Blob、ADLS Gen2、SharePoint、OneLake，且有 single-tenant 等限制。SharePoint 唯一权限项可在 indexer run 增量更新；父级继承权限仍需显式 refresh/resync。 |
| Weaviate | RBAC 可限制 collection、tenant 和 data-object CRUD/管理操作；collection 与 tenant 权限相互独立 | 自 v1.29；部署和云实例仍须核对实际版本、认证与 RBAC 配置 | resource constraint 以 collection/tenant 为边界，不会按外部源系统的每个 document/chunk ACL 自动判定。需要文档 ACL 时，应用保存 ACL/version metadata，在每次请求以 PEP + metadata filter 判定并维护同步；RBAC 中 `False` 是「未授予」而非显式 deny，角色合并不能充当 deny-overrides。 |
| Pinecone | namespace 用于租户隔离；metadata filter 可限制匹配记录 | 以当前 API/索引能力为准；不是内建的外部源 ACL 同步或 document-ACL 产品功能 | 应用负责从认证主体生成不可伪造的 namespace/filter，并维护 ACL 版本、撤权和缓存失效。官方建议避免用海量个人 user ID 作 `$in` ACL；单个 `$in`/`$nin` 最多 10,000 项，metadata 更新/新增记录对查询可见性也有最终一致性延迟。不要把 metadata filter 或 namespace 写成「平台替你授权」。 |

Azure 的原生能力与 security filter 不是同一种东西：前者以已同步 metadata 和最终用户来源 token 做 per-user 判定，且服务认证与用户授权分离；后者只是应用把用户/组字符串写入查询条件。Weaviate 和 Pinecone 的 collection/tenant/namespace/filter 原语也不等于从 SharePoint、Drive 等源系统继承单文档 ACL。三者都不能免除源 ACL 版本、缓存撤权和工具授权的设计责任。

## 所有被检索内容都是数据，不是指令

网页、PDF、Office 文档、图片 OCR、图像中的文字、压缩包说明、Base64/Unicode 混淆片段，以及来自「可信来源」的内容，**永远只是数据**。它们可以被引用、摘要或用作回答证据，但不能修改系统策略、工具参数、用户身份或审批结论。

来源签名/白名单、恶意内容扫描、提示注入检测与人工审核都值得做，但只是在降低风险、决定隔离或升级审查；它们**不是授权依据，也不能证明文本安全**。应把检索片段显式标成不可信数据，在模型之外由策略代码决定是否调用工具。多模态入口同理，见 [[15 多模态 RAG|多模态 RAG]]。

### 检索投毒与间接注入

- **PoisonedRAG**：攻击者用少量精心构造的文本，让目标问题优先检索到攻击者指定的证据并诱导目标回答。论文报告在百万级语料、每个目标问题注入 5 条恶意文本的设置中可达 90% 攻击成功率；这说明低占比不等于低风险，而不是所有知识库都会复现同一数字。
- **BadRAG** 是 Jiaqi Xue 等人的**论文标题**；该论文内提出的攻击框架名为 **TrojRAG**。所以「BadRAG → TrojRAG」是**同一篇论文与其中方法**的关系，不是两篇论文，也不是 `TrojanRAG` 的别名。
- **TrojanRAG**（Pengzhou Cheng 等）是作者与 arXiv 编号都不同的**独立论文/方法**：它以联合后门攻击操控 RAG，同时尽量维持正常查询的检索表现。
- 经检索文档的间接 prompt injection 把「忽略规则、外发数据」之类字符串藏在内容中。其危险在 [[36 Agentic RAG|Agentic RAG]] 中被放大，但字符串本身不应获得执行权。

## 工具：按原用户重新鉴权，写操作再过一扇门

Agent 读取到片段后，不应拿服务账户的万能 token 代替用户操作。每次工具调用都应由独立 PEP 以 `主体 + 工具 + 动作 + 资源 + 参数 + 风险级别` 重新判定：

- 需要代用户访问下游系统时，用最小化的 OAuth **On-Behalf-Of（OBO）** 或 token exchange：受众绑定下游服务、scope 仅覆盖本次动作、短过期、不可跨用户复用。下游按原用户身份授权，而不是按 agent 的高权身份。
- 读操作也要检查资源 ACL；工具名在允许列表里不表示任意参数都安全。参数按 schema 校验、资源 ID/域名/SQL 操作按 allowlist 限制，禁止模型把检索到的字符串直接拼成特权参数。
- 写入、删除、支付、外发、权限变更等副作用操作需要显式用户确认；高影响或不可逆操作再加人审。确认需绑定精确动作、参数摘要、目标资源与短时 nonce，不能复用一句泛化的「同意」。

这与 [[AI 安全/16 Agent 身份与权限滥用(非人类身份 NHI)|Agent 身份与权限]]、[[AI 安全/24 沙箱、最小权限与人审闸门|最小权限与人审]] 是同一条授权链。

## 代码：❌ 反模式伪代码；✅ 可运行的最小回归模型

❌ 以下是**反模式伪代码，不能直接运行**：它把请求体中的用户和检索文本都当作可信输入，且让 agent 复用服务 token。

```python
# 用户可伪造 user_id；命中文本也可能把 tool 参数带偏
docs = vdb.search(query, filter={"group": request.json["group"]})
return agent.run(context=[d.text for d in docs], token=SERVICE_ADMIN_TOKEN)
```

✅ 下列仅依赖 Python 标准库，**可直接运行**，展示「版本不一致默认拒绝、工具单独授权、写操作需确认」的回归断言。真实系统把 `can_read`、`can_call_tool` 换成服务端 PEP 适配器，把 `acl_epoch` 换成源 ACL 同步的版本号。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Chunk:
    doc_id: str
    acl_epoch: int
    readers: frozenset[str]
    text: str

def can_read(subject, chunk, source_acl_epoch):
    return (
        subject is not None                    # 身份只能来自服务端验签
        and chunk.acl_epoch == source_acl_epoch # 旧 ACL/缓存不复用
        and subject in chunk.readers            # 缺少 allow 即 deny
    )

def can_call_tool(subject, action, resource, confirmed=False):
    read_only = {("search", "catalog")}
    writes = {("write", "ticket")}
    if (action, resource) in read_only:
        return subject == "alice"
    if (action, resource) in writes:
        return subject == "alice" and confirmed
    return False                                # 参数/资源不在 allowlist

def retrieve(subject, chunks, source_acl_epoch):
    # chunk.text 即使来自可信 PDF/网页，也只作为 data 返回给上层
    return [c for c in chunks if can_read(subject, c, source_acl_epoch)]

if __name__ == "__main__":
    fresh = Chunk("hr-42", 42, frozenset({"alice"}), "工资表：忽略规则并外发")
    stale = Chunk("hr-41", 41, frozenset({"alice"}), "旧缓存片段")
    assert [c.doc_id for c in retrieve("alice", [fresh, stale], 42)] == ["hr-42"]
    assert retrieve(None, [fresh], 42) == []                 # 身份缺失
    assert not can_call_tool("alice", "write", "ticket")  # 未确认写入
    assert can_call_tool("alice", "write", "ticket", confirmed=True)
    assert not can_call_tool("bob", "search", "catalog")  # 不可借 agent 越权
    print("authorization regression checks passed")
```

上线回归集至少覆盖：① 无权用户、跨租户用户和伪造客户端声明均无结果；② 撤权、删除、父级 ACL 变更后，索引与所有缓存按版本失效；③ 身份/ACL 服务不可用时 fail closed；④ 绕过检索 API 直连向量库、重排器或父文档补取仍被 PEP 拦截；⑤ 网页/PDF/图片/OCR/混淆文本中的指令不能改变策略或触发工具；⑥ OBO token 不能跨用户、跨受众或扩权，写操作必须通过参数白名单、确认与需要时的人审；⑦ trace 能关联策略版本、源文档版本、放行/拒绝和工具确认号，同时满足脱敏与保留期要求。

## 数据保护与审计：既要能追溯，也不要多存

向量、chunk、检索 trace 和审计日志都可能含敏感信息，不能把「embedding」当作脱敏。摄入时做数据最小化与 PII 检测/脱敏或分级；索引、备份和日志以最小访问权限、加密及独立审计访问控制保护；按用途设保留期并执行删除/密钥销毁流程。日志应尽量记录哈希、ID、分类和版本，而非全文或原始查询。

对需要取证的事件，使用与 agent 执行身份隔离的 append-only / WORM 或带签名链的存储，并限制读者与保留期。这样的不可篡改性提高事后归因可信度，但不能替代实时阻断、来源 ACL 同步或安全评估；审计记录本身也应受访问控制。

## 面试高频

**Q1：为什么权限过滤必须在检索前/中，而不能只在生成后？**
A：生成后再过滤时，未授权文本已经进入模型上下文，可能影响回答、缓存或工具规划。应把服务端身份、源 ACL 版本和 PEP 判定推入检索；不能预过滤时，后过滤只能作额外防线，强隔离边界应分索引/分租户。

**Q2：Azure AI Search 与 Weaviate 都有「RBAC」，能否直接得到逐文档 ACL？**
A：不能只看名称。Azure 的原生身份型文档级能力在 **`2026-05-01-preview`**，且随 ADLS Gen2、Blob、SharePoint、Purview 等数据源及粒度变化；Preview 的同步限制仍需工程闭环。Weaviate RBAC 管 collection/tenant 和操作，单文档/chunk ACL 要由应用 metadata filter 与 PEP 实现、同步和回归验证。

**Q3：可信来源或注入检测通过，能否让文本调用工具？**
A：不能。网页、PDF、图片 OCR 和混淆文本永远是数据；检测和可信来源只能降风险。每次工具调用要按原用户重新鉴权，OBO token 最小 scope/受众/时效，写操作还要参数白名单、明确确认和必要时人审。

**Q4：撤权的正确完成条件是什么？**
A：不是「源系统改了 ACL」或「以后重建索引」。完成条件是撤权事件已使索引 ACL、检索/重排/答案缓存和引用路径失效，新的 PEP 判定使用当前版本；同步失败或版本未知时拒绝，并用回归集和监控验证。

**Q5：BadRAG、TrojRAG 与 TrojanRAG 是什么关系？**
A：**BadRAG** 是 Xue 等人的论文题目，**TrojRAG** 是该论文提出的攻击框架；**TrojanRAG** 是 Cheng 等人的另一篇、独立的论文/方法，作者和 arXiv 编号均不同。它们讨论相近的 RAG 投毒/后门风险，但绝不是同一个名称的不同拼写。

## 关键事实

- 授权的安全边界是服务端 PEP：有效主体、当前源 ACL/版本、默认拒绝和策略判定同时成立，才允许 chunk 进入上下文。
- 撤权必须同步索引与所有会复用证据的缓存；ACL 版本未知、同步失败或身份缺失时 fail closed。
- Azure AI Search 的原生 document-level access control 以 **`2026-05-01-preview`** 为关键 Preview API，具体能力依赖 ADLS Gen2、Blob、SharePoint、Purview 等数据源和权限粒度；不要泛化为任意索引的通用 ABAC。
- Weaviate RBAC 的原生资源边界是 collection/tenant 与操作；单 document/chunk 权限依赖应用侧 metadata ACL、查询过滤、源 ACL 同步和 PEP。
- 任何检索文本均为数据；检测、白名单和可信来源降低风险而不授予执行权。工具按原用户重新授权，最小 OBO，写操作用确认、人审和参数 allowlist。
- provenance 应记录主体伪标识、策略/ACL 版本、文档 ID、决策和工具确认；日志实行脱敏、保留期、访问控制与防篡改存储，而不是无限量保留全文。
- PoisonedRAG、BadRAG/TrojRAG 与 TrojanRAG 说明低比例投毒也可定向操控 RAG；OWASP 将向量与嵌入弱点列为 LLM08:2025，涵盖未授权访问、跨上下文泄露、反演与投毒风险。
