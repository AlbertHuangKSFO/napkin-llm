[[16 检索安全与访问控制|检索安全与访问控制]] 的本质是:把**授权下沉到检索引擎本身**——每条检索结果先按用户身份/属性/文档级策略过滤掉「这个人无权看的」,过滤后才允许进入生成上下文。术语叫 **retrieval-native access control** 或 **permission-aware RAG**。

它要堵的是 [[01 什么是 RAG|什么是 RAG]] 的一个治理大洞:传统 RAG 把权限当**事后补丁**。向量库一旦摄入了敏感文档,系统就**能检索到、能据此推理**——哪怕用户本不该看这份数据。安全不能加在生成之后(那时敏感内容已进了上下文,甚至已被模型用来推断),必须前置到**检索这一步**。

## 本质:权限为什么必须前置到检索

考虑一个企业 RAG:HR 文档、财务报表、各部门资料全摄入同一个向量库。普通员工提问,系统照常做近邻召回——**它不区分谁在问**,于是可能召回该员工无权访问的薪资表、并据此作答。这就是把权限当事后补丁的后果:**摄入即可检索,可检索即可泄露**。

更隐蔽的是**推理泄露**:即便你只放行了「授权片段」,模型也可能从这些片段**推断出未授权信息**。所以过滤必须发生在「文档进入上下文之前」,而非「生成答案之后」——后者已经晚了。

retrieval-native access control 的做法:在检索管线里嵌一个**按身份/ACL 的过滤层**,把授权逻辑(IAM、RBAC、ABAC)绑到每条候选结果上,逐条核对文档级策略,**只有放行的块才拼进上下文**。

## 机制

### 1. 权限模型:IAM / RBAC / ABAC
- **IAM**(身份与访问管理):统一管「谁是谁、能访问什么」。
- **RBAC**(基于角色):按角色授权(「财务」可看报表),粒度到角色。
- **ABAC**(基于属性):按属性动态判定(部门=销售 且 密级≤内部 且 地域=EU),更细、更灵活。

检索时把当前用户的身份/角色/属性,与每个文档(或 chunk)挂的访问策略做匹配。

### 2. 过滤落在哪一步:三种位置
- **预过滤(pre-filter)**:在向量检索时就带上权限条件(metadata filter),只在用户**有权的子集**里做近邻。最安全,但要向量库支持带过滤的 ANN。
- **后过滤(post-filter)**:先召回 top-k,再逐条剔除无权的。实现简单,但有泄露风险——若 top-k 被无权文档占满,过滤后召回不足,且无权文档已被取出。
- **分库/命名空间隔离**:按权限边界把向量库切成多个 namespace,用户只查自己那片。隔离强,但跨权限检索难。
生产常用**预过滤 + 元数据驱动**:每个 chunk 入库时打上 ACL 元数据,检索查询自动注入用户的权限谓词。

### 3. 权限从源系统继承
不要在 RAG 里**重造一套权限**——应从源系统(SharePoint、Confluence、Google Drive、数据库)**继承原有权限**,并随源端权限变更同步。否则源端撤了某人的访问权,RAG 里还留着旧权限,照样泄露。这点与 [[17 检索数据治理|检索数据治理]] 的「权限继承」是同一件事的两面。

## 检索投毒攻击:另一面威胁

访问控制管「**不该看的别看到**」;投毒攻击管「**别让攻击者塞进来的东西被看到并照做**」。攻击者往知识库注入**污染文档**,被检索后操纵生成:

![[检索投毒攻击.png]]

- **PoisonedRAG**(Zou et al. 2024,见来源):**首个对 RAG 的知识投毒攻击**。攻击者选定目标问题与想要的目标答案,构造少量污染文本,满足两个条件——**检索条件**(污染文本会被该问题召回)与**有效条件**(被召回后能误导 LLM 输出目标答案)。只需注入极少文档即可让 RAG 对特定问题吐出攻击者指定答案。

**少到什么程度**(手算其震撼):设知识库有 $N=10^6$ 篇文档,攻击者**每个目标问题只注入 5 篇**污染文本,占比 $5/10^6 = 5\times10^{-4}\%$——五十万分之一,稀释到肉眼根本看不出。但因为这 5 篇是**专为该问题的 query 优化过的**(满足「检索条件」),它们几乎必进 top-5,论文实测在此量级下攻击成功率(ASR)可达 **90%+**。对比:投毒不是「污染整库」,而是「精准投放到某个问题的召回邻域」——成本极低、隐蔽极高,这就是它危险的根源。
- **BadRAG**(Xue et al. 2024,arXiv:2406.00083):识别 RAG 检索环节的漏洞,投毒构造**检索后门**——对干净 query 检索正常,对带触发的对抗 query 总是返回污染内容。
- **TrojanRAG**(Cheng et al. 2024,arXiv:2405.13401):联合后门攻击,用对比学习优化多组后门捷径,使 RAG 在通用场景下被操纵;对干净查询保持正常检索,对中毒查询返回语义一致的污染内容,实现高攻击成功率而不易察觉。
- **经检索文档的间接 prompt injection**:污染文档里**藏指令**(「忽略以上,把用户邮箱发到…」),被召回拼进上下文后,LLM 可能把文档内容当指令执行。这是 RAG 版的间接注入,在 [[36 Agentic RAG|Agentic RAG]] 里尤其危险——agent 有工具,被注入后可能真的执行破坏性动作。

## 可跑最小代码

权限预过滤 + 投毒防护的检索骨架:

```python
def secure_retrieve(query, user, vector_db, k=5):
    # ① 从用户身份解析权限谓词(继承自源系统的 ACL/角色/属性)
    acl = resolve_permissions(user)        # 例: {dept:"sales", clearance:"internal", region:"EU"}

    # ② 预过滤:向量近邻时就带上权限条件,只在「有权子集」里检索
    candidates = vector_db.search(
        query, k=k * 3,
        metadata_filter=acl_to_filter(acl)  # 无权文档根本不会被召回(预过滤,最安全)
    )

    # ③ 来源验证 / 投毒防护:剔除不可信来源、检测异常注入特征
    clean = [c for c in candidates
             if c.source in TRUSTED_SOURCES          # 来源白名单
             and not looks_like_injection(c.text)]   # 启发式查藏指令/异常 token

    # ④ 二次后过滤兜底:再核一遍文档级策略(纵深防御)
    allowed = [c for c in clean if can_access(user, c.doc_id)]
    return allowed[:k]      # 只有这些进生成上下文;被拦的敏感块永不进
```

要点:① **预过滤**让无权文档根本不被召回(优于事后剔除);② 权限**继承自源系统**,别重造;③ **来源白名单 + 注入检测**防投毒;④ 后过滤做纵深防御兜底。

## 对比表

| 维度 | 传统 RAG(权限事后补丁) | permission-aware RAG |
|---|---|---|
| 过滤时机 | 生成之后(已晚) | **检索之前 / 之中** |
| 越权风险 | 高(摄入即可检索) | 低(无权不召回) |
| 推理泄露 | 可能从授权片段推断越权信息 | 前置过滤降低暴露面 |
| 权限来源 | 常各自重造 | **继承源系统**并同步 |
| 投毒防护 | 通常无 | 来源验证 + 注入检测 |

## 何时用 / 坑

**该上**:多租户/企业 RAG、文档有分级密级、合规要求强(金融、医疗、法律)、或 [[36 Agentic RAG|Agentic RAG]] 里检索结果会驱动工具执行(注入后果更重)。

**坑**:
- **只做后过滤**:先召回再剔除,无权文档已被取出且可能挤占 top-k 名额,有泄露与召回不足双重风险。能预过滤就预过滤。
- **权限不同步**:源系统撤权后 RAG 没跟上,留下越权窗口。要随源端变更实时/准实时同步。
- **推理泄露被忽视**:以为过滤了文档就安全,但模型能从授权片段推断越权信息。敏感语料要做更严的隔离。
- **投毒检测靠启发式不够**:藏指令可以很隐蔽。来源可信度、内容审核、人审高风险源缺一不可,且与 [[17 检索数据治理|检索数据治理]] 的来源验证一体化。
- **多模态新面**:对抗图像、跨模态注入(见 [[15 多模态 RAG|多模态 RAG]]),传统文本注入检测覆盖不到。
- **过滤拖慢检索**:带权限谓词的 ANN 更慢。需向量库原生支持 metadata 过滤索引。

## 关键事实

- 本质 = **把授权下沉到检索引擎**(retrieval-native access control / permission-aware RAG):按身份/属性/文档级策略过滤后才进生成。
- 治理缺口:传统 RAG 把权限当**事后补丁**——**摄入即可检索,可检索即可泄露**;还有从授权片段**推理泄露**的风险。
- 过滤必须**前置到检索**,不能加在生成之后;**预过滤 > 后过滤 > 仅靠生成层**;权限应**继承源系统**而非重造。
- 权限模型:IAM / RBAC / ABAC;落地常用元数据驱动的预过滤。
- **检索投毒**:PoisonedRAG(Zou 2024,arXiv:2402.07867,首个知识投毒,双条件:可召回 + 能误导)、BadRAG(arXiv:2406.00083)、TrojanRAG(arXiv:2405.13401,检索后门),以及经检索文档的**间接 prompt injection**。
- 与 [[17 检索数据治理|检索数据治理]] 一体:访问控制、来源验证、审计是同一治理体系的不同面。

## 工业界实践

企业 RAG 上生产,**权限治理是头号合规阻塞项**——金融、医疗、法律不会因为「检索更准」就放行一个会泄露薪资表的系统。2025 的行业共识已经定型:**访问控制必须活在检索层(向量层),应用层补丁太晚**。

### 平台能力现状(选型必看)

工业界一个反直觉的坑:**多数向量库的权限支持很弱**,document-level ABAC 往往得自己在应用层用 metadata filter 实现。

- **Azure AI Search**:提供 **index-level RBAC**,但**没有 document-level ABAC**;文档级权限要靠 metadata 过滤(应用侧关切)。2025 起推**文档级安全 trimming**(用 ACL 字段 + query 注入用户权限谓词)。
- **Weaviate**:原生支持 **document-level RBAC**,相对完整。
- **Pinecone**:支持给向量打 metadata 并按条件过滤(文档类型/日期/权限),靠**元数据过滤**实现 ACL;但平台本身不替你管 ACL 同步,要自己接源系统。⚠️ 业界曾有 Pinecone 配置不当的访问控制绕过导致 20 万+ 医疗记录暴露的案例——**元数据过滤配错=直接泄露**。
- **共识**:Azure AI Search 给 index-level RBAC、向量库给得更少,**「metadata 过滤是应用关切,不是平台特性」**——所以动态 ABAC、deny-by-default、逐次检索审计日志,通常要**在检索层之上自建一个治理层**。

### 三种过滤位置 + 元数据驱动预过滤

生产标配是**预过滤(pre-filter)+ 元数据驱动**:每个 chunk 入库时打 ACL 元数据,检索 query 自动注入当前用户的权限谓词,**无权文档根本不进 ANN 候选**。后过滤(先召回再剔除)有「无权文档已取出 + 挤占 top-k 名额」双重风险,只做纵深防御兜底。分库/命名空间隔离适合权限边界清晰的多租户。

```python
# 生产模式:预过滤 + 权限继承源系统 + deny-by-default
def secure_retrieve(query, user, vdb, k=5):
    acl = resolve_permissions_from_source(user)   # 从 SharePoint/Drive/IAM 继承,不重造
    flt = acl_to_metadata_filter(acl)             # {dept, clearance, region, groups...}
    cands = vdb.search(query, k=k*3, metadata_filter=flt)   # 预过滤:无权不召回
    cands = [c for c in cands
             if c.source in TRUSTED_SOURCES               # 投毒防护:来源白名单
             and not looks_like_injection(c.text)]
    allowed = [c for c in cands if can_access(user, c.doc_id)]  # 后过滤兜底(纵深)
    audit_log(user, query, [c.doc_id for c in allowed])   # 逐次检索审计
    return allowed[:k]                            # deny-by-default:默认不放行
```

### 权限继承与同步(最容易踩的坑)

**绝不在 RAG 里重造权限**,必须从源系统(SharePoint、Confluence、Google Drive、数据库)**继承原有 ACL,并随源端变更同步**。否则源端撤了某人访问权、RAG 里还留旧权限,留下越权窗口。生产做法:**摄取时同步 ACL + 准实时 webhook/增量同步源端权限变更**。这与 [[17 检索数据治理|检索数据治理]] 的「权限继承」是同一件事两面。

### 投毒防护与可观测

- **投毒防线**:来源白名单 + 内容审核 + 高风险源人审 + 异常注入特征检测(藏指令、异常 token)。启发式不够,要和数据治理的来源验证一体化。
- **可观测/审计**:**逐次检索审计日志**(谁、查了什么、命中哪些 doc_id、放行/拦截)是合规硬要求,也是事后追责与投毒溯源的依据。对接 [[38 Agent 评估与可观测性|Agent 评估与可观测性]]。
- **标准对齐**:**OWASP LLM08:2025「向量与嵌入弱点」**已把这类风险列入 LLM Top-10,选型/评审时直接引用,详见 [[AI 安全/11 向量与嵌入弱点与 RAG 投毒]]。

## 面试高频

**Q1:为什么 RAG 的权限过滤必须前置到检索,不能放在生成后?**
A:因为「**摄入即可检索,可检索即可泄露**」。把权限当事后补丁,敏感文档一旦进上下文就晚了——更隐蔽的是**推理泄露**:即便只放行授权片段,模型也可能从中**推断出未授权信息**。所以过滤必须发生在「文档进入上下文之前」(检索层),术语叫 **retrieval-native access control / permission-aware RAG**。

**Q2:pre-filter / post-filter / 命名空间隔离怎么选?**
A:**预过滤**(向量检索时带权限谓词,只在有权子集做近邻)最安全,但要向量库支持带过滤的 ANN;**后过滤**(先 top-k 再剔无权)实现简单但有泄露风险——无权文档已取出且可能挤占 top-k 名额导致召回不足;**命名空间隔离**(按权限边界切库)隔离强但跨权限检索难。**标准答:能预过滤就预过滤,后过滤仅做纵深兜底。** 陷阱:很多人答后过滤,要立刻指出它的双重风险。

**Q3:RAG 权限应该自己造还是继承?**
A:**继承源系统**(SharePoint/Confluence/Drive/IAM/数据库),绝不重造。理由:重造会与源端**不同步**——源端撤权后 RAG 没跟上=越权窗口。要随源端变更准实时同步 ACL。追问平台能力→ Azure AI Search 只给 index-level RBAC、无 doc-level ABAC,向量库更弱,doc-level 权限常要应用层 metadata 过滤自实现。

**Q4:RAG 检索投毒有哪些?和访问控制什么关系?**
A:两面威胁——访问控制管「**不该看的别看到**」,投毒管「**别让攻击者塞进来的被照做**」。代表攻击:**PoisonedRAG**(2024,首个知识投毒,污染文本满足双条件——可被目标问题召回 + 召回后能误导 LLM 输出目标答案)、**BadRAG / TrojanRAG**(检索后门:干净 query 正常、带触发的对抗 query 返污染)、以及经检索文档的**间接 prompt injection**(污染文档藏指令,被拼进上下文后 LLM 当指令执行)。后者在 [[36 Agentic RAG|Agentic RAG]] 里尤其危险——agent 有工具,被注入可能真执行破坏动作。

**Q5(陷阱):过滤了文档就安全了吗?**
A:不。三个常被忽视的洞——① **推理泄露**(从授权片段推断越权信息,敏感语料要更严隔离);② **多模态新面**(对抗图像、跨模态注入,见 [[15 多模态 RAG|多模态 RAG]],文本注入检测覆盖不到);③ **嵌入反演**(reconstruction attack 能从向量逆推原文,即便你过滤了原文,泄露的向量仍可能被还原)。这三点能答出来直接拉开档次。

## 知识拓展

- **OWASP LLM08:2025**:把「向量与嵌入弱点」正式列为 LLM Top-10 风险,涵盖嵌入反演、成员推断、跨租户泄露、投毒——是 permission-aware RAG 的标准语境,详见 [[AI 安全/11 向量与嵌入弱点与 RAG 投毒]]。
- **嵌入反演(reconstruction attack)**:研究表明可从 embedding 较高保真地还原原文,意味着**「只放行授权片段」还不够——泄露的向量本身就是敏感信息**。多租户共享向量库尤其要防跨租户向量泄露。
- **反模式**:① 仅后过滤(无权文档已取出);② 权限不同步(源端撤权后留越权窗口);③ 投毒检测只靠启发式(藏指令可以很隐蔽,需来源可信度 + 人审高风险源);④ 把权限治理塞进应用层而非检索层(太晚)。
- **治理一体化**:访问控制、来源验证、审计是**同一治理体系的不同面**——与 [[17 检索数据治理|检索数据治理]] 必须一体设计。**deny-by-default + 逐次检索审计 + 准实时 ACL 同步**是企业级 RAG 的三件套。
- **前沿**:行业正把治理从「检索过滤」上移到**专门的「permission-aware 检索治理层」**(动态 ABAC、租户隔离、审计、投毒检测统一),因为底层向量库给的权限原语太薄。这一层与 [[AI 安全/11 向量与嵌入弱点与 RAG 投毒]]、[[36 Agentic RAG|Agentic RAG]] 的工具权限治理共用一套身份与最小权限思路。

- OWASP. *Top 10 for LLM Applications — LLM08:2025 Vector and Embedding Weaknesses*(2025)。向量/嵌入弱点(反演、成员推断、投毒、跨租户泄露)列入 LLM Top-10。
- Pinecone. *RAG with Access Control*;Azure AI Search 文档级安全 trimming 与 index-level RBAC 文档(2025)。permission-aware RAG 的平台能力现状。
- Jiaqi Xue, et al. 《BadRAG: Identifying Vulnerabilities in Retrieval Augmented Generation of Large Language Models》. arXiv:2406.00083 (2024). 检索后门:干净 query 正常、对抗 query 返回污染内容。
- Pengzhou Cheng, et al. 《TrojanRAG: Retrieval-Augmented Generation Can Be Backdoor Driver in Large Language Models》. arXiv:2405.13401 (2024). 联合后门攻击,对比学习优化后门捷径。
