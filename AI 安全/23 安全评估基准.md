[[23 安全评估基准|安全评估基准]]不是“跑几个红队 prompt 看有没有越狱”，而是把 agent 安全拆成 **task、trial、grader、transcript、outcome、harness** 六个可审计对象。对 agent 来说，评估的关键不是模型“嘴上说了什么”，而是**环境终态是否安全、轨迹是否合规、grader 是否抗作弊**。这也是为什么它要与 [[25 监控、可观测与事件响应|可观测]] 共用同一套 trace 基础设施。

直觉类比：安全评估像考驾照。题库分数只是其中一层；真正关键的是你在封闭场地里做了哪些动作、最终车停在哪、有没有碰线、考官的判分规则会不会被投机取巧绕过。agent eval 也是同理——只看最后一句回复，信息量不够。

先用一个小数说明为什么要做 repeated trials。假设同一任务真实成功率是 $60\%$。只跑 1 次，结果只能是 0 或 1，噪声极大。若跑 5 次，出现 3 次成功，则估计值是

$$
\hat p = \frac{3}{5}=60\%
$$

若另一个候选 agent 是 4/5=80%，你至少知道差距来自 5 次重复后的平均，而不是一次幸运命中。对多步 agent，**单次试跑的偶然性** 比单轮问答大得多，因此 repeated trials 不是“更严谨一点”，而是基础配置。

Anthropic 2026 对 agent eval 的定义可以直接拿来当词典：

- **task**：一个有明确输入与成功标准的测试样例。
- **trial**：同一 task 的一次运行。
- **held-out / 留出集 / 未见任务**：训练、prompt 调参、grader 调参都不应反复直接看的独立测试集，用来回答“系统对**没见过**的任务还能不能过关”，防止把评估做成记题库。
- **grader**：给 transcript 或 outcome 打分的逻辑。
- **transcript / trace / trajectory**：完整运行记录，含工具调用、中间结果和输出。
- **outcome**：trial 结束时环境里的真实终态，不是 agent 自己声称的状态。
- **evaluation harness**：跑任务、隔离环境、收集轨迹、执行 grader、汇总指标的基础设施。

因此一个安全 eval 最少要回答三件事：

1. **有没有完成任务**：功能正确性。
2. **有没有越过边界**：安全策略、权限、引用、数据最小化是否被破坏。
3. **是不是靠作弊过关**：有没有读取别的 trial 残留、利用 grader bug、利用未清理状态投机。
4. **对未见任务是否还成立**：在 held-out 集上是否仍然有效，而不是只对调参时反复看过的样例有效。

```python
# ❌ 朴素：只看最终字符串，agent 说“完成了”就算过
def grade(task, final_text):
    return "已完成" in final_text


# ✅ 分层：检查 transcript 与 environment outcome，且抗作弊
def grade(task, transcript, env):
    checks = {
        "goal": env.outcome_matches(task.success_criteria),
        "policy": no_disallowed_tool_calls(transcript, task.allowed_tools),
        "citation": citations_grounded(transcript, env),
        "terminal_state": env.is_clean_and_reversible(),
        "cheating": not leaked_from_prior_trials(transcript, env),
    }
    return checks, all(checks.values())
```

这里要特别修正一个常见误区：**raw CoT 不是安全评估的必要观测对象**。生产评估更稳妥的观测对象是可审计轨迹：输入、工具调用、参数、工具结果、显式计划摘要、环境终态、引用与副作用。模型内部或私有 reasoning 若不可得，eval 仍然可以成立；关键是 transcript 和 outcome 是否足以验证行为。

## 面试高频

回链：[[AI 安全面试题库]]

**Q1：task、trial、grader、outcome 各指什么？**
task 是题目；trial 是一次运行；grader 是打分器；outcome 是环境中的真实终态。agent 说“我订到票了”不算 outcome，数据库里真的有订单才算。

**Q2：为什么 agent eval 一定要看 terminal state？**
因为很多失败不是回答错，而是环境被改坏了、权限被越了、数据被泄了。只看最后一句回复会错过真正的损害。

**Q3：为什么 repeated trials 很重要？**
多步 agent 有更高方差。同一 task 一次成功、一次失败很常见；不重复试验，你分不清是系统能力还是偶然性。

**Q4：held-out / 留出集到底在防什么？**
它防的是“把评估做成背题”。如果团队一边看题一边改 prompt、改工具、改 grader，最后再拿同一批题报成绩，分数会高估真实泛化。held-out 集要求这些任务在调参阶段尽量不被反复消费，用来测系统对未见任务的真实迁移能力。

**Q5：怎样防 evaluator 被 agent“作弊”？**
隔离 trial 环境、清空缓存与 git 历史、避免 grader 只做字符串匹配、把成功条件绑定到 outcome、读 transcript 查越权与投机路径。

## 关键事实

- Anthropic 在 **2026-01-09** 发布《Demystifying evals for AI agents》，明确给出 **task / trial / grader / transcript / outcome / evaluation harness / evaluation suite** 的定义，并强调多步 agent 需要 repeated trials、稳定环境与抗作弊 grader。
- 同文明确指出：agent eval 的 grader 既可以看 transcript，也可以看 outcome；其中 outcome 是 trial 结束时环境里的真实状态，而不是 agent 的自述。
- Anthropic 同时给出反作弊经验：若环境不隔离、残留 git 历史或缓存，agent 可能从 previous trials 获得不公平优势；因此 harness 必须让每次 trial 从干净环境开始。
- 对 exploit 类安全 eval，Anthropic 2026 还专门强调 grader 要能抵御 hardcoding、地址复用等作弊方式，说明“抗投机”本身就是 grader 设计的一部分，而不是附加项。

在基准层面，经典越狱数据集仍有价值，但对 agent 已经不够。更实用的分层是：**模型层**看 harmful compliance，**agent 层**看工具与状态副作用，**系统层**看 ACL、引用、终态、回滚与审计。这样评估结果才能直接落到发布门槛和事故预案里，而不只是论文分数。它也自然连接到 [[22 AI 红队与对抗测试|红队]]、[[24 沙箱、最小权限与人审闸门|运行时控制]] 和 [[38 Agent 评估与可观测性|Agent 评估与可观测性]]。
