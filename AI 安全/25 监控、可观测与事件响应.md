[[25 监控、可观测与事件响应|监控、可观测与事件响应]]是 AI 安全的"事后能看清、事中能止损"能力底座:[[24 沙箱、最小权限与人审闸门|沙箱与闸门]] 是预防,这一层管的是当攻击真的发生时——你能不能**实时发现、快速遏制、事后归因**。没有可观测轨迹,审计、取证、信任都无从谈起。

## 五环闭环
埋点 → 检测 → 响应 → 取证 → 回灌:
1. **可观测埋点(telemetry)**:端到端 tracing,每步一条 span——输入 prompt、思维链、工具选择与参数、工具返回、最终输出;配结构化日志与**决策轨迹(decision trace)**,才能回答"agent 为什么这么做"。
2. **实时检测**:goal-drift 检测、异常检测、越权工具调用、成本/速率突增。
3. **事件响应(IR)**:遏制 → 评估 → 根除 → 恢复。
4. **取证(forensics)**:基于不可变 trace 重建时间线、归因攻击源。
5. **回灌防御**:把攻击样本喂回 [[22 AI 红队与对抗测试|红队库]] / [[23 安全评估基准|评估基准]],检测规则固化进 [[21 Guardrails 与输入输出防护|护栏]]。

## goal-drift 检测:agent 的核心运行时信号
**goal-drift(目标漂移)**= agent 的实际行为逐步偏离最初目标。它可能是 [[14 Excessive Agency 与 Goal Hijack|目标劫持]] 的征兆,也可能是 [[17 Memory 与 Context Poisoning|上下文/记忆投毒]] 累积的结果。检测手段:对 embedding 与 LLM 输出做漂移检测,捕捉响应语义随时间的细微偏移;比对当前动作链与声明目标的一致性。这是把 [[19 人机信任利用与 Rogue Agents|Rogue Agent]] 在彻底失控前抓出来的关键早期信号。

## 监控 vs 评估:同一套 trace,两个战场
监控与开发期的 [[38 Agent 评估与可观测性|Agent 评估]] **共用同一套 tracing 基础设施**,区别只在跑在哪:
- **评估**:在**测试集**上离线跑,发版前打分(对应 [[23 安全评估基准|安全评估基准]])。
- **监控**:在**生产流量**上在线跑,实时盯异常。

所以可观测性投资是一鱼两吃:同一条 trace 既喂评估也喂监控。主流平台 LangSmith / Langfuse / Arize / Datadog 均围绕这套 trace 模型构建。

## 事件响应(IR)四步
针对 AI 系统的 IR 与传统安全同构,但遏制对象是 agent:
1. **遏制(contain)**:熔断、撤销 token、隔离会话——对 [[18 Agent 间通信安全与级联失败|级联失败]],遏制速度直接决定爆炸半径。

**遏制速度 → 爆炸半径手算(为什么 MTTC 是指数级杠杆)**。级联沿信任链按扇出度 $d$ 指数扩散(见 [[18 Agent 间通信安全与级联失败|级联失败]]):设每跳传播耗时 $\tau=2\text{s}$、扇出 $d=3$,则被波及节点数随遏制时间(MTTC,mean-time-to-contain)按 $N(t)=d^{\,t/\tau}$ 涨。检测到 goal-drift 后,**人工响应**典型 MTTC $=60\text{s}\Rightarrow$ 传播 $60/2=30$ 跳,$N=3^{30}\approx2\times10^{14}$(早已打穿全网、纯被预算/配额上限截断);**自动遏制**(检测即熔断)MTTC $=2\text{s}\Rightarrow$ 仅 1 跳,$N=3^{1}=3$。差距是 $3^{29}\approx6.9\times10^{13}$ 倍——**遏制每慢一跳($\tau$),爆炸半径就乘以 $d$**。这就是「有告警必须配自动遏制」的算术根据:在指数扩散面前,人工响应的几十秒延迟不是「慢一点」,而是「差十几个数量级」;监控的价值不在「看见」,而在把 MTTC 从「人反应的秒级」压到「机器熔断的亚秒级」。
2. **评估(assess)**:影响面、波及的数据与下游 agent。
3. **根除(eradicate)**:撤回被投毒的记忆/上下文,封堵注入源。
4. **恢复(recover)**:回滚到可信检查点。

## 何时用 / 坑
- **何时用**:任何上生产的 agent 都需监控;高危(执行代码、动钱、碰隐私、多 agent)系统必须有 goal-drift 检测 + IR 预案 + 可取证日志。
- **坑 1**:只埋最终输出,不埋思维链与工具调用。出事后无法回答"为什么",取证断链。
- **坑 2**:日志可变/可被 agent 自己改。取证依赖**不可变** trace,日志写入要与 agent 执行权隔离。
- **坑 3**:有告警无响应剧本。检测到 goal-drift 却没有自动遏制(熔断/撤权),等于只看着失控发生。
- **坑 4**:监控不回灌。事件复盘出的攻击样本不进基准/护栏,同类攻击反复得手。
- **坑 5**:漂移阈值难调。太敏感误报淹没,太钝放过真劫持;需按业务基线持续校准。

## 关键事实(含出处)
- AI agent 可观测性核心:端到端 tracing(prompt / 思维链 / 工具选择与参数 / 输出)+ 决策轨迹,是审计与取证前提。
- goal-drift / 输出漂移检测:对 embedding 与 LLM 输出做漂移检测,捕捉语义随时间偏移。
- 监控与评估共用 trace 基础设施(LangSmith / Langfuse / Arize / Datadog 等),区别在测试集 vs 生产流量。
- IR 四步(遏制/评估/根除/恢复)与取证依赖不可变决策轨迹。

## 工业界实践
生产里这一层落成"标准化 trace + 实时检测规则 + IR 剧本 + 不可变取证日志"。下面给标准、平台、检测规则与 IR runbook。

### tracing 标准:OpenTelemetry GenAI 语义约定
工业界正收敛到 **OpenTelemetry GenAI Semantic Conventions**(OTel GenAI SIG 自 2024-04 起制定,2026 仍多为 experimental)作为统一埋点标准,避免各平台各埋一套:
- 标准属性:`gen_ai.request.model`、`gen_ai.usage.input_tokens` / `output_tokens`、`gen_ai.response.finish_reasons`,以及(opt-in 后)prompt / completion / tool_call / tool_result 全文。
- 配套项目:**OpenLLMetry**(自动埋点)、各平台原生支持(Datadog 自 OTel v1.37 起原生支持 GenAI 约定)。
- 好处:换平台不用重埋,trace 一份既喂评估也喂监控也喂取证。

### 监控平台与一鱼三吃
| 平台 | 定位 |
|---|---|
| **LangSmith** | LangChain 生态,强 trace + 评估 |
| **Langfuse** | 开源,自托管友好 |
| **Arize Phoenix** | 开源,强漂移/质量监控 |
| **Datadog LLM Observability** | 全栈可观测一体,原生 OTel GenAI |
所有平台围绕同一套 trace 模型:**同一条 trace 既喂开发期 [[38 Agent 评估与可观测性|评估]](测试集离线)、又喂生产监控(在线)、还喂事后取证**——可观测性投资是一鱼三吃。

### 实时检测规则(示意)
```python
# 在每条 span 上跑的检测器
detectors = [
    GoalDriftDetector(embed_drift_threshold=0.4),  # 输出语义偏离声明目标
    AnomalyDetector(baseline="rolling_7d"),         # 偏离业务基线
    UnauthorizedToolCall(allowlist=task.caps),      # 调了不该调的工具
    RateSpikeDetector(calls_per_min=100),           # 速率/成本突增
    PIILeakDetector(),                              # 输出含 PII
]
# 命中 → 告警 + 自动遏制(熔断/撤 token,接 [[24 沙箱、最小权限与人审闸门|闸门]])
```

### IR Runbook(AI 系统事件响应剧本)
```
detect  → goal-drift / 越权工具 / 成本突增告警触发
contain → 熔断该 agent + 撤销其 token + 隔离会话(级联场景:同时冻结下游 agent)
assess  → 从不可变 trace 重建时间线:哪步被注入、波及哪些数据/下游 agent
eradicate → 撤回被投毒的记忆/上下文、封堵注入源(如某 RAG 文档、某 MCP server)
recover → 回滚到可信检查点,恢复服务
postmortem → blameless 复盘,攻击样本回灌 [[22 AI 红队与对抗测试|红队库]] + [[23 安全评估基准|基准]],检测规则固化进 [[21 Guardrails 与输入输出防护|护栏]]
```
关键:**有告警必须配自动遏制**——检测到 goal-drift 却只告警不熔断,等于看着失控发生。

## 面试高频
**Q1:AI agent 的可观测性该埋哪些点?只埋最终输出够吗?**
标准答:不够。要端到端 tracing,每步一条 span——输入 prompt、思维链、工具选择与参数、工具返回、最终输出,外加决策轨迹(decision trace)。只埋最终输出,出事后无法回答"agent **为什么**这么做",取证直接断链。

**Q2:什么是 goal-drift?为什么它是 Agent 监控的核心信号?**
标准答:goal-drift(目标漂移)= agent 实际行为逐步偏离最初目标,可能是 [[14 Excessive Agency 与 Goal Hijack|目标劫持]]的征兆或 [[17 Memory 与 Context Poisoning|记忆/上下文投毒]]累积的结果。检测靠对 embedding 与 LLM 输出做漂移检测,捕捉语义随时间的细微偏移、比对动作链与声明目标的一致性。它是把 [[19 人机信任利用与 Rogue Agents|Rogue Agent]] 在彻底失控前抓出来的关键早期信号。
- 追问"阈值怎么调?"→ 太敏感误报淹没、太钝放过真劫持,需按业务基线持续校准(漂移阈值难调是真实痛点)。

**Q3:监控和评估是两套系统吗?**
标准答:不是,**共用同一套 tracing 基础设施**,区别只在跑在哪——评估在测试集上离线跑(发版前打分,对应 [[23 安全评估基准|基准]]),监控在生产流量上在线跑(实时盯异常)。同一条 trace 一鱼多吃,这也是为什么 OTel GenAI 标准化埋点这么重要。

**Q4(陷阱):为什么取证日志必须"不可变"?**
标准答:若日志可被 agent 自己改(同一执行权限既能动作又能改日志),被劫持的 agent 会篡改/删除痕迹掩盖攻击,取证就失效。所以日志写入要与 agent 执行权**隔离**(append-only、独立写入凭证、WORM 存储),保证 trace 不可篡改才能支撑归因。

**Q5:AI 系统的 IR 和传统安全 IR 有何异同?**
标准答:**同构**——都是遏制/评估/根除/恢复四步;**不同**在遏制对象是 agent:遏制手段是熔断+撤 token+隔离会话(级联场景遏制速度直接决定爆炸半径),根除要撤回被投毒的记忆/上下文、封堵注入源,恢复要回滚到可信检查点。且复盘样本要回灌红队/基准/护栏闭环。

## 知识拓展
- **OTel GenAI 语义约定**(2024–,experimental):正成为 LLM 可观测性事实标准,统一 model/token/tool/cost 等属性;OpenLLMetry 提供自动埋点。引用时注明仍在 experimental 阶段。
- **漂移检测方法**:embedding 漂移(余弦距离/分布距离)、输出分布漂移、行为-目标一致性打分;借鉴传统 ML 的 data/concept drift 监控思想迁移到 LLM 输出。
- **不可变审计**:append-only 日志、WORM、内容寻址(hash 链)是取证可信的前提,与传统 SIEM/SOC 实践一脉相承。
- **对抗演化**:高级攻击会**规避监控**——慢速渐进 goal-drift 躲过阈值、在多个会话间分散动作躲过单会话异常检测、诱导 agent 删自己日志。所以检测要跨会话关联、日志要不可变、阈值要随基线动态校准。
