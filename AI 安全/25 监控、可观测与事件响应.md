[[25 监控、可观测与事件响应|监控、可观测与事件响应]]讲的是：当 agent 已经进生产，安全不再只是“能不能拦住”，还包括**能不能看见、能不能止损、能不能复盘**。预防靠 [[24 沙箱、最小权限与人审闸门|最小权限与闸门]]，运行时安全靠 `trace + detection + containment + recovery` 闭环。这里的观测重点不是 raw CoT，而是**可审计轨迹与环境终态**。

直觉类比是飞行记录仪。航空事故调查不会要求拿到飞行员脑内每个念头，而是需要航向、速度、舵面动作、塔台通联和最终残骸位置。agent 也一样：真正支撑监控与 IR 的，是 prompt、工具调用、参数、工具结果、状态变更、权限使用、引用和终态，而不是私有推理链全文。

先算为什么自动遏制比“有人盯告警”强得多。假设失控 agent 每分钟最多触发 3 个下游动作，连续传播 4 轮，那么波及节点数近似为

$$
N = 1 + 3 + 3^2 + 3^3 + 3^4 = 121
$$

若第 1 轮就自动熔断，只波及 $1+3=4$ 个节点；若等到第 4 轮才人工处置，可能已到 121。不是“晚几分钟而已”，而是**按几何级数放大**。

更一般地，扇出度为 $d$、传播轮数为 $h$ 时，累计波及面近似为

$$
N(h)=\sum_{i=0}^{h} d^i = \frac{d^{h+1}-1}{d-1}
$$

所以监控的价值不只在发现异常，更在于把 MTTC（mean time to contain）压到足够小。

可观测面建议按四层埋：

1. **request 层**：模型、token、延迟、用户/任务/租户标识。
2. **tool 层**：调用了什么工具，用了什么参数，拿回了什么结果。
3. **retrieval / memory 层**：召回了哪些证据、分数、来源、ACL 是否匹配。
4. **outcome 层**：环境终态、是否有副作用、是否可回滚、是否触发审批。

```python
# ✅ 记录可审计轨迹，而不是要求 raw CoT
def record_agent_step(span, task_id, model, tool_call=None, tool_result=None):
    span.set("gen_ai.request.model", model)
    span.set("task.id", task_id)
    if tool_call:
        span.set("tool.name", tool_call.name)
        span.set("tool.args.redacted", redact(tool_call.args))
    if tool_result:
        span.set("tool.result.redacted", redact(tool_result))
    span.set("policy.decision", current_policy_decision())
    span.set("env.outcome_hash", snapshot_environment_hash())
    append_only_store.write(span.export())
```

这里要修正两处常见误解：

- **误解 1：监控必须抓 raw CoT。** 不对。很多生产系统拿不到或不应存 raw reasoning；监控依然可以通过工具轨迹、状态变更、引用和 outcome 做有效审计。
- **误解 2：有 trace 就够了。** 不对。trace 若可被 agent 自己改写，取证就不可信；日志与执行权限必须分离，最好是 append-only / WORM / 独立凭证写入。

OpenTelemetry 这块也要写准确：截至 **2026-07-19**，OpenTelemetry 官网明确把语义约定整体标为 **Development**，GenAI 语义约定已迁移到独立仓库，相关属性（如 `gen_ai.request.model`、`gen_ai.usage.input_tokens`、`gen_ai.retrieval.documents`、`gen_ai.tool.call.arguments`、`gen_ai.tool.call.result`）都带有“可能包含敏感信息”的警告。因此工程上应该做 **opt-in、截断、脱敏、按租户隔离保留期**，而不是默认全量记录。

## 面试高频

回链：[[AI 安全面试题库]]

**Q1：生产 agent 该监控什么？**
监控 request、tool、retrieval/memory、outcome 四层。核心是“做了什么、用了什么权限、改了什么状态、最后环境成了什么样”。

**Q2：为什么说 raw CoT 不是审计前提？**
因为真正可验证的是行为与终态，不是模型脑内文本。很多系统出于隐私、产品或供应商限制也拿不到 raw CoT；这不妨碍你用可审计轨迹做监控和 IR。

**Q3：监控和评估是什么关系？**
同一套 trace 基础设施，离线跑是 eval，在线跑是 monitoring。前者看回归与候选模型，后者看真实流量与事故。

**Q4：为什么日志必须与 agent 执行权限分离？**
否则 agent 一旦被劫持，就能删自己痕迹。可观测性就从“审计资产”变成“被攻击面”。

## 关键事实

- Anthropic 在 **2026-01-09** 的 agent eval 指南中把 **transcript / trace / trajectory** 定义为评估与调试的核心对象，并将 **outcome** 定义为 trial 结束时环境里的真实最终状态；这正是生产监控应优先采集的对象。
- OpenTelemetry 官网截至 **2026-07-19** 仍将语义约定总体标记为 **Development**；GenAI 属性已迁移到独立仓库维护，不应把它写成“已完全稳定定稿的标准”。
- OTel 文档明确对 `gen_ai.retrieval.query.text`、`gen_ai.system_instructions`、`gen_ai.tool.call.arguments`、`gen_ai.tool.call.result` 等属性标出“可能包含敏感信息”的告警，因此默认策略应是 **最小采集、按需开启、可过滤与可截断**。
- OpenTelemetry 2026 的 GenAI 可观测性官方博客明确展示：同一套 GenAI telemetry 可用于定位慢工具调用、token 成本、模型切换和 retrieval 证据问题，说明运行时监控的最小单位已从“最终回答”扩展到完整链路。

真正好用的 IR 剧本通常是：**detect → contain → assess → eradicate → recover → backfill evals**。也就是先发现异常，再熔断与撤权，再看影响面，再清理污染源，再恢复服务，最后把样本回灌到 [[23 安全评估基准|安全评估]] 和 [[22 AI 红队与对抗测试|红队]]。这样监控才不是“出事后看日志”，而是安全闭环的一部分。
