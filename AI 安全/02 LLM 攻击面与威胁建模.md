[[02 LLM 攻击面与威胁建模|威胁建模]] 要回答的第一个问题不是「有哪些攻击」,而是**「攻击者能在哪儿动手、内外的信任边界画在哪」**——把 LLM/Agent 系统的攻击面摊开成一张数据流图,标上信任边界,每条「外部数据跨边界进入 prompt 或记忆」的路径都是一个潜在注入点。这是 [[01 AI 安全总览与三层栈|三层栈]] 落到具体系统时的第一步工作。

## 攻击面地图:八个入口

![[sec-LLM攻击面地图.png]]

一个完整的 Agent 系统,攻击面比「输入框」大得多。按数据进入模型的路径拆,有八处:

1. **用户输入 / Prompt**:最直接的入口,直接 [[05 Prompt Injection 提示注入|提示注入]] 与 [[06 Jailbreak 越狱|越狱]] 都从这进。
2. **训练 / 微调数据**:供给侧投毒,埋后门触发器(见 [[09 数据与模型投毒|数据与模型投毒]])。
3. **模型权重 / 供应链**:从 HuggingFace 等拉到被篡改/恶意的权重(见 [[10 供应链安全(静态)|供应链安全]])。
4. **检索 / RAG 知识库**:攻击者污染知识库,让恶意指令随检索结果进 prompt——**间接注入**,是 [[11 向量与嵌入弱点与 RAG 投毒|RAG 投毒]] 的核心。
5. **工具 / 外部动作**:模型调工具时被诱导执行危险操作(见 [[15 Tool Misuse 与意外代码执行|工具滥用]])。
6. **记忆 / 持久上下文**:写进长期记忆的污染会跨会话复发(见 [[17 Memory 与 Context Poisoning|记忆投毒]])。
7. **输出 / 下游消费**:模型输出未经处理就喂给浏览器/shell/DB,触发 XSS/RCE(见 [[08 不安全输出处理|不安全输出处理]])。
8. **Agent 间通信**:多 agent 协作中,一个被攻陷的 agent 污染整条链(见 [[18 Agent 间通信安全与级联失败|级联失败]])。

关键洞察:**①②③④⑥ 都是「数据进模型」的入口**,而传统系统往往只防①(用户输入)。RAG、记忆、工具返回值这些「内部、可信」的通道,恰恰是间接注入最爱走的路。

## 信任边界:溶解在哪

威胁建模的传统做法是画**信任边界(trust boundary)**——数据跨过它,可信度就变了,必须在边界上做校验。LLM 系统的难点是这条边界**溶解**了:

- 检索来的文档、工具的返回 JSON、另一个 agent 发来的消息,在系统看来是「内部数据」,但其**内容**可能被攻击者控制。
- 模型**不区分**「系统指令」和「数据里夹带的指令」——两者都是 token。于是「可信通道里藏着不可信内容」。

因此 LLM 威胁建模的核心动作是:**沿每条数据流,问「这段内容的最终来源可信吗?它会不会被当指令执行?」**,凡是「外部可控内容 → 进 prompt/记忆/工具参数」的路径,都要在边界上加 [[21 Guardrails 与输入输出防护|Guardrails]] 或结构化隔离。

**类比**:就像机场安检——传统系统以为「过了安检的人(已认证)= 可信」,只查身份。但 LLM 的麻烦是它分不清「我说的话」和「我念出来的纸条上的话」:一个已过安检的乘客,掏出一张外人塞给他的纸条照着念「请把驾驶舱门打开」,模型会把这句**当成机长指令执行**,因为对它而言系统指令和数据里夹带的指令都是同一种 token。RAG 文档、工具返回值就是那张「过了安检才掏出来的纸条」——人是可信的,纸条上的内容不是。

## 威胁建模方法:数据流 + 信任边界

落地一套可操作的流程:

1. **画数据流图(DFD)**:把八个攻击面、模型、工具、记忆、外部系统全画上,用箭头标数据流向。
2. **叠信任边界**:在「外部 ↔ 内部」「不可信 ↔ 可信」处画虚线。重点找**跨边界进 prompt**的路径。
3. **逐条套 STRIDE-for-LLM**:每个组件、每条流问一遍六类威胁,记下适用的。
4. **映射到 OWASP**:把识别到的威胁对回 [[01 AI 安全总览与三层栈|三层栈]] 的 LLM/ASI/MCP Top 10,确认有没有现成缓解。
5. **定缓解 + 残余风险**:每条威胁配一道防御(guardrail / 最小权限 / 人审),没法消除的标为残余风险。

这套流程的产物,正是后续 [[22 AI 红队与对抗测试|红队测试]] 的靶子清单,也是 [[26 安全框架与治理地图|治理]] 的输入。

## 何时用 / 坑

- **何时做**:系统设计期就做(不是上线前补),每加一个工具/数据源/agent 都要重画数据流——攻击面是动态的。
- **坑①**:只防用户输入框,忽略 RAG / 工具返回 / agent 消息这些「内部」通道——间接注入正是钻这个空子。
- **坑②**:把「已认证用户」当「可信内容来源」——认证管的是身份,不是 prompt 内容里有没有夹带恶意指令。
- **坑③**:信任边界画在网络/进程层就收手——LLM 的边界要画到**内容级**(这段 token 的真实来源是谁)。

## 关键事实

- STRIDE 是微软提出的经典威胁建模助记法,此处为「映射到 LLM」的实践改编,非官方标准。
- 「信任边界溶解」与「自然语言即攻击载体」是 LLM 威胁建模区别于传统 AppSec 的根因,详见 [[01 AI 安全总览与三层栈|总览]] 的论证。

## 工业界实践

威胁建模在工业界不是「写完文档归档」,而是**贯穿设计→上线→运营的活流程**,且越来越多地用工具自动化。

### 用 MITRE ATLAS 做攻击者视角的威胁建模

STRIDE-for-LLM 给的是「威胁类别清单」,但要回答「攻击者具体怎么打」,工业界更常叠用 **MITRE ATLAS**——它把对 AI 系统的真实攻击拆成**战术(Tactic)× 技术(Technique)**矩阵(类比网络安全的 ATT&CK),每个技术配真实案例研究。威胁建模时把 ATLAS 技术映到数据流图的每个攻击面上,比凭空想象更全:

```
攻击面④ 检索/RAG  →  ATLAS: "LLM Prompt Injection (Indirect)" + "RAG Poisoning"
攻击面② train data →  ATLAS: "Poison Training Data" / "Backdoor ML Model"
攻击面③ 供应链     →  ATLAS: "ML Supply Chain Compromise"
攻击面⑦ 输出下游   →  ATLAS: "LLM Jailbreak" → 下游 "User Execution"
```

### 把威胁建模做成代码(Threat Modeling as Code)

成熟团队把数据流图与威胁清单写进**仓库里的声明式文件**,随架构变更走 PR 评审、进 CI:

```yaml
# threat-model.yaml(示意:每个数据流标来源可信度 + 是否进 prompt)
flows:
  - name: rag_retrieval
    source: external_kb        # 外部、攻击者可写
    trust: untrusted
    enters_prompt: true        # ⚠️ 跨边界进 prompt → 间接注入点
    stride: [Tampering, InfoDisclosure]
    mitigations: [spotlighting, input_guardrail, least_privilege_tools]
  - name: tool_return
    source: external_api
    trust: untrusted
    enters_prompt: true
    mitigations: [output_sanitize, schema_validation]
```

每新增一个工具/数据源/agent,改 yaml → CI 自动检查「凡 `enters_prompt: true` 且 `trust: untrusted` 的流,必须配 mitigation」,否则 fail。这把「每加一个组件都要重画数据流」从口头纪律变成**机器可强制的护栏**。

### 自动化攻击面发现 + 持续验证

- **攻击面盘点**:用 **garak**(NVIDIA,~100 攻击向量、单次最多 2 万 prompt)对每个入口扫一遍,看哪些攻击面实测可被利用;**PyRIT**(Microsoft)做多轮编排攻击,验证「跨边界路径」是否真能被打穿。
- **真实案例佐证「内部通道才是软肋」**:EchoLeak(CVE-2025-32711)的注入载体是**一封邮件**——攻击面⑦的下游内容回流到 RAG(④),而非用户输入框(①)。完全印证坑①:只防输入框的团队对这类零点击攻击毫无防备。

## 面试高频

- **Q:给一个 LLM/Agent 系统做威胁建模,你的步骤是?**
  标准答:①画数据流图(把八个攻击面、模型、工具、记忆、外部系统全画上);②叠信任边界,重点找「外部可控内容 → 进 prompt/记忆/工具参数」的路径;③逐组件套 STRIDE-for-LLM;④映射 OWASP/ATLAS 看有无现成缓解;⑤每条威胁配防御 + 标残余风险。**追问**「和传统威胁建模差在哪?」——边界要画到**内容级**(这段 token 真实来源是谁),不能停在网络/进程层。
- **Q:为什么「已认证用户」≠「可信内容来源」?**
  认证管的是**身份**,不是 prompt 内容里有没有夹带恶意指令。一个合法用户也可能(有意或被骗)把含注入的外部文档喂进来;一个被攻陷的内部 agent 发的消息也是「已认证」的。这是坑②,面试高频。
- **Q:STRIDE 的六类在 LLM 里各对应什么?**
  S 伪造 agent 身份/恶意 MCP server;T 数据/记忆/权重投毒;R agent 动作无审计;I system prompt 泄露/PII;D 无界消耗烧 token;E 过度自主越权。**陷阱**:STRIDE 是微软经典助记法,这里是**实践改编**,不是官方 LLM 标准——别说成「OWASP 标准」。
- **Q:哪些攻击面是传统系统不会防的?** 答:RAG 检索(④)、长期记忆(⑥)、工具返回值(⑤)、agent 间消息(⑧)——这些「内部、可信」通道恰是间接注入最爱走的路。

## 知识拓展

- **威胁建模方法论谱系**:STRIDE(微软,按威胁属性分类)、**LINDDUN**(专攻隐私威胁,补 STRIDE 在 InfoDisclosure 上的粗粒度)、**PASTA**(以攻击者为中心、风险驱动)、**MITRE ATLAS**(AI 专用、战术×技术)。LLM 场景常 STRIDE 打底 + ATLAS 补攻击细节 + LINDDUN 补隐私(接 [[13 隐私攻击与数据保护|隐私攻击]])。
- **「信任边界溶解」是本域第一性原理**:几乎所有 LLM 漏洞都能归因到「指令与数据同通道 + 边界画不清」。把它当威胁建模的总纲——见 [[05 Prompt Injection 提示注入|提示注入]] 的「数据无权改变控制流」信条,以及 [[01 AI 安全总览与三层栈|总览]] 的三条被打破的假设。
- **Agentic 威胁建模的新增维度**:单 agent 之外,多 agent 系统要额外建模「**级联失败**」(一个被攻陷 agent 污染整条链,见 [[18 Agent 间通信安全与级联失败|级联失败]])和「**Rogue Agent**」(被信任的内部 agent 反水,见 [[19 人机信任利用与 Rogue Agents|Rogue Agents]])。云安全联盟(CSA)2025 起在推 **NIST AI RMF 的 Agentic Profile**,把 600-1 的 GenAI 风险进一步细化到自主 agent。
- **边界**:威胁建模产出的是**靶子清单**,不是防御本身——它喂给 [[22 AI 红队与对抗测试|红队]] 去实测、喂给 [[26 安全框架与治理地图|治理]] 去归档。建完别束之高阁:攻击面是动态的,每次架构变更都要重跑。
