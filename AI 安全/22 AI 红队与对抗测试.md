[[22 AI 红队与对抗测试|AI 红队(red teaming)]]是**主动**对自家 AI 系统发起对抗攻击、抢在真实攻击者之前把漏洞挖出来的方法论。它不是"跑个测试集打个分",而是带着敌意、开放式地探索系统在哪会崩——是 [[21 Guardrails 与输入输出防护|护栏]] 与对齐有没有用的试金石。

## 红队 ≠ 评估基准
两者常被混为一谈,但职责相反:
- **红队**=主动**找**漏洞。开放、对抗、靠人的创造力,产出"这里能被攻破"的新发现。
- **[[23 安全评估基准|评估基准]]**=量化**已知**漏洞。固定数据集、可复现、可横比,产出一条能随版本追踪的分数曲线。

红队挖到的新攻击会沉淀进基准;基准跑出的弱项又指引下一轮红队。二者互为输入,缺一不可。

**回归指标手算。** 设一轮固定的 held-out 攻击集有 $T=50$ 个 trial,预先定义「绕过护栏且达成有害终态」为成功,其中 $S=3$ 个成功,则
$$\mathrm{ASR}=\frac{S}{T}=\frac{3}{50}=0.06=6\%.$$
这 6% 只在同一攻击集、模型/系统版本、工具权限、采样设置、judge rubric 与日期下可比较;它不是跨产品的安全排名。还应同时报告拒绝误伤、终态危害级别、成本和未覆盖威胁。

## 自动化 vs 人工红队
- **自动化红队**:用工具规模化重放已知攻击模式(越狱模板、注入载荷、PII 套取),覆盖广、跑得勤、能进 CI。
- **人工红队**:人去做多轮自适应攻击(如 Crescendo——逐步升级把模型一步步引偏),挖自动化覆盖不到的、上下文相关的创造性漏洞。

成熟实践两者都要,且是**持续红队(continuous red teaming)**:不是发版前测一次,而是常驻流水线,每次改动自动回归。

## 主流工具
- **PyRIT**(Microsoft):Python 攻击编排框架,擅长自定义多轮攻击(内置 Crescendo、TAP),集成 Azure AI Foundry,攻击库来自微软测真实系统的经验。适合需要定制编排的安全研究者。
- **Garak**(NVIDIA):模型级漏洞扫描器,120+ 探针(probe),回答"这个**基座模型**能不能安全部署";对 agentic/RAG 场景覆盖有限。
- **Promptfoo**:应用层测试框架,可用于 CI/CD 与对抗测试。**截至 2026-03-09**,OpenAI 公布的是「拟收购」并说明交割后计划把技术整合进 OpenAI Frontier;公告没有披露价格,也不应把公告写成已完成收购或断言未来许可状态。
- **DeepTeam**(Confident AI):OWASP LLM Top 10 映射最清晰、上手最简单,与 DeepEval 同框架,适合已用 DeepEval 做评估的团队。

一句话选型:Garak 给模型层深探针,Promptfoo 给应用层 CI 集成,二者互补;PyRIT 给定制多轮编排;DeepTeam 给最低门槛与最清 OWASP 对齐。

## 何时用 / 坑
- **何时用**:任何要上线的 LLM/Agent 系统,发布前必做红队;高危场景(能执行代码、动钱、碰隐私)需持续红队。
- **坑 1**:只跑自动化。模板化攻击覆盖不到新型、组合型、上下文相关的漏洞,真正危险的往往是人工才能挖到的。
- **坑 2**:红队报告不闭环。挖到漏洞不回灌成护栏规则 + 基准 case,下次照样翻车。
- **坑 3**:只测模型不测系统。真实攻击面在整个 [[02 LLM 攻击面与威胁建模|应用链路]](RAG、工具、记忆、agent 间通信),只用 Garak 扫基座模型会漏掉一大半。
- **坑 4**:把 ASR 当唯一指标。攻击"成功"的判定本身有主观性,不同基准的 judge 口径不一,横比要小心。

- Garak:NVIDIA 开源,120+ 探针,模型级扫描。
- Promptfoo:开源应用层红队/评估框架。OpenAI 于 **2026-03-09** 公布**拟收购** Promptfoo,交割后计划整合其技术到 OpenAI Frontier;官方公告未披露交易价格。来源:[OpenAI — *OpenAI to acquire Promptfoo*](https://openai.com/index/openai-to-acquire-promptfoo/)(核验:2026-07-18)。部署时应以当前仓库的许可证、release 和服务条款为准。

## 工业界实践
成熟团队把红队做成**流水线里的常驻能力**,而非发版前一次性活动。下面给工具矩阵、攻击技法库、CI 集成与闭环流程。

### 工具选型矩阵
| 工具 | 厂商 | 层次 | 强项 | 适用 |
|---|---|---|---|---|
| **PyRIT** | Microsoft | 编排框架 | 自定义多轮攻击(内置 Crescendo、TAP),集成 Azure AI Foundry | 安全研究者做定制编排 |
| **Garak** | NVIDIA | 模型级扫描 | 120+ 探针,回答"基座模型能否安全部署" | 模型选型/上线前体检 |
| **Promptfoo** | 独立项目；OpenAI 于 2026-03-09 公布拟收购 | 应用层 + CI | 可接 CI/CD,带合规映射 | 应用层持续回归 |
| **DeepTeam** | Confident AI | 应用层 | OWASP LLM Top 10 映射最清,门槛最低,与 DeepEval 同框架 | 已用 DeepEval 的团队 |
| **Giskard / Garak+自研** | — | 混合 | RAG/幻觉专项扫描 | RAG 系统 |

一句话:**Garak 给模型层深探针,Promptfoo/DeepTeam 给应用层 CI,PyRIT 给定制多轮编排**——多数生产团队是"Garak 体检模型 + Promptfoo 守 CI + PyRIT 做专项研究"组合拳。

### 攻击技法库(红队的"弹药清单")
- **单轮**:GCG 对抗后缀、角色扮演(DAN 类)、编码混淆(base64/ROT13/leetspeak)、低资源语言、ASCII art。
- **多轮/自适应**:**Crescendo**(逐步升级,把模型一步步引偏,每条单看都"干净")、**TAP**(Tree of Attacks with Pruning,[[Agent/14 树搜索：ToT 与 LATS|树搜索]]+剪枝自动生成越狱)、**PAIR**(攻击者 LLM 迭代改 prompt)。
- **Agent 专属**:间接注入(把载荷藏进 RAG 文档/工具返回/网页)、工具滥用诱导、记忆投毒、跨 agent 级联(见 [[18 Agent 间通信安全与级联失败|级联失败]])。
- **判定(judge)**:用关键词匹配(快但脆)或 [[LLM/112 人评、LLM-as-judge 与 Arena|LLM-as-judge]](准但贵且有口径漂移);前沿做法用 **StrongREJECT** 式 rubric judge(先 CoT 再给二元拒答分 + 两个 5 级 Likert 分),与人工判定一致性最高。

### CI 集成参考(持续红队)
```yaml
# .github/workflows/redteam.yml (示意)
on: [pull_request, schedule]   # 每次改 prompt/工具 + 每日定时
jobs:
  redteam:
    steps:
      - run: promptfoo eval -c redteam.yaml   # 应用层:重放越狱/注入载荷库
      - run: garak --model_type rest --probes jailbreak,promptinject  # 模型层探针
      - run: python pyrit_crescendo.py         # 专项:多轮自适应
      # 任一 ASR 超阈 → fail PR;新 case 自动归档进回归库
```
关键不是"跑一次",而是**回归库随每次红队增长**——挖到的新攻击固化成 case,下次改动自动重测。

### 闭环最佳实践
红队真正的价值在**闭环**:发现 → 回灌护栏规则([[21 Guardrails 与输入输出防护|护栏]])+ 沉淀成 [[23 安全评估基准|基准 case]] → 下轮自动回归。不闭环的红队 = 每次重复挖同一个洞。高危系统(执行代码、动钱、碰隐私)需**持续红队**常驻流水线,而非发版前测一次。

## 面试高频
**Q1:红队和评估基准有什么区别?**
标准答:职责相反但互补。红队=主动**找**未知漏洞,开放、对抗、靠人的创造力,产出"这里能被攻破";基准=量化**已知**漏洞,固定数据集、可复现、可横比,产出能随版本追踪的分数。红队挖到的新攻击沉淀进基准,基准跑出的弱项指引下轮红队。

**Q2:自动化红队和人工红队怎么分工?能只做自动化吗?**
标准答:自动化规模化重放已知模式(模板越狱、注入载荷),覆盖广、能进 CI;人工做多轮自适应攻击(如 Crescendo),挖上下文相关的创造性漏洞。**不能只做自动化**——模板化覆盖不到新型、组合型、上下文相关漏洞,真正危险的往往只有人工才能挖到。成熟实践是两者都做且持续化。

**Q3(陷阱):防御为什么不可能彻底?红队能"测完"吗?**
标准答:攻击面是**开放且演化**的——护栏越强,攻击越往绕护栏走(编码混淆、低资源语言、多轮 Crescendo)。红队量化的永远是某一时刻的已知攻击,新攻击持续出现,所以红队是**持续过程不是一次性验收**。声称"测完了所以安全"是错误答法。

**Q4:为什么不能只用 Garak 扫基座模型就算红队完成?**
标准答:真实攻击面在整个**应用链路**(RAG、工具、记忆、agent 间通信),Garak 是模型级扫描,会漏掉间接注入、工具滥用、记忆投毒、级联失败这一大半 Agent 风险。要补应用层(Promptfoo/DeepTeam)+ 编排层(PyRIT)。

**Q5(陷阱):ASR 高就一定危险、低就一定安全吗?**
标准答:不一定。ASR 的"成功"判定本身有主观性,不同基准 judge 口径不一(关键词 vs LLM judge),**不能裸跨基准比**;且 Agent 场景要看"越狱后真能不能办成多步坏事"(HarmScore)而非"嘴上答应"。只看单一 ASR 数字会误判。

**Q6:如何处理红队工具的厂商/收购新闻?**
标准答:把「工具能力」和「公司交易状态」拆开。选择工具时验证当前版本、许可证、部署方式、数据边界、CI 集成和可重复的评测卡;对收购只引用官方公告的状态与日期。**陷阱**:公告写「to acquire」不等于已经交割,未公开价格不能补成市场传闻数字。

## 知识拓展
- **多轮越狱**:**Crescendo**(Microsoft,2024)、**TAP**(arXiv:2312.02119)、**PAIR**(arXiv:2310.08419)是自适应越狱代表;它们专门绕"单条 prompt 输入闸",因为每一轮单看都无害。
- **judge 演进**:**StrongREJECT**(2024)指出很多越狱的"成功"是 judge 误判,提出 rubric-based 评估器(可配任意 LLM)+ 微调 Gemma-2B 评估器,与人工一致性 SOTA;红队报告引用 ASR 时应说明用的哪种 judge。
- **持续红队产品化**:Microsoft 的 AI Red Team 经验沉淀进 PyRIT;Gray Swan、HackerOne 等推出 AI 红队众测;前沿实验室(Anthropic/OpenAI)发布前做内部红队 + 外部专家红队 + 自动化对抗评估三层。
- **对抗演化**:红队与护栏是"军备竞赛"——红队挖洞→护栏补→新越狱绕护栏→红队再挖。所以红队库与 [[21 Guardrails 与输入输出防护|护栏规则]]、[[23 安全评估基准|基准]] 必须协同迭代。
