[[044 专家容量、丢弃与负载均衡损失]]:让 MoE 训得起来的三件套——给每个专家设一个**容量上限**、超出的 token 直接**丢弃**(只走残差),再加一个**辅助负载均衡损失**逼 [[043 门控路由与 top-k 选择|门控]] 把 token 均摊到各专家,防止"专家坍缩"。

## ① 直觉:为什么会坍缩,以及怎么救

[[043 门控路由与 top-k 选择|门控]] 的输出既选专家又当权重,天然"强者愈强":某专家一开始被选得多 → 训得更好 → 门控更爱选它 → 形成**正反馈**。最坏情况退化成只有一两个专家在干活、其余饿死,这叫**专家坍缩(routing collapse)**。坍缩=白白浪费了大部分容量,MoE 的意义就没了。

两个独立但配合的机制把它救回来:

- **容量 + 丢弃(系统层面)**:GPU 上各专家的 buffer 是**定长**的(为了静态形状、能批处理)。给每个专家定一个容量 $C$,先到先得;某专家被路由超过 $C$ 个 token 时,**溢出的 token 被丢弃**——这一层不过任何专家,只靠残差直通。这保证了张量形状固定、通信可预测。
- **辅助负载均衡损失(训练层面)**:光丢弃只是"截断症状",不解决"门控偏心"。再加一个**辅助损失 $L_{\text{aux}}$**,显式惩罚"负载不均",把门控往"均摊"方向推。

直觉:容量丢弃是"硬性限流",均衡损失是"软性引导";两者一起才让所有专家都被充分训练。

## ② 例子:容量因子与丢弃,小数字

设一个 batch 有 $T=12$ 个 token,$N=4$ 个专家,top-1 路由。理想下每专家 $12/4=3$ 个。

**容量** $C = \text{容量因子}\times \dfrac{T}{N}$。取容量因子 $=1.25$,则 $C=1.25\times 3 = 3.75 \to 4$(取整)。

假设门控实际把 token 分成:E1 收 6、E2 收 4、E3 收 1、E4 收 1。

- E1 收 6 > $C=4$ → **丢弃 2 个**(t8、t10 这种,只走残差)。
- E2 恰好 4 个,全处理。
- E3、E4 没满,全处理。

这一步**丢弃率 = 2/12 ≈ 17%**。容量因子调大(如 2.0)→ 丢弃几乎为 0,但每个专家 buffer 更大 → 显存和通信更贵。所以容量因子是"丢弃率 ↔ 成本"的旋钮:训练常用 $1.0\sim1.25$,推理可放宽到 $2$ 甚至无丢弃。

**为什么 buffer 必须定长(不能动态)?** GPU 上 all-to-all 通信和矩阵乘都要**静态形状**才高效:每个专家收多少 token 事先不知道(动态路由),但张量得提前开好。于是「定容量 $C$ + 超出丢弃 + 不足补零(padding)」把不规则的路由结果**裁成规整的 $[N_{\text{experts}}, C, d]$ 张量**,这样才能批处理、跨卡通信。代价就是丢弃(浪费输入)和补零(浪费算力)——容量因子就是在这两种浪费间找平衡。

**top-2 下容量怎么算?** 上面是 top-1。top-2 时每个 token 占用 2 个专家槽位,容量公式变成 $C=\text{cf}\times\dfrac{k\cdot T}{N}$。$T=12,N=4,k=2,\text{cf}=1.25$:$C=1.25\times\dfrac{2\times12}{4}=1.25\times6=7.5\to8$。槽位总需求 $kT=24$、总容量 $NC=32$,留了余量吸收不均。

## ③ 原理:负载均衡损失公式

以 Switch / GShard 的可微分负载均衡损失为例。对一个 batch 的 $T$ 个 token、$N$ 个专家,定义两个量:

- $f_i$:**实际被路由到专家 $i$ 的 token 占比**(取 argmax 后统计,离散、不可导):

$$
f_i = \frac{1}{T}\sum_{t=1}^{T} \mathbb{1}\big[\arg\max_j g_j(x_t) = i\big]
$$

- $P_i$:**门控分配给专家 $i$ 的平均概率**(softmax 输出的均值,可导):

$$
P_i = \frac{1}{T}\sum_{t=1}^{T} g_i(x_t)
$$

辅助损失定义为两者的内积、乘以 $N$:

$$
L_{\text{aux}} = \alpha\cdot N\cdot\sum_{i=1}^{N} f_i\,P_i
$$

**为什么这个式子能均衡?** 注意 $f_i$(虽不可导,当常数看)是"实际有多少 token 落到 $i$",$P_i$(可导,梯度从这进)是"门控想给 $i$ 多大概率"。把它们相乘求和:某专家既被路由得多($f_i$ 大)、门控又给它高概率($P_i$ 大),乘积就大,损失就大 → 梯度去**压低这个专家的 $P_i$**。在约束 $\sum_i f_i=\sum_i P_i=1$ 下,$\sum f_i P_i$ 当 $f_i=P_i=1/N$(完全均衡)时取最小 $1/N$,故乘 $N$ 把最优值归一到 1。$\alpha$ 是权重系数(Switch 取 $10^{-2}$ 量级),太大伤主任务、太小压不住坍缩。

总损失:

$$
L = L_{\text{CE}} + \alpha\,L_{\text{aux}}\;(+\;c_z\,L_z,\ \text{见 [[048 路由稳定性：router z-loss|z-loss]]})
$$

其中 $L_{\text{CE}}$ 是主任务的 [[30 交叉熵与负对数似然|交叉熵]]。

**逐数字验证「均衡时损失最小」**。$N=4$:

- 完全均衡 $f=P=[0.25,0.25,0.25,0.25]$:$\sum f_i P_i = 4\times0.25\times0.25=0.25=1/N$,乘 $N$ 后 $L_{\text{aux}}/\alpha = 4\times0.25=1.0$ → **最小值 1**。
- 严重坍缩 $f=P=[0.85,0.05,0.05,0.05]$:$\sum f_iP_i=0.85^2+3\times0.05^2=0.7225+0.0075=0.73$,乘 $N=4$ → $2.92$ → 损失大近 3 倍。

可见越不均、损失越大,梯度就把门控往「压低过载专家的 $P_i$」推。这就是这个看似奇怪的「$f_i\cdot P_i$ 内积」为什么能均衡。

**两个相关但不同的损失,别混**:Shazeer 2017 还提过 **importance loss**(惩罚各专家「门控概率总和」的变异系数平方 $\text{CV}^2$)和 **load loss**(惩罚实际分配数的方差)。Switch/GShard 的 $\alpha N\sum f_iP_i$ 是把「重要性」与「实际负载」合到一个可微式子里的简洁版,是现在最常引用的那个。

![[moe-负载均衡.svg]]

补充:也有"**无辅助损失**"路线——[[047 DeepSeek MoE：细粒度与共享专家|DeepSeek]] 后续(V2/V3)用 per-expert 可学习偏置(bias),在路由打分上动态加减偏置来均衡,避免辅助损失对主任务梯度的干扰。

**层级均衡:expert-level vs device-level**。专家分布在多卡时,光「每个专家均衡」还不够——还要「每张卡均衡」,否则某卡上的几个专家都热门 → 这张卡被打爆、别的卡闲着(木桶效应,见 [[049 专家并行 EP 与 MoE 部署|EP]])。DeepSeekMoE 因此同时用 **expert-level**(专家间均衡)和 **device-level**(设备/卡间均衡)两种辅助损失;V3 进一步加「设备受限路由」(每 token 最多发往固定数量的节点)压跨机通信。

## ④ 代码:负载均衡损失 + 容量丢弃(❌只丢弃 vs ✅丢弃+均衡损失)

```python
import torch, torch.nn.functional as F

def moe_loss_and_route(logits, capacity_factor=1.25, alpha=1e-2):
    # logits:(T, N) 门控原始打分
    T, N = logits.shape
    g = F.softmax(logits, dim=-1)                  # (T, N)
    assign = g.argmax(-1)                           # 每 token 选的专家 (top-1)

    # ---- 辅助负载均衡损失 ----
    f = torch.zeros(N).scatter_add_(0, assign, torch.ones(T)) / T   # 实际占比 f_i
    P = g.mean(0)                                   # 平均门控概率 P_i(可导)
    L_aux = alpha * N * torch.sum(f.detach() * P)   # f 当常数(detach),梯度从 P 走

    # ---- 容量丢弃 ----
    C = int(capacity_factor * T / N)                # 每专家容量
    keep = torch.ones(T, dtype=torch.bool)
    for e in range(N):
        idx = (assign == e).nonzero(as_tuple=True)[0]   # 路由到该专家的 token
        if idx.numel() > C:
            drop = idx[C:]                          # 先到先得,超出的丢弃
            keep[drop] = False                      # 被丢的 token 只走残差
    return L_aux, assign, keep

# ❌ 错:只设容量丢弃,不加 L_aux
#    → 门控仍偏心,把 token 都挤向少数专家,丢弃率居高不下、专家坍缩
# ✅ 对:L_aux 把门控往均摊推,丢弃率自然降下来,各专家都被训练
logits = torch.randn(12, 4, requires_grad=True)
L_aux, assign, keep = moe_loss_and_route(logits)
print(L_aux.item(), keep.sum().item(), "/", keep.numel())   # 损失值、保留 token 数
```

## 面试高频

- **Q:什么是专家坍缩,为什么会发生?** 门控输出既选专家又当权重 → 强者愈强的正反馈,导致少数专家抢走多数 token、其余饿死,浪费容量。
- **Q:负载均衡损失的两个量 $f_i$、$P_i$ 各是什么?** $f_i$=实际路由到专家 $i$ 的 token 占比(离散、当常数);$P_i$=门控给 $i$ 的平均 softmax 概率(可导、梯度入口)。$L_{\text{aux}}=\alpha N\sum f_i P_i$,在 $f_i=P_i=1/N$ 时最小。
- **Q:$f_i$ 不可导,损失怎么训?** 把 $f_i$ detach 当常数,梯度只从 $P_i$(softmax 输出)回流,等价于"对实际负载大的专家压低门控概率"。
- **Q:容量因子是什么、怎么权衡?** $C=\text{容量因子}\times T/N$;调大→丢弃少但显存/通信贵,调小→省但丢弃多。训练常 $1.0\sim1.25$。
- **Q:被丢弃的 token 怎么办?** 这一层不过任何专家,只靠 [[009 残差连接与梯度流|残差]] 直通,信息不彻底丢失但少了一次专家加工。
- **Q:有没有不用辅助损失的均衡法?** 有,[[047 DeepSeek MoE：细粒度与共享专家|DeepSeek-V2/V3]] 用 per-expert 可学习偏置做无辅助损失均衡,避免辅助损失干扰主任务梯度。
- **Q:为什么 buffer 要定长?** all-to-all 通信和矩阵乘需要静态形状;容量 + 丢弃 + 补零把动态路由裁成规整张量 $[N,C,d]$,才能高效批处理与跨卡通信。
- **Q:expert-level 和 device-level 均衡有何不同?** 前者保证各专家均摊 token,后者保证各 GPU/节点均摊负载(防某卡被打爆拖慢整批);多卡 MoE 两者都要。
- **Q:top-2 的容量公式?** $C=\text{cf}\times kT/N$(top-1 即 $k=1$);每 token 占 $k$ 个专家槽位,所以分子带 $k$。
- **Q:均衡损失为什么能用 $f_i\cdot P_i$ 内积?** 过载专家「实际负载 $f_i$ 大且门控概率 $P_i$ 大」→ 乘积大 → 损失大 → 梯度压低其 $P_i$;均匀分布时取最小 $1/N$。

## 关键事实

- 专家容量、token 丢弃、可微分负载均衡损失 $L_{\text{aux}}=\alpha N\sum_i f_i P_i$ 由 GShard(Lepikhin et al., 2020,arXiv:2006.16668)与 Switch Transformer(Fedus et al., 2021,arXiv:2101.03961)确立。
- Switch 中辅助损失系数 $\alpha=10^{-2}$,容量因子常用 $1.0\sim1.25$(训练)。
- $\sum_i f_i=\sum_i P_i=1$,故 $\sum_i f_i P_i$ 在均匀分布 $1/N$ 时取最小 $1/N$,乘 $N$ 使最优值为 1。
- 无辅助损失均衡(auxiliary-loss-free,per-expert bias)由 DeepSeek-V2(2024,arXiv:2405.04434)/V3(2024,arXiv:2412.19437)采用,减少辅助损失对主任务的干扰。
- Shazeer 2017 早期用 importance loss($\text{CV}^2$ of 门控概率和)+ load loss(分配数方差);Switch/GShard 的 $\alpha N\sum f_iP_i$ 是合二为一的简洁可微版。
- 多卡 MoE 需 expert-level + device-level 双重均衡;DeepSeek-V3 加设备受限路由(每 token ≤4 节点)压跨机 all-to-all。
- 定长 buffer + 容量 + 丢弃/补零是为了静态张量形状,服务于高效 all-to-all 与批处理(见 [[049 专家并行 EP 与 MoE 部署|EP]])。
- 路由 logits 还可能整体漂移变大,需配 [[048 路由稳定性：router z-loss|router z-loss]];均衡与稳定是两个不同问题。
