[[050 分词总览与子词动机|分词总览与子词动机]] 讲的是:模型只认整数,所以先得把文本切成一个个**token**再映射成 id;切成「词」会词表爆炸又遇 OOV(未登录词),切成「字符」序列又太长,**子词(subword)**在「词表大小 ↔ 序列长度 ↔ 覆盖率」这个三角里取平衡,是当代 LLM 的标准做法。

## 直觉

神经网络吃的是向量,不是字符串。所以喂模型前要走一条流水线:**文本 → 切成 token → 每个 token 查词表得整数 id → id 查嵌入表得向量**(见 [[054 词嵌入层与权重绑定|嵌入层]])。「怎么切」就是**分词(tokenization)**,它决定了词表长什么样、序列多长。

最朴素的两端各有死穴:

- **按词切**:`"the cat sat"` → `[the, cat, sat]`。序列短、语义整。但英语词形千变万化(low/lower/lowest/lowing…),要全收进词表得几十万条,**词表爆炸**;更要命的是**OOV**——训练时没见过的词(拼写错误、新词、专有名词)只能映射成一个 `[UNK]`,信息全丢。
- **按字符/字节切**:`"cat"` → `[c, a, t]`。词表极小(英文几十个、字节级 256 个)、**永不 OOV**。但序列**暴长**,而注意力是 [[014 注意力复杂度 O(n²) 与瓶颈|O(n²)]],逐字符算太贵;且每个字符语义稀薄,模型得花容量先把字母拼成词,浪费。

**子词**取中间:**高频词整块保留,低频词拆成有意义的片**。`"lowest"` → `[low, est]`,`"unhappily"` → `[un, happ, ily]`。这样:① 词表可控(常 3 万~15 万);② 没见过的词也能拆成已知子词,**几乎不 OOV**;③ `low`、`lower`、`lowest` 共享 `low` 这个子词,模型天然知道它们相关。三种主流子词算法是 [[051 BPE 与 Byte-level BPE|BPE]]、[[052 WordPiece、Unigram 与 SentencePiece|WordPiece / Unigram]]。

一句话:**子词 = 用「能拼出任意词」的中等词表,同时躲开「词表爆」和「序列长」两个坑。**

## 例子

**同一句话三种切法,数字对比一下**。句子 `"the lowest cats"`(假设训练时见过 `the`、`cats`,没见过 `lowest`):

| 粒度 | 切分结果 | token 数 | 词表大小 | 遇到 "lowest" |
|---|---|---|---|---|
| 词级 | `[the, [UNK], cats]` | 3 | ~30 万 | ✗ 变 UNK,丢信息 |
| 子词 | `[the, low, est, cats]` | 4 | ~5 万 | ✓ 拆成 low+est |
| 字符级 | `[t,h,e,l,o,w,e,s,t,c,a,t,s]` | 13 | ~30 | ✓ 但序列 3 倍长 |

子词在「token 数只比词级多一点、词表只有词级的 1/6、还不丢信息」上全面占优。

**词表大小 vs 覆盖率的权衡**。词表越大,高频整词越多、序列越短,但嵌入表(词表 × `d`)越大、长尾词训练越不充分。实践经验值:英文为主约 3 万~5 万;多语言/代码模型放到 10 万~25 万(LLaMA-3 用 12.8 万、GPT-4 的 cl100k 约 10 万)。这是个**速度(序列短)↔ 参数(嵌入表大)** 的折中。

**嵌入表多大?** 词表 $V$、隐藏维 $d$,嵌入表参数 = $V\times d$。LLaMA-2($V=32000,d=4096$):$\approx 1.3$ 亿;LLaMA-3 把 $V$ 涨到 128256:$\approx 5.2$ 亿——光嵌入表就大了 4 倍。但因为序列更短(token 更省),整体推理算力反而可能下降。这就是「扩词表」的账:**嵌入表大一点,换序列短一截**,对长文本/多语言/代码尤其划算。

**fertility 与 bytes-per-token 手算**。fertility = 平均一个「词」被切成几个 token:

- 英文 `tokenization` 在好的 BPE 下约 2 个 token(`token` + `ization`)→ fertility ≈ 1(多数常见词 1 个 token)。
- 同一句中文「分词器」可能被切成 3~6 个 token(字节级下每个汉字 = 多字节,见 [[051 BPE 与 Byte-level BPE|字节级]])→ fertility 高、上下文更费。
- bytes-per-token:英文好 BPE 约 4(每 token 覆盖约 4 个字节),中文字节级常 < 2 → 同样信息中文吃更多 token。

结论:**同一段「意思」,换语言/换分词器,token 数能差 2~3 倍**——这直接决定 API 费用和上下文占用。

## 原理

**1. 分词器是确定性程序,不是网络。** 它分两步学/用:**训练期**(一次性)在语料上统计、学出「合并规则 / 子词词表」然后**冻结**;**使用期**对任意输入做确定性切分。编码 `encode` 与解码 `decode` 互逆。模型从头到尾**只看 id**,看不到原始字符——这点是后面所有「分词坑」的根源(见 [[055 分词的坑：数字、代码、多语言与 token 攻击面|分词的坑]])。

**2. 为什么 OOV 是词级的硬伤。** 词级词表 $V$ 是个固定集合。任何 $w\notin V$ 都映射到同一个 `[UNK]`,于是「拼写错的 teh」「新词 GPT-5」「人名」全被压成同一个 token,模型无法区分。子词把单位降到「片段」,只要片段都在词表里就能拼出任意词,OOV 趋近于零;字节级(见 [[051 BPE 与 Byte-level BPE|Byte-level BPE]])因 256 个字节是文本的最小单位,**理论上零 OOV**。

**3. 序列长度的代价是平方的。** 设句子 $n$ 个字符。词级 token 数 $\approx n/5.5$(英文平均词长),子词 $\approx n/4$,字符级 $=n$。注意力计算 $\mathcal{O}(n_{\text{tok}}^2)$、KV-Cache 显存 $\mathcal{O}(n_{\text{tok}})$。字符级把 $n_{\text{tok}}$ 放大 4~5 倍,平方项放大 16~25 倍——这就是字符级虽零 OOV 却没人用作主力的原因。

**4. 压缩率视角。** 好的分词器 ≈ 好的无损压缩器:让常见字节序列用更少 token 表示。常用指标 **bytes-per-token**(每 token 平均覆盖几个字节,越大越省;英文好的 BPE 约 4)和 **fertility**(一个词平均切成几个 token,越接近 1 越好)。子词算法 [[051 BPE 与 Byte-level BPE|BPE]] 本就脱胎于数据压缩算法。

## 代码

```python
# 用一个 mini「词表」演示三种粒度怎么把同一句话变成 id
text = "the lowest cats"

# ❌ 词级：没见过的词直接 UNK，信息全丢
word_vocab = {"the": 1, "cats": 2, "[UNK]": 0}
word_ids = [word_vocab.get(w, word_vocab["[UNK]"]) for w in text.split()]
print("词级:", word_ids)          # [1, 0, 2]   "lowest"->0(UNK) 丢了

# ✅ 子词级：罕见词拆成已知片段，不丢信息（这里手工模拟切分结果）
sub_vocab = {"the":1, "cats":2, "low":3, "est":4}
sub_tokens = ["the", "low", "est", "cats"]    # 子词算法切出来的
sub_ids = [sub_vocab[t] for t in sub_tokens]
print("子词:", sub_ids)           # [1, 3, 4, 2]   保住了 lowest=low+est

# 字符级：永不 OOV，但序列暴长
char_ids = [ord(c) for c in text if c != " "]
print("字符级长度:", len(char_ids))   # 13  —— 比子词的 4 长 3 倍多
```

```python
# 量一量「序列长度」的代价：注意力 ~ O(n^2)
for name, n_tok in [("词级", 3), ("子词", 4), ("字符级", 13)]:
    print(f"{name}: token={n_tok}, 注意力相对成本 ~ {n_tok**2}")
# 词级 9 / 子词 16 / 字符级 169 —— 字符级平方项爆炸
```

```python
# 量一量「fertility」:同样的词,不同分词器切几片?(此处用模拟切分演示概念)
def fertility(words, tokenize):
    n_words = len(words)
    n_tokens = sum(len(tokenize(w)) for w in words)
    return n_tokens / n_words
words = ["the", "tokenization", "lowest"]
en_bpe = {"the": ["the"], "tokenization": ["token", "ization"], "lowest": ["low", "est"]}
print("英文 fertility =", fertility(words, lambda w: en_bpe[w]))  # 5/3 ≈ 1.67
# 中文/罕见词 fertility 更高 → 同样内容更费 token、更占上下文、更贵
```

## 特殊 token 与对话模板(下一篇的引子)

真实分词器除了「正文 token」,还塞了一批**特殊 token** 用来控制结构,零基础常忽略:

- `[CLS]`/`[SEP]`(BERT)、`<|endoftext|>`/`<|im_start|>`/`<|im_end|>`(GPT/chat)、`<s>`/`</s>`(序列起止)、`<pad>`、`<unk>`。
- **chat template**:把多轮对话编码成一条序列时,用特殊 token 标「这是 system / user / assistant 的话」,如 `<|im_start|>user\n你好<|im_end|>`。模型靠这些标记知道「现在该我(assistant)说话了」。
- ⚠️ 坑:不同模型的特殊 token 不同,**用错模板**(比如拿 LLaMA 模板喂 Qwen)会让模型行为异常。详见 [[053 词表、特殊 token 与对话模板|词表、特殊 token 与对话模板]]。

## 面试高频

- **Q:为什么不直接按词或按字符分,要用子词?** A:词级词表爆炸(数十万)且遇 OOV 丢信息;字符级序列太长(注意力 O(n²) 爆)、语义稀薄。子词在「词表可控(几万)+ 几乎不 OOV + 序列适中」三方面平衡,是当代 LLM 标准。
- **Q:OOV 是什么?子词怎么解决?** A:OOV(未登录词)指训练时没见过的词,词级只能映射成单个 `[UNK]`、信息全丢。子词把单位降到片段,任何词都能拆成已知子词拼出来;字节级因 256 字节是最小单位可做到零 OOV。
- **Q:词表越大越好吗?** A:不是。大词表让序列更短、整词更多,但嵌入表(词表×d)更大、长尾词训不充分、softmax 更慢。是「序列长度 ↔ 参数量/速度」的折中,英文常 3万~5万,多语言/代码 10万~25万。
- **Q:分词器是模型的一部分吗,会被反向传播训练吗?** A:不是网络。分词器在语料上一次性学好合并规则/词表后**冻结**,使用时是确定性查表程序,不参与反向传播。只有它后面的**嵌入表**是可训练参数(见 [[054 词嵌入层与权重绑定|嵌入层]])。
- **Q:怎么衡量分词器好坏?** A:bytes-per-token(每 token 覆盖几字节,越大越省)、fertility(一词切几片,越接近 1 越好)。本质是无损压缩率:常见序列用更少 token。
- **Q:嵌入表多大,扩词表代价是什么?** 嵌入表 = $V\times d$;LLaMA-3 把 $V$ 从 3.2 万扩到 12.8 万,嵌入表从 1.3 亿涨到 5.2 亿,但序列更短、长文本/多语言/代码更省,整体常划算。
- **Q:fertility 和 bytes-per-token 怎么解读?** fertility = 一词切几片(越接近 1 越好);bytes-per-token = 一 token 覆盖几字节(越大越省)。中文/代码 fertility 高、bytes-per-token 低 → 更费 token。
- **Q:特殊 token 是干嘛的?** 标记结构(起止/分隔/对话角色),如 `<|im_start|>`、`[SEP]`;chat template 用它们告诉模型谁在说话。用错模板会行为异常(见 [[053 词表、特殊 token 与对话模板|对话模板]])。
- **陷阱**:① token ≠ 词 ≠ 字,计费/上下文长度都按 token 算;② 同一文本不同分词器 token 数差很多(中文、代码差距尤其大);③ 编码解码必须用同一份分词器,否则乱码。

## 关键事实

- 子词分词由 **Sennrich 等(2016,arXiv:1508.07909)**用 BPE 引入 NMT,解决罕见词/OOV,成为开放词表翻译的标配,后被 GPT/BERT 等全面采用。
- 主流三系:**BPE**(GPT 系、LLaMA;见 [[051 BPE 与 Byte-level BPE|BPE]])、**WordPiece**(BERT 系)、**Unigram LM**(T5、ALBERT,常经 SentencePiece;见 [[052 WordPiece、Unigram 与 SentencePiece|WordPiece、Unigram 与 SentencePiece]])。
- 现代词表规模参考:GPT-2 50257、BERT 30522、LLaMA-2 32000、LLaMA-3 128256、GPT-4(cl100k_base)约 100k。
- 字节级(GPT-2 起)以 256 字节为基,理论零 OOV,任意 Unicode/二进制都可切。
- 分词直接影响成本与上下文:API 按 token 计费、上下文窗口按 token 计长度;同义内容用不同语言/分词器 token 数可差数倍(中文、代码尤甚,见 [[055 分词的坑：数字、代码、多语言与 token 攻击面|分词的坑]])。
- 嵌入表 = 词表 × $d$:LLaMA-2 约 1.3 亿、LLaMA-3 约 5.2 亿(词表 32000→128256);扩词表换序列变短。
- 衡量指标:**fertility**(一词切几片,越近 1 越好)与 **bytes-per-token**(一 token 几字节,越大越省);本质是无损压缩率。
- 特殊 token 与 chat template 是分词器的一部分:控制序列结构与对话角色,用错会出问题(见 [[053 词表、特殊 token 与对话模板|053]])。
