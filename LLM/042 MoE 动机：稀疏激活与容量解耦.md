[[042 MoE 动机：稀疏激活与容量解耦]]:Mixture-of-Experts 把一层的单个 [[008 前馈网络 FFN(为何 4 倍、为何两层)|FFN]] 换成 E 个“专家 FFN”+ 一个路由器,每个 token 只激活其中 top-k 个——于是**总参数(容量)和每 token 算力被解耦**:参数能涨好几倍,算力几乎不变。

## 直觉:稠密模型“参数=算力”绑死了
在普通(稠密)Transformer 里,**每个 token 都要过完整的 FFN**。想让模型更聪明、记更多知识,就得把 FFN 做大;可一旦做大,**每个 token 的计算量同步暴涨**——参数和算力被死死绑在一起。这是 [[079 Scaling Law 与 Chinchilla 最优|scaling]] 里最贵的一笔账:容量上去,推理/训练成本也跟着上去。

MoE 的破局点:**为什么每个 token 都要用全部参数?** 一句话里,处理 “the” 和处理 “光合作用” 需要的知识完全不同。MoE 因此放很多个专家 FFN,让一个**路由器**按 token 内容动态挑 top-k 个专家来算,其余专家**这一步根本不参与计算**。

于是“参数”和“算力”被拆成两条独立的轴:
- **总参数 $\propto E$(专家数)**——决定模型容量(能记多少知识),也决定显存占用。
- **每 token 算力 $\propto k$(激活专家数)**——决定推理/训练成本。

**同样的每 token 算力下,MoE 能塞进数倍的参数。** 这就是“稀疏激活、容量与算力解耦”。

## 例子:8 选 2 的账(小数字)
一层标准 FFN 假设有参数量 $P$,每 token 算力也 $\propto P$。

换成 MoE:放 **8 个**同样大小的专家 FFN,路由器每 token 选 **top-2**:
- **总参数 ≈ $8P$**(8 个专家全在,容量 8 倍);
- **每 token 算力 ≈ $2P$**(只过 2 个专家)——只比稠密多一点(top-2 vs 1)。

也就是说:用约 2× 的算力,换来约 8× 的参数容量。Mixtral 8×7B 就是这个思路:总参数约 47B,但每 token 只激活约 **13B**。DeepSeek-V3 更极致:总 **671B**、每 token 仅激活约 **37B**(约 5.5%)。

⚠️ 但**显存没省**:8 个专家的参数全都要常驻显存。MoE 省的是**算力(FLOPs)**,不是显存。这是面试最爱挖的坑。

**两本账分开记(算力 vs 显存)**。同一个 8×7B 模型,两个数字完全不同:

| | 决定于 | Mixtral 8×7B | DeepSeek-V3 |
|---|---|---|---|
| 显存(放权重) | 总参 $\propto E$ | ≈ 47B | ≈ 671B |
| 算力/带宽(每 token 前向) | 激活 $\propto k$ | ≈ 13B | ≈ 37B |
| 「免费」倍率 | $E/k$ | 47/13 ≈ 3.6× | 671/37 ≈ 18× |

所以一句精确的话:**MoE 用「更多显存」换「更大有效容量而算力几乎不变」**。它适合「显存够、但想在固定推理算力下塞更多知识」的场景;若显存才是瓶颈,MoE 反而更吃紧。

**和稠密模型的等价直觉**。一个 47B 总参、激活 13B 的 MoE,效果大致介于「13B 稠密」和「47B 稠密」之间——比 13B 强(容量大),但通常不及同等总参的 47B 稠密(稀疏激活有损)。它的卖点是**用 13B 的推理成本拿到接近大模型的效果**,不是「免费的 47B」。

**实测对照(MMLU 5-shot)**。Mixtral 8×7B(激活 13B)约 **70.6%**,明显高于同激活量级的 Llama2-13B 稠密(约 **54.8%**),也略胜 Llama2-70B 稠密(约 **68.9%**)——但要记住 Mixtral 总参 47B,论「每参数」并不占便宜。一句话:Mixtral **用 13B 的算力打平甚至超过 70B 稠密**,正是「稀疏激活省算」的实证;而非「13B 凭空变 70B」。

## 原理:用专家替换 FFN + 门控加权
**结构**:把 Transformer 块里那一个 FFN 替换成 $E$ 个专家 $\{\text{FFN}_1,\dots,\text{FFN}_E\}$ 加一个路由器(门控网络)$g$。对输入 token $x$:

**① 路由打分**:线性层给每个专家算一个分数,softmax 成权重:
$$s = \text{softmax}(W_g\,x)\in\mathbb{R}^{E}$$

**② 选 top-k**:只保留分数最高的 $k$ 个专家(其余权重当 0),通常对选中的再归一化:
$$\mathcal{T}=\text{TopK}(s,k),\qquad g_i = \frac{s_i}{\sum_{j\in\mathcal{T}} s_j}\ \ (i\in\mathcal{T})$$

**③ 加权求和**:只计算被选中的专家,按门控权重合并:
$$y = \sum_{i\in\mathcal{T}} g_i\,\text{FFN}_i(x)$$

关键:第 ③ 步**只对 $k$ 个专家做前向**,未选中的专家这一步零计算 → 算力 $\propto k$ 而非 $E$。门控、top-k 的细节(以及为什么需要负载均衡)见 [[043 门控路由与 top-k 选择|门控路由与 top-k 选择]]。

**为什么不会“算力爆炸”**:稠密 FFN 算力 $\propto P$;MoE 把容量摊到 $E$ 个专家($\propto EP$),但每步只激活 $k$ 个($\propto kP$)。只要 $k\ll E$,容量大涨而算力近似不变——这正是解耦的数学本质。

**代价(没有免费午餐)**:
- **显存**:$E$ 个专家参数全常驻,显存 $\propto E$(省算不省显存);
- **负载均衡**:若路由总把 token 送给少数专家,其余专家“饿死”、被浪费,还会训练不稳——需辅助均衡损失,见 [[043 门控路由与 top-k 选择|门控路由]];
- **工程**:专家可能分布在不同设备,token 要做 all-to-all 通信,批处理更复杂。

## 代码:一层 MoE 前向(可运行)
```python
import torch, torch.nn as nn, torch.nn.functional as F

class Expert(nn.Module):                       # 一个专家 = 一个普通 FFN
    def __init__(self, d, hidden):
        super().__init__(); self.net = nn.Sequential(
            nn.Linear(d, hidden), nn.GELU(), nn.Linear(hidden, d))
    def forward(self, x): return self.net(x)

class MoE(nn.Module):
    def __init__(self, d, hidden, n_experts=8, k=2):
        super().__init__()
        self.k = k
        self.gate = nn.Linear(d, n_experts)                       # 路由器
        self.experts = nn.ModuleList(Expert(d, hidden) for _ in range(n_experts))
    def forward(self, x):                                          # x:(B*T, d) 逐 token
        scores = F.softmax(self.gate(x), dim=-1)                  # (N, E)
        topv, topi = scores.topk(self.k, dim=-1)                  # 选 top-k
        topv = topv / topv.sum(-1, keepdim=True)                 # 对选中的重新归一化
        y = torch.zeros_like(x)
        for slot in range(self.k):                                # ✅ 只跑被选中的专家
            idx = topi[:, slot]                                    # 每个 token 第 slot 个专家
            w   = topv[:, slot].unsqueeze(-1)
            for e in range(len(self.experts)):
                m = idx == e
                if m.any():                                       # 只对路由到 e 的 token 算
                    y[m] += w[m] * self.experts[e](x[m])
        return y

moe = MoE(d=512, hidden=2048, n_experts=8, k=2)
x = torch.randn(16, 512)
print("总专家参数(容量) ∝ 8;每 token 实算专家数(算力) =", moe.k)  # → 2
```

# ❌ 误解:以为 MoE 既省算又省显存(于是觉得“白嫖”)

# ❌ 另一个坑:把所有专家都算一遍再 mask
y = sum(g[:, e:e+1] * self.experts[e](x) for e in range(8))   # 全算 → 算力没省,失去意义
# ✅ 必须只前向被选中的 k 个专家,算力才 ∝ k

```python
# 把「容量 vs 算力」两本账算清楚
def moe_budget(expert_params, n_experts, top_k):
    total = expert_params * n_experts          # 显存:全部专家常驻 ∝ E
    active = expert_params * top_k             # 算力:每 token 只走 k 个 ∝ k
    return total, active, total / active
for name, ep, E, k in [("Mixtral", 5.9, 8, 2), ("DeepSeek-V3", 2.6, 256, 8)]:
    t, a, r = moe_budget(ep, E, k)
    print(f"{name}: 显存~{t:.0f}B  算力~{a:.0f}B  免费倍率 E/k={r:.1f}x")
# 注:此处 ep 为「专家相关参数」粗估,数值用于体现 总参/激活 与 E/k 的关系
```

## 什么时候该用 MoE,什么时候别用

不是所有场景都该上 MoE,面试爱问「权衡」:

- **该用**:训练/推理算力受限、但显存相对充裕,想在同等每 token FLOPs 下拿更大有效容量(超大基座模型、追知识广度)。
- **别用/慎用**:① 显存才是瓶颈(MoE 总参更大,反而更挤);② 模型本来就小(容量瓶颈不突出,稠密更简单稳);③ 推理 batch 很小、单卡部署(专家利用率低、all-to-all 占比高,见 [[049 专家并行 EP 与 MoE 部署|EP]]);④ 团队没精力调路由(负载均衡、稳定性都是坑)。
- **经验法则**:**小模型偏稠密,超大模型偏 MoE**。MoE 改变的是 [[079 Scaling Law 与 Chinchilla 最优|scaling]] 中「算力—参数」的权衡曲线,而非凭空变强。

## 面试高频
- **MoE 解决什么问题?** 稠密模型“参数=算力”绑死,扩容量必然涨算力。MoE 用稀疏激活**解耦**二者:总参数 $\propto E$(容量),每 token 算力 $\propto k$(成本),$k\ll E$ → 同算力塞更多知识。
- **MoE 省显存吗?** **不省**。所有专家参数都要常驻显存(显存 $\propto E$),省的是**计算量 FLOPs**。这是高频陷阱题。
- **“总参数 47B / 激活 13B”是什么意思?** 47B 是全部专家加起来的**容量**(占显存),13B 是每 token 实际走过的参数(决定**算力**)。Mixtral 8×7B 即此;DeepSeek-V3 是 671B / 37B。
- **为什么要 top-k 而不是只选 1 个?** 只选 1(top-1,如 Switch Transformer)最省算但表达受限、路由更易抖;top-2 在质量与算力间折中,是常见选择。细节见 [[043 门控路由与 top-k 选择|top-k 选择]]。
- **MoE 的主要难点?** 负载均衡(防止专家“饿死/过载”,需辅助损失)、显存占用大、跨设备 all-to-all 通信、训练不稳。
- **MoE 放在 Transformer 哪里?** 替换 **FFN 层**(注意力一般不换);通常隔层或大部分层用 MoE。见 [[040 现代 decoder-only 配方汇总|配方汇总]]。
- **和 Scaling Law 的关系?** MoE 改变了“算力—参数”的权衡:在固定推理算力预算下能获得更大有效容量,是 [[079 Scaling Law 与 Chinchilla 最优|scaling]] 之外的一条“省算扩容”路线。
- **「免费倍率」E/k 是什么?** 总参/激活 ≈ 专家数/激活数:Mixtral 8/2=4×、DeepSeek-V3 256/8=32×(实际算总参/激活 47/13≈3.6、671/37≈18,因有共享部分)。倍率越大,容量相对算力越「便宜」。
- **47B 的 MoE 等于 47B 稠密吗?** 不等。效果通常介于 13B 稠密与 47B 稠密之间——比小的强、不及同总参的稠密;卖点是「用 13B 的算力拿到接近大模型的效果」。
- **什么时候不该用 MoE?** 显存瓶颈、小模型、小 batch 单卡推理、无力调路由时;此时稠密更简单稳。

## 关键事实
- 概念起源:Jacobs et al. 1991 提出 Mixture of Experts;深度学习版稀疏门控:Shazeer et al.,*Outrageously Large Neural Networks*,2017,arXiv:1701.06538(top-k 门控 + 负载均衡损失)。
- Transformer 上的关键工作:GShard(Lepikhin et al. 2020)、Switch Transformer(Fedus et al. 2021,top-1,arXiv:2101.03961)。
- 现代采用:Mixtral 8×7B(top-2,≈47B 总 / 13B 激活,arXiv:2401.04088)、DeepSeek-V3(671B 总 / 37B 激活,256 路由+1 共享,top-8,arXiv:2412.19437)、Qwen3-MoE、GLaM、Switch-C(1.6T)等。
- 两本账:**显存 ∝ E(总参)** 与 **算力 ∝ k(激活)** 必须分开看;免费倍率 ≈ E/k。MoE 是「用显存换有效容量」,不是凭空变强(效果介于「激活规模稠密」与「总参规模稠密」之间)。
- 核心权衡:**总参数 $\propto E$(容量、占显存)** vs **每 token 算力 $\propto k$(成本)**;$k\ll E$ 时解耦成立。MoE **省算力不省显存**。
