[[074 通信原语与计算通信重叠]]:分布式训练靠 NCCL 的四个**集合通信原语**(all-reduce、all-gather、reduce-scatter、all-to-all)在多卡间搬数据;而把这些通信**藏进计算的影子里**(计算通信重叠)是让多卡接近线性加速的关键工程手段。

## ① 直觉:多卡训练 = 算一阵 + 同步一阵,同步不能让 GPU 干等

单卡训练只有"算"。一旦多卡,每张卡算出的东西(梯度、激活分片)必须互相交换、合并,才能继续——这就是**集合通信(collective communication)**。NVIDIA 的 NCCL 库把常见的交换模式封成几个原语,你只要调对原语,它在 NVLink/InfiniBand 上自动跑高效的 ring 算法。

四个最常用的原语,用一句话区分:

- **all-reduce**:每卡各持一份,**求和后人手一份完整结果**。数据并行同步梯度就靠它。
- **all-gather**:每卡持一**片**,**拼成完整向量人手一份**。[[070 ZeRO 与 FSDP|ZeRO/FSDP]] 前向时把分片权重拼回完整就靠它。
- **reduce-scatter**:逐段求和,**每卡只拿走结果的一段**(是 all-reduce 的前半)。ZeRO 反向归约并分片梯度用它。
- **all-to-all**:**转置**——每卡把第 j 段发给第 j 卡。[[049 专家并行 EP 与 MoE 部署|MoE 专家并行]]按路由把 token 分发到各专家卡就靠它。

但光会调原语不够。通信是有代价的:GPU 在等数据到位时如果**干等**,算力就浪费了。于是有了**计算通信重叠**——一边算,一边让后台流异步搬上一步的数据,把通信时间"藏"进计算时间里。

## ② 例子:4 卡同步一份 768×768 梯度要传多少字节

数据并行下,4 卡各算出一份完整梯度 $g$(假设某层 $768\times768$,fp16 = 2 字节),要 all-reduce 求平均。

- 朴素做法(每卡把自己的发给所有人再求和):每卡收发 $(P-1)\times M$,P=4、M = 768×768×2 ≈ 1.18 MB → 收发约 3.5 MB,且带宽随 P 恶化。
- **Ring all-reduce**(NCCL 实际用的):把梯度切成 P 段,先 reduce-scatter(P−1 步,每步发 1/P)再 all-gather(P−1 步)。每卡总收发 $2\frac{P-1}{P}M = 2\times\frac{3}{4}\times1.18 \approx 1.77$ MB,**且与卡数 P 几乎无关**——这是 ring 算法的精髓:不管多少卡,每卡搬的字节数恒定。

再看 all-to-all 的例子(MoE):一个 batch 里 token 被路由到不同专家,专家分布在不同卡上。all-to-all 像发牌——GPU0 把"该去专家1的 token"发给 GPU1、"该去专家2的"发给 GPU2……同时收别人发来的。完成后每卡手里就是"分配给本卡专家的所有 token"。

![[dist-NCCL通信原语.png]]

**重叠的例子**:反向传播是从最后一层往前算的。某层梯度一算完,**不必等整个反向结束**,立刻对这层发起 all-reduce;与此同时 GPU 继续算前面层的反向。这样通信跟后续层的计算并行,理想情况下通信被完全藏住,总时间 ≈ 纯计算时间。

## ③ 原理:原语之间的恒等关系与重叠的条件

**四个原语并非彼此独立**,存在分解关系:

$$
\text{all-reduce} \;=\; \text{reduce-scatter} \;+\; \text{all-gather}
$$

这也是 [[073 序列并行与上下文并行|序列并行]]能零额外通信成本的原因:把一次 all-reduce 劈成两半,中间插序列切分。

**Ring 算法的通信量**。对 P 卡、数据量 M:

$$
T_{\text{all-reduce}} \approx 2\frac{P-1}{P}\,\frac{M}{B} + 2(P-1)\,\alpha
$$

其中 $B$ 是带宽、$\alpha$ 是每次通信的固定延迟。关键看第一项:系数 $2\frac{P-1}{P}\to 2$(当 P 大),**与 P 无关**,所以 ring all-reduce 在大规模下带宽利用率高;但第二项 $2(P-1)\alpha$ 随 P 线性增长,小数据时延迟主导——所以小张量要 **bucket(打包)** 后再传。all-gather、reduce-scatter 各约 $\frac{P-1}{P}\frac{M}{B}$,是 all-reduce 的一半。

**计算通信重叠能藏住多少**。设某段计算耗时 $t_c$、与之并行的通信耗时 $t_o$,则这段墙钟时间是 $\max(t_c, t_o)$ 而非 $t_c+t_o$:

$$
T_{\text{overlap}} = \sum \max(t_{c,i},\, t_{o,i}) \;\le\; \sum (t_{c,i}+t_{o,i}) = T_{\text{serial}}
$$

当 $t_o \le t_c$(通信比它能藏的计算短),通信被**完全藏住**,$T\approx\sum t_c$;一旦 $t_o > t_c$(比如卡间带宽太差、模型太小计算不够多),通信就会"露馅"成为瓶颈。实现上靠 **CUDA 多 stream**:计算在主 stream,通信在独立 stream,NCCL 异步发起,二者并行执行。

## ⑤ 原语全家福与各自通信量(一张表背熟)

除四大常用原语,还有几个底层原语,面试可能追问"broadcast 和 all-gather 啥区别"。设 P 卡、每卡数据量 M,ring 算法下单卡收发量:

| 原语 | 语义 | 单卡通信量(ring) | 典型用途 |
|---|---|---|---|
| **broadcast** | 一卡 → 全卡(复制) | $\sim M$ | 初始化时同步权重、随机种子 |
| **reduce** | 全卡 → 一卡(求和) | $\sim M$ | 把指标汇总到 rank0 打印 |
| **all-reduce** | 全卡求和,人手一份 | $2\frac{P-1}{P}M$ | DP 同步梯度 |
| **gather** | 全卡片 → 一卡拼全 | $\sim M$ | 收集各卡结果到 rank0 |
| **all-gather** | 全卡片 → 人手一份完整 | $\frac{P-1}{P}M$ | ZeRO 取权重、SP |
| **scatter** | 一卡切片 → 各卡一片 | $\sim M$ | 分发数据 |
| **reduce-scatter** | 逐段求和,各拿一段 | $\frac{P-1}{P}M$ | ZeRO 切梯度、SP |
| **all-to-all** | 转置(每卡发第 j 段给卡 j) | $\frac{P-1}{P}M$ | MoE 派 token、Ulysses |

记忆主线:**all-reduce = reduce-scatter + all-gather**(故 all-reduce 量是后两者各自的 2 倍);**all-gather 和 reduce-scatter 互为前向/反向对偶**;**all-to-all 是唯一"换内容不求和"的转置型原语**。

## ⑥ ring vs tree:NCCL 怎么选算法

ring 不是唯一算法。NCCL 还有 **tree all-reduce**,两者在 $\alpha$-$\beta$ 模型下各擅胜场:
- **ring**:带宽项 $2\frac{P-1}{P}\frac{M}{B}\to\frac{2M}{B}$(与 P 无关,**带宽最优**),但延迟项 $2(P-1)\alpha$ **随 P 线性增长**。→ **大张量、卡多** 时 ring 好(带宽主导)。
- **tree**:延迟项 $\sim 2\log_2(P)\,\alpha$(**对数级**,远小于 ring 的线性),但带宽利用率略低。→ **小张量、跨多机** 时 tree 好(延迟主导)。

NCCL 会按张量大小和拓扑**自动选**(可用 `NCCL_ALGO=Ring/Tree` 强制)。这解释了为什么 DDP 要把碎梯度 **bucket 打包**:把上百个小张量合成几个大桶,既摊薄每次通信的固定延迟 $\alpha$、又让 ring 的带宽优势发挥出来。桶太小→延迟主导、桶太大→重叠机会变少(要等整桶梯度算完才发),典型桶 25 MB。

## ⑦ 物理拓扑:为什么 TP 机内、PP/DP 跨机

通信原语的"带宽 $B$"由物理链路决定,差几个数量级:
- **机内 NVLink**(H100 NVLink 4.0):卡间 ~900 GB/s 双向,机内 8 卡全互联(NVSwitch)。→ TP 的每层 all-reduce 走这里。
- **机间 InfiniBand**(NDR):~50 GB/s 级。→ PP 的边界点对点、DP 的梯度 all-reduce 走这里。
- 差距约 **20×**。所以并行策略的铁律(见 [[071 张量并行(Megatron)|TP]]、[[072 流水线并行与气泡|PP]]):**通信最重的 TP 关在机内 NVLink,通信轻的 PP/DP 放跨机 IB**。一旦 TP 跨机,每层 all-reduce 走慢 20× 的网络,吞吐直接崩——这是 3D 并行配比的物理根因。

## ④ 代码:四个原语 + 梯度通信重叠

```python
import torch, torch.distributed as dist

# --- 四个原语的调用形态(PyTorch 封装的 NCCL)---
def primitives_demo(x):                       # x: 本卡的张量
    # all-reduce:原地求和,人手一份完整结果(数据并行同步梯度)
    dist.all_reduce(x, op=dist.ReduceOp.SUM)

    # all-gather:每卡一片 → 拼成 [world_size, *x.shape]
    out = [torch.empty_like(x) for _ in range(dist.get_world_size())]
    dist.all_gather(out, x)

    # reduce-scatter:逐段求和,每卡只收一段(是 all-reduce 的前半)
    chunk = torch.empty_like(x.chunk(dist.get_world_size())[0])
    dist.reduce_scatter(chunk, list(x.chunk(dist.get_world_size())))

    # all-to-all:转置式分发(MoE 把 token 派给各专家卡)
    recv = torch.empty_like(x)
    dist.all_to_all_single(recv, x)

# --- 计算通信重叠:梯度算完即发,不等整个反向结束 ---
# ❌ 错:整个反向跑完,才一次性同步所有梯度 → GPU 在通信时干等
def step_bad(model, loss):
    loss.backward()                            # 全部梯度算完
    for p in model.parameters():
        dist.all_reduce(p.grad)                # 串行同步,纯等待

# ✅ 对:用 hook,某参数梯度一就绪就异步 all-reduce,与后续层反向重叠
def step_good(model, loss):
    handles = []
    for p in model.parameters():
        # 梯度一算出来就触发:异步发起通信(async_op=True 不阻塞)
        p.register_post_accumulate_grad_hook(
            lambda p: handles.append(dist.all_reduce(p.grad, async_op=True)))
    loss.backward()                            # 反向进行中,通信已在后台流跑
    for h in handles: h.wait()                 # 最后统一等通信收尾
# 注:DDP / FSDP 已内置这套重叠 + 梯度 bucketing,生产中直接用框架即可
```

## 面试高频

- **Q:NCCL 四大原语各干什么?** all-reduce=求和后人手一份(同步梯度);all-gather=拼分片成完整(ZeRO 取权重);reduce-scatter=归约后各拿一段(ZeRO 切梯度);all-to-all=转置分发(MoE 派 token)。
- **Q:all-reduce 和 all-gather + reduce-scatter 什么关系?** all-reduce = reduce-scatter + all-gather,字节数相等;这是序列并行不增通信的依据。
- **Q:Ring all-reduce 为什么扩展性好?** 每卡收发约 $2\frac{P-1}{P}M$,带宽项与卡数 P 几乎无关;但延迟项随 P 增长,小张量需打包(bucket)。
- **Q:什么是计算通信重叠?它的前提?** 用独立 CUDA stream 让通信与计算并行,把通信藏进计算影子;前提是被藏的通信时间 ≤ 重叠它的计算时间,否则仍会露馅。
- **Q:为什么 DDP 反向时一边算一边通信?** 反向从后往前,某层梯度先算完就先 all-reduce,与前面层的反向计算并行,无需等整个反向结束。
- **Q:MoE 为什么用 all-to-all 而不是 all-reduce?** MoE 要把不同 token 路由到不同专家卡,是"分发/转置"而非"求和",天然匹配 all-to-all(见 [[049 专家并行 EP 与 MoE 部署]])。
- **Q:NCCL 什么时候用 ring,什么时候用 tree?** 大张量/卡多用 ring(带宽项与 P 无关,带宽最优);小张量/跨多机用 tree(延迟项对数级 $\log P$ 而非 ring 的线性 $P$)。NCCL 按大小和拓扑自动选,可用 `NCCL_ALGO` 强制。
- **Q:梯度 bucket 桶大小怎么权衡?** 太小→每次通信固定延迟 $\alpha$ 占比高、ring 带宽发挥不出;太大→要等整桶梯度算完才发、重叠机会少。典型 25 MB。
- **Q:broadcast 和 all-gather 区别?** broadcast 是"一卡的完整数据复制到全卡"($\sim M$);all-gather 是"每卡各持一片、拼成完整后人手一份"($\frac{P-1}{P}M$)。前者源单一,后者源分布。
- **Q:为什么 TP 必须机内、PP/DP 可跨机(从原语带宽角度)?** 机内 NVLink ~900 GB/s,机间 IB ~50 GB/s,差约 20×。TP 每层 all-reduce 通信最重必须走 NVLink;PP 边界点对点、DP 梯度 all-reduce 通信轻可走 IB。

## 关键事实

- NCCL(NVIDIA Collective Communication Library)实现 all-reduce / all-gather / reduce-scatter / all-to-all / broadcast 等集合原语,在 NVLink、InfiniBand 上用 ring 与 tree 算法(NVIDIA NCCL 文档)。
- Ring all-reduce 的"带宽最优、与卡数无关"特性源自 Baidu 2017 年的工程实践,后被 NCCL 与 Horovod 广泛采用;每卡收发约 $2\frac{P-1}{P}M$ 字节。
- all-reduce = reduce-scatter + all-gather 是分解恒等式,ZeRO(arXiv:1910.02054)与序列并行(arXiv:2205.05198)均依赖它。
- 计算通信重叠 + 梯度 bucketing 是 PyTorch DDP 的核心优化(《PyTorch Distributed》Li et al., 2020, arXiv:2006.15704),FSDP 进一步重叠参数 all-gather 与前向计算。
- all-to-all 是 MoE 专家并行(GShard、Switch Transformer)与 DeepSpeed-Ulysses 序列并行的关键原语;其通信量随专家分布与负载均衡程度变化(见 [[044 专家容量、丢弃与负载均衡损失]])。
- $\alpha$-$\beta$ 通信模型:一次集合通信耗时 $\approx (\text{步数})\alpha + (\text{字节})/B$,$\alpha$=每次发起的固定延迟、$B$=带宽。ring 带宽项 $\to 2M/B$(与 P 无关)、延迟项 $2(P-1)\alpha$ 线性;tree 延迟项 $\sim 2\log_2 P\,\alpha$ 对数。
- 物理带宽量级:H100 机内 NVLink ~900 GB/s,机间 InfiniBand NDR ~50 GB/s 级,差约 20×,是"TP 机内、PP/DP 跨机"并行配比的物理根因。
- 八大原语对偶关系:all-reduce = reduce-scatter + all-gather;all-gather 与 reduce-scatter 互为前向/反向对偶;all-to-all 是唯一转置型(不求和)原语。
